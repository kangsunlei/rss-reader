为了让你搞懂 Loop Engineering，我搭了个让 Agent 持续帮你找工作的最佳实践

6/15/2026, 11:45:00 PM

📌 一句话摘要

本文以「求职岗位发现 Agent」为实战案例，系统讲解 Loop Engineering 的核心思想：围绕长期任务设计外部循环系统，让 Agent 被稳定触发、执行、交付与迭代，而非依赖单次提示词。

📝 详细摘要

文章从 OpenClaw 创始人与 Claude Code 之父提出的「Loop Engineering」概念出发，指出其核心不是提示词技巧，而是围绕长期任务设计一套外部循环系统。作者以「Job Hunt Loop」求职岗位发现 Agent 为完整案例，拆解了 8 个关键模块：触发器（外部控制器唤醒 Agent）、任务队列（去重与状态追踪）、上下文组装（AGENT.md 等稳定文件恢复记忆）、执行器（脚本处理确定性任务，LLM 负责判断）、交付载体（飞书文档作为反馈界面）、反馈学习（用户行为影响后续策略）、停止与降级规则。文章强调 Agent 不应被当作常驻服务，而是被外部循环控制器唤醒的执行器；用户虽在循环外，但其消费行为必须被设计成循环的输入。全文以产品经理视角展开，注重任务流程抽象与工程落地，并附有开源项目地址。

💡 主要观点

  1. Loop Engineering 的核心是设计外部循环系统，而非优化单次提示词。 它解决的是「任务系统如何长期稳定地跑」，包括触发、状态保存、上下文组装、执行、反馈与停止等环节，而非模型该调用什么工具。
  2. Agent 应被设计为被外部循环控制器唤醒的执行器，而非常驻服务。 通过定时、事件或用户反馈等触发器激活 Agent，使其在需要时工作，避免资源浪费与状态混乱。
  3. 长期循环系统需要工程化的记忆管理，而非依赖模型上下文。 使用 AGENT.md、任务队列、审计日志等稳定文件恢复上下文，确保跨 session 执行的一致性。
  4. 用户反馈应被设计为循环的输入，而非被动等待。 通过飞书文档的勾选、评论、沉默等行为捕捉用户意图，驱动系统调整筛选规则与推荐策略。
  5. 可靠的循环系统必须有停止条件、降级策略与人工介入点。 长期循环不是无限循环，需要定义何时继续、沉默、降级或停止，确保可控性。

💬 文章金句

  • 不要把 Agent 当常驻服务，而要把 Agent 当成被外部循环控制器唤醒的执行器。
  • 用户虽然在循环外，但用户的消费行为必须被设计成循环的输入。
  • Loop Engineering 不是无限循环工程，而是可控循环工程。
