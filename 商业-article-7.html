📌 一句话摘要

本文通过真实案例，系统梳理了 OpenAI Codex 的三种电脑操作能力（Computer Use、Chrome 插件、应用内浏览器）的适用场景与选择逻辑，并指出结构化接口优于视觉模拟的核心原则。

📝 详细摘要

文章以「用 Codex 自动完成电商退款」的生动案例开篇，引出 OpenAI Codex 的三种电脑操作能力：Computer Use（全桌面操作，兜底方案）、Chrome 插件（带登录态，适合浏览器内任务）、应用内浏览器（隔离环境，适合开发调试）。作者结合 OpenAI 工程师 Jason Liu 的博客，详细解释了每种能力的原理、适用场景、信任边界与效率权衡，并提炼出核心原则：结构化接口（API/插件）优先于视觉模拟（Computer Use），后者仅作为兜底方案。文章还介绍了 Appshots 作为「指路」工具与三种操作能力的配合方式。整体信息密度高，案例具体，对 AI Agent 的工程实践有清晰的指导价值。

💡 主要观点

  1. Codex 的三种电脑操作能力对应不同的信任边界与效率层级。 Computer Use 权限最宽但最慢，适合无 API 的桌面应用；Chrome 插件带登录态，适合浏览器内任务；应用内浏览器隔离干净，适合开发调试。三者构成从宽到窄的权限体系。
  2. 结构化接口优先于视觉模拟是核心工程原则。 能调用 API 或插件就不要让 AI 模拟鼠标点击，因为视觉操作慢、脆弱、信任成本高。Computer Use 是兜底方案，而非首选。
  3. Chrome 插件通过共享登录态解决了 Agent 操作需认证网站的痛点。 Cookie、配置、登录态、开着的标签页都可被 Codex 使用，使其能像用户本人一样操作 Gmail、Salesforce 等需要登录的网页。
  4. 应用内浏览器最适合开发调试与视觉反馈。 隔离的浏览器环境不带登录态，适合本地开发、复现 bug、检查响应式布局，并支持元素级批注反馈，让页面本身成为需求文档。

💬 文章金句

  • 像人一样点击，是最慢、最脆弱、信任成本最高的那条路。真正想要的，是给 agent 足够结构化的接口，让它尽量用不着去点。
  • 那个看起来最像「AI 终于会用电脑了」的视觉控制，恰恰是整套体系里兜底的一环，结构化工具走不通时，才轮到它上场。
