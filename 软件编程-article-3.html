OpenAI 如何利用 Postgres 扩展至 8 亿用户

2/16/2026, 4:30:36 PM

📌 一句话摘要

本文分析了 OpenAI 如何通过激进的读负载卸载、连接池和故障预防策略，扩展单主 PostgreSQL 架构以支持 8 亿 ChatGPT 用户。

📝 详细摘要

文章详细介绍了 OpenAI 决定扩展 PostgreSQL 而非立即进行数据库分片的非常规决策。尽管负载增长了 10 倍，他们仍通过关注三大支柱实现了 99.999% 的可用性：最小化主库负载、优化查询与连接以及防止级联故障。关键技术实现包括使用 PgBouncer 进行连接池管理、将写密集型工作负载迁移到 Azure Cosmos DB，以及实施缓存锁定以防止惊群效应。文章还探讨了他们如何管理 PostgreSQL 的架构限制（如 MVCC 和模式变更），以及未来通过级联复制扩展到 50 个以上只读副本的计划。

💡 主要观点

  1. 通过优先处理只读副本卸载和严格优化，将单主 PostgreSQL 架构扩展到 8 亿用户是可行的。 通过将绝大部分读取流量路由到近 50 个副本，并仅在主库上保留必要的写相关读取，OpenAI 在处理 10 倍负载增长的同时，避免了数据库分片带来的即时复杂性。
  2. 实施 PgBouncer 进行连接池管理显著降低了延迟，并解决了 Azure PostgreSQL 5，000 个连接的限制。 通过在 Kubernetes 中部署 PgBouncer 作为代理层，OpenAI 将平均连接时间从 50ms 降低到 5ms，使系统能够高效复用连接，并在流量激增期间抵御大规模连接风暴。
  3. 缓存锁定和租约机制对于防止由缓存突发失效引起的级联故障至关重要。 当发生缓存未命中时，仅允许一个请求从数据库获取数据以重新填充缓存。这防止了成千上万个并发请求压垮数据库的“惊群”效应。
  4. 针对模式变更和 MVCC 限制保持严格的操作纪律，是确保大规模数据库达到五个九可用性的必要条件。 OpenAI 对模式变更强制执行 5 秒超时，且仅允许轻量级操作。他们还将写密集型工作负载迁移到 Cosmos DB 等系统，以减轻 PostgreSQL 的写放大和表膨胀问题。
  5. 通过热备机和探索级联复制来进一步扩展读取能力，从而实现高可用性。 通过为主库使用热备机，并与 Azure 合作开发级联复制（即副本将数据转发给其他副本），OpenAI 可以在不超载主库网络带宽的情况下，扩展到超过 100 个只读实例。

💬 文章金句

  • OpenAI 的工程团队选择了一条不同的道路。他们决定看看究竟能把 PostgreSQL 推到什么极限。
  • 该系统在处理每秒数百万次查询的同时，保持复制延迟接近于零。
  • 团队的成功并非源于采用最新的分布式数据库技术，而是源于对工作负载特性的深度理解并消除瓶颈。
  • OpenAI 的经验表明，PostgreSQL 能够比传统观念认为的更可靠地支持更大规模的读密集型工作负载。
  • 当多个请求在同一个缓存键上未命中时，只有一个请求会获取锁并从 PostgreSQL 获取数据以重新填充缓存。
