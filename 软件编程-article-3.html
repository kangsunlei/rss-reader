「缓存命中率」是个伪指标，应该看未命中的缓存

6/27/2026, 8:58:49 AM

📌 一句话摘要

文章提出在 AI 编程工具 OpenCode 中，缓存命中率百分比是伪指标，应改用未命中绝对 token 数来衡量缓存效率，并基于 16 万条消息实测给出不同模型的表现差异及可视化工具。

📝 详细摘要

文章以 AI 编程工具 OpenCode 的缓存问题切入，指出缓存命中率作为百分比指标存在根本缺陷：分母受上下文长度、新输入量、子 Agent 数量等用户使用方式影响，无法真实反映 provider 缓存质量。作者提出改用未命中绝对 token 数（上一条总 token 数减当前从缓存读回的 token 数），理想值为 0，值越大浪费越多。作者基于自己 16 万条消息的实测数据，展示了 DeepSeek-v4、GLM-4.7、GPT-5.5 等模型在输出侧 KV 缓存复用上的巨大差异（85%、63%、0.3%），并提供了一个开源可视化看板工具，可直接读取 OpenCode 本地 SQLite 数据库，按日下钻到具体会话查看缓存细节。文章观点清晰，数据扎实，对使用 OpenCode 的开发者有直接实用价值。

💡 主要观点

  1. 缓存命中率是伪指标，因分母受用户使用方式影响。 命中率百分比的总 token 数取决于上下文长度、新输入量和子 Agent 数量，与 provider 缓存质量无关，无法诊断问题。
  2. 应改用未命中绝对 token 数来衡量缓存效率。 未命中 token 数=上一条总 token 数-当前从缓存读回的 token 数，直接反映浪费量，理想值为 0，飙升说明缓存异常。
  3. 不同模型的输出侧缓存复用能力差异巨大。 作者实测 16 万条消息发现 DeepSeek-v4 有 85%对话能缓存上一轮输出，GLM-4.7 为 63%，而 GPT-5.5 仅 0.3%，不支持 KV 复用的模型浪费严重。

💬 文章金句

  • 一个百分比把「你怎么用」和「 provider 缓存好不好」混在一起，根本看不出问题出在哪。
  • 发现不同模型差异巨大：DeepSeek-v4 有 85% 的对话连上一轮的输出都能缓存住，GLM-4.7 有 63%，但 GPT-5.5 只有 0.3%。
