Netflix 如何构建面向互联网规模的实时分布式图数据库

1/21/2026, 4:31:00 PM

📌 一句话摘要

Netflix 利用 Kafka、Flink 以及在 Cassandra 之上构建的自定义键值抽象层，打造了实时分布式图（RDG），以处理超过 1500 亿条边和每秒 600 万次的写入。

📝 详细摘要

为了统一成员在流媒体、游戏和直播活动中的体验，Netflix 开发了实时分布式图（RDG）。RDG 摆脱了孤立的微服务数据库，采用三层架构：通过 Apache Kafka 进行摄取，利用 Apache Flink 进行近实时处理，以及一个可扩展的存储层。值得注意的是，由于水平扩展限制和运维复杂性，Netflix 绕过了 Neo4j 和 AWS Neptune 等专业图数据库。相反，他们利用了“KVDAL”（一个基于 Apache Cassandra 的内部抽象层），通过邻接表和二级映射来模拟图结构。这种方法使他们能够管理超过 80 亿个节点和 1500 亿条边，并保持个位数毫秒级的延迟，同时为每种节点/边类型使用独立的命名空间，以确保运维隔离和线性扩展能力。

💡 主要观点

  1. Netflix 选择在键值存储上模拟图功能，而非使用原生图数据库。 Neo4j 和 Neptune 等原生解决方案在水平扩展和高吞吐写入方面表现不佳；利用在 Cassandra 方面的内部专业知识提供了更好的可靠性和规模化能力。
  2. 该架构在 Kafka 主题和 Flink 作业之间采用 1:1 映射，以获得更好的可调优性。 最初的单体作业因吞吐量模式各异而失败；将作业分离允许针对不同的数据流进行独立扩展并简化维护。
  3. KVDAL 使用二级映射和命名空间来实现大规模扩展和运维隔离。 通过以键值格式存储邻接表，并将每种节点/边类型分配到唯一的命名空间，Netflix 可以独立扩展存储集群而互不影响。
  4. 实时处理优先于传统的基于批处理的数据仓库。 使用 Kafka 和 Flink 使图能够即时反映成员行为，这对于批处理系统无法支持的跨平台个性化体验至关重要。

💬 文章金句

  • Netflix 发现，在现有数据存储系统中模拟类图关系，比采用专门的图基础设施更简单。
  • 原生图数据库难以针对大规模实时数据集进行水平扩展。其性能通常会随着节点和边数量的增加而下降。
  • 有时正确的解决方案并非显而易见。Netflix 根据运维现实，选择使用键值存储来模拟图功能。
  • 系统维持着大约每秒 200 万次读取和 600 万次写入。
  • 在大规模环境下，隔离性和独立性至关重要。将每个节点和边类型分离到各自的命名空间中，实现了独立调优并缩小了问题的影响范围。
