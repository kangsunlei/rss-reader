我们在 Workers 中发布了 FinalizationRegistry：为什么你不应该使用它

6/11/2025, 2:00:01 PM

📌 一句话摘要

解释了 JavaScript FinalizationRegistry API，说明了尽管其具有非确定性，为何仍将其添加到 Cloudflare Workers，并推荐通过显式资源管理实现可预测的清理。

📝 详细摘要

本文讨论了将 JavaScript FinalizationRegistry API 集成到 Cloudflare Workers 中，主要是为了在使用 WebAssembly ( Wasm ) 时辅助内存管理。文章对比了 JavaScript 的自动垃圾回收和 Wasm 的手动内存管理，强调了两者之间共享内存的挑战，例如潜在的内存泄漏。虽然 FinalizationRegistry 允许为垃圾回收对象注册清理回调，但其非确定性特性（回调可能运行延迟或根本不运行）使其不适合可靠的资源管理。Cloudflare 启用它是为了支持高级 Wasm 用例，但也添加了安全措施，例如阻止在回调中进行 I/O 操作，并分析了其安全影响（混淆代理、GC 定时器），得出现有隔离模型是足够的结论。文章强烈推荐使用更新的、确定性的显式资源管理提案（`using`/`await using`）作为在 JavaScript 中实现可预测资源清理的更好替代方案。

💡 主要观点

  1. JS ( GC ) 和 Wasm ( 手动 ) 之间的内存共享复杂且容易出现内存泄漏。 JavaScript 自动管理内存，而 WebAssembly 需要手动释放。在 JS 中操作 Wasm 内存需要小心处理以避免内存泄漏，尤其是在 Workers 等受限环境中。
  2. FinalizationRegistry 在 GC 时提供回调，但它是非确定性的，对于关键清理不可靠。 该 API 允许注册终结器，但不能保证它们何时或是否会运行，因此对于重要的资源释放逻辑来说，这是一个糟糕的选择。
  3. Cloudflare 添加了 FinalizationRegistry 并采取了安全措施，阻止在回调中进行 I/O 操作。 为特定的 Wasm 用例启用，Cloudflare 限制了回调以防止开发者依赖非确定性时序来实现副作用，从而减轻误用。
  4. 显式资源管理是推荐的、确定性的清理替代方案。 `using`/`await using` 语法提供了一种可靠的方式来确保资源在超出作用域时能够可预测地被清理，这与非确定性的 GC 终结器不同。

💬 文章金句

  • 然而，尽管它可用，我们的总体建议是：**在大多数情况下避免直接使用它。**
  • 虽然偶尔的内存泄漏可能不会立即造成问题，但随着时间的推移，它们会导致内存使用量增加并降低性能，尤其是在像 Cloudflare Workers 这样的内存受限环境中。
  • FinalizationRegistry 存在一个根本性问题：垃圾回收是非确定性的，可能会在将来的某个任意时间清理你的未使用内存。
  • 考虑到其非确定性特性，开发者很少将终结器用于任何重要的程序逻辑。将其视为最后的安全网，而不是主要的清理机制...
  • 显式资源管理...引入了一种确定性方法来处理需要手动清理的资源...
