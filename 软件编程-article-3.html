小心！你的 DDL 变更可能正悄悄搞垮 MySQL 性能……

10/12/2025, 11:16:00 PM

📌 一句话摘要

深入解析了基于 gh-ost 的 DDL 变更在单行大记录场景下，如何导致 MySQL 表空间膨胀、统计信息偏差，进而引发慢 SQL 的根因及解决方案。

📝 详细摘要

文章详细剖析了在得物（DeWu）平台，业务 DDL 变更后 MySQL 表存储空间膨胀近 100%、统计信息严重偏差并导致部分 SQL 慢查的问题。核心原因在于，基于 gh-ost 二次开发的无锁 DDL 变更工具，其“全量数据复制+增量 binlog 回放”的并行交叉处理机制，导致数据写入顺序的非预期性（即非主键顺序写入）。当单行记录较大（如 5KB）时，这种写入顺序会触发 MySQL B+tree 页分裂的“瑕疵”，使得一个 16KB 的页只存储 1 条记录，造成大量空间浪费。页膨胀又导致 InnoDB 采样统计信息时，因内部优化逻辑（对单页唯一值减 1）在单行页上产生严重偏差，最终误导优化器选择次优索引，引发慢 SQL。文章提供了临时使用原生 DDL 修复和长期修改变更工具流程的解决方案。

💡 主要观点

  1. 基于 gh-ost 的 DDL 变更机制导致数据写入顺序的非预期性（即非主键顺序写入） 工具的全量复制与增量 binlog 回放并行交叉，可能使主键 ID 大的记录先写入，小 ID 记录后写入，这种非预期的写入顺序为后续表膨胀问题埋下伏笔。
  2. 异常写入顺序叠加单行大记录触发 MySQL 页分裂瑕疵导致表膨胀 当单行记录较大时，特殊的写入顺序会使 MySQL 在页分裂时，一个 16KB 的页仅存储一条记录，造成大量存储空间浪费。
  3. 表膨胀导致 InnoDB 统计信息严重偏差 页内记录数过少，结合 InnoDB 统计信息收集算法中“减 1”修正逻辑，使主键索引基数统计值远低于实际，影响优化器判断。
  4. 统计信息偏差间接导致 SQL 优化器选择次优索引引发慢查询 错误的表总行数估算，特别是对于带 ORDER BY LIMIT 的 SQL，会使优化器错误倾向于选择有序索引，忽略实际业务数据分布，导致性能下降。
  5. 通过调整 DDL 工具流程可长期解决该问题 将 DDL 工具的流程调整为先完成全量数据复制，再进行增量 binlog 回放，可避免异常写入顺序，从根本上解决表膨胀和统计信息偏差问题。

💬 文章金句

  • 这种写入特性叠加单行记录过大的时候（业务表单行记录大小 5k 左右），会碰到 MySQL 页分裂的一个瑕疵（暂且称之为瑕疵，或许是一个 Bug），导致了一个页只存储了 1 条记录（16k 的页只存储了 5k，浪费 2/3 空间），放大了存储问题。
  • 表空间膨胀跟统计信息出错是同一个问题导致，而统计信息出错间接导致了部分 SQL 出现了慢查，下面带着这些问题开始一步步分析找根因。
  • 为了避免相邻两次 dive 统计到连续的相同的两个数据，因此减 1 进行修正。本来一个页面就只有 1 条记录，再进行减 1 操作就变成 0 了，根据上面的公式得到的索引总唯一值就偏差非常大了。
  • 但一个最重要的因素被 MySQL 忽略了，就是实际业务数据分布并不是按它给的这种公式来，往往需要扫描很多数据才能满足 limit 值，造成慢 SQL。
  • 可控的情况下选择在低峰期对表执行原生 alter table xxx engine=innodb 语句， MySQL 内部重新整理了表空间数据，相关问题恢复正常。
  • 既然在变更过程中复制全量数据和 binlog 增量数据回放存在交叉并行执行的可能，那么如果我们先执行全量数据复制，然后再进行增量 binlog 回放是不是就可以绕过这个页分裂问题。
