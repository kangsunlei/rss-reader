📌 一句话摘要

本文详细介绍了 vivo 将万台规模 YARN 集群从 Hadoop 2.6.0 升级至 Hadoop 3.1 的完整实践，重点阐述了调度器平滑切换、性能优化、业务连续性保障及引擎兼容性等核心难点与解决方案。

📝 详细摘要

文章系统回顾了 vivo 大数据平台将 YARN 集群从 2.6.0 升级至 3.1 版本的完整历程。面对万台规模、日均百万任务的挑战，团队围绕四大核心难点展开攻坚：一是调度器从 Fair Scheduler 切换至 Capacity Scheduler，通过回迁 35 个社区 PR 实现全路径队列名支持，并自研配置自动转换工具；二是对 Capacity Scheduler 进行深度性能优化，包括引入排序缓存、避免无效分配、以指标替代日志输出等，将排序操作减少 96% 以上；三是保障升级过程中的业务连续性，通过增强低版本 NodeManager 的异常容错能力和引入动态序列化开关机制，实现组件间的无缝升降级；四是解决计算引擎兼容性问题，统一 Hadoop 依赖、规范提交节点配置、升级 Hive 客户端，并设计了一套基于调度平台的 JAR 任务灰度切换流程。此次升级不仅解决了历史技术债，还为未来 Federation、GPU 调度等高级特性奠定了基础。

💡 主要观点

  1. 通过回迁 35 个社区 PR，在 YARN 3.1 上实现了对全路径队列名的支持，解决了调度器切换的核心兼容性问题。 低版本公平调度器支持全路径队列名，而 YARN 3.1 的容量调度器仅支持叶子队列短名。团队以 YARN-9879 为目标，逐个回迁并适配了 35 个相关 PR，成功兼容了现有任务的提交方式。
  2. 引入排序缓存机制，将调度器排序操作减少 96% 以上，显著提升万台集群的调度性能。 通过新增两个配置参数控制队列和应用排序结果的缓存有效期，将每分钟 50 万次排序降至约 1.8 万次，大幅降低 ResourceManager 的 CPU 负载。
  3. 通过增强低版本 NodeManager 的异常容错能力，实现安全、可控的版本回退。 高版本 NodeManager 新增了 15 个状态字段，导致低版本回退时 recovery 失败。团队在低版本的反序列化逻辑中增加异常容错，遇到无法识别的字段时安全忽略，避免了大规模代码修改。
  4. 设计动态序列化开关机制，解决跨版本 Token 序列化格式不兼容问题。 高版本 YARN 将 Token 序列化从 Java 字节流迁移至 Protobuf，导致低版本 NodeManager 无法解析。团队在 ResourceManager 中新增开关，升级初期使用旧格式，全量升级完成后切换至新格式。
  5. 基于调度平台设计 JAR 任务灰度切换流程，实现从 Hadoop 2 到 Hadoop 3 的平滑过渡。 通过标签标记、分批灰度、失败自动回退和兼容整改三步流程，在不中断业务的前提下，将大量黑盒 JAR 任务平稳迁移至 Hadoop 3 依赖。

💬 文章金句

  • 单纯依靠机器堆叠来满足不断扩张的大数据需求，是一种投入产出比极低的粗放模式。
  • 通过该机制，可有效限制单位时间内的排序调用频次。仍以每分钟 50 万次分配为例，若将缓存有效期设为 10 毫秒，则每分钟最多仅需执行约 1.8 万次排序操作，相比原始方案的 50 万次排序，减少超过 96%。
  • 该方案兼具安全性与前瞻性：保障升级期间任务连续性，无需改变升级顺序，保留高版本全部功能能力，通过配置开关实现平滑过渡。
  • 通过依赖统一化、配置中心化、统一底层 hive 客户端依赖三大措施，系统性解决了计算引擎与 Hadoop3 的集成难题。
