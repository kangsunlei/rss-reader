我们如何为 GitHub Enterprise Server 重建高可用搜索架构

3/3/2026, 6:45:12 PM

📌 一句话摘要

GitHub Enterprise Server 将其搜索架构从单一的扩展 Elasticsearch 集群迁移到通过跨集群复制 (CCR) 同步的独立集群，以增强高可用性。

📝 详细摘要

本文详细介绍了 GitHub Enterprise Server (GHES) 为解决其搜索组件中长期存在的高可用性 (HA) 问题而进行的重大架构转变。此前，GHES 使用跨越主节点和副本节点的单一 Elasticsearch 集群，如果主分片在维护期间迁移到只读副本，往往会导致系统锁定或数据损坏。为了解决这个问题，GitHub 工程团队转向了领导者/跟随者模型，其中每个 GHES 实例都作为一个独立的单节点 Elasticsearch 集群运行。通过利用 Elasticsearch 的跨集群复制 (CCR)，数据在 Lucene 段级别进行持久化复制。文章解释了此次迁移的技术挑战，包括需要自定义引导逻辑和自动跟随策略，以管理原生 CCR 之外的索引生命周期。

💡 主要观点

  1. 之前的“扩展集群”架构由于不受控的分片移动导致了可用性风险。 Elasticsearch 可能会将主分片移动到只读副本节点，在维护期间创建循环依赖，即副本等待一个健康的集群，而集群在没有副本的情况下无法恢复。
  2. 为每个 GHES 实例转换到独立的单节点集群消除了循环依赖。 通过转向具有独立集群的领导者/跟随者模型，GitHub 确保关键数据保留在主节点上，并且对一个节点的维护不会锁定整个搜索系统。
  3. Elasticsearch 跨集群复制 (CCR) 提供了一种在 Lucene 段级别复制数据的原生且持久的方式。 CCR 在数据持久化到 Lucene 段后进行复制，确保只有持久存储的信息被复制，这符合 GitHub Enterprise Server 根深蒂固的领导者/跟随者模式。
  4. 需要自定义编排来管理完整的索引生命周期，包括引导和自动跟随策略。 由于 CCR 仅处理文档复制，GitHub 设计了用于故障转移、索引删除和升级的自定义工作流，以确保现有和未来的索引在节点之间得到正确管理。

💬 文章金句

  • 如果他们没有严格按照正确的顺序执行维护或升级步骤，搜索索引可能会损坏并需要修复，或者可能会被锁定并在升级期间引发问题。
  • Elasticsearch 可能会将主分片（负责接收/验证写入）移动到副本。如果该副本随后因维护而关闭，GitHub Enterprise Server 可能会陷入锁定状态。
  • 通过这种模式，我们正转向使用多个‘单节点’ Elasticsearch 集群。现在，每个 Enterprise Server 实例都将作为独立的单节点 Elasticsearch 集群运行。
  • Elasticsearch 仅处理文档复制，而我们负责索引生命周期的其余部分。
