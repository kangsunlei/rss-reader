RFC 规范中的 CNAME 排序如何导致 Cloudflare 1.1.1.1 故障

2/7/2026, 11:32:00 AM

📌 一句话摘要

Cloudflare 的 1.1.1.1 服务在一次内存优化后发生故障，该优化无意中重新排列了 DNS 响应中的 CNAME 记录，导致依赖特定记录顺序的 glibc 等旧版客户端解析失败。

📝 详细摘要

本文分析了 Cloudflare 1.1.1.1 DNS 服务的一次重大故障，该故障由旨在减少内存消耗的常规更新引起。通过更改构建 DNS 响应的内部逻辑，Cloudflare 意外地将 CNAME 记录移动到了应答部分的末尾（位于最终 A 记录之后）。虽然现代解析器通常与顺序无关，但旧版实现（最著名的是 glibc 中的 getaddrinfo 函数）在别名未置于地址之前时会解析失败。这次事件是海勒姆定律（Hyrum's Law）的教科书级案例，即系统的可观测行为会成为事实上的契约。作为回应，Cloudflare 已向 IETF 提交了一份新的规范提案，旨在正式确定 DNS 记录排序，以防止未来出现类似的互操作性问题。

💡 主要观点

  1. 内存优化导致 DNS 响应结构发生了细微但具有破坏性的变化。 为了减少内存分配，Cloudflare 的代码开始将 CNAME 附加到现有应答列表的末尾，而不是置于开头，导致 CNAME 记录出现在 DNS 响应中最终 IP 地址之后。
  2. glibc 等旧版 DNS 客户端依赖特定的记录顺序进行解析。 虽然许多现代系统与顺序无关，但 glibc 的 getaddrinfo 会按顺序迭代，并期望 CNAME 记录出现在最终答案之前，这导致在发布期间出现了解析失败。
  3. 该事件凸显了分布式系统中模糊的 RFC 规范所带来的风险。 较旧的 DNS 标准并未明确规定响应部分内的记录顺序，导致服务器端优化与客户端解析逻辑之间出现了分歧。
  4. 海勒姆定律解释了为什么技术上“有效”的更改仍可能导致灾难性故障。 当用户群足够大时，系统的每一个可观测行为（即使是合同或标准中未承诺的行为）最终都会被生态系统的某些部分所依赖。
  5. Cloudflare 正在寻求正式的标准化以永久解决歧义。 该公司已向 IETF 提交了一份互联网草案，明确定义应如何处理 DNS 响应中的 CNAME 记录，旨在将“最佳实践”转变为正式要求。

💬 文章金句

  • 虽然大多数现代软件认为 DNS 响应中的记录顺序无关紧要，但 Cloudflare 团队发现某些实现期望 CNAME 记录出现在所有其他记录类型之前。
  • 为了节省一些内存分配和拷贝，代码被更改为将 CNAME 附加到现有应答列表。结果，1.1.1.1 返回的响应有时会将 CNAME 记录显示在底部。
  • 当一个 API 的用户达到足够数量时，你在契约中承诺了什么并不重要：你系统的所有可观测行为都会被某人所依赖。
  • Cloudflare 提议了一项 RFC，明确定义了如何正确处理 DNS 响应中的 CNAME 记录。
  • 该更改于 2025 年 12 月 2 日引入，12 月 10 日发布到测试环境，并于 2026 年 1 月 7 日开始部署。
