📌 一句话摘要

本文深入分析了在华为昇腾 910C 上对大模型推理进行源码级和算子层优化，通过多流重叠、host 开销优化、融合算子、静态 kernel 编译等手段，实现了 TPOT 延迟从基线 14.1ms 降至 5.0ms 的显著提升，并验证了这些优化在真实业务场景中的有效性。

📝 详细摘要

在上一篇介绍完基础参数调优后，本文继续深入 vllm-ascend 源码，针对 MoE 共享专家、decode host 侧开销、Block Table 映射、GDN 路径、采样与投机解码等多个方面进行了专项优化。同时，通过编译 MC2 通信融合、SuperKernel、自研 910C 融合算子，以及修复静态 kernel 编译，进一步压缩了计算和通信开销。最终，在真实业务场景中，TPOT 延迟较基线下降了 64.8%，证明了这些优化方法的有效性和实用性。

💡 主要观点

  1. MoE 共享专家多流重叠优化 通过将 shared expert 的计算和 AllReduce 放到独立的 side stream，与 routed experts 并行执行，并移除冗余的同步事件，实现了计算和通信的重叠，显著降低了 MoE 层的执行时间。
  2. decode host 侧开销优化 分析发现 c=1 decode 时 host 侧的拷贝和提交操作占用了大量时间，通过引入上一轮状态跟踪，跳过不必要的 block table 提交和数据拷贝，并优化了 positions 的计算路径，大幅减少了 host 侧的开销。
  3. 算子层优化与编译融合 利用 FUSED_MC2 实现了通信-计算融合，通过 SuperKernel 合并了多个小 kernel，并自研了 matmul_allreduce_add_rmsnorm_910c 融合算子，这些都有效减少了 kernel launch 次数和 HBM 访问，提高了执行效率。
  4. 静态 kernel 编译与 MTP 兼容性 修复了静态 kernel 编译中的路径问题，实现了 100% 的编译成功率。同时，调整了 cudagraph 的捕获尺寸，使其与 MTP 投机解码后的 token 数匹配，确保了投机解码模式下的性能稳定性。

💬 文章金句

  • 优化的另一半工作是证伪。在 910C 上，MatmulAllReduce、FlashComm 等在文档中被推荐的特性，实际测试后发现支持不完整或无收益，甚至有负向影响。
