淘宝闪购本体平台：让人与 AI Agent 共用一份实时可信的业务知识

11/18/2026, 10:29:00 AM

📌 一句话摘要

本文介绍了淘宝闪购本体平台的架构设计，通过三层元模型和治理链路，将业务知识组织为可版本化的定义，解决了人与 AI Agent 获取一致业务口径的核心问题。

📝 详细摘要

本文系统阐述了淘宝闪购本体平台的核心设计目标和实现方案。该平台通过构建三层元模型（实体层、关系层、策略层），结合治理链路和查询链路，解决了数据口径对齐问题。文章详细介绍了平台的五个核心模块职责划分，以及从知识生产、变更发布到查询消费的完整流程。随后阐述了平台经历的三代架构演进，从读写分离到实时多模，最终实现了跨引擎拼装的统一。文章还讨论了平台的边界、能力上限以及后续演进方向，最后总结了四条核心承诺和四条避坑指南。

💡 主要观点

  1. 平台通过三层元模型构建业务知识 实体层定义业务对象、语义数据集、表对象和指标；关系层统一边的定义方式；策略层包含术语、视角、事件、决策、方法论、行动和剧本七类，确保业务知识结构化可追溯。
  2. 治理链路确保知识定义的可信度 通过版本化管理、审批流程和变更留痕，保证每一份定义都有明确的责任人和生效时间，解决了人与 Agent 获取一致口径的核心问题。
  3. 三代架构演进实现查询一致性 从第一代的读写分离，到第二代的跨引擎拼装，再到第三代的实时多模，平台不断优化查询链路，最终实现了从离线到实时的知识同步。
  4. 平台只提供定义，不承担计算 接口设计定位为知识定义服务，计算由业务系统负责，确保了责任边界清晰，避免了平台因计算问题导致的口径变更责任。
  5. 场景子图快照保证查询范围可控 通过场景管理模块圈选子图快照，确保查询在特定范围内，防止 Agent 获取范围外的错误答案，同时明确知识的时效性边界。

💬 文章金句

  • 淘宝闪购本体平台要解决的就是这件事：把业务对象、关系、术语、分析方法和约束组织成一份可版本化的知识，经确认与审批发布，再通过 Web、OpenAPI、HSF 与 MCP 交给人和 Agent。
  • 光把口径写下来还不够，定义有没有被确认过、变更有没有被留住、查询跟不跟得上，这三件事才决定它能不能用。
  • 平台的核心承诺是：单一生效版本、每次变更留痕、读模型可重建、范围可限定。
  • 判断一套知识是否具备'机器可读性'，只需追问三个问题：这一版是谁确认的？发生变更后，引用的上下游是否能感知？超出范围时，它会不会给出错误答案？
  • 平台只输出自己能归因的量，不认领业务侧的收益。
