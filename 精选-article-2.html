拆解小红书存储底座 05｜RedTAO 2.0：万亿级图数据库的设计与实践

11/12/2026, 9:59:00 AM

📌 一句话摘要

本文详解了小红书自研的分布式图数据库 RedTAO 2.0 的三层架构设计，包括计算、缓存、存储层的职责划分及实现方案，以及如何在万亿级数据规模下支持低延迟的在线查询和跨区域多活。

📝 详细摘要

本文聚焦小红书自研分布式图数据库 RedTAO 2.0 的设计与实践。文章首先阐述了图数据库在点赞、关注、收藏等场景下的演进需求，随后介绍了 RedTAO 采用的三层分工架构：计算层通过无状态的 GraphServer 提供一跳 API 和多跳 Gremlin 查询，缓存层由 Cache Server 和 Vertex Server 负责关系集合、顶点属性和计数的高频数据快速访问，存储层采用 MySQL 作为持久化底座，围绕读密集场景调整数据组织方式。文章进一步详细描述了查询优化策略、缓存组织方式、存储数据布局以及跨区域部署下的同步机制。最后，作者展望了 RedTAO 的未来发展方向，包括面向大规模数据的复杂图计算、内存组织优化以及从 MySQL 演进到 RedDB 的计划。

💡 主要观点

  1. 三层分工架构设计 RedTAO 将系统划分为计算层、缓存层和存储层，分别围绕计算资源、内存容量和存储容量独立扩展，支持在线性能、业务扩展与异地多活的平衡。
  2. 计算层的查询优化策略 采用基于规则的优化，将常见查询模式的优化经验沉淀为可解释、可扩展的规则，同时结合存储层能力，尽量让筛选和结果裁减靠近数据完成，降低传输与中间计算开销。
  3. 缓存层的组织方式 按访问模式划分职责，Cache Server 服务关系集合，Vertex Server 服务顶点属性与计数；Vertex Server 通过数据冗余减少 RPC 扇出，适合读密集、批量点读较多且数据规模可控的场景。
  4. 存储层的数据组织与同步机制 以 MySQL 作为持久化底座，让经常一起读取的关系靠近存放，提前维护常用统计；跨区域部署下，各单元独立维护自身的统计贡献，再通过异步同步和本地汇总形成结果。
  5. 未来演进方向规划 RedTAO 将沿着复杂图计算、内存组织优化和从 MySQL 演进到 RedDB 三个方向继续演进，以降低成本并将图能力融入多模数据库的统一底座。

💬 文章金句

  • RedTAO 是小红书自研的分布式图数据库。它从支撑核心在线业务的一跳关系访问起步，逐步演进为支持多跳查询的图数据库。
  • 截至 2026 年 11 月，目前已部署近百个集群，单集群最大承载超过万亿行点边数据，在线查询规模超过千万 QPS。
  • RedTAO 将系统划分为计算层、缓存层和存储层，分别围绕计算资源、内存容量和存储容量独立扩展。
  • 计算层首先要把业务表达转化为可执行的查询计划。业界通常通过规则改写，或结合统计信息比较执行方案，减少不必要的访问。
  • RedTAO 当前以 MySQL 作为生产持久化底座，复用成熟的存储与复制能力，并围绕读密集场景调整数据组织。
