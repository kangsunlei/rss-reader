淘宝 AI 购物助手在线评测落地实践

10/12/2026, 2:59:00 AM

📌 一句话摘要

淘天团队分享了 LLM-as-a-Judge 在日均海量会话、多域异构的电商 AI 购物助手场景中的日级在线工业化评测体系与归因闭环实践。

📝 详细摘要

大淘宝技术团队系统梳理了将学术界 LLM-as-a-Judge 方法落地于电商 AI 购物助手（购后多域）日级全量在线评测的工程实践。文章指出，工业落地的核心瓶颈不在 Judge 模型本身，而在数据清洗和评测标准的持续校准。团队通过四层清洗管线治理线上脏数据；采用「数仓与推理平台解耦」的分布式批量架构解决时效与稳定性瓶颈；提出 CNT 六层漏斗 Rubric 标准与短路机制；在 Prompt 设计上实施事实锚定、时间戳拼接与跨轮上下文隔离；并建立四层归因框架（数据层、Prompt 层、Rubric 层、Agent 真实质量），跑通了从日级观测、根因定位到定点修复核验的完整优化闭环。

💡 主要观点

  1. 评测可信度的瓶颈不在 Judge 模型，而在输入数据清洗与标准对齐 线上日志存在碎片化、卡片信息缺失、tool_calls 内部提示词噪声与语义不一致等问题。团队设计了四层清洗管线（格式修复、语义对齐、干扰屏蔽、入口过滤精化），直接决定了 Judge 判定的稳定性与可信度。
  2. 构建 CNT 六层漏斗 Rubric 统一框架与短路机制 涵盖 CTX（上下文门控）、OOSR（越界拒答）、OOC（能力边界）、TCC（工具链路）、CNT（内容与文本）以及 RED（安全红线），串行层采用任一判 0 即短路的原则，RED 并联恒评，兼顾主因定位与安全兜底。
  3. 数仓与推理平台解耦，支撑多域大规模日级批量评测 坚持「数据归数据、推理归推理」原则，预处理和后处理聚合全在数仓 SQL 完成，推理平台仅做模型调度。各域独立 workflow 并行运行，设置 Check 节点防丢防重，大幅提高调试与迭代效率。
  4. 精细化 Prompt 工程压制幻觉，发现上下文并非越多越好 通过输入变量明确声明、反向证据摘录、提问时间戳拼接解决时效误判；同时发现全对话工具链会导致注意力分散与跨轮信息串扰，改为仅保留当轮 tool_calls 后通过率大幅跃升。
  5. 建立四层归因闭环，将评测报数转化为技术迭代支撑 将存疑样本严格归因为数据层、Prompt 层、Rubric 层与 Agent 真实缺陷，避免盲目调优 Prompt 掩盖真问题；通过 SQL 可复跑规则在修复前后比对命中数，驱动定向收敛验证。

💬 文章金句

  • 实践表明，评测可信度的瓶颈不在 Judge 模型本身，而在数据质量和评测标准的持续校准。
  • 全对话工具链中前几轮的工具返回被 Judge 用来评判当前轮的 Agent 回复，导致跨轮信息互相干扰串味
  • 给 Judge 更多上下文不一定更好。
  • 早期没有归因机制时，看到通过率下降的第一反应是调 Prompt，结果有时越调越差，因为根因在数据层或 Rubric 层，改 Prompt 只是在掩盖问题。
  • 多轮打标优化的目标不是"让通过率变高"，而是"让通过率更可信"。
