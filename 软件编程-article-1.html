【第 3625 期】写 TypeScript 不等于安全：边界设计才是关键

12/15/2025, 1:01:00 AM

📌 一句话摘要

文章指出 TypeScript 只保证代码类型自洽，不保证运行时逻辑正确，强调边界设计、数据验证和架构思维才是真正实现类型安全的关键。

📝 详细摘要

文章深入探讨了 TypeScript 在实际开发中带来的“安全幻觉”，阐明 TypeScript 作为编译时工具，只能确保代码内部的类型一致性，却无法验证外部数据和防止运行时错误。作者通过具体案例（如网络请求返回数据）揭示了 TypeScript 中的“逃生通道”及其局限性。文章通过对比 Elm 语言，强调了良好边界设计的重要性，即区分不安全的基础设施层和处理已验证数据的领域层。最后，文章提出在 TypeScript 项目中实现真正类型安全的实践建议，包括边界验证、禁用逃生通道、关注点分离和测试失败场景，呼吁开发者提升架构思维，而非盲目依赖工具。

💡 主要观点

  1. TypeScript 仅保证代码类型自洽，不代表运行时逻辑正确或数据安全。 TypeScript 在编译时检查类型一致性，但对来自外部世界的不可信数据无能为力，易使开发者产生虚假安全感。
  2. TypeScript 存在多种“逃生通道”，如 any、as 等，可能导致数据不安全流入系统。 在大型项目中，这些机制可能被滥用，使得类型系统失去其应有的保护作用，增加了潜在的运行时错误风险。
  3. 实现真正的类型安全需关注清晰的边界设计和运行时数据验证。 应将处理外部数据的基础设施层与处理已验证数据的领域层分离，并在边界处使用校验工具进行严格验证，才能有效防止错误。

💬 文章金句

  • TypeScript 编译器给出的那个绿色对勾，只能说明你的代码在类型层面上是自洽的 ------ 却不能保证它是正确的。
  • TypeScript 给了你一种 "安全感"，但不是 "安全" 的保证。而那种 "感觉与现实之间、编译时与运行时之间、代码与真实世界之间" 的差距 ------ 正是线上 Bug 滋生的地方。
  • 在 TypeScript 里，没有这样的强制机制。你可以把未经验证的数据传到任何地方。
  • TypeScript 本质上是一个非常先进的 Linter（代码检查工具）。它非常擅长捕捉拼写错误、重构失误，以及在代码内部误用 API 的问题。但它不是安全保证，不是验证机制，更不是替代思考的工具。
  • 你在任何系统中 ------ 无论是 TypeScript、Elm，还是其他语言 ------ 你都需要清楚：哪些地方是不安全的，哪些地方才变得安全。
