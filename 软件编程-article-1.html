文章介绍了一款零侵入、不改代码、不需代理的 Chrome 插件，通过劫持浏览器网络请求实现高效前端 Mock，解决开发痛点。

📝 详细摘要

本文深入探讨了一款名为“Quick Mock”的 Chrome 扩展程序，旨在解决前端开发中 API 联调的常见痛点，特别是传统 Mock 工具如 APIfox 带来的资源占用高、操作繁琐等问题。该插件的核心亮点在于其“零侵入”特性，即在不修改业务代码、不开启代理的情况下，通过巧妙地在网页加载初期劫持并重写浏览器原生的`fetch`和`XMLHttpRequest`方法，高效实现接口 Mock。文章还清晰地解释了 Chrome 扩展中`content.js`和`injected.js`脚本隔离与通信机制，并通过`postMessage`实现安全的数据交换。此外，文中提供了详细的项目结构、安装指南及关键技术点总结，对前端开发者而言具有极高的实用价值和参考意义。

💡 主要观点

  1. 零侵入 Mock 解决了传统工具的痛点并提升开发效率。 现有 Mock 工具如 APIfox 占用资源大、操作繁琐，而该插件通过无客户端、不改代码的方式，大幅简化了前端联调和调试流程，显著提升开发效率。
  2. 核心原理是通过劫持浏览器原生网络请求实现 Mock。 插件在页面加载前替换`fetch`和`XMLHttpRequest`，使所有请求先经过自定义逻辑判断是否需要返回假数据，实现无感 Mock。
  3. Content Script 与 Injected Script 的分离设计是实现插件功能的基础。 Content Script 负责访问 Chrome API 读取用户配置，Injected Script 则在网页真实环境中重写`fetch`和`XMLHttpRequest`，两者职责分离是克服浏览器脚本隔离的关键。
  4. `postMessage`是隔离脚本间实现数据交换和指令传递的关键机制。 由于 Content Script 和 Injected Script 运行在隔离的 JavaScript 环境中，它们通过`postMessage`机制进行安全高效的通信，确保 Mock 规则能够从插件配置传递到请求拦截逻辑。

💬 文章金句

  • 现在 mock 不用 APIfox，内存占用降了不少，电脑顺多了，浏览器里一键 Mock，调试又快又省心。
  • 在网页加载前，偷偷替换掉浏览器原生的 fetch 和 XMLHttpRequest ，让所有网络请求先经过我们的"检查站"，符合规则的就返回假数据，不符合的就放行。
  • content.js = 银行金库管理员 - 有钥匙（Chrome API 权限） - 能读取保险箱（chrome.storage） - 但不能直接接触客户（网页 JavaScript）。
  • injected.js = 银行大堂经理 - 直接面对客户（网页代码） - 能拦截客户请求（重写 fetch） - 但没有金库钥匙（无法访问 chrome.storage）。
  • Content Script 运行在隔离的沙箱中，无法访问网页的 window.fetch。
