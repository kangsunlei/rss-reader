一文搞懂 MCP 开发

11/3/2026, 12:45:00 AM

📌 一句话摘要

本文系统阐述了 MCP（Model Context Protocol）协议的核心概念、架构设计、传输机制及安全模型，解释了其在 AI 应用与外部系统集成中的标准化作用，帮助读者理解何时如何正确采用 MCP。

📝 详细摘要

文章从 MCP 出现的背景谈起，指出传统 AI 应用接入外部系统时需为每一种 Host-数据源组合编写专属集成代码，形成 M×N 的规模问题。MCP 通过在中间引入标准协议，将此简化为 M+N：每个数据源实现一个 Server，每个 AI 应用完成一次 Client 适配。文章详细解释了 MCP 的三大核心机制：能力暴露（Tools、Resources、Prompts 三种原语）、反向能力（Sampling、Elicitation）以及安全模型（Host 不信任 Server，Server 不信任 Client）。随后阐述了两种部署模式：本地 stdio 与远程 Streamable HTTP，分析了为何弃用早期的 SSE 长连接设计。最后以 Vercel MCP 为例，展示了 OAuth 2.1 鉴权、权限裁剪及实际使用场景，全面总结了 MCP 的设计思想与落地实践。

💡 主要观点

  1. MCP 通过标准化协议将 AI 应用与外部系统的集成问题从 M×N 降为 M+N 传统模式下，3 个 AI 应用 × 3 个数据源需要 9 套集成代码；MCP 后仅需每个数据源实现一个 Server（3 个），每个 AI 应用完成一次 Client 适配（3 个），显著降低开发成本。
  2. MCP 定义三种原语暴露能力：Tools（模型驱动调用）、Resources（应用注入上下文）、Prompts（用户主动选择模板） Tools 由模型依据描述决定调用时机，Resources 由 Host 主动拉取注入对话，Prompts 由用户在界面中选择触发，三者按控制权归属区分，支撑不同交互场景。
  3. 安全模型强调信任边界：Host 不信任 Server，Server 不信任 Client，反向能力由 Host 完全控制 Tool Annotations 为自我声明建议，Host 必须基于自身策略引擎做出安全决策；Sampling 与 Elicitation 请求均由 Host 拦截审核，防止 Server 越权访问模型或用户。
  4. 远程 MCP 采用 Streamable HTTP 传输，配合 OAuth 2.1 实现集中鉴权与权限裁剪 相较早期的 stdio+SSE 双通道设计，Streamable HTTP 无状态、易水平扩展；OAuth 2.1 统一签发 token，同一端点根据 scope 动态返回不同工具列表，提升安全性与可维护性。
  5. Vercel MCP 案例展示了统一端点、凭证集中管控及按权限暴露能力的实际落地效果 用户只需配置一个 URL，即可在 Cursor、Claude、VS Code 等多种 Host 中共享同一套能力；模型可自动编排工具调用链，无需手动打开 Dashboard，提升使用便利性。

💬 文章金句

  • MCP 的方案是在中间引入一层标准协议，将"如何建立连接、如何发现能力、如何调用工具"统一约定
  • 由此 M×N 降为 M+N：每个数据源实现一个 Server，每个 AI 应用完成一次 Client 适配
  • Function Calling 定义了"模型如何表达调用意图"，MCP 定义了"调用意图如何标准化地到达外部系统"
  • Host 信任用户，不信任 Server。Server 提供的 Tool Annotations、工具描述、返回内容均可能包含恶意信息
  • 同一个 URL 根据 token 的 scope 动态裁剪 tools/list 的返回结果
