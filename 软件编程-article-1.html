应对 GitHub 近期的可用性问题

3/11/2026, 9:41:55 PM

📌 一句话摘要

GitHub 针对近期发生的重大停机事件，分析了架构耦合和数据库过载等根本原因，并概述了以迁移至 Azure 和服务解耦为核心的恢复策略。

📝 详细摘要

这份来自 GitHub 的官方事后分析报告探讨了 2024 年初发生的一系列重大可用性问题。工程团队确定了导致不稳定的三个主要驱动因素：前所未有的负载增长、导致级联故障的紧密架构耦合，以及缺乏健壮的负载丢弃（load-shedding）机制。具体而言，2 月 9 日的事件是由核心数据库过载引起的，原因是第三方应用的 API 流量激增了 10 倍，同时缓存 TTL 被大幅缩短。GitHub Actions 的其他故障则追溯到遥测数据缺失以及 Redis 故障转移程序中的潜在配置错误。为了恢复平台可靠性，GitHub 正在实施短期修复措施，例如重新设计用户缓存系统和隔离关键依赖项。其长期策略包括大规模迁移至 Azure 基础设施以实现更好的水平扩展，并将单体架构拆分为隔离的微服务和数据域，以防止局部故障影响整个平台。

💡 主要观点

  1. 架构耦合和快速增长是近期平台不稳定和服务降级的主要驱动因素。 GitHub 当前的架构导致特定数据库集群或服务中的局部问题会级联影响到整个平台。一段时期的极速使用增长加剧了这一情况，暴露了现有的扩展限制和单点故障。
  2. 2 月 9 日的数据库过载是配置变更与意外外部 API 流量激增共同导致的“完美风暴”。 为了推出新模型，缓存 TTL 从 12 小时缩短至 2 小时，恰逢热门客户端应用的读取流量增加了 10 倍。这使核心身份验证数据库不堪重负，而当时该数据库缺乏细粒度的流量阻断开关。
  3. GitHub Actions 的故障转移机制失败是由于遥测缺失和潜在配置问题，而非容量限制。 在一个案例中，遥测缺失触发了错误的安全性策略，导致虚拟机元数据访问被阻断。在另一个案例中，Redis 故障转移由于一个仅在生产事件中才暴露的隐藏配置错误，导致集群没有可写的节点。
  4. 迁移至 Azure 和拆解单体架构是 GitHub 长期韧性策略的核心支柱。 通过在 7 月前将 50% 的流量迁移至 Azure，GitHub 旨在利用托管服务和水平扩展。同时，他们正在将单体架构分解为隔离的数据域，以实现独立扩展和局部负载丢弃。

💬 文章金句

  • 我们未能达到自己的可用性标准，我们深知可靠性是您日常工作的基石。
  • 架构耦合导致局部问题级联影响到关键服务，且系统无法充分丢弃来自异常客户端的负载。
  • 该架构最初是出于简单性考虑而选择的，当时模型非常少……但随着时间的推移，每个用户几字节的数据增长到了几千字节。
  • 我们正按计划在 7 月前通过 Azure 处理 GitHub 50% 的流量。
  • 根据需要将单体架构拆分为更隔离的服务和数据域，以便我们可以独立扩展，并实施关于流量丢弃的局部决策。
