从淘小蜜分流模型的实践，聊聊 Jev 与 System One

11/10/2026, 10:01:00 AM

📌 一句话摘要

本文通过淘小蜜客服 Agent 分流模型的实践经验，分析了 Jev 的实现原理及其与 System One 任务的关联，探讨了候选 logits 打分、动态选项映射、概率校准等关键技术细节。

📝 详细摘要

文章从淘小蜜客服 Agent 分流模型的演进讲起，详细梳理了三阶段迭代方案：第一阶段使用通用 LLM 做 ICL few-shot 分类，第二阶段对 7B 模型做 SFT，第三阶段将分类改为选择题形式。通过动态选项映射、std_sigmoid 筛选 hardcase、两阶段训练等技术手段，显著提升了模型在 Goodcase 和 Badcase 上的准确率。文章进一步分析了 Jev 的实现原理，倾向于通过读取生成模型候选 token logits 来计算结果；同时探讨了候选分数和概率校准的问题，指出直接使用 softmax 或 std_sigmoid 并不能得到真实的正确率。最后从业务场景出发，阐述了 System One 模型在客服场景中的潜在应用价值，包括 Agent 分流、双工判断、意图选择等多任务决策。

💡 主要观点

  1. 淘小蜜分流模型通过三阶段迭代实现了从通用 LLM 到选择题形式的分类转型 第一阶段使用 ICL few-shot 分类成本高且泛化差，第二阶段 SFT 受标签比例和位置捷径影响，第三阶段改为选择题并引入动态选项映射和 std_sigmoid 筛选 hardcase，有效提升了模型在边界 case 上的判别能力。
  2. Jev 可能通过读取候选 token logits 实现运行时选判断 结合 SemIf、open-bonsai-jev 等社区复现项目的验证，以及自身的分流训练经验，认为 Jev 采用冻结生成模型读取候选 logits 而非额外的分类 head，这种方式能实现快速响应和类型安全。
  3. 候选分数与概率校准是 System One 模型的关键挑战 直接对 logits 做 softmax 可得到概率分布，但不一定能真实反映正确率；通过温度缩放等校准方法可以提升置信度的可靠性，但无法改变错误答案的正确性。
  4. 动态选项映射有助于削弱模型对固定字母和位置的依赖 通过在不同 epoch 或样本中随机变换标签到字母的映射，防止模型形成“某个词对应 A”的捷径，增强模型依赖输入和选项内容进行判断的能力。
  5. System One 模型在客服场景可实现多任务快速决策 将 Agent 分流、双工判断、意图选择等任务统一交给 System One 模型处理，可显著降低高并发链路下的推理延迟和成本，提升整体响应速度。

💬 文章金句

  • Jev 没有公开模型结构和具体训练方法。
  • Jev 当前提供 Choice、Score 和 Noul 三种问题类型。
  • TypeSafe 把这类任务定义为 System One 任务：给定足够的信息后，可以在很短时间内完成的聚焦判断。
  • 我们使用的 V4 基线已经是 Stage 2 模型，所以分析训练收益时，要把 Stage 1 和 Stage 2 分开看。
  • System One / System Two 的分工可以更具体：慢模型负责理解复杂诉求、规划步骤、生成最终答复；快模型在每轮对话和执行过程中处理分流、守卫、工具路由、打断和结果校验。
