真正烧 Token 的不是代码，而是模型反复看同一份上下文

9/17/2026, 12:45:00 AM

📌 一句话摘要

本文结合轻量云多 Agent 研发工作流 DevFlow 的真实实践，揭示了长上下文在多轮请求中被反复携带导致 Token 消耗被放大的核心问题，并系统阐述了通过渐进式加载、响应级批量、批量编辑工具 replace_batch 及 Hook 降级机制等四层优化，实现 Developer 和 Test Engineer 阶段 Token 分别下降 26.58%-62.94% 的量化成果。

📝 详细摘要

本文以腾讯轻量云团队搭建的多 Agent 开发工作流 DevFlow 为背景，深入分析了 Agent 系统中 Token 消耗被放大的两个核心因素：单轮上下文长度与模型调用轮数。文章通过真实研发实践揭示了一个关键问题——当 Developer 的上下文达到 120K tokens 时，即使修改只有几十行代码，也会因多轮请求而反复携带长上下文，导致成本被显著放大。作者从信息生命周期治理和动作表达粒度两条主线提出四层优化方案：一是控制信息进入上下文的时机，包括将代码探索委托给短生命周期 Code Explorer、低频模板按需加载、减少正常流程中的 Main 中转；二是响应级批量，要求模型在同一轮响应中表达多个独立的 Read、Write 或验证操作；三是工具级批量 replace_batch，将原生 replace_in_file 向量化为支持多文件多处修改的事务性批量编辑工具，并通过原始快照、精确匹配、预校验、事务写入和失败回滚确保一致性；四是 Hook 机制实现批量编辑的默认路径与故障降级。文章最后通过两个模型（Claude Opus 5 和 GLM 5.2）在涉及 6 个 HTTP 接口改造的真实需求上的量化对比，验证了优化方向：Developer 和 Test Engineer 两个高频修改阶段 Token 消耗分别下降 26.58%-62.94% 和 35.05%-50.47%，完整流程 Token 下降 25.69%-41.95%。文章提出的核心 Harness 设计原则——模型擅长判断应该做什么，工具和运行时负责稳定执行——具有广泛的可复用价值。

💡 主要观点

  1. 长上下文在多轮请求中被反复携带是 Token 消耗放大的核心根因 当 Developer 的上下文达到 120K tokens 时，即使修改只有几十行代码，也会因多轮请求而反复携带长上下文。真正昂贵的不是代码本身，而是一个本可以用更少模型请求完成的任务，被拆成多轮以后，同一份长上下文需要一次又一次参与后续调用。放大公式为：已有长上下文 × 额外模型请求。
  2. 信息生命周期治理通过短生命周期 Agent 和按需加载减少不必要的上下文驻留 代码探索改为短生命周期 Code Explorer，只返回约 500 字的结构化摘要，原始搜索结果随 Agent 生命周期结束而退出；低频模板和 Skill 按需加载，只在对应阶段读取 developer-deliverables.md 中的报告和 API 文档模板。关键判断维度包括：当前阶段是否必需、是否只使用一次、是否能够通过明确触发条件按需加载。
  3. replace_batch 工具通过工具级批量将多处关联修改下沉为事务性操作 replace_batch 将原生 replace_in_file(file_path， old_str， new_str) 向量化，支持同一文件多处修改和多文件修改。执行流程为：全部读取与校验 → staging → 检查并发变化 → 统一替换 → 失败时按原始快照回滚。通过原始快照避免偏移量变化，通过预校验和事务写入保证一致性，解决了多个独立 replace_in_file 无法保证的一致性问题。
  4. Hook 机制实现批量编辑的默认路径与故障降级，确保成本优化不影响流程稳定性 PreToolUse Hook 在阻断单点编辑前先进行轻量探活（启动 replace_batchMCP → initialize → tools/list），探活成功则拒绝单点编辑；探活失败或 2 秒超时则 fail-open 允许原生编辑降级执行。批量不是越大越好，批次边界由'这些修改能否基于同一份代码状态同时确定和验证'决定，强行合并未确定或相互依赖的修改会降低成功率。
  5. 量化验证显示 Developer 和 Test Engineer 阶段 Token 消耗显著下降，验证了优化方向 在涉及 6 个 HTTP 接口改造的真实需求中，Claude Opus 5 的 Test Engineer 单阶段减少约 4.69M Tokens（下降 35.05%），Developer 下降 26.58%；GLM 5.2 的 Developer 下降 62.94%，Test Engineer 下降 50.47%。完整流程 Token 分别下降 25.69% 和 41.95%。两个模型的方向一致，但绝对幅度差别大，不适合写成固定收益承诺。

💬 文章金句

  • 真正拉高 Token 消耗的往往不是代码本身，而是长上下文在多轮请求中被反复携带
  • 已有长上下文 × 额外模型请求
  • 把人工研判经验结构化沉淀为规则引擎，而不是锁在个人经验里
  • 模型擅长判断应该做什么；当一组动作已经确定后，工具和运行时负责稳定地把它执行出来
  • Prompt 适合描述目标、条件和执行原则。对于'同一轮多 Read / Write'这种模型已经具备的能力，可以通过 Prompt 明确使用方式。但如果某种行为已经关系到成本、质量或流程稳定性，仅靠 Prompt 提高发生概率还不够，就需要继续下沉到工具协议、Hook 和执行引擎
