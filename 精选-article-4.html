Tinder API 网关：日处理十亿次滑动的技术解析

7/15/2025, 3:31:06 PM

📌 一句话摘要

本文详细介绍了 Tinder 如何构建 TAG，一个基于 JVM 的自定义 API 网关框架，该框架利用 Spring Cloud Gateway，通过提供可扩展、安全且面向开发者的 API 管理来处理每日超过十亿次的滑动。

📝 详细摘要

本文阐述了 Tinder 鉴于现有 API 网关的局限性以及内部设置的碎片化，选择构建其自有 API 网关框架 TAG (Tinder API 网关) 的原因。Tinder 拥有超过 500 个微服务和庞大的全球用户群，需要一种能够提供精确控制、与云技术栈深度集成、助力产品团队实现快速迭代，并提供强大的安全性以抵御恶意流量的解决方案。TAG 基于 Spring Cloud Gateway 构建，是一个基于 JVM 的工具包，它允许每个应用团队部署和管理其定制的网关实例。这种设计通过配置驱动的变更加速了开发流程，通过隔离增强了安全边界，并优化了共享过滤器的重用。本文详细阐述了 TAG 的高效启动流程（预处理配置）及其请求生命周期，具体包括 Geo IP 查找、模式扫描、会话管理以及各种预处理/后处理过滤器等步骤，从而确保可预测且高性能的请求处理。TAG 已成为 Match Group 旗下品牌的标准，赋予团队自主性，保证一致性，并实现可扩展性。

💡 主要观点

  1. 开箱即用的 API 网关无法满足 Tinder 的规模和特定需求。 现有解决方案缺乏 Tinder 在其全球化、高容量和快速演进的微服务环境中所要求的精确性、深度集成、部署灵活性和强大的安全功能。
  2. TAG 是一个基于 JVM 的自定义框架，支持分布式、团队拥有的 API 网关实例。 TAG 并非集中式网关，而是一个基于 Spring Cloud Gateway 构建的工具包，它允许每个团队启动具有配置驱动的路由和过滤器的定制实例，从而增强自主性、安全性和开发速度。
  3. TAG 的设计通过编译阶段配置和可预测的请求生命周期来优化性能和可维护性。 通过在启动时加载所有路由逻辑并定义清晰的过滤器管道（例如，Geo IP、会话管理、预处理/后处理过滤器），TAG 确保最小的运行时损耗和一致的请求处理。

💬 文章金句

  • 许多团队最初会选择 AWS API 网关、Apigee 或 Kong 等开箱即用的解决方案。在许多用例中，这些工具表现良好，但有时可能无法充分满足需求。
  • 工程团队需要的不仅仅是一个 API 网关，而是一个可以随着组织扩展、与内部工具深度集成，并使团队能够快速行动且不影响安全性的框架。
  • TAG，即 Tinder API Gateway 的缩写，是一个构建于 Spring Cloud Gateway 之上的 JVM 框架。它不是一个即插即用的产品，也不是一个单一的共享网关实例，而是一个网关构建工具包。
  • 完整的路由表被加载到内存中，因此当 TAG 开始接收流量时，无需任何运行时解析或配置评估。
  • 本文的重点并非建议所有公司都构建自定义网关，而是强调在特定规模下，标准工具在灵活性、一致性和性能方面存在局限性。
