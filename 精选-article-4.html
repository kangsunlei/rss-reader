MCP 会取代向量搜索吗？— LlamaIndex — 基于企业数据构建知识助手

📌 一句话摘要

探讨模型上下文协议 (MCP) 是否取代企业 AI 中的向量搜索/RAG，结论是它们在数据访问方面是互补的。

📝 详细摘要

本文分析了新兴的模型上下文协议 (MCP) 及其对传统的、利用向量搜索帮助 AI 代理访问企业数据的 RAG（检索增强生成）管道的潜在影响。文章介绍了 MCP 在结构化数据（如 SaaS 工具）的实时联邦搜索方面的潜力，它通过直接访问源 API 来提供最新信息和操作。然而，它强调了纯粹的联邦方法的显著缺点，包括缺乏跨来源的全局理解、性能/延迟问题以及对第三方搜索质量的依赖。文章强调了对于绝大多数非结构化企业数据来说，强大的预处理和索引层仍然必不可少。最终，文章认为最有效的 AI 代理系统将采用混合架构，利用 RAG 实现对索引数据（特别是非结构化数据）的快速查找，并利用 MCP 实现对特定结构化来源的深入查询、实时状态查询、操作以及可能更好的认证集成。

💡 主要观点

  1. 联邦 MCP 通过直接 API 调用实现对结构化数据源的实时查询。 AI 代理可以直接访问 SaaS 工具的实时数据，绕过对 Jira 或 Salesforce 等来源的索引，为组织良好的数据提供最新结果。
  2. 纯联邦搜索（通过 MCP）缺乏全局理解，并且面临跨多个来源的性能问题。 单独查询不同系统会阻止统一排名，并且与集中式索引相比，会遇到“最慢环节”的延迟问题。
  3. 非结构化企业数据不管有没有 MCP 都需要预处理和索引。 文档（PDF、PPT）需要先进行解析、提取、分块和索引成可搜索格式，然后 AI 代理才能有效利用其内容。
  4. MCP 在操作服务和处理复杂结构化查询方面具有优势。 直接 API 访问允许 AI 代理执行操作（发送电子邮件、创建工单）并执行超出语义搜索能力的精确查询（SQL/JQL）。
  5. 最佳 AI 代理架构结合了 RAG 和 MCP 工具。 混合方法利用 RAG 实现对索引数据的快速初始查找，并利用 MCP 实现深入查询、实时数据、操作以及可能更好的认证集成。

💬 文章金句

  • 我们的论点是，AI 代理仍然需要预处理和索引层来进行快速语义查找和非结构化数据搜索。
  • 如果没有理解跨来源关系的统一排名算法，AI 代理将难以呈现最相关的信息。
  • 如果你试图仅仅通过将 AI 代理连接到一堆联邦 MCP 服务器来复制 RAG，你的用户将遇到更长的等待时间、不太相关的结果以及取决于哪些系统恰好包含其答案的不一致质量。
  • 尽管 MCP 对结构化数据源有潜力，但 90% 的企业数据是以 PDF、PPT、扫描件和电子表格的形式存在—这些格式缺少原生查询 API。
  • 在我们看来，最佳 AI 代理将使用 MCP 工具的组合：直接连接第三方服务的工具，以及对预索引数据执行检索的工具。
