B 站消息新架构升级

11/21/2025, 4:03:00 AM

📌 一句话摘要

B 站消息系统架构升级，通过分层、微服务和多级存储，解决私信慢查询、存储瓶颈及耦合，提升性能与扩展性。

📝 详细摘要

文章详细阐述了 Bilibili 消息系统，特别是私信业务在面对海量用户和高并发挑战时的架构升级实践。它首先分析了现有架构中会话慢查询、私信内容存储和写入性能瓶颈，以及服务端代码耦合等核心问题。针对这些痛点，文章提出了一套分层的消息域架构，包括接入层、业务层、平台层和触达层。在具体实现上，引入了 BFF 层进行业务逻辑上浮与微服务拆分，实现了冷热数据分离的多级缓存（Redis+Taishan+MySQL），并对单聊会话、收件箱和私信内容存储进行了深度优化，包括主动预热、双持久化、长尾优化、基于 Binlog 的最终一致性方案以及异步写入和新的分库分表策略。此外，还提升了批量私信的发送能力。整个升级旨在实现系统的稳定性、扩展性和业务解耦度，并在实践中取得了显著进展。

💡 主要观点

  1. 通过分层架构和微服务拆分实现业务解耦和系统扩展 将消息系统划分为接入、业务、平台和触达四层，并抽象出多个独立微服务，有效解决代码耦合，提升系统可维护性和应对高并发的能力。
  2. 采用多级缓存与读写分离策略优化会话查询性能 结合 Redis、Taishan 和 MySQL 实现冷热数据分离，利用读写分离技术将复杂查询导向从库，大幅减少慢查询，提升响应速度。
  3. 引入异步写入和新的分库分表规则解决内容存储瓶颈 将私信内容写入异步化，并依据时间戳和 msgkey 取余进行月度分库分表，有效分散数据热点，提升写入性能和存储容量。
  4. 基于 Binlog 和 CAS 机制确保新老架构数据最终一致性 通过订阅 MySQL Binlog 并结合 Redis Lua 脚本的 CAS 操作，以 mtime 作为版本控制，保证新旧服务间数据同步的最终一致性。

💬 文章金句

  • 技术上数据量越大，降级概率越大，但消息业务场景上数据量大的是影响力更大的 UP，业务不接受技术降级，如何破？
  • Mysql 能承载的瞬时 QPS 受当时应用总连接数和 sql 平均响应速度的影响，连接数打满时会给前端返回空会话列表。
  • 一个兼顾复杂列表查询架构和 IM 架构的消息域框架，整体分四层：接入层、业务层、平台层、触达层。
  • 新服务剥离了历史包袱，也解决一些在老服务难解的功能 case，优化了用户体验，比如消息页不同类型消息的功能一致性；重新设计会话缓存结构和更新机制，优化 Mysql 索引，优化 Mysql 查询语句，减少了一个量级的慢查询。
  • 通过消费路线高性能设计保证泰山异步更新的延迟在 1 秒以内，并在特殊情况延迟突破 1s 时有效告警。
