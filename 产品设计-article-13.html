我们把单 Agent 拆成多智能体之后，翻了三次车

10/27/2026, 10:30:00 AM

📌 一句话摘要

本文通过一个合同审核的真实业务案例，复盘了将单 Agent 拆分为多智能体系统时遇到的三大经典翻车场景，并总结出结构化契约、核心逻辑硬编码以及可观测性前置的三条工程铁律。

📝 详细摘要

文章以中型律所的合同审核 AI 项目为例，剖析了单 Agent 在面对复杂业务时因“一人身兼数职”导致注意力分散、误差指数级放大的天花板。作者深入分享了在引入多智能体架构后遭遇的三次典型翻车：一是 Agent 间传递纯文本导致上下文漂移和“打架”，通过结构化 JSON 契约解决；二是“总控 Agent”因完全依赖大模型而成为不稳定的最大坑，通过硬编码 if-else 逻辑规避；三是定位困难的“调试地狱”，必须从第一天起做足全链路可观测性日志。文章强调，多智能体本质上是将传统系统的微服务拆分逻辑搬到 AI 领域，用工程手段把大不确定性拆解为多个小而可控的不确定性。

💡 主要观点

  1. 单 Agent 面对复杂任务时存在能力天花板，容易因身兼数职导致误差放大。 当任务跨越多个专业领域时，单个 Agent 的 Prompt 过长且矛盾，上下文窗口被塞满，注意力分散会导致输出质量崩溃。
  2. 翻车一：Agent 之间传大段文本导致“打架”，必须采用结构化契约。 下游 Agent 容易因长文本输入产生注意力漂移。通过类似 API 接口设计的结构化 JSON 契约，让下游只接收所需字段，可有效隔离噪音。
  3. 翻车二：“总控 Agent”本身常成为最大不稳定源，编排逻辑需“该写死就写死”。 完全依靠大模型进行任务调度和逻辑判断极易出错。简单的流程控制应采用代码编写的 if-else 或小模型加规则兜底，而不是让 LLM 灵光一闪。
  4. 翻车三：多智能体调试如同开盲盒，可观测性必须从第一天做起。 多环节链条中某个上游组件的数据微小瑕疵会导致下游全面崩塌，必须完整记录每个 Agent 的输入输出和可追溯日志以支持排查。

💬 文章金句

  • 单 Agent 没死，但它的天花板已经肉眼可见了。
  • 多智能体干的事情说白了就是把组织设计的思路搬到 AI 系统里------拆岗位、定职责、设流程、建质检。
  • 该用 AI 的地方用 AI，该写死的地方就写死。这是我们交了学费才悟出来的。
  • 多智能体不是银弹，它是一种工程手段，用来解决单 Agent 在复杂任务上的能力瓶颈。
