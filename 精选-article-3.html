基于大模型的领域场景开发：从单智能体到多智能体的 React 框架设计与实现

8/4/2025, 12:30:00 AM

📌 一句话摘要

文章详细阐述了饿了么团队如何基于大模型构建领域场景应用，特别是设计并实现了从单智能体到多智能体的 React 框架，以提升研发生产力。

📝 详细摘要

本文深入剖析了饿了么团队在基于大模型进行领域场景开发中的实践经验。文章首先回顾了大模型工程从提示词工程到 RAG 再到流程编排的演进，并介绍了团队在该领域的现有成果。核心内容聚焦于如何设计并实现一个智能体 React 框架，特别是采用了“Planning As Tool”的决策模式，使大模型能够自主规划和调用工具，摆脱了传统 Prompt 工程的限制。文章详细阐述了该框架的技术选型（ElemMcpClient+多平台 LLM 调用客户端），并给出了选择原因。随后，深入介绍了系统架构设计，包括 Agent 分类、长期/短期记忆管理、规划过程的五个核心节点（startNode， ProcessNode， ToolManagerNode， StepNode， SendNode）以及 LLM 客户端的封装。最后，文章探讨了多智能体架构的升级方案，对比了层级指挥和自由协作两种模式，并指出了未来在上下文管理和动态压缩方面的迭代重点。整体而言，文章提供了企业级大模型应用开发的宝贵实践经验和架构思考。

💡 主要观点

  1. “Planning As Tool”模式提升了智能体的自主规划和工具调用能力 通过将思考规划抽象为一个工具，引导大模型进行自主决策和行动，有效解决了传统 Prompt 工程中参数解析和意图识别的复杂性，使应用更加灵活。
  2. 定制化 React 框架解决了企业级大模型应用开发的痛点 文章详细阐述了放弃 SpringAI 和原生 MCPSdk，选择自研 ElemMcpClient+多平台 LLM 客户端的理由，该方案更符合企业内部复杂的交互需求和多模型支持的灵活性。
  3. 多智能体架构是复杂场景下提升效率和降低成本的关键 通过将单智能体职责细化并引入多智能体协作，能有效降低 Token 消耗，提高各 Agent 的专业性，从而更好地处理复杂任务并优化资源利用。

💬 文章金句

  • 基于大模型的领域场景开发，说到底无非是借助基座模型对语义的理解推理能力，将通用 AI 变为专有 AI 工具的过程。
  • 单智能体更丰富的工具体系，自主选择工具调用，摆脱传统 prompt 工程参数解析、意图识别等 coding 或节点配置过程。
  • Planning As Tool------将思考规划作为一个单独的工具，告诉大模型有这样一种工具，且入参定义为思考、行动、规划，借助工具入参来引导大模型思考规划。
  • 如果无脑做 ToolCalls 调用，带来的问题有：1.烧 token；2.无关信息可能会导致每个 agent 调用时产生幻觉。
  • 单智能体本身就是为了解决足够复杂的任务，为什么还需要多智能体？这里给一些个人的看法：1.烧 token，每次中心 agent 对模型的请求完全是无脑拼接，如果拆分成多智能体，中心 agent 对模型的发起只用某个 agent 返回的结果即可。2.单智能体职责不够清晰，产出的交付物不如 多智能体的"专业的事交给专业的人"
