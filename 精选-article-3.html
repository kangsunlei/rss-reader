天坑面试题：亿级“微信步数”排行怎么设计？

9/27/2025, 11:15:00 PM

📌 一句话摘要

文章详细阐述了如何设计一个支持亿级用户、实时好友步数排行的分布式系统，重点在于高并发写入、实时查询和数据可靠性。

📝 详细摘要

本文以一道经典的字节跳动面试题为引，深入剖析了设计亿级用户微信步数排行榜系统所面临的四大挑战：写入地狱、查询噩梦、存储黑洞和关系迷宫。作者提出了“三板斧”解决方案：首先，通过消息队列（MQ）实现写入流程的异步解耦和削峰填谷，利用 Redis ZSET 高效存储步数；其次，查询流程采用动静分离策略，将用户关系存储在 MySQL 分库分表，步数从 Redis 批量获取，并在内存中快速排序；最后，针对热点用户问题提出预计算加缓存方案，并通过 Redis 高可用部署和 MQ 消息回放机制确保数据可靠性。整套方案思路清晰，技术选型合理，为解决大规模分布式系统设计难题提供了全面的实践指导。

💡 主要观点

  1. 写入流程采用异步解耦和削峰填谷策略应对高并发 利用消息队列（如 Kafka/RocketMQ）作为缓冲，将瞬时高并发的步数上报请求异步化，减轻后端服务压力，并通过 Redis ZSET 高效存储和更新步数，确保系统稳定性和响应速度。
  2. 查询流程实现动静分离和内存计算以支持实时排行 将相对静态的用户关系数据存储在 MySQL 分库分表，实时变化的步数存储在 Redis ZSET。查询时先获取好友 ID，再批量从 Redis 获取步数，最后在服务内存中进行快速排序，实现秒级响应。
  3. 提供热点用户优化和数据可靠性保障的完整方案 对拥有大量好友的热点用户，采用后台预计算加缓存的方式优化查询。同时，通过 Redis 主从+哨兵模式保证高可用，并利用 MQ 消息回放机制确保数据最终一致性和可恢复性，提升系统健壮性。

💬 文章金句

  • 这道题看似人畜无害，其实是道'天坑'题！它把海量数据下的高并发写入、实时查询、存储扩展等经典难题全揉到了一起。
  • 我们的核心思路是——让消息队列（MQ）做'蓄水池'。
  • ZADD 命令简直是为排行榜而生的神器！它会自动覆盖旧的步数，并且时间复杂度只有 O(logN)，性能炸裂！
  • 核心思想是'动静分离'：'静'的是关系，'动'的是步数。
  • 对这类用户，我们会采用'预计算 + 缓存'的策略。
