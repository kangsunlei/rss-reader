从 Prompt 到 Harness：企业级 Agent 工程的完整演进之路

7/20/2026, 2:34:00 AM

📌 一句话摘要

本文系统回顾了企业级 AI Agent 平台从 Prompt 工程到 Harness 工程的完整演进，提出四层上下文防线、三层记忆架构和赋能范式设计哲学。

📝 详细摘要

文章以作者在阿里云构建企业级 AI Agent 平台的实际经验为基础，从大模型的四个结构性约束（上下文窗口稀缺、注意力稀释、数据搬运谬误、无状态）出发，系统梳理了技术演进的三个阶段：Prompt 工程阶段（S1 MVP）暴露了无容错、上下文膨胀、无反思等结构性缺陷；Context 工程阶段构建了四层上下文防线（工具结果压缩、语义压缩、对话压缩、数据总线）和三层记忆（State、Working Memory、Transcript），将 Token 消耗降低 60%以上，使 Agent 在 30+步复杂任务中稳定执行；Harness 工程阶段则围绕“从防御到赋能”的设计哲学，构建了完整的 Agent 运行时引擎，包括 parameterBindings 声明式绑定、step_control 显式表达、working_memory 自主记录、Action Space 动态裁剪等机制，并提出了五层架构的 Agent 操作系统愿景。文章还深入讨论了单一表示原则、预算预检、三层记忆的动态平衡等工程细节，以及防御范式与赋能范式的对比。

💡 主要观点

  1. 大模型有四个结构性约束，工程化必须围绕它们构建。 上下文窗口稀缺、注意力稀释效应、数据搬运谬误、无状态缺陷是 LLM 的先天限制，不会随模型变大而消失，所有工程努力都在这些约束内做文章。
  2. 上下文管理需要分层防御，不能指望单点优化。 四层防线（L1 工具结果压缩、L2 语义压缩、L3 对话压缩、L4 数据总线）按数据膨胀的时间顺序逐层拦截，每层解决特定粒度的膨胀问题，组合覆盖全场景。
  3. 赋能范式优于防御范式：消除错误发生的条件而非修复后果。 通过 parameterBindings 声明式绑定、step_control 显式表达、working_memory 自主记录等机制，将数据搬运和意图猜测从 LLM 职责中移除，让系统做确定性的事，LLM 做推理的事。
  4. 单一表示原则是上下文管理的宪法条款。 同一份上游数据在任一后续步骤的 LLM 上下文中只允许出现一种表示形态，避免模型因多种描述产生幻觉或浪费 token 做交叉验证。
  5. 事前治理优于事后修复：预算预检和编译时约束。 在调用 LLM 前估算上下文成本，超预算时按固定顺序降级；在 PromptBuilder 中运行时检查单一表示，拒绝组装违规 prompt，让问题不可能发生。

💬 文章金句

  • 上下文窗口的'物理容量'和'有效容量'是两回事。128K 的窗口塞满了 70%的噪音数据，有效容量可能还不如一个精心管理的 32K 窗口。
  • 不要用更大的模型掩盖工程层面的问题。模型从 32K 升级到 128K 不会解决注意力稀释——它只是把天花板从第 5 步推迟到第 8 步，恶化的趋势不变。
  • 让 LLM 做它擅长的事（理解意图、规划、推理），让系统做它擅长的事（数据搬运、格式转换、精确传递）。
  • 在数据流转管道中，确定性永远优先于智能性。能用 substring 的地方不用 LLM，能用声明式绑定的地方不用模型搬运。
  • 事前治理优于事后修复。预算预检、单一表示检查、强制存储阈值——这些都是'编译时'约束，让问题不可能发生，而非'运行时'检测到问题再修复。
