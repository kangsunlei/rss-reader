WorkBuddy/CodeX 都这么强了，企业还要花钱自研智能体吗？

9/17/2026, 7:03:09 AM

📌 一句话摘要

企业落地 Agent 应拆分为「搭运行底座」与「开发业务 Agent」两件事，通用 Agent 加 MCP/Skills 可先试跑，但内部工具封装、业务规则梳理、可观测与评测反馈这些工作省不掉，且通用 Agent 缺少完整执行日志是接入真实业务的主要障碍。

📝 详细摘要

文章回应「通用 Agent 已经很强，企业还要不要自研」这一问题，提出把企业开发 Agent 的工作拆成两件事：一是搭建 Agent 运行底座（即 Harness，含记忆管理、会话压缩、工具治理、异常处理等），二是开发自己的业务 Agent（含内部工具开发、业务规则梳理、流程梳理和效果验证）。作者认为前者通用产品已较完善、可复用，后者无论自研还是用通用 Agent 都省不掉。文章以售后 Agent 为例展开：不建议把为前端界面设计的业务 API 直接套一层 MCP 暴露给 Agent，而应封装成面向场景的工具，并处理金额单位、失败返回、幂等、权限传递等细节；Skill 要把员工默认知道的隐性经验显性化，业务规则不清时改提示词无用。此外还需可观测性（把模型调用与工具执行关联到任务、可追溯配置版本）、评测（用业务结果而非 Agent 回复判断成功，覆盖正常与异常场景）和反馈闭环（业务反馈—观测定位—工具规则修复—评测验证—上线复检）。结论是先选范围明确的业务在现成产品上试跑，但通用 Agent 普遍不提供完整执行日志、形同黑盒，若真要接入业务，可考虑 agentScope、deepseek harness 等开源框架。

💡 主要观点

  1. 企业做 Agent 应拆成「运行底座」和「业务 Agent」两件事，前者可复用，后者省不掉 运行底座即 Harness，涉及记忆管理、会话压缩、工具治理等，通用 Agent 已较完善；业务 Agent 涉及内部工具开发、业务规则梳理、流程梳理和效果验证，无论自研还是用通用 Agent 都必须自己做。
  2. 通用 Agent 加 MCP 和 Skills 是值得先尝试的路径，但不能把现有业务 API 直接套一层 MCP 公司已有 API 是为前端界面服务的，不是给 Agent 定制的工具。直接暴露底层接口会让 Agent 自己判断查哪些数据、按什么顺序查，应封装成面向场景的工具，一次返回处理所需信息。
  3. 工具封装要处理单位、失败返回、幂等和权限传递等工程细节 金额单位要在工具描述里写清；查询失败不能返回空结果，否则 Agent 会误判订单不存在；写操作要处理超时重试导致的重复创建，通过幂等机制避免；发起任务的用户身份要传递到执行环节，不能因调用方变成 Agent 就跳过原有授权规则。
  4. Skill 的难点在于把员工默认知道的隐性经验显性化，业务规则不清时改提示词无用 现有 SOP 常省略员工默认知道的内容，如「特殊订单联系主管处理」中的「特殊订单」定义；需要找业务同学确认具体条件，并说明转人工时要带哪些信息。若两个部门对同一规则理解不一致，必须先确认业务规则。
  5. 可观测、评测与反馈闭环是业务上生产的必要条件，且不能只看 Agent 的回复判断成功 可观测要把模型调用和工具执行关联到每次任务，并追溯模型、工具、Skill 及配置版本；评测要确认售后系统里确实创建了退款申请且金额正确，而非只看 Agent 说「已提交」；反馈闭环则把业务反馈、观测定位、工具规则修复、评测验证和上线复检串起来。

💬 文章金句

  • 一件是自己搭建 Agent 的运行底座，另一件是在已有底座上开发自己的业务 Agent。
  • 开发工具和 Skills，很大一部分工作是在理解业务、整理规则，再把它们变成可以执行和验证的能力。
  • Agent 总会尽可能的帮助我们完成任务，不管中间有没有报错，还是最终的结果对不对，它都会生成一个看是合理的成功的回复，业务上我们一定需要自己做好检查。
  • 业务反馈提供问题，观测帮助定位原因，工具和规则承载修复，评测验证改动，上线后的结果再检验效果。
  • 现在的通用 Agent 基本都不会提供完整的执行日志，所以我们看到的就是一个巨大的黑盒。
