使用 glm5.2 完成了一个复杂 2d 渲染桥接引擎，很强， opus 级别的

6/13/2026, 5:17:00 PM

📌 一句话摘要

作者使用 glm5.2 模型，以极高 token 消耗完成了一个将 HTML/CSS/JS 翻译为 Kotlin 声明式 UI 并桥接到 Minecraft 渲染引擎的复杂项目，并指出这种高推理强度的使用场景对模型提供商而言盈利不佳。

📝 详细摘要

文章作者分享了自己使用 glm5.2 模型完成的一个极具挑战性的项目：首先模仿 JetBrains Compose DSL 实现了一套 Kotlin 声明式 UI 框架，然后编写 HTML 解析器，将 HTML、CSS 和 JavaScript 翻译成这套 DSL，并实现了 JS 状态与 Kotlin 的双向绑定，最终将渲染引擎桥接到 Minecraft 的 DrawContext 上完成 2D 渲染。作者将模型的推理强度（effort）开到最大，每小时消耗约 10M tokens，但大部分时间用于推理（decode），对话轮数显著降低。作者指出，这种高推理强度、低轮数的使用场景对模型提供商（如智谱）来说是最不利的，因为其盈利模式依赖于快速的多轮对话来收取缓存费用，并推测未来可能会暗改推理强度。

💡 主要观点

  1. 使用 glm5.2 完成了一个复杂的 2D 渲染桥接引擎。 项目涉及 Kotlin 声明式 UI、HTML 解析、JS 双向绑定以及桥接到 Minecraft 渲染引擎，技术栈复杂，体现了模型在长链条、高复杂度任务上的能力。
  2. 高推理强度场景对模型提供商不利。 作者将 effort 开到最大，每小时消耗 10M tokens，但大部分时间用于推理，对话轮数少。模型提供商的盈利模式依赖快速多轮对话以收取缓存费用，这种场景下利润低，可能促使厂商暗改推理强度。

💬 文章金句

  • 把 effort 开到 max 之后，每个小时大概消耗 10M tokens ，干活挺慢，大部分时间在推理，对话轮数显著降低了，这对于模型提供商来说是最不利的场景。
  • 模型提供商最喜欢的场景是快速的触发多轮对话，每一轮对话都要把前一轮所有历史收一次缓存读的钱。
