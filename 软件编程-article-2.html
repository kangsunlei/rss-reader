商业客户端 Harness 资产管理与应用实践

8/17/2026, 10:00:00 AM

📌 一句话摘要

本文复盘商业客户端 Harness 资产从单文件同步到仓库整体插件化的四阶段演进，提出「ACX 唯一事实源 + 三层资产治理 + 每日自动同步」的工程实践，为规模化落地多 Agent 研发模式提供可复制的资产管理范式。

📝 详细摘要

本文复盘百度商业客户端 Harness 资产管理的工程实践。面对多产品线、多端、多 Agent（Claude Code、Codex）与多台 Mac 本地部署的复杂场景，作者先梳理了两大 Agent 对 rules、skills 的加载机制差异，指出 Codex rules 是命令策略而非 Markdown 行为规范、allowed-tools 并非跨宿主通用 meta 等容易踩坑的点。随后按四个阶段还原 ACX 资产部署演进：从单 Agent 文件同步、脚本化安装、~/.acx 软连接中枢，最终升级为 ACX 仓库整体插件化，使仓库成为唯一事实源，由各宿主按原生插件协议加载。实践层面提出行为规范、能力执行、宿主集成三层资产治理，通过每日自动同步、生效汇报、渐进式加载与五维匹配（端、产品线、场景、需求类型、交付阶段）实现规范统一与上下文效率兼顾。

💡 主要观点

  1. 多 Agent 并存时，同一份资产需按不同宿主语义正确加载。 Claude Code 与 Codex 对 rules、skills 的加载机制差异显著：Codex rules 是命令执行策略而非 Markdown 行为规范，需通过 AGENTS.md bridge 或插件机制接入，不能简单复用同一套目录。
  2. ACX 仓库整体插件化是解决配置漂移的最终形态。 从单 Agent 文件同步、脚本化安装、~/.acx 软链接中枢到仓库插件化四阶段演进，让宿主按原生插件协议识别 ACX，团队资产与个人资产边界清晰，用户本地不再维护双份资产。
  3. Harness 资产应按行为规范、能力执行、宿主集成三层治理。 行为规范层影响模型如何思考与编码，能力执行层将重复流程固化为可调用能力，宿主集成层负责插件发现、启用状态与加载边界，nad-acx-init 将前两层注册到第三层。
  4. 渐进式加载与五维匹配兼顾规范统一与上下文效率。 利用 rules/skills 不递归加载子目录的特性，必要资产放根目录自动加载、非必要资产放子目录按需触发；再按端、产品线、场景、需求类型、交付阶段五维标记，由 story-pilot skill 查表精准匹配。
  5. 每日自动同步与生效汇报形成治理闭环，让配置始终可追溯。 rule 自动加载与 skill 被动触发结合实现每日首次会话自动同步，Agent 在任务结束时汇报实际生效的 rules/skills，让配置生效情况透明可核查。

💬 文章金句

  • 软连接不是插件生命周期，无法表达“插件身份、来源、版本、启用状态、分类、更新策略”。
  • ACX 仓库成为唯一事实源，rules、skills、manifest、init 脚本都在 ACX 仓库内迭代。
  • 从“文件同步”升级为“插件源治理”；从“多宿主共用目录”升级为“多宿主各自按插件协议加载”。
