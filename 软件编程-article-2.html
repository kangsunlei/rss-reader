📌 一句话摘要

本文记录了一个因错误使用 git revert 撤销 merge commit 导致线上代码被意外回滚的典型事故，并分析了 MR diff 未提示大量文件变更的根本原因。

📝 详细摘要

作者在开发中遇到一个 git 操作陷阱：在 feature 分支上通过 `git revert -m 1` 撤销了一个 merge commit，随后将 feature 分支合并到 master。MR 的 diff 只显示了作者手动修改的一个文件，看似正常，但上线后发现 master 上原本存在的 20+ 个文件被意外回退。文章复盘了事故经过，并借助 AI 分析解释了原因：git revert 一个 merge commit 会撤销该 merge 引入的所有变更，而 MR 的 diff 是基于 feature 分支与 master 的最终状态对比，Git 认为 feature 分支「主动撤销了这些改动」，因此在合并时将其同步到了 master。作者认为 Git 的 MR diff 设计存在误导性，未能提前暴露风险。

💡 主要观点

  1. 错误使用 git revert 撤销 merge commit 会导致其引入的所有变更被回退。 `git revert -m 1` 针对 merge commit 时，会撤销该 merge 带来的全部差异，而不仅仅是作者想回退的部分。
  2. MR diff 基于分支最终状态对比，无法预警 revert 带来的隐性风险。 MR 的 diff 只显示 feature 分支与 master 的最终差异，Git 将 revert 视为「主动对齐」，因此 diff 中不会显示被 revert 的文件变更，造成安全假象。
  3. revert merge commit 是 Git 操作中隐蔽且危险的高频陷阱。 该操作会通过 MR 将回退效果「传染」到目标分支，且 diff 检查难以发现，是团队协作中需要重点防范的场景。

💬 文章金句

  • MR diff 是 最新状态对比，feature 上的 revert ，对 Git 来说：✅ 不是「删除文件」✅ 而是「对齐 master 并取消 merge 引入的差异」
  • 这是 revert merge commit 最隐蔽、最危险的地方
