如何在本地构建端到端机器学习平台：从实验跟踪到 CI/CD

3/17/2026, 8:33:56 PM

📌 一句话摘要

一份全面的实践指南，介绍如何使用 MLflow、Feast 和 FastAPI 等行业标准工具在本地构建端到端 MLOps 平台，以弥合 Jupyter Notebook 与生产环境之间的鸿沟。

📝 详细摘要

本文探讨了机器学习中的“最后一英里”挑战——如何从 Jupyter Notebook 迁移到可靠的、可用于生产的系统。它提供了一个分步教程，用于构建本地欺诈检测 ML 平台。作者首先演示了一种“朴素”方法，以突出常见的陷阱，例如缺乏可重现性、训练-服务偏差和性能衰减。为了解决这些问题，本指南引入了一个强大的 MLOps 技术栈：MLflow 用于实验跟踪和模型注册，Feast 作为特征存储以确保数据一致性，Great Expectations 用于数据验证，以及 Evidently 用于监控漂移。工作流程最后通过 Docker 进行容器化，并使用 GitHub Actions 实现自动化 CI/CD，为以工程为中心的 ML 开发提供了一个完整的蓝图。

💡 主要观点

  1. 机器学习的“最后一英里”需要强大的工程能力，而不仅仅是更好的算法。 从 Jupyter Notebook 迁移到生产环境的失败原因包括漂移、管道中断和缺乏版本控制；这些都是通过可重复的管道和自动化检查来解决的工程挑战。
  2. 朴素的部署方法缺乏长期可靠性所需的基础设施。 没有实验跟踪或验证的简单训练和 API 服务会导致可重现性问题和“垃圾进，垃圾出”的情况，从而损害模型的信任度。
  3. 像 Feast 这样的特征存储对于消除训练-服务偏差至关重要。 通过为离线训练和在线推理提供统一的 API，特征存储确保模型服务期间使用的数据与训练分布完全匹配。
  4. 持续监控和数据验证是机器学习模型的“安全网”。 Great Expectations 和 Evidently 等工具能及早检测出格式错误输入和性能衰减（漂移），从而防止生产环境中的静默故障。
  5. CI/CD 和 Docker 等标准软件工程实践对机器学习至关重要。 自动化测试和环境容器化确保了开发和部署之间的一致性，减少了复杂 ML 技术栈中“在我的机器上能运行”的问题。

💬 文章金句

  • 机器学习项目并非在 Jupyter Notebook 中训练完模型就结束了。真正的难点在于“最后一英里”：将 Notebook 中的模型转化为可以可靠运行的东西。
  • 这些问题都无法通过更好的算法来解决，它们需要通过工程手段来解决：可重复的管道、验证、版本控制、监控和自动化检查。
  • 可以把这想象成在你的机器学习模型周围构建一个“安全网”。我们添加的每个工具都能捕捉到不同的故障模式，就像机器学习的防御性驾驶一样。
  • 在只有 2% 欺诈的情况下，准确率极具误导性！一个总是预测“非欺诈”的模型可以达到 98% 的准确率，但却无法捕捉到任何欺诈。
  • 难点在于将 Notebook 中的模型转化为可以可靠运行、安全更新并长期信任的东西。
