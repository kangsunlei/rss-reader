工具调用依赖：Koog 中 LLM 模式的调试

7/28/2025, 1:33:14 PM

📌 一句话摘要

本文通过调试 Koog AI 代理，揭示了 LLM 如何过度依赖重复的工具调用模式，导致其忽略明确指令。文章还提出了针对上下文压缩和连续性的结构性解决方案。

📝 详细摘要

本文详细介绍了一个基于 JetBrains 的 Kotlin 框架 Koog 构建的 AI 代理的调试过程。作者遇到的问题是，LLM 在多次工具调用后，对这种交互模式产生了过度依赖，忽略了摘要请求，并在触发上下文压缩时导致“失忆”。核心问题是重复的消息结构强化了一个无意的少样本学习示例。解决方案包括两个关键部分：首先，通过将整个对话历史包装在自定义的类 XML 标签中来打破消息模式，将其视为单个内容块而不是单独的消息；其次，让 LLM 本身以助手角色解释上下文压缩，以保持自洽性和连续性，使其能够无缝地恢复任务。这些见解强调，LLM 上下文窗口会积极地塑造行为，并且结构性变化比单纯的指令更能有效地破坏模式，从而为构建强大的 AI 代理提供关键指导。

💡 主要观点

  1. LLM 可能会无意中学习并过度依赖重复的消息模式，从而覆盖明确的指令。 当 LLM 观察到一种强大且一致的模式（例如，tool_call -> tool_result 重复出现）时，它的注意力机制可能会固化于这种结构，即使明确指示以不同的格式响应，也难以做到。
  2. 打破 LLM 学习到的行为模式通常需要对输入进行结构性更改，而不仅仅是语义指令。 使用自定义标签来封装并将一系列消息呈现为单个、结构上不同的输入块，可以有效地破坏无意的模式，并允许 LLM 正确地处理新指令。
  3. 利用 LLM 的自洽性对于维持跨上下文边界的连续性至关重要。 通过让 LLM 本身（通过助手角色）承认并解释上下文压缩或记忆丢失，它可以“认可”自己的陈述并无缝地恢复任务，从而克服潜在的“失忆”问题。

💬 文章金句

  • 在 100 个“工具调用 → 工具结果 → 工具调用 → 工具结果”模式的示例之后，该模型已经了解到，此对话只有一种可接受的响应格式：更多的工具调用。
  • 该模型的注意力机制——决定关注上下文哪些部分的系统——完全锁定在工具调用模式上。
  • 关键的见解是，LLM 使用特殊 token（如 `< |im_start| >` 和 `< |im_end| >`）来处理对话，这些 token 标记了消息边界。
  • 上下文窗口不仅仅是记忆——它是主动训练数据，可以实时塑造行为。当该上下文中的模式足够强大时，它们可以覆盖明确的指令。
  • 通过让助手角色解释情况，我们利用了模型信任并保持与其自身陈述一致的倾向。
