从一次 LLM 调用到完整 Harness，Agent 到底经历了什么？

9/7/2026, 9:36:00 AM

📌 一句话摘要

本文系统梳理了从单次 LLM 调用到完整 Agent Harness 的演化路径，并对比 Pi、OpenCode、Codex、Hermes 四个框架在上下文装配、事件驱动、安全执行与自进化上的不同设计取舍。

📝 详细摘要

本文以「模型撞上边界，工程补上部件」为主线，系统梳理 Agent 系统从单次 LLM 调用逐步演化为完整 Harness 的过程。文章先回顾 LLM、Q&A Bot、ReAct、Tool Calling、Memory 五个基础阶段，说明上下文装配、行动循环、结构化工具调用与长期记忆各自解决什么问题。随后引入 Agent Harness 概念，指出当任务变长、副作用变强、客户端变多时，会话恢复、权限沙箱、上下文压缩、多客户端连接、扩展装配与子 Agent 并行等工程问题会凝结为独立的运行时层。文章重点拆解四个代表性框架：Pi 以极简工具集与紧致上下文压低成本；OpenCode 用 Agent Profile 与结构化 Session Events 实现多身份与可恢复状态；Codex 以 Thread/Turn/Item 生命周期与双层安全边界支撑长任务监督与恢复；Hermes 通过外部记忆与技能沉淀实现跨会话自进化。最后指出 Harness 不会因模型变强而消失，未来竞争在于为同一模型搭建更好的上下文、循环、边界与记忆。

💡 主要观点

  1. Agent 的复杂性不是一次设计出来的，而是模型每次撞上单次调用边界后，工程系统在外部逐层补上的部件。 模型记不住历史于是出现上下文装配，碰不到世界于是出现工具，一步做不完于是出现循环，上下文装不下于是出现记忆，副作用变强于是出现权限与沙箱。每一层都是对上一轮边界问题的工程回答。
  2. Agent 与 Bot 的分水岭不是「会思考」，而是建立了模型→动作→环境→观察→模型的闭环，运行时负责持续驱动这个循环。 模型本身只生成 token，真正决定「继续运行」的是模型外面的程序：它必须解析模型输出、判断是否结束、调用环境并把观察结果写回上下文。
  3. Agent Harness 是 Agent Loop 外围凝结出的独立运行时层，负责装配资源、管理会话、约束工具、持久化事件并调度子 Agent。 当任务变长、副作用变强、客户端变多，会话恢复、权限沙箱、上下文压缩、多客户端连接、扩展装配与并行调度等问题无法再塞进单一应用，于是凝结为 Harness 层。
  4. Pi、OpenCode、Codex、Hermes 四个框架共享基本能力，却在成本、控制力、可恢复性与长期学习之间做出不同取舍。 Pi 以极简工具集与紧致上下文压低成本；OpenCode 用 Profile 与结构化事件换取多身份与可恢复状态；Codex 围绕 Thread 生命周期与双层安全边界支撑长任务监督；Hermes 把注意力延伸到下一次任务，实现跨会话自进化。
  5. 模型越能行动，Harness 越不能含糊；未来的分水岭不只是模型更聪明，更是谁能搭出更好的上下文、循环、边界与记忆。 模型能力增强不会让运行时消失，反而对上下文装配、权限边界、事件持久化与长期记忆管理提出更高要求。

💬 文章金句

  • 模型看见的一切，都是运行时系统为它构造出来的。
  • Agent 决定下一步做什么；Harness 决定这一步在什么上下文、权限、生命周期与持久化规则下发生。
  • Agent 真正的分水岭不是"会思考"，而是建立了 模型 → 动作 → 环境 → 观察 → 模型 的闭环。
  • 模型没有突然获得跨轮记忆，是聊天应用在每次请求前重新装配了历史。
  • 模型还会继续变强，但 Harness 不会因此消失。模型越能行动，外面的运行时越不能含糊。
