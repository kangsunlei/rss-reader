OpenAI Codex 是如何工作的

3/18/2026, 3:30:41 PM

📌 一句话摘要

本文探讨了 OpenAI Codex 的工程架构，详细介绍了其智能体循环、提示词管理以及自定义双向协议如何实现跨平台的强大编码助手功能。

📝 详细摘要

本文深入剖析了围绕 OpenAI Codex 的“外壳”（harness），并指出编排层比底层模型本身更为关键。文章描述了“智能体循环”（Agent Loop），即模型通过迭代调用 shell 命令和测试套件等工具来解决复杂任务。很大一部分篇幅致力于探讨提示词管理的挑战：由于 OpenAI 优先考虑无状态性和零数据保留（Zero Data Retention），提示词会呈二次方增长，因此需要先进的提示词缓存和上下文窗口压缩技术。此外，文章解释了 OpenAI 为何放弃模型上下文协议（MCP），转而采用自定义的 JSON-RPC “应用服务器”协议，以支持流式进度显示和破坏性操作的用户确认等丰富的双向交互。这种架构使得单一的“Codex 核心”能够一致地驱动 VS Code、Web 和桌面端界面。

💡 主要观点

  1. AI 模型仅仅是一个组件；真正的工程价值在于智能体的编排外壳。 虽然模型提供了推理能力，但周边系统负责管理提示词组装、工具执行、内存限制和跨平台兼容性，这些才是生产环境中更难解决的问题。
  2. Codex 利用迭代式智能体循环来自主执行多步骤的软件工程任务。 该系统不仅生成代码；它还在一个持续的循环中进行推理、执行 shell 命令、运行测试并修复 lint 错误，直到用户的宏观需求得到满足。
  3. 无状态 API 设计导致提示词呈二次方增长，通过复杂的预填充缓存（prefix caching）来缓解。 为了保持零数据保留，每个请求都携带完整的历史记录。OpenAI 使用提示词缓存来复用之前轮次的计算结果，尽管这种机制很脆弱，容易因微小的上下文变化而失效。
  4. 在 MCP 被证明不足以应对复杂的智能体交互后，开发了一种自定义的双向协议。 标准协议缺乏对流式推理、暂停以等待用户确认以及输出结构化差异（diff）的支持，这促使 OpenAI 构建了一个基于 JSON-RPC 的应用服务器，用于多端集成。
  5. 通过项目特定的 AGENTS.md 文件和潜在状态压缩来优化上下文管理。 开发者可以使用本地配置文件来引导智能体，而系统则通过用加密的、具有代表性的模型状态摘要替换完整历史记录，来处理上下文窗口限制。

💬 文章金句

  • 模型是组件，智能体是系统。大部分工程工作都在系统层面。
  • 真正的智能体所需的丰富交互模式……无法与 MCP 提供的功能完美映射。因此，团队从零开始构建了一个新协议。
  • 正确的抽象通常在你尝试过错误的抽象之后才会出现。
  • OpenAI 有意接受这种成本 [二次方数据传输]……因为这样做会破坏每个请求的无状态性。
  • 管理上下文窗口是一个首要的工程问题，而不是事后才考虑的事情。
