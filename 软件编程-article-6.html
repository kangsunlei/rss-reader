Java 并发实战：来自一线的经验教训

1/12/2026, 1:00:00 PM

📌 一句话摘要

本次演讲分享了关于 Java 并发的实用"一线"经验，涵盖并行流、`CompletableFuture`、线程池管理和流量控制，以解决 Netflix 遇到的 I/O 密集型问题。

📝 详细摘要

本次演讲展示了从 Netflix 一个项目中获得的关于 Java 并发的真实世界经验教训。演讲者作为一名产品开发者，分享了解决高 I/O 密集型问题的实用见解，对比了顺序、并行和并发执行，以及同步与异步处理。演讲详细介绍了使用并行流的初步尝试，重点指出了常见的陷阱，如嵌套并行化、`flatMap` 意外的顺序行为以及线程上下文问题。随后演进到使用 `ExecutorService` 和 `CompletableFuture` 来处理 I/O 密集型工作负载，解决了诸如由于队列累积导致的 `OutOfMemory` 错误以及意外地对依赖服务进行 DDoS 攻击等挑战。解决方案涉及智能线程池管理、分离请求/响应处理、使用信号量和速率限制器进行流量控制，并最终利用 gRPC 内部背压机制的非阻塞 I/O 来实现更简单、更健壮的解决方案。

💡 主要观点

  1. 有效区分顺序、并行和并发执行，以及 CPU 密集型和 I/O 密集型任务，为并发设计提供依据。 理解这些基础概念对于选择合适的 Java 并发工具至关重要。例如，CPU 密集型任务受益于在多核上的并行处理，而 I/O 密集型任务则需要异步非阻塞模式来最大化资源利用率。
  2. 谨慎使用并行流，特别是在嵌套调用、`flatMap` 行为和线程上下文传播方面。 嵌套并行流可能因上下文切换增加和资源竞争而导致性能下降。OpenJDK 中的 `flatMap` 在内部将并行流转换为顺序流，从而抵消了预期的性能提升。线程上下文（例如用户信息）在 ForkJoinPool 线程之间通常会丢失，需要自定义解决方案。
  3. 当使用 `ExecutorService` 和 `CompletableFuture` 处理 I/O 密集型任务时，仔细管理线程池以避免 OutOfMemory 错误。 为请求提交和响应处理分离线程池可以防止大型响应对象在单个队列中无限累积，从而导致 OOM。不同的 `thenApply` 选项在性能、灵活性和上下文保留方面提供了权衡。
  4. 实施流量控制机制，如信号量和速率限制器，以保护依赖服务并防止级联故障。 信号量控制正在进行的并发调用数量，保护本地资源免受过载。速率限制器调节对外部服务的调用频率，防止它们被 DDoS。通常，两者结合使用对于健壮的系统保护是必要的。
  5. 拥抱非阻塞 I/O，并在可能的情况下利用内置框架背压，以实现更简单、更高效的并发管理。 转向完全非阻塞模式，特别是使用像 gRPC 这样提供内部背压机制的框架，可以显著简化复杂的并发逻辑，减少在应用层面对显式信号量和速率限制器的需求。

  • 虚拟线程的理念是它们非常廉价。你创建虚拟线程，销毁虚拟线程，你不需要为它们维护一个池。它们非常适用于 I/O 密集型的流程。
  • 如果我们看一下这个规模，最终，我们必须解决大约每秒 27 万次请求的产品问题。
  • LLM 是一个助手，不是一个自主可靠的编码器。我是高级开发人员；LLM 的存在是为了加速我的工作，而不是取代我的判断。
  • 背压实际上是由 gRPC 框架本身施加的。我们在 gRPC 内部有一些信号量和控制机制，所以我实际上是在利用这些优势，用一个单一的杠杆来控制我所有的并发。
