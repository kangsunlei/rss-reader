📌 一句话摘要

文章深度剖析了 R8 编译优化工具中 ApiModel 外联设计缺陷导致 Android 应用 Native 崩溃的问题，并提供了详细的复现条件、原理分析及多种解决方案。

📝 详细摘要

文章详细分析了得物技术在升级 Android Gradle Plugin (AGP) 后，R8 编译优化工具的 ApiModel 外联功能引发的 Native 崩溃问题。该崩溃源于多生成了一个未调用构造方法的 `new-instance` 指令，导致 `SurfaceTexture` 对象在 GC 时触发内存访问错误。文章首先阐述了 ApiModel 外联的背景和目的——规避低版本设备上的类验证耗时。随后，通过对 Java、Dex 和 IRCode 文件转换过程的深入剖析，揭示了 `new-instance` 指令多生成的原因在于 R8 的 `canSkipClInit` 方法判断不全面，未能区分入参计算逻辑与类初始化逻辑。此外，文章还解释了 `try-catch` 和 `synchronized` 语句块如何通过生成 `FALLTHROUGH` 指令，间接导致同样的问题。最后，文章提供了禁用 ApiModel、官方修复、自行修复以及推荐的业务改造等多种解决方案，并强调了对重大升级进行独立灰度验证的重要性。

💡 主要观点

  1. ApiModel 外联旨在规避低版本 ART 虚拟机类验证耗时 ApiModel 将调用高版本 API 的代码抽离到单独的生成类中，使主类在低版本设备上能通过 AOT 类验证，避免运行时耗时。
  2. 多余 new-instance 指令是 R8 的 canSkipClInit 方法判断缺陷导致 R8 的 `canSkipClInit` 方法在构造函数外联时，错误地将入参计算或 `FALLTHROUGH` 指令视为类初始化逻辑，导致多余的 `new-instance` 指令未被移除，引发未初始化对象回收崩溃。
  3. try-catch/synchronized 语句块通过生成 FALLTHROUGH 指令间接引发问题 `synchronized` 编译后生成 `try-catch`，`try-catch` 转 Dex 时添加 `FALLTHROUGH`。R8 4.0.26 对 `FALLTHROUGH` 的处理导致生成 GOTO 指令，被误判为类初始化，进而引入额外 `new-instance`。
  4. 提供了多种解决方案，业务改造结合告警和黑名单是推荐实践 文章提供了禁用 ApiModel、官方修复、自行修复和业务改造等方案。推荐业务改造，即通过在 R8 外联函数生成处打印日志来识别受 ApiModel 影响的类，并进行针对性修改，同时结合日志告警和类黑名单机制，以兼顾 App 稳定性和应对三方库问题。

💬 文章金句

  • 这次的 ApiModel 外联优化问题就是一个很好的例子——它只在特定条件下才会暴露，但一旦出现就是必现的 native 崩溃。
  • AGP 新增的 ApiModel 功能是为了防止在低版本设备上不可能执行的代码引起类验证错误，从而降低 App 启动耗时。
  • 问题重点就在于 canSkipClInit 这个函数的实现。它会检查 new-intance 指令和 invoke 指令之间是否存在任何局部变量声明以外的指令，如果存在，他会认为这些指令是这个类初始化的逻辑，因此为了保留源代码的执行顺序，这种情况下就是需要额外执行一次 new-instance 指令来触发类初始化。
  • FALLTHROUGH 指令表示指令自然流转，没有实际含义，它主要是为了帮助优化器识别哪些指令是可达的。
  • 在 Android 开发中，即使是 AGP、R8 这样的官方工具链升级，也要保持足够的警惕。毕竟 Android 生态太过复杂，再加上开发者们千奇百怪的代码写法，不论多么完善的测试流程都无法规避这类特定场景的 bug。
