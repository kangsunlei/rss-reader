Agent 插件工程化：如何让 Skill 可验证、可维护、可演进

8/9/2026, 6:11:00 AM

📌 一句话摘要

本文探讨 Agent 插件工程化实践，提出通过规格驱动、上下文编排、确定性验证、行为评测和证据闭环五个环节，将 Agent Skill 从简单的提示词提升为可维护的软件资产。

📝 详细摘要

文章结合 Better Harness 的开发实践，分析了 Agent 插件在规模化使用时面临的维护难题。作者主张将 Skill 视为软件而非单纯的 Prompt，构建了一套完整的工程化体系：首先通过规格驱动（Spec-driven）定义可验证的行为契约；其次通过上下文编排实现知识的渐进式披露与路由验证；第三利用静态检查和契约测试等确定性机制守住边界；第四通过正负例行为评测验证 Agent 的实际执行情况；最后通过对照实验建立证据闭环，证明 Skill 确实带来了结果的改善。全篇强调「证据链」在 Agent 能力演进中的核心作用。

💡 主要观点

  1. 将 Agent Skill 从提示词思维转向软件工程思维。 当 Skill 进入插件生态被广泛调用时，需解决行为契约、变更验证、环境兼容和效果评估等软件工程问题，而非仅靠优化 Prompt。
  2. 采用规格驱动（Spec-driven）建立可验证的行为契约。 在实现前定义明确的验收条件（AC），约束可观察行为而非具体措辞，将运行时模糊性转移到设计时。
  3. 构建渐进式披露的上下文编排与确定性验证机制。 通过合理的目录结构和路由验证确保知识准确抵达，同时用 Lint 和契约测试处理边界明确的问题，避免模型盲目猜测。
  4. 建立从「已存在」到「有效果证据」的完整证据链。 通过对照实验（无 Skill vs 当前版 vs 候选版）验证结果改善，并结合执行轨迹检查过程覆盖，防止「已路由但未执行」的假象。

💬 文章金句

  • Skill 一旦从个人 Prompt 进入插件生态，它面对的问题就越来越像软件，而不是提示词。
  • 能被程序明确判定的，就不要交给模型猜；需要语义判断的，也不要硬塞进字符串断言。
  • Skill 的演进，不应该从「生成更多经验」开始，而应该从「证明这次修改确实让下一次做得更好」开始。
