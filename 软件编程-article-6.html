Oracle 翻车之作：MySQL Cluster 的失败根源与设计原罪

11/16/2025, 12:02:00 AM

📌 一句话摘要

文章深入剖析了 Oracle 的 MySQL Cluster（NDB）产品失败的深层原因，揭示其设计原罪、技术局限性及与市场需求脱节的问题。

📝 详细摘要

本文深入剖析了 Oracle 旗下 MySQL Cluster（NDB）产品失败的深层原因。NDB 最初为电信计费等特定短事务、毫秒响应场景设计，其分片和“shared nothing”内存架构虽擅长主键查询，但在复杂查询（如 JOIN、GROUP BY）上性能极差，不适用于通用数据库应用。文章引用专家辩解，并指出 NDB 对硬件、配置、调优知识的高要求，且与传统 MySQL 应用不兼容。历史溯源显示，NDB 源于爱立信收购，而非 Oracle 自研，导致其与 Oracle RAC 理念及市场定位冲突。最终，文章总结了 NDB 在分布式架构、数据一致性、SQL 功能支持和管理复杂性等方面的致命缺陷，确立其作为 Oracle“失败杰作”的地位。

💡 主要观点

  1. MySQL Cluster 的设计初衷与通用数据库需求严重脱节 NDB 最初为电信行业特定场景（毫秒响应、短事务）设计，其分片架构导致其在复杂查询上性能极差，无法满足广泛的通用数据库应用需求。
  2. NDB 架构存在固有缺陷，导致复杂查询性能瓶颈 Shared Nothing In Memory 架构虽能提供高速主键查询，但跨节点 JOIN 和范围查询需耗费大量网络通信，且缺乏分布式性能优化器，导致复杂 SQL 查询效率低下。
  3. 产品定位模糊与技术栈不兼容导致推广失败 Oracle 试图将其包装成类似 RAC 的高可用方案，但其与 MySQL 传统功能不兼容、高昂的硬件和运维成本，以及现有应用难以移植，使其难以被市场接受。
  4. 收购历史揭示了产品设计理念的冲突 NDB 是收购爱立信的产物，而非 Oracle 自研，这解释了其与 Oracle 核心数据库产品在设计理念和目标客户上的根本差异，进一步证明了其产品定位的失误。

💬 文章金句

  • MySQL 的 NDB，一个类似 Oracle 的 RAC 的东西，最初是为电信计费设计的，他强调的事毫秒响应时间，高可用以及分布式冗余，并且要求在此上的事务高度结构化，且短事务。
  • 但是 MySQL Cluster 在数据节点对上以分片方式分割数据的方式意味着，如果查询是通过主键查找特定行，它最支持查询。范围查询可能必须跨越许多数据节点。连接查询也必须跨越许多数据节点。复杂的报告查询性能很差。
  • 这上面这位仁兄的解释是，不支持复杂查询不是 MySQL Cluster 的弱点，而是分片结构的弱点。
  • 后来查了一下这个系统的历史，这个系统并不是 Oracle 自研的，而是收购 Ericsson 而来了，而当初这个系统的产生完全是针对电信行业特定的系统而生，并不是为了广泛的数据库应用而设定的。
  • 综上所述，MySQL CLUSTER 系统是一个 ORACLE 在自己数据库产品中失败的杰作，收购，且针对极为特殊的业务场景，与当前的大部分数据库系统相比，无法完成基本的 JOIN SQL 查询的工作，系统扩展后，并不能得到系统的性能提升，种种问题。
