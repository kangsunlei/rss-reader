Cloudflare 2026 年 2 月 20 日故障报告

2/21/2026, 12:00:00 AM

📌 一句话摘要

Cloudflare 详细说明了 2026 年 2 月发生的一起持续 6 小时的故障，该故障由自动化 BYOIP 清理任务中的逻辑漏洞引起，导致 25% 的客户 BGP 前缀被意外撤回。

📝 详细摘要

本次复盘分析了影响 Cloudflare 自有 IP (BYOIP) 服务的一次重大服务中断。该事件由 Addressing API 中一个新的自动化清理子任务漏洞触发。由于对空查询参数的处理不当，系统将针对特定删除的请求误判为删除所有 BYOIP 前缀及其关联服务绑定的指令。这导致了 BGP 撤回和“BGP 路径收敛（Path Hunting）”行为，使得服务无法访问。由于部分服务配置从边缘服务器中被完全清除，必须进行手动恢复，从而阻碍了恢复进程。Cloudflare 概述了补救措施，包括 API Schema 标准化、引入运行状态快照以及用于防止大规模意外网络变更的“熔断机制”。

💡 主要观点

  1. API 参数处理中的逻辑漏洞触发了大规模意外删除。 一个自动化任务发送了带有空 pending_delete 标志的 GET 请求。服务器将空字符串解释为请求所有前缀而非特定子集，导致系统将所有 BYOIP 前缀排队等待删除。
  2. 边缘侧服务绑定的删除显著延迟了恢复工作。 虽然部分客户可以通过重新发布前缀来自行修复，但其他客户的基础服务配置（如 Magic Transit 或 CDN 绑定）已被清除。恢复这些配置需要向每台机器进行全局配置推送，延长了故障持续时间。
  3. 预发布环境和测试未能模拟自主服务级变更。 现有测试侧重于手动用户驱动的 API 操作。它们未考虑到后台任务运行器可能在没有明确用户输入的情况下独立执行数据变更的场景，凸显了基础设施服务自动化测试覆盖范围的缺失。
  4. Cloudflare 正在实施“熔断机制”以限制网络变更的影响范围。 为防止未来出现失控进程，Cloudflare 计划监控 BGP 撤回速率。如果变更发生得太快或范围太广，系统将自动触发熔断器以禁用部署，直到进行人工调查。
  5. 将运行状态与配置状态分离对于快速回滚至关重要。 通过转向在生产部署中使用数据库状态快照的系统，即使底层权威数据库损坏或配置错误，工程师也可以近乎即时地恢复到已知的良好状态。

💬 文章金句

  • 由于客户端传递的 pending_delete 没有值，此处 Query().Get("pending_delete") 的结果将是一个空字符串 ("")，因此 API 服务器将其解释为对所有 BYOIP 前缀的请求。
  • 系统将其解释为所有返回的前缀都已排队等待删除。随后，新的子任务开始系统地删除所有 BYOIP 前缀及其所有相关的依赖对象。
  • 虽然我们的工程师成功测试了客户会遵循的确切流程，但测试并未涵盖任务运行器服务独立执行用户数据变更的场景。
  • 我们将改进监控，以检测变更是否发生得太快或范围太广（例如快速撤回或删除 BGP 前缀），并在发生这种情况时禁用快照部署。
  • 这次故障本身并非全球性的，但影响范围和冲击力大得令人无法接受，这进一步强化了“橙色代码：减小故障范围”作为优先事项的重要性。
