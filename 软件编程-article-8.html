Harness 工程实践：如何让 Agent 完成自主迭代

7/8/2026, 11:37:00 AM

📌 一句话摘要

本文复盘了阿里技术团队如何借鉴 Harness 工程理念，让 AI Agent 自主运行 17 小时完成 16 轮 prompt 迭代优化，并分享了防止早停、上下文打爆与 reward hacking 的实战方案。

📝 详细摘要

文章详细记录了阿里技术团队将 Harness 工程应用于线上业务 Agent 优化的完整实践。团队面对 badcase 修复速度跟不上新增速度的困境，受 OpenAI Harness 工程启发，构建了一套让 AI 自主完成「修改 prompt → 部署 → 评测 → 分析结果 → 继续迭代」的闭环系统。文章重点剖析了落地过程中的三大核心挑战：一是将研发工具（部署、评测）改造为 Agent 可调用的 MCP 或 CLI 能力；二是通过禁止提问、父子 Agent 拆分等 prompt 技巧解决长程任务中的早停、空转与上下文窗口爆满问题；三是借鉴机器学习训练集/验证集分离与 champion-challenger 打擂台机制，有效防止模型在迭代中产生 reward hacking 与策略退化。文中展示了 AI 在 17 小时内自主完成 16 轮迭代、最终产出可上线版本的真实案例，并坦诚分享了评测集质量与平台稳定性等冰山下的工程陷阱。最后，作者展望了从 prompt 优化小循环走向 badcase 全流程自动化大循环的下一步方向。

💡 主要观点

  1. Harness 工程的核心是将软件研发从「人手写代码」转为「人定义目标与验收，Agent 执行、验证、修复与交付」。 作者将研发流程抽象为定义问题、提出方案、开发、测试、上线五步，指出 Harness 工程让 Agent 承担了 80% 的执行工作，人则聚焦于最难的定义与验收环节。
  2. 落地 Harness 工程必须补齐三大能力：工具 Agent 化、长程任务稳定性、防 reward hacking 机制。 团队将部署与评测平台改造为 Agent 可调用的 skill；通过「禁止提问」「一次只做一件事」「父子 Agent」等 prompt 技巧解决早停与上下文问题；引入训练/验证集分离与 champion-challenger 机制防止策略退化。
  3. Champion-challenger 机制是保证 AI 持续正向迭代的关键。 该机制要求 AI 必须从历史最佳策略（champion）出发改进，并在验证集上全面超越 champion 后才能成为新基线，有效避免了模型在错误路径上越走越远。
  4. AI 自主迭代的成功高度依赖评测集质量与工程环境稳定性，Harness 工程没有银弹。 作者坦诚分享了 16 轮迭代中仅 1 轮可用的教训，指出评测标准不合理或平台不稳定会导致 AI 被错误信号带偏，强调业务复杂度不会因 AI 而自动消失。
  5. 实践 Harness 工程应使用顶级模型，并通过「带实习生」的方式沉淀 Skill。 作者建议使用最强的 Coding Agent，并先手把手教 AI 完成一次完整流程，再让其将过程总结为可复用的 Skill，而非将其当作「许愿机」。

💬 文章金句

  • Harness 工程是短期被高估，但长期被低估的东西。
  • 软件工程从来就没有银弹，不存在说有了 AI 之后，这些业务复杂度和系统复杂度的问题就自动消失了。
  • 我们成了帮 AI 点击页面按钮的工具人。
