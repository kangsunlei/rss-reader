没人能彻底搞懂 Linux 内核的 3500 万行代码！Linus 谈未来演进：掌控“大局”、别指望 Rust 能修复所有 Bug、486 时代该结束了

📌 一句话摘要

本文整理 Linus Torvalds 在 Linux 7.1 发布后的围炉谈话，涉及内核开发模式、淘汰 486S、Rust 与 C 的比较、AI 对社区的双面影响以及社区治理等核心议题。

📝 详细摘要

文章基于 Linus Torvalds 与 Dirk Hohndel 的现场对话，完整呈现了 Linux 内核最新版本（7.1）发布后的关键讨论。Linus 解释了为何不再追求“亮点”功能而坚持稳定增量迭代；正式淘汰 486S 及更早的浮点模拟代码，强调维护旧硬件的成本大于收益；明确表态 Rust 能解决内存安全问题但无法修复逻辑错误，呼吁降低对 Rust 的期望；深入分析 LLM 给内核社区带来的双面影响——既帮助发现多年隐藏的 Bug，也产生大量垃圾报告和“创可贴式补丁”，仍缺失系统级的工程品位；同时收紧合并窗口规则，反对在最后期限集中提交修复，强调开源项目的核心是建立长期信任而非仅关注代码。

💡 主要观点

  1. Linus 已从一线编码转为架构把控，依赖信任与合作历史而非逐行审查代码。 面对 3500 万行代码，他承认无人能完全理解，因此通过阅读详细说明和信任长期维护者来把握全局方向，仅在冲突或说明不清时才深入代码。
  2. 逐步淘汰老旧硬件支持（如 486S、浮点模拟代码），以降低维护负担。 这些硬件已无实际用户，每项修改仍需兼容测试，清理有助于保持代码库的健康可维护性。
  3. Rust 不能成为修复 Bug 的万能药，逻辑错误仍会大量存在。 Linus 指出 Rust 能避免内存安全漏洞，但无法解决错误的逻辑设计；近期内核中影响大的 Bug 恰恰都是逻辑错误而非内存问题。
  4. LLM 在发现 Bug 方面能力显著提升，但生成代码缺乏工程品位，需要人类中间人。 高质量的 Bug 报告需要 LLM 使用者参与后续讨论和修复方案设计；直接生成的补丁常是“盲目的创可贴”，仅掩盖表面问题。
  5. 开源项目的核心压力来自人际沟通而非技术难题。 Linus 强调代码冲突可以解决，但管理长期合作者之间的关系、处理不同意见是更困难的部分，信任建立在数十年合作之上。

💬 文章金句

  • 我完全不反对 Rust，但我也希望降低大家对它的期待，不要认为 Rust 能够像魔法一样修复所有 Bug。
  • Linux 内核有 3500 万行代码，没有人能够真正理解全部代码。
  • 代码很容易修复，但人的性格和相处问题并不总是那么容易解决。
