为什么 DeepSeek 大规模部署很便宜，本地很贵

7/7/2025, 7:18:00 AM

📌 一句话摘要

文章深入解析了大型语言模型（如 DeepSeek-V3）在大规模部署中高效低成本，而在本地运行时效率低下的原因，主要归因于推理批处理、GPU 效率、MoE 架构和管道气泡等关键技术权衡。

📝 详细摘要

本文详细探讨了大型 AI 模型（特别是专家混合模型如 DeepSeek-V3）在不同部署场景下性能差异的深层原因。核心在于 AI 推理服务商为模型选择的“批处理大小”，即通过跨多个并发用户请求进行批处理来提升 GPU 效率。文章解释了 GPU 擅长大型矩阵乘法，而批处理能将多个小操作合并为大操作，从而显著提高吞吐量。接着，文章分析了专家混合模型（MoE）和大型管道化模型（多层 Transformer）对大批处理量的需求，指出 MoE 模型需要大批次以确保每个专家都能被充分利用，而多层管道模型则需要大批次来避免“管道气泡”导致的 GPU 空闲。文章强调了吞吐量和延迟之间的基本权衡，即高吞吐量通常伴随高延迟。最后，文章总结了为何 DeepSeek 等模型在大规模服务时表现出色，而在单用户场景下效率低下，并推测了 OpenAI 等公司模型响应迅速的可能原因，为读者提供了对 AI 推理服务底层机制的深刻理解。

💡 主要观点

  1. GPU 在大型矩阵乘法上最高效，促使推理服务采用批处理策略。 通过将多个用户请求的 token 堆叠成一个大型矩阵进行计算，GPU 能以更高效率处理数据，从而提升整体 token 吞吐量，而非逐个处理小批次。
  2. 专家混合模型和多层管道架构需要更大的批处理量以提升效率。 MoE 模型需要大批次来确保其众多专家模块被充分利用；多层模型则需大批次以避免因“管道气泡”导致的 GPU 空闲，从而提升吞吐量并降低实际延迟。
  3. 推理提供商在吞吐量和延迟之间进行权衡，以适应模型特性。 服务商通过调整批处理大小和“收集窗口”时长，平衡用户请求等待时间与 GPU 利用率，为不同架构模型（如 DeepSeek）选择最优服务模式。

💬 文章金句

  • 基于 Transformer 的大型语言模型的一个奇特特性是，同时计算一批补全几乎和计算单个补全一样快。
  • GPU 想要执行少量的大型矩阵乘法，但如果有很多专家，你会被迫做很多小型乘法。除非你以整个批次进行推理，否则这意味着吞吐量很低。
  • 如果你有很多层，你的收集窗口非常短，有时最终处理的 token 数量可能少于层数。这被称为“管道气泡”。
  • 你将多少 token 打包到一个“tick”中（即你等待收集 token 的时间），就是你的批次大小。这些 token 来自不同的用户。
  • 一些模型（如 DeepSeek）是具有许多层的专家混合模型，因此需要大批次大小和高延迟，否则吞吐量会急剧下降。这就是为什么说 DeepSeek 很难在个人场景中使用。
