如何在 Kubernetes 中对用户进行身份验证：x509 证书、OIDC 和云身份

4/6/2026, 8:31:43 PM

📌 一句话摘要

一份关于 Kubernetes 身份验证机制的深度技术指南，涵盖了内部身份验证器链、x509 证书实现以及与 Dex 的现代 OIDC 集成。

📝 详细摘要

本文从第一性原理出发，解释了 Kubernetes 在没有内部用户数据库的情况下如何处理身份。文章探讨了可插拔的身份验证器链，区分了面向机器的 Service Account 和外部管理的 User。作者提供了创建 x509 客户端证书的实操演示，强调了其局限性（如缺乏吊销机制），并详细介绍了如何使用 Dex 和 kubelogin 设置用于生产环境的、基于浏览器的 OIDC (OpenID Connect) 登录。文中特别提到了 Kubernetes v1.30 中引入的现代 AuthenticationConfiguration，使其成为当前基础设施安全实践中极具参考价值的资源。

💡 主要观点

  1. Kubernetes 依赖外部身份验证器链而非内部用户数据库来验证请求签名。 API Server 将凭据传递给一系列身份验证器（x509、OIDC、IAM 等）；第一个验证凭据成功的身份验证器生效，否则请求将被视为匿名请求。
  2. User 不是 Kubernetes 对象；它们是由 CA 或 OIDC 提供商等外部系统断言的身份。 与属于命名空间对象的 Service Account 不同，User 是在外部管理的。Kubernetes 仅从已验证的断言中提取用户名和组。
  3. x509 证书将通用名称 (CN) 映射为用户名，将组织 (O) 映射为组，但在生产环境中存在显著局限性。 主要问题在于缺乏对证书吊销列表 (CRL) 的支持，以及手动轮换和分发带来的高运营开销。
  4. OIDC 通过使用短效 JWT 和基于浏览器的流程，实现了无状态、可扩展且安全的身份验证。 API Server 使用提供商的公钥在本地验证 JWT 签名，无需在每次请求时都联系身份提供商。
  5. 身份验证与授权是解耦的；已验证的身份仍需要 RBAC 角色才能执行任何操作。 通过身份验证层仅能识别用户“是谁”；RBAC 则根据 RoleBinding 决定他们被允许“做什么”。

💬 文章金句

  • Kubernetes 不知道你是谁。它没有用户数据库，没有内置的登录系统，也没有密码文件。
  • 理解这种模型是区分“能够调试身份验证失败的工程师”与“只会复制 kubeconfig 文件并祈祷一切顺利的工程师”的分水岭。
  • Kubernetes 不会检查证书吊销列表 (CRL)。如果开发者的 kubeconfig 被盗，嵌入的证书在过期前将一直有效。
  • Kubernetes API Server 不会在每次请求时联系 OIDC 提供商……这使得 OIDC 身份验证具有无状态性和可扩展性。
  • 有效的证书能让你通过大门。至于进去后能做什么，那是 RBAC 的工作。
