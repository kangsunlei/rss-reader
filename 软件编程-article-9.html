📌 一句话摘要

本文阐述了 Compose Hot Reload 1.0.0 背后的技术历程，详细介绍了 JetBrains Runtime、DCEVM、Java agents 和构建系统集成如何为 Compose Multiplatform 实现动态代码和 UI 更新，并解决了编译器方面的重大挑战。

📝 详细摘要

本文详细介绍了 Compose Multiplatform 的新稳定功能 Compose Hot Reload 1.0.0 的开发历程和技术实现。它解释了 Hot Reload 如何在无需重新编译的情况下实现运行中应用程序的动态代码更新和 UI 刷新，显著提升了开发者体验。核心机制包括：利用 JetBrains Runtime 的 DCEVM 实现实现无限制的动态代码演进；使用 Java agents 进行 API 访问和后台任务处理；与 Gradle 等构建系统深度集成以高效检测和应用代码变更。文章重点讨论了面临的挑战，特别是 Kotlin 编译器 lambda 命名规范的不一致性，以及如何解决这些问题以确保可组合函数的热重载稳定性。该过程还涉及使用 ASM 进行字节码分析以跟踪 Compose 组变更，并通过智能 UI 失效机制尽可能保留状态。

💡 主要观点

  1. Compose Hot Reload 通过利用 JetBrains Runtime 的 DCEVM 实现实现动态代码更新 DCEVM（动态代码演进虚拟机）扩展了 JVM 的热交换能力，支持近乎任意的代码变更，如添加/删除字段和方法，这对高级热重载功能至关重要
  2. 使用 Java agent 附加到应用程序，访问 DCEVM API 并管理重载请求 agent 在 JVM 启动前运行，使用 Java Instrumentation API 观察、修改和重定义类。它启动后台任务，在代码变更时调用 instrumentation.redefineClasses
  3. 与 Gradle 和 Amper 等构建系统的深度集成确保零配置开发者体验 构建系统插件管理应用程序启动、编译代码、获取类路径快照（热区和冷区），并协调向 agent 发送重载请求，实现变更的自动检测和应用
  4. 执行字节码分析以跟踪 Compose 组变更并智能失效 UI 组件 使用 ASM，agent 分析类字节码以识别 Compose 组、它们的依赖关系和语义变更（通过哈希值），允许运行时仅重新渲染必要的 UI 部分同时保留状态
  5. 克服了 Kotlin 编译器 lambda 命名规范相关的重大挑战以实现稳定热重载 基于类（ComposableSingleton）和 indy lambda 的编译器生成名称不一致导致过度失效和错误。JetBrains 对 Compose 和 Kotlin 编译器的修改引入了基于组键和范围唯一索引的稳定命名

💬 文章金句

  • DCEVM 提出"Java 的无限制安全动态代码演进"，它解除了限制并支持几乎任意的代码变更
  • Compose Hot Reload 严重依赖 JetBrains Runtime 来运行用户代码。JetBrains Runtime 不仅专门用于构建 UI 应用程序，而且至今仍是唯一实现 DCEVM 提案的 JVM
  • Compose 将代码分割成称为**组**的部分，并为每个组分配唯一的整数键。近似地说，你可以认为每个**作用域**（例如代码中的每个 `{}` 对）对应一个单独的组
  • 许多问题源于 Kotlin 编译器和 Compose 插件在设计时并未考虑 DCEVM 和热交换。因此，这些工具生成的字节码在热重载期间经常表现出意外行为
  • 从 2.1.20 版本开始，Compose 编译器使用**组键**作为可组合 lambda 的稳定唯一名称
