📌 一句话摘要

本文从源码层面深度剖析 Claude Code 的多 Agent 实现机制，涵盖 Subagent 隔离、父子通信、Fork Subagent 缓存优化和 Coordinator 并行协作模式。

📝 详细摘要

文章以 Claude Code 泄露的源码为基础，系统拆解了其多 Agent 系统的四大核心机制。首先从 Multi-Agent 的基本概念入手，解释了为何需要多 Agent 以及三种常见形态（父子型、平级协作型、主从型）。随后深入分析了 Subagent 的隔离机制，包括工具隔离（通过黑/白名单过滤）和上下文隔离（按字段语义独立决策，如克隆文件缓存、关闭全局状态写入、保留任务注册通路）。接着讲解了父子 Agent 之间的异步消息驱动通信方式，父 Agent 通过 SendMessage 工具向子 Agent 的「信箱」投递消息，子 Agent 通过 XML 格式的 task-notification 伪装成用户消息返回结果。文章还重点介绍了 Fork Subagent 这一缓存优化机制，通过确保子 Agent 的 API 请求前缀与父 Agent 字节级一致，复用 Anthropic 的 prompt 缓存，将成本降至 10%。最后详细阐述了 Coordinator 模式，主 Agent 退化为纯协调者，通过内部工具集并行派发 Worker，实现高并发任务拆解。文章总结了多 Agent 设计的工程启示：角色分离、并发优先、合成不转发、扁平不递归。

💡 主要观点

  1. Claude Code 的多 Agent 系统包含三种机制：常规 Subagent、Fork Subagent 和 Coordinator 模式。 常规 Subagent 对应父子型架构，Fork Subagent 是父子型的缓存优化版本，Coordinator 模式对应主从型架构，三者各有适用场景。
  2. Subagent 的隔离机制分为工具隔离和上下文隔离两个维度。 工具隔离通过全局黑名单、自定义 agent 加严、异步白名单三道门过滤；上下文隔离按字段语义单独决策，如克隆文件缓存、关闭全局状态写入、保留任务注册通路。
  3. 父子 Agent 之间采用异步消息驱动通信，而非函数调用。 父 Agent 通过 SendMessage 工具向子 Agent 的 pendingMessages 信箱投递消息，子 Agent 在循环边界自行读取；子 Agent 完成时通过 XML 格式的 task-notification 伪装成用户消息返回。
  4. Fork Subagent 通过字节级对齐 API 请求前缀来复用 prompt 缓存，大幅降低成本。 Fork Subagent 的 system prompt、工具池、对话历史前缀等五项内容必须与父 Agent 字节级一致，从而命中 Anthropic 的 prompt 缓存，将成本降至约 10%。
  5. Coordinator 模式下主 Agent 退化为纯协调者，最大化并发能力。 主 Agent 只负责派发 Worker、收结果和合成答案，通过内部工具集实现并行派发，遵循「并行是超能力」的原则，适合大任务高并发拆解。

💬 文章金句

  • 所谓上下文隔离，不是一刀切地「全隔离」或者「不隔离」，而是按每个状态的语义单独决策。
  • 成本优化本身就是能力的一部分。
  • 并行是你的超能力，worker 全是异步的，能并行的绝不串行，多找机会一口气派一堆出去。
  • 协调者必须「理解」而不能「转发」。
  • 不要假设所有 agent 都能用所有工具，按 agent 类型做细粒度的权限控制。
