流言终结者：Rust 的性能优势是否名副其实？

9/18/2025, 9:03:00 AM

📌 一句话摘要

Momento 从 Kotlin 迁移到 Rust 的旅程表明，Rust 虽有显著性能优势，但生产环境中的低尾延迟仍需深入调试。同时，生态系统的复杂性也不容忽视。

📝 详细摘要

Momento 是一个无服务器数据平台，最初使用 Kotlin 构建其缓存服务，旨在缩短产品发布周期。然而，他们很快遇到了与垃圾回收、Netty 问题以及 Graviton (ARM 架构) 上的次优性能相关的性能瓶颈。尽管各种 Kotlin 优化仅产生了增量收益，但对复杂数据类型和流式 API 的新产品需求促使他们重新评估。在 Rust 的内存安全、无 GC 以及内部倡导的推动下，Momento 决定逐步将其路由服务迁移到 Rust。这个决定伴随着已知的风险，包括大量的开发人员时间、运行双系统的必要性，以及较年轻的 Rust 生态系统固有的不稳定性 ( `hyper` 的重大变更和 `tonic` 中影响生产的缺陷均体现了这一点 )。迁移后，Rust 提供了最初的性能提升，实现了 32K TPS，而 Kotlin 为 20K TPS。然而，在更高的负载下，出现了新的性能问题，表现为突然的尾延迟峰值。通过深入的调试，利用 Tokio 指标和火焰图，将根本原因确定为 `h2` crate ( HTTP/2 实现 ) 中长期存在的互斥锁竞争问题，而 gRPC 在持久连接上的多路复用加剧了这个问题。文章总结说，虽然 Rust 功能强大，但它并非能够一蹴而就，强调生产环境中的性能优化需要细致的测量、深入的技术理解，以及对底层库复杂性的谨慎处理。

💡 主要观点

  1. 迁移到 Rust 以提高性能需要彻底调查生态系统的稳定性以及潜在的新瓶颈。 Momento 由于不稳定的 Rust crates ( `tonic`，`h2` ) 而经历了生产中断和性能峰值，这表明，仅靠语言选择无法保证性能和稳定性，必须重视底层库的问题及其成熟度。
  2. 优先考虑可预测的低尾延迟需要深入关注单节点性能和详细的调试。 他们将低延迟作为核心目标，因此在扩展前充分优化单节点性能。通过细致的指标分析和火焰图，最终发现了 `h2` 互斥锁竞争等潜在问题。
  3. 将核心生产服务迁移到一种新语言是一项高风险的尝试，需要仔细的计划和增量策略。 Momento 通过采用增量迁移、运行双系统并积极构建内部 Rust 专业知识来降低风险，同时也认识到开发时间与新功能开发之间存在权衡。

💬 文章金句

  • 我们的首要目标是为该产品提供可预测的低尾延迟。
  • Rust 带来了显著的初始性能提升。然而，在单节点性能扩展至极限时，我们遇到了更多问题。这些问题不仅与 Rust 本身相关，更与 gRPC 生态系统及我们的特定用例密切相关。
  • 问题的关键在于 HTTP/2 使用多路复用，因此在单个 TCP 连接上，它具有流的概念，这是一个独立的消息序列。`h2` 正在做的是使用互斥锁来协调同一连接上的不同流。
  • 我们想要指出的最后一个风险是，Rust 生态系统不如旧语言那么稳定。
  • 这是一个不受欢迎的事实，但你也可以用 Rust 编写慢代码。
