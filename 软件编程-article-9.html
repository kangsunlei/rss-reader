如何在 FastAPI 中使用 OpenTelemetry 构建端到端 LLM 可观测性

3/13/2026, 4:13:16 PM

📌 一句话摘要

本技术指南演示了如何在 FastAPI 中使用 OpenTelemetry 实现手动、代码优先的 LLM 可观测性，以跟踪 RAG 流水线、token 使用和模型性能。

📝 详细摘要

本文探讨了观测非确定性 LLM 应用所面临的独特挑战，指出传统的如延迟和错误率等基础设施指标不足以应对。它提倡使用 OpenTelemetry Python SDK 的“代码优先”方法，而非不透明的供应商特定智能体。作者概述了检索增强生成（RAG）系统的参考架构，将请求生命周期分解为不同的、可追踪的 span：检索、提示构建、LLM 调用和后处理。该指南提供了一个完整的 FastAPI 实现示例，展示了如何捕获关键的语义属性，例如 token 计数、预估成本和模型配置，同时通过对敏感提示和响应数据进行哈希处理来强调隐私。

💡 主要观点

  1. LLM 可观测性需要从确定性监控转向概率分析。 传统工具未能涵盖 LLM 特有的维度，如 token 消耗、幻觉率和提示构建延迟，因此需要基于追踪的方法来理解模型为何产生特定结果。
  2. 结构化的 span 层级对于隔离 RAG 流水线中的故障至关重要。 通过为检索、提示构建和推理创建独立的 span，工程师可以判断糟糕的响应是由不相关的上下文检索还是模型的推理能力造成的。
  3. 手动插桩比自动化 SDK 提供卓越的控制力和供应商中立性。 明确设计追踪和语义属性可确保可观测性数据在不同的后端（如 Jaeger 或 Grafana Tempo）之间移植，同时避免专有智能体的“黑盒”性质。
  4. 隐私和安全必须通过数据哈希整合到遥测设计中。 在追踪中存储原始提示和响应会带来安全风险；使用 SHA-256 哈希可以实现请求关联和调试，而不会在可观测性平台中暴露敏感用户数据。
  5. 语义属性应捕获 LLM 配置的完整上下文。 将温度、模型版本和 top-k 值等参数记录为 span 属性，使团队能够将配置更改与成本、延迟和响应质量的变化关联起来。

💬 文章金句

  • 传统的可观测性工具通常关注基础设施层面的信号……尽管这些指标仍然重要，但它们不足以理解 LLM 应用在生产环境中的行为方式。
  • 我们不依赖专有监控智能体或不透明的供应商 SDK，而是采用代码优先的插桩方法。
  • 目标是每个用户请求对应一个追踪，子 span 代表每个逻辑 LLM 步骤。
  • 将 LLM 视为大型系统中的一个组件，而不是系统本身。这种思维方式对于构建可靠的生产应用至关重要。
  • 原始提示有意不作为 span 属性存储……这允许在不暴露内容的情况下进行跨追踪关联。
