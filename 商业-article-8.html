Claude Code 团队如何使用 Claude Code 丨 Claude

9/3/2026, 1:44:00 PM

📌 一句话摘要

Claude Code 团队成员分享他们如今 70% 至 80% 的工作由 Claude Tag 完成，通过先交付目标再关注系统决策、用循环处理反馈、多路 Agent 并行审查，并在模型能力快速迭代中学会放手细节，让 Agent 参与产品改进。

📝 详细摘要

本文记录 Claude Code 团队三位成员（Thariq Shihipar、Sid Bidasaria、Robert Boyce）使用自身产品的真实经验。团队已将日常开发重心转向 Claude Tag，在 Slack 里直接交付目标，由 Agent 自主查找背景、做原型并实现，人工仅在必要时介入。随着模型能力每两个月发生根本变化，一些曾经的「必要」功能（如待办清单）已自然淘汰，团队学会不依恋旧工具。在工程实践上，他们用云端 Loops 让任务跨会话持续运行，以多路并行 Agent 进行对抗式代码审查，并通过自证机制减少人工验证负担。文章也坦诚了失去部分「钻研快乐」的代价，但整体呈现出一种更高效、更系统化的 AI 辅助开发范式。

💡 主要观点

  1. 先交付目标，再按需介入细节 团队成员将 70%～80% 的工作交给 Claude Tag，只在真正需要时才进入终端或桌面应用。不再关注每一步执行过程，而是在有疑问时追查，从而保留注意力用于产品与系统层面的判断。
  2. 模型能力快速迭代，工具设计应接受短期有效而非永久存在 团队形容自己处于时间流速特别快的房间，模型大约每两个月发生根本变化。曾经的短板修复（如待办清单）随能力提升而自然失效，因此工具应设计为可删减，不必为当前模型过度定制。
  3. 用云端循环替代本地开发环境，让任务跨会话持续运行 过去合上电脑 Agent 就停止，现在托管容器让 Loops 和 routines 能在后台持续执行。例如每天自动读取用户反馈、按重要性分类，并修复 Agent 有较高把握解决的问题。
  4. 代码审查从逐行纠错转向系统背景判断与对抗式复核 不再以挑小毛病证明认真，而是追问 API 设计、服务边界等深层原因；采用多路并行 Agent 分别查找潜在错误，再交叉对抗式复核，过滤大量误报，只把值得关注的部分交给人。
  5. 少了对细节钻研的快乐，但获得了处理更大问题的空间 成员怀念手工调性能、叠 CSS 日子的满足感，但承认 Claude 已超越多数人的水平。现在更多精力放在把想法变成原型、将原型变成可用产品，软件工程的核心仍是解决问题，只是问题范围更大。
