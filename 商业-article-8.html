Agent 基建不是设计出来的，是被 Kimi K3 和一堆应用公司卷出来的

8/18/2026, 10:23:00 AM

📌 一句话摘要

Agent 基建不是设计出来的，是被 Kimi K3 和一堆应用公司卷出来的，TiDB 通过数据库、内存、文件系统等统一存储层支持 Agent 的状态持久化与弹性执行。

📝 详细摘要

文章以 TiDB 团队服务 Kimi、Dify 等 AI 团队的实践为切入点，梳理了 Agent 时代基础设施的演变路径：从早期解决用户增长与数据库容量问题，到工作空间直接申请数据库，再到 Agent 自行创建和释放资源。针对 Agent 需要持久化状态、记忆、文件以及可解释的执行环境，TiDB 分别推出了虚拟数据库（秒级就绪、scale-to-zero）、TiDB Cloud Memory（跨 session 可检索记忆）、TiDB Cloud Filesystem（保存代码仓库与工作区）以及 TiDB Cloud Lake（统一交易与分析语义），形成 TiDB Agent Stack。文章提出 Agent 时代的计算单位是 Agent 本身，阐述了六个关键问题和三个架构判断（先算空闲成本、拆开执行与状态、减少系统边界），并指出 AI 不会消除基础设施，而是让基础设施再次显现。全文数据详实、逻辑清晰，为正在构建 Agent 产品的创业者提供了具体的技术与成本考量。

💡 主要观点

  1. Agent 的计算单位是 Agent 本身，用户身边可能有十到上百个 Agent 同时运行。 每个 Agent 需要独立的状态、记忆和数据，这使得资源分配与隔离的粒度从用户/会话转向了 Agent。
  2. 执行环境可以临时，但产生的数据、状态必须持久化，这是 Agent 从 Demo 走向生产的分水岭。 TiDB 通过虚拟数据库实现秒级就绪的按需实例，空闲时释放计算资源，从而控制大量低频 Agent 的空闲成本。
  3. Agent 需要统一的持久层来保存数据、记忆、文件、Git 工作区和操作记录，才能成为 full‑stack agent。 TiDB 分别提供 Memory（跨 session 可检索记忆）、Filesystem（保存代码与工作区）、Lake（统一交易与分析语义）以及 Starter 数据库，形成 Agent 的统一状态底座。
  4. 创业团队在设计 Agent 基础设施时应先评估空闲成本、从第一天就拆开执行与状态、并尽量减少系统边界。 这三个判断来源于真实客户付出的成本，能够帮助团队在规模化前避免资源浪费和系统复杂度失控。
  5. AI 不会消除基础设施，反而会让基础设施再次显现，模型越强越暴露基建缺口。 正如 Kimi K3 等强大模型推动 Agent 能力边界外扩，随之而来的是对数据库、文件系统、记忆等基础设施的更具体、更迫切的需求。

💬 文章金句

  • Agent 时代的计算单位，不是用户，不是会话，是 Agent 本身。
  • 执行环境可以临时，数据与状态必须持久。
  • AI 不会消除基础设施，AI 会让基础设施再次显现。
