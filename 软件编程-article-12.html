我们值得拥有更好的 JavaScript Streams API

2/27/2026, 2:00:08 PM

📌 一句话摘要

对 WHATWG Streams 标准的批判性架构分析，重点讨论了其性能瓶颈、设计缺陷以及对现代 JavaScript 原生替代方案的需求。

📝 详细摘要

Node.js 核心维护者兼 Cloudflare 工程师 James Snell 认为，Web Streams API 在现代 JavaScript 开发中存在根本性缺陷。该 API 设计于异步迭代（ES2018）之前，依赖复杂的锁定模型和过多的 Promise 创建，导致了显著的性能开销——有时比潜在的替代方案慢 120 倍。文章详细介绍了手动锁定管理如何导致资源泄漏、BYOB（Bring Your Own Buffer）实现为何在实际使用中过于复杂，以及背压机制如何被轻易绕过，从而在 SSR 和流克隆（teeing）等场景中导致内存耗尽。结论指出，虽然运行时已经实现了各种“原生路径”优化来缓解这些问题，但仍有必要利用现代语言原语进行根本性的重新设计。

💡 主要观点

  1. Web Streams API 设计于异步迭代之前，导致了不直观的锁定模型。 由于早于 ‘for await...of’ 出现，该规范引入了手动的读取器获取和锁定管理，这产生了大量的样板代码和脆弱的代码结构。
  2. 手动锁定机制经常导致流的永久损坏和资源泄漏。 忘记调用 ‘releaseLock()’ 或未能消耗已获取的正文可能会永久锁定流或耗尽连接池，这是生产环境中的常见陷阱。
  3. BYOB (Bring Your Own Buffer) API 过于复杂，且很少提供可衡量的收益。 基于转移的内存模型和专门的读取器类型使得零拷贝读取难以正确实现，导致大多数开发者宁愿接受分配开销。
  4. Web Streams 中的背压是建议性的，通常无法防止内存的无限增长。 即使超过容量，‘controller.enqueue()’ 等函数也会成功，而像 ‘tee()’ 这样的操作如果其中一个分支较慢，可能会导致隐蔽的大规模内存堆积。
  5. 热点路径中过多的 Promise 创建会导致显著的性能下降和 GC 压力。 规范要求为每个读/写操作建立 Promise 链，这产生了巨大的对象分配开销，对于 SSR 等高频任务来说尤其致命。

💬 文章金句

  • 这些问题不是 Bug，而是十年前可能合理的设计决策所带来的后果，但它们与当今 JavaScript 开发者的编写代码方式并不一致。
  • 在基准测试中，这种替代方案在我测试过的每个运行时中都比 Web Streams 快 2 到 120 倍。
  • 忘记 releaseLock() 会永久损坏流。locked 属性会告诉你流已被锁定，但不会告诉你原因、由谁锁定，或者该锁是否仍然可用。
  • BYOB 对用户和实现者来说都很复杂，但在实践中很少被采用。大多数开发者坚持使用默认读取并接受分配开销。
  • JavaScript 引擎花费大量时间回收短寿命对象，而不是执行有用的工作。随着 GC 暂停中断请求处理，延迟变得不可预测。
