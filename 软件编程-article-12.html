Kubernetes 1.35 发布：引入原地 Pod 扩容与 AI 优化调度

12/31/2025, 10:00:00 AM

📌 一句话摘要

Kubernetes 1.35 “Timbernetes” 引入了原地 Pod 扩容、AI 优化的成组调度（Gang Scheduling），以及针对可变性、可观测性和证书管理的重大增强，标志着云原生和 AI/ML 工作负载的一次重要更新。

📝 详细摘要

Kubernetes 1.35 代号为 “Timbernetes”，其发布重点在于可变性以及对 AI/ML 工作负载的优化支持。核心特性包括原地 Pod 扩容（In-Place Pod Resize）正式商用（GA），允许在不重启的情况下动态调整运行中 Pod 的 CPU 和内存，这对 Java 应用和资源效率提升具有显著意义。此版本还引入了成组调度（Gang Scheduling）的 Alpha 支持和全新的 PodGroup API 资源，实现了相互依赖 Pod 的原子化调度，这对于此前由 Volcano 或 Kueue 等外部项目管理的 AI/ML 训练任务至关重要。`/flagz` 和 `/statusz` 端点的增强提升了可观测性和自动化故障排除能力。水平 Pod 自动扩缩器（HPA）的可配置容忍度已进入 Beta 阶段，提供了更灵活的扩缩容方案。此外，PodCertificateRequests 移至 Beta 阶段，简化了 Pod 的 mTLS 证书管理。文章还提到社区正逐渐从 Ingress NGINX 控制器转向 Gateway API 等现代替代方案。总体而言，1.35 版本引入了 60 项增强功能，巩固了 Kubernetes 作为高性能云原生和 AI/ML 应用平台的地位。

💡 主要观点

  1. 原地 Pod 扩容现已正式商用，支持在不重启的情况下动态调整运行中 Pod 的资源。 该功能显著提高了资源利用率和应用效率，对于资源需求波动的应用（如启动阶段需要更多资源的 Java 应用）特别有利。
  2. Kubernetes 1.35 引入了对成组调度的原生支持和新的 PodGroup API，优化了 AI/ML 工作负载的调度。 这些 Alpha 特性允许将 AI/ML 训练中常见的相互依赖的 Pod 作为一个单元进行调度，减少了失败率并提高了复杂分布式应用的资源分配效率。
  3. 通过改进 `/flagz` 和 `/statusz` 端点以及可配置的 HPA 容忍度，增强了可观测性和自动化水平。 核心组件提供的机器可解析输出简化了故障排除，而灵活的 HPA 容忍度允许更精确且针对特定工作负载的自动扩缩容配置，提升了集群运营效率。
  4. PodCertificateRequests 简化了 Pod 的 mTLS 证书管理，社区信号显示正逐渐放弃 Ingress NGINX。 Pod 级别的自动化证书生成提高了安全性并简化了 mTLS 流程。Ingress NGINX 的弃用则鼓励用户采用更现代、集成度更高的网络解决方案，如 Gateway API。

💬 文章金句

  • 1.35 版本的一个核心特性是原地 Pod 扩容的正式商用。该功能允许集群操作员在不触发容器重启的情况下，调整运行中 Pod 的 CPU 和内存资源。
  • 为什么它对 Java 至关重要？你可以在启动时为 Pod 分配额外的 CPU，然后在启动后将其缩小。这样应用启动快，且 Pod 始终使用适量的资源。
  • 成组调度确保了一组相互关联的 Pod（例如 AI/ML 训练任务）能够同时被调度，否则就都不调度。
  • 社区决定逐步停止支持 Ingress NGINX 控制器，反映了向更集成解决方案迁移的趋势，鼓励用户考虑 Gateway API 等现代替代方案。
