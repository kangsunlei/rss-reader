浅谈 SKILL 研发的最佳实践——以百补详情助手为例

8/21/2026, 2:47:00 AM

📌 一句话摘要

本文以百亿补贴详情助手 Skill 为例，从架构设计、研发效能、运行优化、呈现方式四个维度总结 Agent Skill 的研发与迭代实践，提出上下文工程决定 Skill 质量上限、让 Agent 自己写 Skill 是元能力的核心观点。

📝 详细摘要

本文以天猫团队为百亿补贴详情页开发的 bybt-detail-assistant Skill 为例，总结 Agent Skill 研发与迭代的实践方法论。作者先梳理业界最佳实践：Anthropic Claude Skills 的渐进式披露与控制调优、MiniMax 的标准化仓库与工业化生产，以及社区总结的 Skill 设计模式。随后从架构设计、研发效能、运行优化、呈现方式四个维度展开具体做法：通过桥接器解耦本地 Skill 与远程 Agent，用决策树实现按需加载、减少 SKILL.md 中的次要信息；研发时直接用最强模型辅助开发、按任务动态切换上下文工作区、小步提交并让 Agent 看到真实运行时数据；运行上通过强制「原文直出」对抗模型总结冲动、用 sessionId 保持会话记忆、优先输出 HTML 报告提升信息密度，并在执行前后主动引导用户澄清与递进分析。作者认为，Skill 质量上限由上下文工程能力决定，让 Agent 自己写 Skill 是一种元能力，开发者正从编写者转变为审查者与上下文提供者。

💡 主要观点

  1. Skill 质量上限由上下文工程能力决定，而非写作技巧。 在对的时机把真实案例、错误堆栈、API 返回结构等关键信息以合适粒度递到模型面前，才是 Skill 迭代的核心竞争力，SKILL.md 只是能力载体。
  2. 用桥接器解耦本地 Skill 与远程 Agent，隔离稳定与高频迭代。 远程分析能力每周迭代，放在远程 Agent 可依托成熟的灰度发布与回滚机制；本地保留薄客户端，避免用户频繁更新，代价是多出一层网络链路和协议契约。
  3. 开发阶段直接用最强模型，让 AI 帮写并迭代 Skill。 用中端模型省 token 反而因反复纠错消耗更多，开发者应把官方最佳实践与真实案例一并交给最强模型，再验证弱模型兼容性。
  4. 用决策树按需加载路径、压缩 SKILL.md 次要信息，控制模型注意力。 按执行路径拆分逻辑互斥的分支，用脚本固化埋点解读等低自由度逻辑，把模型的注意力留给真正需要判断的任务。
  5. 运行时现场是 Agent 迭代的关键上下文。 端到端验证必须用带热点的真实商品与日志，脚本异常时把错误堆栈、源码和触发数据打包给 Agent，让它自己收敛修复。

💬 文章金句

  • Skill 的质量上限由“上下文工程”能力决定，而非写作技巧。
  • 在对的时机（Agent 要做判断的那一刻），把对的信息（真实案例、错误堆栈、API 返回结构），以对的粒度（不多不少，刚好够做决策）递到模型面前------对于 Skill 迭代而言，这才是真正的核心竞争力，而 SKILL.md 只是这种能力的载体之一。
  • 不能持续迭代的 Skill，说到底只是一次性的 demo。
  • 当 SKILL.md 接近 500 行阈值时，每次新增内容都要问：“删掉这句话会不会导致 Agent 出错？”如果不会，就不应该加。
