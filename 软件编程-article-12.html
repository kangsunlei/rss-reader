《Kingbase 护城河》——数据库存储空间全景探测与精细化瘦身实战

6/19/2026, 3:14:59 AM

📌 一句话摘要

本文以金仓数据库为例，构建了一套从操作系统物理层到数据库内核 MVCC 层再到企业架构层的磁盘空间排查与治理框架，并提供了可操作的 SQL 命令与架构方案。

📝 详细摘要

文章围绕数据库磁盘空间不足这一生产级问题，提出了一套系统化的排查与治理方法论。作者从操作系统物理层入手，通过 `df -Th` 和 `du -sh` 定位磁盘占用来源，区分业务数据与日志/归档文件导致的膨胀。随后进入数据库逻辑层，使用 `sys_database_size` 和 `sys_total_relation_size` 等系统函数进行实例级与表级容量透视，并解释了 TOAST 机制对空间占用的影响。文章核心部分深入剖析了 MVCC 多版本并发控制机制导致「DELETE 后空间不释放」的根本原因——表膨胀（Table Bloat），并通过 `sys_stat_user_tables` 视图演示了膨胀率的检测方法。最后，作者提出了两个企业级架构解决方案：使用表空间（Tablespace）进行物理层空间转移，以及采用时间范围分区表（Range Partition）替代高频 DELETE，实现秒级空间释放。全文以金仓数据库为实践载体，但方法论与原理适用于所有基于 MVCC 的关系型数据库。

💡 主要观点

  1. 磁盘空间排查应遵循「OS 物理层 → DB 逻辑层 → MVCC 内核层 → 架构层」的递进框架。 作者强调不能仅凭数据库内的 SQL 查询判断空间问题，需先通过 `df -Th` 和 `du -sh` 确认磁盘占用是否来自数据库本身，再逐层深入，避免误判。
  2. MVCC 机制是 DELETE 后空间不释放的根本原因。 金仓等数据库使用 MVCC 实现高并发读写，DELETE 操作仅标记数据为 Dead Tuple，并不立即回收物理空间，导致表膨胀（Table Bloat）。
  3. VACUUM FULL 可回收空间但会锁表，生产环境需谨慎使用。 VACUUM 仅标记空间可复用，不释放物理文件；VACUUM FULL 通过重建物理文件回收空间，但会加 AccessExclusiveLock，阻塞所有读写，仅适合停机维护。
  4. 表空间（Tablespace）可实现物理层空间转移，缓解单盘压力。 当系统盘空间不足时，可通过 CREATE TABLESPACE 在新磁盘创建表空间，再用 ALTER TABLE SET TABLESPACE 将大表动态迁移，无需停机。
  5. 时间范围分区表是替代高频 DELETE 的终极架构方案。 按月份创建分区子表，过期数据直接 DROP TABLE 子表，底层执行 unlink 操作，0.1 秒内释放百 GB 空间，不产生表膨胀，不影响当前写入。

💬 文章金句

  • 搞数据库的人，其实不能只看着表面头痛医头。
  • 你删了百万级的数据以后，去 CentOS 上用 `du -sh` 看底层的物理文件，大小还是一点都不变。
  • `DROP TABLE` 根本不走 MVCC 机制，也就不会产生什么死亡标记。它在 Linux 底层直接就把那个物理文件给抹掉了。
