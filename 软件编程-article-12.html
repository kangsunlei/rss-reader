慢 SQL 优化实战：从一例线上慢 SQL 探究执行引擎工作过程

8/6/2025, 12:01:00 PM

📌 一句话摘要

通过一个线上慢 SQL 案例，深入分析 MySQL 执行引擎的 Join 和 OrderBy 算法，并利用 Optimizer_trace 揭示真实瓶颈，最终通过索引优化大幅提升查询性能。

📝 详细摘要

文章以一个耗时分钟级的线上慢 SQL 为例，详细阐述了 MySQL 中 Join 操作的 Block Nested-Loop Join (BNL) 和 Index Nested-Loop Join (NLJ) 算法，以及 OrderBy 操作的全字段排序和 Rowid 排序原理。作者首先通过 Explain 命令进行初步分析，随后利用 Optimizer_trace 工具对 SQL 的真实执行过程和成本进行深入剖析，发现优化器预估与实际瓶颈的差异。文章指出，尽管优化器认为排序开销最大，但实际瓶颈在于 BNL 算法导致被驱动表多次全表扫描。最终，通过在被驱动表关联键上添加索引，成功将低效的 BNL 优化为高效的 NLJ，使 SQL 响应时间从分钟级降至毫秒级，有效解决了性能问题。文章总结了 SQL 调优的基本思想，强调了理解原理、辅助工具和实验验证的重要性。

💡 主要观点

  1. 深入理解 MySQL Join 和 OrderBy 算法是 SQL 优化的基础。 文章详细介绍了 BNL、NLJ、全字段排序和 Rowid 排序的工作原理，为读者提供了优化 SQL 所需的理论知识，是进行性能分析和问题定位的前提。
  2. 结合 Explain 和 Optimizer_trace 能精准定位 SQL 真实性能瓶颈。 仅凭 Explain 可能无法完全揭示真实执行成本，Optimizer_trace 能提供更细致的执行过程和开销数据，帮助识别优化器预估与实际情况的差异，避免误判。
  3. 引导执行引擎选择更高效的算法是 SQL 调优的关键策略。 通过添加索引等方式，将低效的 BNL 算法转换为高效的 NLJ 算法，能显著提升查询性能，实现从分钟级到毫秒级的优化，是解决此类问题的有效手段。

💬 文章金句

  • 本文通过一个线上慢 SQL 案例，介绍了 Join 的两种算法和 Order by 的工作原理，并通过 Explain 和 Optimizer_trace 工具完整推演了慢 SQL 的执行过程。
  • 当两张表的行数（m、n 大小）固定的情况下，m 对结果的影响更大，m 越小整体扫描的代价越小，所以执行引擎优先选择数据量更小的表作为驱动表(符合"小表驱动大表"的说法)。
  • 综合执行引擎的预估的执行计划和真实的执行结果参数可以得出，执行引擎预估最大的执行开销为排序，但实际上排序并未使用磁盘临时文件，且 Rowid 排序的回表操作是在内存中进行的（在内存临时表中进行回表），3000 条数据的内存排序开销是极快的，所以真实的最大开销是 BNL 算法导致的对被驱动表多次进行全表扫描的开销。
  • 对于 BNL 算法，可以通过在被驱动表添加索引使其转化为 NLJ 算法来进行优化（此处注意一些索引失效的场景，笔者在实际调优中遇到了字符集不同导致的索引失效场景）。
  • 首先，需要了解 SQL 语句中的关键字（Join、Order by...）的基本工作原理，并辅助一些执行过程数据（Explain、Optimizer_trace），通过实验验证猜想，最终达成调优的目的。
