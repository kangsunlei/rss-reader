为什么有些依赖必须 import *引入使用？

10/1/2025, 12:31:00 AM

📌 一句话摘要

文章深入探讨了 ECharts 等库为何必须使用`import * as`进行导入，并详细解析了 ESM、CommonJS 模块规范差异及 ECharts 背后的兼容性与 API 设计考量。

📝 详细摘要

本文以 ECharts 为例，解决了前端开发中常见的`import * as`导入方式的疑惑。文章首先介绍了 ES Module 中默认导入、具名导入和命名空间导入的几种常见用法。接着，通过分析 ECharts 的入口文件，揭示了其采用具名导出和`export =`（CommonJS 风格）而非`export default`的原因，主要是为了兼容 ESM、CommonJS 和 UMD 多种模块规范，以及遵循其“命名空间式 API”的设计思路。文章还列举了 lodash-es 和 Node.js `path`模块等其他需要`import *`的场景。最后，提供了判断模块导入方式的实用方法，包括查阅官方文档、检查`.d.ts`类型定义文件以及利用 AI 编译器智能提示。整体而言，文章对 JavaScript 模块化原理的讲解深入浅出，具有很强的实践指导意义。

💡 主要观点

  1. 某些库（如 ECharts）要求使用 `import * as` 导入，是因为它们采用具名导出而非默认导出。 ECharts 等库为了兼容 ESM、CommonJS 和 UMD 多种模块规范，并维持其命名空间式 API 设计，通常不提供`export default`，而是通过具名导出或`export =`方式，导致在 ESM 环境下需要`import * as`来导入所有成员。
  2. ECharts 采用 `export =` 导出而非 `export default` 是出于历史兼容性和 API 设计考量。 ECharts 早期基于 UMD 发布，后迁移至 TypeScript 时延续了`export =`以更好地兼容 CJS/UMD，同时保持其"命名空间式 API"的调用习惯，避免了`export default`可能带来的兼容性问题。
  3. 开发者可通过查阅文档、源码或利用 AI 工具智能提示来判断正确的模块导入方式。 面对不确定的模块导入方式时，最直接的方法是参考官方文档，或检查库的`.d.ts`类型定义文件，此外，现代 AI 编译器也能提供准确的导入建议，提高开发效率。
