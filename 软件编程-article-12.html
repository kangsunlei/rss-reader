从应用架构的视角看退小宝 AI 助手落地现状

2/11/2026, 9:29:00 AM

📌 一句话摘要

本文从应用架构视角深入探讨了 AI 原生应用的构建范式，结合“退小宝”实战案例，系统阐述了从简单 API 调用到复杂工作流编排的演进路径及工程实践要点。

📝 详细摘要

文章系统性地对比了传统 Web 架构与 AI 应用架构在响应时间、准确性、成本等维度的差异，强调了 AI 原生应用在处理意图灵活性与创造性方面的独特优势。作者详细解析了 AI 应用的核心组件（LLM、Message、Tool、RAG、State），并重点介绍了以 Workflow 为核心的低代码图结构实现方案。通过“退小宝”在离线数据查询（Text2SQL）和图表生成方面的落地经验，分享了如何通过 RAG 优化、DSL 转换及权限管控等工程化手段，解决 LLM 在业务场景中的准确性、上下文超限及安全性挑战，为开发者提供了从理论到实践的完整参考。

💡 主要观点

  1. AI 原生应用应独立于传统 Web 架构进行设计，而非简单的模块嵌入。 传统 Web 架构追求高可用与确定性，而 AI 应用在响应时延、结果准确性上存在天然差异，采用 AI 原生设计能更好地适配 LLM 的流式输出与非确定性特征。
  2. 工作流（Workflow）是当前 AI 应用落地比 ReAct Agent 更具可控性的范式。 工作流通过图结构组织节点，能有效结合低代码的灵活性与程序逻辑的严谨性，特别适合处理需要流式对接、复杂分支控制及自定义存储的业务场景。
  3. 上下文管理（State）是 AI 应用的核心，其本质是对 Message 列表的精细化维护。 AI 应用的差异化体现在 Message 列表的组装与工具的选择上。通过管理 State，可以实现时间回溯、上下文压缩等高级功能，从而提升 LLM 的决策质量。
  4. 权限管控必须由应用程序或工具层硬编码实现，严禁交给 LLM 决策。 LLM 存在不确定性，权限校验应在工具调用前通过 State 中的可靠身份标识进行拦截，确保数据安全不依赖于模型的推理结果。
  5. Text2SQL 的落地需通过 RAG 优化与推理过程显式化来提升准确率。 针对表结构超限和逻辑复杂问题，应将 Schema 存入知识库进行动态召回，并允许 LLM 输出推理过程，再通过固定程序提取 SQL 以保证语法正确。

💬 文章金句

  • AI 原生应用（而非简单在旧系统中嵌入 AI 模块）是更可行路径。
  • AI 应用之间现在不同的差异在于 message 列表和工具列表的差异。
  • 权限管理无法交给 LLM 去做，可由工具、AI 应用程序本身、MCP 机制等去做权限管控。
  • 如果一个取数是业务很需要的，业务会经常看和使用，会固定为报表逻辑；如果一个取数是临时的，人工比 AI 能力一定强。
  • AI 应用目标的业务场景需要容忍结果的正确率不为 100%，如果错误即有较大负面影响，则无可行性。
