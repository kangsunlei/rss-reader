如何为大型 Next.js 应用构建可复用的架构

4/3/2026, 6:00:09 PM

📌 一句话摘要

一份关于如何利用 App Router 的并置（colocation）、基于特性的结构、Turborepo 和 Server Components 为大型 Next.js 应用构建可扩展、分层架构的综合指南。

📝 详细摘要

本文提供了一份构建大型 Next.js 应用的实用蓝图，旨在防止技术债务和紧密耦合。文章概述了一种六层架构方法：利用 App Router 的并置模型处理路由特定的逻辑，实施基于特性的文件夹结构并配合严格的公共 API（barrel 文件），以及使用 Turborepo 管理 Monorepo 以实现跨多个应用的代码共享。此外，文章还探讨了如何将 Server Components 作为数据获取的架构边界，使测试策略与代码库层级保持一致，并优化 CI/CD 流水线以仅构建变更部分。该指南强调了封装、清晰的边界以及“邻近原则”（rule of proximity），以确保长期的可维护性。

💡 主要观点

  1. 利用 App Router 的并置特性和邻近原则。 文件应尽可能靠近其使用位置。App Router 允许路由段（route segments）拥有自己的布局、组件和数据获取逻辑，使重构更安全、更直观。
  2. 按领域特性而非文件类型组织代码。 将相关逻辑分组到特性文件夹中（例如 auth、billing），并使用 barrel 文件（index.ts）定义公共 API，防止内部实现细节泄漏到整个代码库中。
  3. 使用 Turborepo 在多个应用间共享逻辑。 Monorepo 结构允许通过内部包共享 UI 原语、身份验证工具和数据库客户端，确保面向客户的应用、管理后台和营销站点之间的一致性。
  4. 将 Server Components 视为架构边界。 将“use client”边界尽可能下推到组件树的底层。使用 Server Components 处理繁重的数据获取，仅在交互式的“叶子”节点使用 Client Components，以优化性能和包体积。
  5. 使测试粒度与架构层级保持一致。 应用测试金字塔模型：对共享包进行单元测试，对特性模块进行集成测试，并将 E2E 测试保留给结账或身份验证等关键用户流程。

💬 文章金句

  • 答案几乎总是架构，或者更确切地说，是缺乏架构。
  • 文件应该尽可能靠近其使用位置。
  • 不要按文件类型（组件、钩子、工具）对文件进行分组，而应按它们的功能进行分组。
  • “use client” 指令并不意味着“这段代码只在浏览器中运行”，它意味着“这是服务器到客户端交接开始的边界”。
  • 过早的抽象和完全没有抽象一样具有破坏性。
