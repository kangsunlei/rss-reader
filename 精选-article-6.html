小红书推荐系统的 Agentic 发布：跨昼夜任务 Harness 实践

9/30/2026, 9:59:00 AM

📌 一句话摘要

小红书推荐系统将跨昼夜发布流程沉淀为近 20 万字 SKILL 后仍出现模型幻觉导致推全事故，转而构建长程任务 Harness，以任务持久化、模板约束、引擎推进和效果查证保障 Agent 可靠完成发布。

📝 详细摘要

小红书推荐核心服务的一次发布横跨十几个部署组、数千个 Pod，平均持续 10 多个小时，并需等待次日真实流量验证，同时具备 Long-Running 与 Long-Horizon 特征。团队最初将发布知识整理成近 20 万字 SKILL 供 Agent 读取，但一次模型幻觉导致参数漏传，使本应灰度的版本直接推全，暴露出提示词方案无法提供持久化、并发控制、幂等、恢复和效果查证。为此团队构建 Harness，位于 Agent 与生产环境之间，包含流程模板、任务、引擎和提案四个核心实体：任务独立于会话保存权威状态，通过版本号乐观锁协调并发；模板以声明式定义步骤、条件与约束；引擎以类似 Kubernetes Reconciliation Loop 的方式推进，中断后从当前事实重新计算；外部动作采用 Transactional Outbox 加 at-least-once 与效果查证，不承诺 exactly-once；Agent 通过 plan and apply 两段式提案处理异常与临时调整，并需满足可观测、可停止或回退、影响范围可控、判断可靠四项准入条件。当前每次发布平均仍需约 2 次人工介入，团队通过执行闭环与治理闭环逐步扩大自主范围。

💡 主要观点

  1. 跨昼夜发布的核心难点在环节之间的衔接，而非单个环节的自动化 构建、测试、发布和检测早已各自自动化，但上一个平台产生结果后由谁确认事实、检查条件并启动下一步，等待数小时后由谁恢复任务，计划变化时由谁判断哪些动作已失效，这些衔接问题无法由一次模型会话承担。
  2. SKILL 能传递知识，不能承载执行责任 近 20 万字操作手册让模型理解了流程，但一次模型幻觉导致参数漏传，使本应灰度发布的版本直接在全部部署组推全。SKILL 可以描述必须灰度，却不能强制每次平台调用携带正确范围，持久化、并发控制、幂等、恢复和效果查证必须交给模型之外的 Harness。
  3. Harness 通过任务、模板、引擎、提案四个实体分离决策与执行 任务在会话之外保存权威状态，模板以声明式固化步骤与约束，引擎依据当前状态推导下一步并写回结果，Agent 只负责处理无法预先穷举的信息并生成提案，不直接组装生产平台调用。
  4. 外部动作以实际效果为准，采用 at-least-once 加效果查证 每个动作发出前先通过 Transactional Outbox 写入任务及稳定标识，中断后沿用同一标识，结果不明确时回到平台查证。系统不承诺 exactly-once，后续步骤只依据已写回任务的平台事实判断，API 返回成功不直接成为继续放量的依据。
  5. Agent 自主范围由实际验证结果逐步扩大，而非设计决定 一类判断需同时满足可观测、可停止或回退、影响范围可控、判断可靠四项准入条件并取得授权，才进入自主执行范围。当前每次发布平均仍需约 2 次人工介入，团队通过执行闭环与治理闭环将反复出现的异常转化为评测样本，验证后再纳入自主范围。

💬 文章金句

  • 发布知识可以写进 SKILL，执行责任必须交给模型之外的 Harness。
  • 任务保存的是已经发生的事实，而不是某个 Agent 对历史过程的记忆。
  • 系统采用 at-least-once 加效果查证，不承诺 exactly-once。
  • Agentic 程度并非来自设计，而是来自实际验证。
  • Harness 所保障的，不是模型永远正确，而是模型出错、进程中断或环境变化时，任务仍能停在可判断、可恢复的位置，并依据真实结果继续执行。
