老年代的“滞留对象”：一次由提前晋升引发的线上内存告警排查

8/25/2025, 12:32:00 AM

📌 一句话摘要

文章详细记录了一次线上 Java 应用 G1 GC 老年代内存告警的排查过程，揭示了高 QPS 下临时对象提前晋升及 Mixed GC 未及时触发导致的内存滞留问题，并提供了解决方案。

📝 详细摘要

本文以一次线上内存告警为切入点，深入剖析了 Java 应用中 G1 垃圾回收器老年代内存持续增长的现象。作者通过内存 dump 分析，发现大量不可达的 NioChannel 对象滞留在老年代。文章系统排除了长生命周期对象和大对象直接晋升的可能性，最终定位问题为 Survivor 区不足导致的临时对象提前晋升，以及 G1 的 InitiatingHeapOccupancyPercent 参数设置过高，导致 Mixed GC 未能及时触发回收这些不可达对象。为解决此问题，作者通过调整 JVM 参数（如减小堆空间、Region 大小、降低 IHOP 阈值）成功促使 Mixed GC 回收了老年代对象，并提出了调整 SurvivorRatio 以避免提前晋升的根本性建议。整个排查过程逻辑清晰，论证严谨，提供了丰富的 GC 日志作为支撑。

💡 主要观点

  1. 高 QPS 场景下，临时对象可能因 Survivor 区不足而提前晋升至老年代。 在 Young GC 时，如果 Survivor 空间不足以容纳所有存活对象，部分年轻对象会被迫直接晋升到老年代，导致老年代短期内存使用量增加，甚至滞留。
  2. G1 GC 的 InitiatingHeapOccupancyPercent 参数过高会延误 Mixed GC 触发时机。 IHOP 参数决定了老年代占用比例达到多少时触发并发标记，若设置过高，即便老年代存在大量不可达对象，Mixed GC 也无法及时清理，造成内存堆积。
  3. 通过调整 JVM 参数可有效优化 G1 GC 行为，解决老年代内存滞留问题。 通过降低 IHOP 阈值、调整堆大小和 Region 大小，可以使 Mixed GC 更早、更频繁地介入，及时回收老年代中的不可达对象；同时调整 SurvivorRatio 能增大 Survivor 区，减少提前晋升。
  4. 线上内存告警排查应遵循先止血、后分析、再解决的流程。 文章展示了从紧急 dump 和 FullGC 止血，到通过内存分析工具定位问题对象、逐一排查晋升原因，最终通过参数调优解决问题的完整实践流程，具有很强的指导意义。

💬 文章金句

  • 对于老年代的对象，大部分人第一印象是因为多次 GC 没有被回收所以晋升到老年代的。其实不然，本文对于老年代中发现大量不可达对象深入排查了一下，发现部分高 QPS 场景下临时对象的提前晋升问题和难以回收的现象。
  • 实际上问题就是因为一大堆的不可达对象，占用了老年代并且没有触发 FullGC，从而导致了内存使用较高引发的告警。
  • 对象提前晋升到 Old 区可能发生在 Young/Mixed GC 的时候，当动态分配的 Survivor 区域的空间小于本次 GC 要晋升的对象所需空间总和时，就会将部分未'年满'的对象直接放到 Old 区。
  • 这个 InitiatingHeapOccupancyPercent 的值设置不宜较大也不宜过小，较大可能导致 FullGC 的次数较多，而 Mixed 次数较少，从而导致 STW 的时长较长。过小的会就又会频繁的依法标记清理行为，GC 的负担较重，吞吐量下降。
  • 现在回头来看，让 Old 区域增加的原因是因为提前晋升导致的。那么我们从源头上解决这个问题，就是如何避免这种'未老先升'的情况产生。
