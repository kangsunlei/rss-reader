AWS 老兵：新的软件开发生命周期

8/2/2026, 2:42:55 AM

📌 一句话摘要

AWS 老兵 Heitor Lessa 深度拆解 Agent 驱动的软件开发生命周期，分享他为 1400 名工程师设计的从产品发现到合并检查的完整工作流，以及重构时烧掉 2 亿 token 的惨痛教训。

📝 详细摘要

本期对话 AWS 老兵、Lambda Powertools 创始人 Heitor Lessa，他首次完整展示了自己为 1400 名工程师设计的 Agent 驱动开发工作流。Heitor 详细拆解了产品循环（从客户发现、白板讨论到 /roadmap 命令固化），以及开发循环中通过 Open Spec 规范驱动开发，并采用三档模型策略（SOTA 模型探索、中档模型实施、小模型审查）来控制成本。他强调了对抗性评审与合并检查机制的重要性，以防止 Agent 伪造证据，并通过 /retro 命令实现工作流的持续改进。此外，Heitor 还分享了本地优先架构（LFA）的理念，以及学习相邻岗位技能、苏格拉底式提问法、纸质笔记等对工程师个人成长的建议。

💡 主要观点

  1. Agent 驱动开发需要全新的结构化工作流 传统 PRD 文档需转变为思维模型融入工程环节。Heitor 设计了「产品循环」和「开发循环」，通过 /roadmap、/new work 等确定性命令，确保人对开发流程的主导，防止 Agent 偏离目标。
  2. 三档模型策略是平衡智能与成本的关键 为应对 1400 名工程师规模的 AI 成本，采用 SOTA 模型做探索与理解，中档模型负责实施，小模型进行高频审查，避免一味使用最强模型导致财务失控。
  3. 对抗性审查与合并检查是代码质量的最终防线 为防止 Agent 伪造测试证据或跳过审查，团队设置了 15 个「对抗性审查员」。CI 流程会确定性验证审查是否真实执行、是否阅读了相同文件，确保「没时间审查的代码不能合并」。
  4. /retro 命令将 Agent 的不确定性转化为确定性流程 通过与 Agent 的苏格拉底式回顾，分析人工纠正的环节，将原本因 Agent 非确定性而导致的问题，提炼为下一次可以自动执行的确定性规则和 Hooks，实现开发流程的自我进化。
  5. 工程师的职业成长在于学习相邻岗位技能 从资深工程师晋升时，硬技能的重要性相对下降。学习开发者营销、技术写作、沟通影响力等相邻技能，能更好地理解业务决策和公司运转，从而掌控自己的职业生涯。

💬 文章金句

  • 我们想做爵士乐队，不想做军乐队。
  • 让职业生涯成长的最好方式，不是学更多东西，让自己在现有岗位上更高效，而是去学相邻岗位的东西。
  • 当领导层开始质疑：等一下，我需要为一个工程师每月多付 5000 块、3000 块，就为了让他们干活？这笔账算不过来。
  • 我怎么确保这种事不会发生？所以，我没时间审查的代码，我不会放进来。
  • 苏格拉底式提问法是一种方式，让你几乎像在调查模式里，但用的是好奇心的视角。
