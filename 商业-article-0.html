Modal CTO：你的 AI 应用不该跑在 K8s 上，Agent 时代的云应该长什么样

7/9/2026, 1:46:11 AM

📌 一句话摘要

Modal CTO Akshat Bubna 深度解析为何 Kubernetes 等传统云架构不适应突发性、算力密集型的 AI 工作负载，并分享了用“自供应运行时”和“代码即配置”理念为 AI Agent 重新设计云平台的实战经验。

📝 详细摘要

本期播客深度探讨了专为 AI 工作负载设计的云平台 Modal 的技术哲学与产品实践。联合创始人兼 CTO Akshat Bubna 详细阐述了传统云架构，尤其是 Kubernetes，在处理 AI 推理与训练时面临的本质矛盾：它们是为中心化的、常驻型 Web 服务设计的，扩缩容缓慢，而 AI 负载是去中心化、突发性的。他强调 Agent 体验的核心与开发者体验一致，都是让使用者（人或 AI）用最简单的方式表达意图，而非陷入 YAML 配置文件的地狱。Modal 的方案是通过代码中的装饰器声明需求，由平台自动供应资源。讨论还覆盖了弹性推理作为核心用例的深度优化，如引入推测解码技术 DFlash 实现乘法级性能提升，以及如何为 Agent 构建具备硬边界、网络控制和持久化能力的沙箱环境。Akshat 还分享了公司在全球 17 家云厂商之上构建“超级云”，通过软件层提供统一可靠性的轻资产策略，并对 AI 基础设施的未来进行了展望。

💡 主要观点

  1. Kubernetes 从根本上不适合突发性、去中心化的 AI 工作负载 Kubernetes 是为慢速扩缩容和常驻型 Web 服务设计的，而 AI 负载需要快速伸缩和专门化的运行环境，Modal 从底层重新构建了运行时来满足这一需求。
  2. Agent 体验与开发者体验的本质高度一致：简化意图表达 无论是人类开发者还是 AI Agent，都不应该去处理复杂的 YAML 和多层配置文件。通过代码装饰器声明需求，平台自动供应资源的方式，对二者都大幅提升了效率。
  3. 推测解码（Speculative Decoding）带来的性能提升是乘法级的 与优化 kernel 带来的几个百分点提升不同，通过 DFlash 提高草稿模型 Token 的“接受长度”，可以实现 2-4 倍的推理加速，且不牺牲模型质量，这是推理基础设施的关键创新。
  4. 未替代 LLM 的安全沙箱需要 LLM 之外的硬边界 为了保护数据安全，沙箱层面不能仅依赖 LLM 来中介权限，必须要有操作系统级别的硬护栏作为底线，LLM 只能作为软护栏的补充，这是基础设施构建者对安全的基本坚持。
  5. 在多家云厂之上构建“超级云”平台，形成独特竞争优势 Modal 坚持轻资产策略，专注于在 17 家云厂商之上构建可靠性抽象层，以软件为核心竞争力，能为用户提供远超其自行获取的 GPU 容量和更高的可靠性。

💬 文章金句

  • 你为什么要让一个 Agent 去读几百个 Kubernetes 文件、写那种连类型都没有的 YAML？它明明只需要改几个装饰器里的参数，就能得到一个自供应的运行时，直接看到自己的改动实时生效。
  • Kubernetes 是为慢速扩缩容设计的，更适合 Web 服务器那种场景。而这些工作流需要快速伸缩，运行环境也越来越专门化。
  • 优化 Kernel 通常只能带来几个百分点的提升，而提高接受长度，带来的可是乘法级的降低。
  • 我对沙箱层面用 LLM 来中介权限持怀疑态度，因为你确实需要硬边界。不然的话，别人显然可以把数据偷出去。
  • 我们一直刻意避开的一件事，就是给模型提供 API。我们一直想服务的是那些在打造产品、需要更多灵活性的公司，而不只是要一个 API。
