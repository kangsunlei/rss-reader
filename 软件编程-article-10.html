OpenSandbox 再进化：Credential Vault 让真实密钥不再进入沙箱

6/26/2026, 8:07:00 AM

📌 一句话摘要

OpenSandbox 推出 Credential Vault 功能，通过出站代理在沙箱外注入凭据，使 AI Agent 沙箱不再需要保存真实密钥。

📝 详细摘要

文章分析了 AI Agent 沙箱中直接使用密钥的安全风险，如 Prompt Injection、恶意依赖、日志泄露等。然后介绍了 OpenSandbox 新推出的 Credential Vault 方案：真实凭据保存在沙箱外，由 egress sidecar 在出站请求经过时按规则注入认证信息；沙箱内仅使用假值，确保密钥不进入环境变量、命令行、文件系统和日志。文章以 Claude Code 调用模型 API、私有 Git 仓库 clone、内部 API 访问等典型场景说明工作原理，并建议与默认拒绝的出站网络策略配合，实现更细粒度的安全边界。同时指出当前不支持与透明 service mesh sidecar 共存。最后总结该功能将沙箱隔离从进程/文件/网络层推进到凭据隔离层，是 AI Agent 生产化的重要补全。

💡 主要观点

  1. 沙箱内直接暴露密钥会放大 Prompt Injection、恶意依赖、日志泄露等风险。 AI Agent 执行链路长且不可预测，密钥一旦进入沙箱环境变量、命令行或配置文件，任意工具链环节失控都可能导致密钥泄露。
  2. Credential Vault 通过 egress sidecar 在出站请求时注入认证信息，沙箱内只保存假值。 宿主 SDK 将真实凭据和绑定规则写入 sidecar，沙箱进程仅持有假 API Key 等；当匹配的出站请求经过时，sidecar 自动注入 real auth header，密钥决不进入沙箱。
  3. 该方案适用于模型 API、Git clone、内部 API 等多种开发者工具场景。 无论 HTTP Basic Auth、Header Token 还是复杂路径匹配，Credential Vault 都可通过绑定规则实现精确授权。
  4. 建议与默认拒绝的出站网络策略配合，实现凭据与服务、路径、方法的多维绑定。 只允许工具真正需要的服务 Host，再通过 Vault 将凭据限制到更窄的请求范围，提升安全边界精细度。
  5. 当前不支持与 Istio/Envoy 等透明 service mesh sidecar 共存。 两层 sidecar 在同一网络命名空间内会冲突，平台需注意部署环境的兼容性。

💬 文章金句

  • 真实密钥应该留在沙箱外，由平台在受控的出站链路上按规则注入。
  • 沙箱负责执行，Vault 负责授权，egress policy 负责边界。
  • Credential Vault 不是让沙箱更方便地保存密钥，而是让沙箱不再需要保存真实密钥。
