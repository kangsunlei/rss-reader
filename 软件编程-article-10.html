开源之后再补偿，智谱 ZCode 能否重建信任？

9/28/2026, 2:34:00 PM

📌 一句话摘要

本文深度分析了智谱 ZCode 因未经许可上传代码库快照引发的信任危机，探讨了其通过开源和第三方核查尝试重建信任的局限性，并揭示了 Coding Agent 在执行链上的广泛安全风险。

📝 详细摘要

本文详细回顾了智谱 AI 编程工具 ZCode 因被开发者发现存在将本地代码库快照上传至云端的链路而引发的争议。尽管智谱在短时间内采取了道歉、删除数据、引入第三方核查及整体开源等补救措施，但作者指出，由于开源仓库缺乏历史提交记录（Git history），外界难以还原事故真相及数据生命周期。文章进一步将讨论升华为 Coding Agent 的整体安全问题，结合 Plugin4Shell 漏洞，指出 Agent 权限的集中化使得其攻击面从模型本身扩展到了包含 Shell、MCP、插件在内的整个执行链，强调厂商需提供更可追溯、可审计的验证机制才能真正重建用户信任。

💡 主要观点

  1. ZCode 数据上传事件揭示了 Coding Agent 复杂的数据边界问题。 事件起因于 ZCode 默认开启的 Repo Wiki 功能触发了本地仓库快照上传。这表明判断 Agent 安全不能仅看是否上传代码库，还需审视模型上下文、MCP Server、插件及 Shell 等多条潜在的数据流向。
  2. 缺乏 Git 历史记录的“快照式开源”难以完全恢复安全信任。 ZCode 开源仓库仅包含两个 commit，抹去了事故发生时的代码演进过程。这导致外部研究者无法通过版本 diff 追踪功能引入时间、决策逻辑及修复细节，使得“开源”在取证层面价值有限。
  3. Coding Agent 的安全威胁已从模型层转移至整个执行链。 结合 Plugin4Shell 漏洞，作者指出 Agent 拥有读取源码、运行 Shell、访问凭据等高权限。攻击者可通过插件供应链漏洞继承这些权限，使得安全边界扩展到 Harness、Git、MCP 等所有组件。
  4. 厂商需建立可独立验证的透明机制而非依赖单一声明。 面对高权限 Agent，简单的“第三方核查结论摘要”不足以消除疑虑。厂商应通过保留完整 Git history、公开 Security Advisory、提供可复现构建等方式，让用户能够独立审计权限滥用风险。

💬 文章金句

  • 一款能够读取整个代码库的 Coding Agent，究竟把哪些数据带离了开发者的电脑，外界又能在多大程度上验证这一点？
  • 判断一款 Coding Agent 如何处理用户数据，单独确认"是否上传 repository"还不够。
  • 如果开源同时承担了安全事件之后恢复信任的作用，代码历史同样是重要的安全证据。
  • Coding Agent 本身又处在一个权限很高的位置。它需要读取源码才能理解项目，需要运行 Shell 才能测试，需要访问 GitHub 才能提交 PR。
  • 用户把整个代码库和越来越多的系统权限交给 Agent 之后，厂商准备拿什么证明这些权限没有被滥用？
