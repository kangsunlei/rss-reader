IntelliJ 平台 UI 冻结问题分析 | JetBrains 平台博客

📌 一句话摘要

本文旨在诊断和解决 IntelliJ 平台 IDE 中的 UI 冻结问题。主要方法是通过分析线程转储和常见的阻塞场景。

📝 详细摘要

本文深入探讨了 JetBrains IDE 中 UI 冻结的常见原因。这些 IDE 构建于单线程的事件分发线程 (EDT) 之上。文章解释说，当 EDT 被阻塞时，会发生冻结，从而阻止用户交互。本文的核心概述了各种冻结场景和详细的调查方法，包括使用线程转储，以及在适用的情况下使用协程转储。讨论的具体原因包括读写锁争用、导致获取写锁意图失败的后台写入操作、Kotlin 协程中 `Dispatchers.Default` 和 `Dispatchers.IO` 调度器的线程池中的线程饥饿、服务初始化期间的死锁，以及由阻碍取消的 `runBlocking` 调用引起的问题。文章还指出，`SuvorovProgress` 只是紧急模式的表象，并非根本原因。对于每种情况，文章都提供了说明性的堆栈跟踪示例和可操作的建议，例如确保频繁调用 `ProgressManager.checkCanceled`，将阻塞操作从 `Default` 调度器移出，以及在服务初始化期间仔细管理读取/写入操作以防止死锁。总体目标是使插件开发人员能够提高 IDE 的响应能力。

💡 主要观点

  1. IntelliJ 平台 UI 冻结的主要原因是单线程 EDT 被长时间运行的操作阻塞。 事件分发线程 (EDT) 处理所有 UI 绘制和用户输入。任何长时间阻塞 EDT 的操作都可能导致 UI 无响应。例如，长时间的写锁获取或无法取消的读取操作。
  2. 有效诊断 UI 冻结依赖于对线程转储和协程转储的细致分析。 通过分析堆栈跟踪中的特定模式，例如写锁获取时的 `TIMED_WAITING` 或 `SUSPENDED` 协程，可以找到根本原因，从而定位确切的阻塞代码或线程饥饿问题。
  3. 解决 UI 冻结需要仔细管理可取消操作，并确保线程和锁的正确同步。 解决方案包括确保频繁调用 `ProgressManager.checkCanceled`，从关键调度器卸载阻塞任务，以及通过正确排序服务初始化期间的读取和写入操作来防止死锁。

💬 文章金句

  • 当 IDE 无法在 EDT 上执行操作时，就会发生 UI 冻结，从而阻止与 IDE 的交互。
  • 在绝大多数情况下，只需查看**线程转储**即可获得有关 UI 冻结所需的信息。
  • EDT 被写锁阻塞，表明有线程正在持有读锁运行。
  • 要解决线程饥饿问题，需要将阻塞操作移出 `Default` 调度器。
  • 通常，冻结是由插件代码与 IntelliJ 平台之间的合作不足引起的。
