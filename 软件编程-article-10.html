Entire Git Forge：面向编码智能体重构 Git 协作方式

11/23/2026, 9:34:00 AM

📌 一句话摘要

Entire 是面向 AI 编码智能体重构 Git 协作方式的托管平台，提出 trails 轨迹体系和 continuous memory 持续记忆概念，以评估分数驱动多轮迭代，解决传统 PR 流程在 AI 智能体高速生成、评审和迭代代码时的痛点。

📝 详细摘要

Entire 是一个专为人类开发者与 AI 编码智能体协同而设计的 Git 代码托管平台。它认为传统软件开发基础设施，尤其是 PR 模式，并不适合 AI 智能体高速生成、评审、迭代代码的场景。其核心组件是 trails（轨迹），用来解决 AI 代码智能体给传统 PR 开发模型带来的痛点：合并请求的时间线已经变成只有智能体才会去读的审计日志，无法给开发者提供足够信息，让开发者有把握判断是否可以合并。Trail 会把最重要的信息置顶展示，以评估分数的形式呈现，每次代码推送都会更新分数。开发者可以借助这些分数判断该 PR 是否已经稳定，或是需要让 AI 智能体继续编码、评审，进入下一轮迭代。评估智能体既可以在 Entire 平台界面配置，也可以通过仓库级 JSON 文件配置。评审智能体可以给出修复建议或优化方案，这些内容在 Trail 开启期间保持可见。所有评审发现的问题必须在合并前解决或关闭。开发者还可以配置仓库级的 Gates（门禁），定义合并通过的条件。Entire 引入的另一个基础概念是 continuous memory（持续记忆），它将所有累积的知识保存在仓库中，让智能体能够跨会话复用这些知识，而不是从头开始。持续记忆由两个开源工具实现：一个构建 Git 仓库的预计算图谱，另一个通过将代码库图谱与之前的智能体会话以及 Git 历史中记录的信息相结合，创建一个持久的记忆层。这让智能体总能在合适的时机拿到正确的上下文，也就是变更内容背后的变更原因。另外，Entire 支持集成 Buildkite、Depot 等 CI 平台。

💡 主要观点

  1. 传统 PR 模式不适配 AI 智能体的高速生成、评审和迭代 AI 智能体会将合并请求的时间线变成只有自身才会读的审计日志，导致人类开发者难以判断是否可以合并。
  2. Trails 轨迹体系通过评估分数驱动多轮迭代 每次代码推送都会更新评估分数，开发者可据此判断 PR 是否稳定；多轮迭代直到评分趋于稳定是智能体编码成功的关键。
  3. Continuous Memory 持续记忆实现跨会话知识复用 通过构建 Git 仓库的预计算图谱和结合智能体会话历史，创建持久记忆层，让智能体在合适时机获取正确上下文。
  4. 引入 Gates 门禁机制控制合并条件 开发者可配置仓库级门禁，定义合并通过的具体条件，确保所有评审发现的问题在合并前解决或关闭。
  5. 支持集成 Buildkite、Depot 等 CI 平台 平台兼容主流 CI/CD 工具链，提升企业级落地可能性。

💬 文章金句

  • 合并请求的时间线已经变成只有智能体才会去读的审计日志，无法给开发者提供足够信息，让开发者有把握判断是否可以合并。
  • 只有当置信度高、风险低且所有问题都已清除时，才应进行合并。
  • 每轮评估都会显示最近 5 轮结果和当前结果。我们认为这一点至关重要，因为单次评估经常会漏掉关键问题。
  • 这让智能体总能在合适的时机拿到正确的上下文，也就是变更内容背后的变更原因。
  • 推理过程在人与产出物之间被丢弃了。提交说明一直都很糟糕，文档容易过时，'为什么这里有这段代码'只能靠记得的人来解释。
