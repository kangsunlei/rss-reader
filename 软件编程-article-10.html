Claude Code 之父：每半年清空一次 claude.md、skills 和 hooks，模型自己会想办法

📌 一句话摘要

本文通过对 Claude Code 创始人 Boris Cherny 的访谈，探讨了大模型能力快速迭代下的提示词工程、产品能力缺口以及持续实验与删除旧提示词的实践。

📝 详细摘要

文章整理了 InfoQ 中文对 Claude Code 创始人 Boris Cherny 的访谈内容。Boris 介绍了 Opus 5 模型在连续运行时长、抗提示词注入方面的显著提升，解释了每半年清空 claude.md、skills 和 hooks 的做法，并通过消融实验验证哪些提示词仍然有效。他提出了「产品能力缺口（product overhang）」与「hobbling」的概念，认为今天的模型已具备许多尚未被产品充分利用的能力，开发者应通过给模型更具挑战性的任务并提供验证手段来挖掘这些潜力。文中还详细描述了使用 Dynamic Workflows、Loops/Routines 等机制让数千个智能体协同工作的实践案例，例如将 Electron 桌面端重写为 Swift 的长时任务。最后，Boris 强调使用模型应转向经验科学：通过实际任务观察模型表现、根据反馈迭代提示词或技能，而非依赖固定的提示词工程套路。

💡 主要观点

  1. Opus 5 能够连续运行数月且显著提升抗提示词注入能力。 通过将对齐良好的模型与提示词注入分类器结合，三层防护使得以前可能被利用的注入攻击如今难以实现。
  2. 每六个月清空 claude.md、skills 和 hooks，通过消融实验判断哪些提示词仍有价值。 每代新模型性能不同，旧的提示词往往过时；通过删除后逐行加回并观察影响，可保持系统提示词的精简与有效。
  3. 产品能力缺口（product overhang）与 hobbling 是理解模型与产品关系的两个互补视角。 模型已具备许多尚未被产品充分利用的能力；相反，产品设计有时会阻碍模型发挥，需通过给予更高层次任务和验证机制来「解除束缚」。
  4. Dynamic Workflows、Loops/Routines 等机制可让数千个智能体协同完成复杂任务，如将 Electron 桌面端重写为 Swift。 通过在沙箱中启动虚拟机并让 Claude 调度大量智能体，实现高效的测试时计算编排，使得过去需要数十人工程师的工作能由智能体自主完成。
