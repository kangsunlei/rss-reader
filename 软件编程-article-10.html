得物 OceanBase 落地实践

📌 一句话摘要

得物团队分享了 OceanBase 数据库从选型验证到生产落地的完整实践，包含 DBA 压测验证、业务 POC 案例、SQL 优化方法论及迁移问题解决方案，并给出具体性能提升与成本收益数据。

📝 详细摘要

得物技术团队系统分享了 OceanBase 在公司内部的落地实践。文章首先介绍多品类数据库现状与选型理由，阐述 OceanBase 在灵活架构、成本压缩（40%+）与高可用（RPO=0，RTO<8s）方面的优势，并通过与 DuckDB、StarRocks 的对比测试验证其 AP 性能（JOIN 聚合查询领先 DuckDB 81.5 倍）。核心内容聚焦 DBA 验证评估与两个业务 POC 案例：通过五大优化手段（计划缓存、分区裁剪、列存索引、多核并行、Hint 指定算法）将复杂 SQL 性能提升 130-200 倍；首个业务迁移实现 SQL 平均耗时下降 88.3%、降本 43%；StarRocks 替换案例实现存储压缩率 94%、聚合查询响应时间降低 65%。文章还总结了迁移挑战（语法兼容、物化视图冲突）、运维体系转型与团队能力建设路径，并给出三阶段规划与 AIOps 演进方向。

💡 主要观点

  1. OceanBase 五大优化特性可将复杂 SQL 性能提升 130-200 倍。 通过计划缓存复用、分区裁剪、列存索引破最左前缀瓶颈、多核并行执行、Hint 指定算法，从计划生成到执行调度全链路优化，SQL2 从 4s 降至 0.02s，SQL1 从 1.3s 降至 0.01s。
  2. 首个业务迁移实现 SQL 耗时下降 88.3%、总体降本 43%。 多套 MySQL 整合为 1 套 OB 集群，存储压缩率 80%+，简单字段场景压缩比 10:1，ECS CPU 利用率从 50% 提升至 100%，业务超时接口清零。
  3. StarRocks 替换案例中 OceanBase 聚合查询响应时间降低 65%，存储压缩率 94%。 消除 MySQL + StarRocks 双链路与应用层手动分流，实现行列混存一体化，存储从 TB 级降至百 GB 级，查询完全实时无延迟。
  4. 迁移需关注语法兼容性与新特性限制，建立准入审核与监控机制。 实时物化视图与 DDL 冲突、SQL 语法差异等问题需通过业务适配或参数调整解决，引入新特性时须建立严格的准入审核、监控告警和故障演练机制。
  5. 运维模式从实例级转向租户级 + 集群级，工具链全面升级。 从 MySQL 管控体系切换为 OCP + OMS + diag + ODC 体系，通过「基础培训—深度实践—认证培养」三层路径建立 OceanBase 知识体系。

💬 文章金句

  • OceanBase 通过计划缓存复用、分区裁剪减少扫描、列存索引破最左前缀瓶颈、多核并行执行提速、Hint 指定算法五大特性，从「计划生成→数据扫描→索引选择→执行调度→算法决策」全链路压缩复杂 SQL 的执行开销。
  • OceanBase 的执行计划 Hint 不是日常调优工具，而是优化器偏差时的兜底干预能力——当生产 SQL 突发劣化、统计信息失准或关联条件复杂导致选错算法时，DBA 可直接在 SQL 中指定算法纠正执行计划，无需改写 SQL，这份能力是 MySQL 所不具备的。
