MySQL 8 的老大难问题，从 5.7 延续至今，有这么难？

📌 一句话摘要

文章深入剖析了 MySQL 8 及 5.7 中`prefer_ordering_index`优化参数在数据分布不均时可能导致的性能问题，并建议在多数情况下将其关闭以避免错误索引选择。

📝 详细摘要

本文详细探讨了 MySQL 优化器参数`prefer_ordering_index`（默认 ON）在特定场景下可能引发的性能问题。该参数旨在优化包含`ORDER BY`或`GROUP BY`与`LIMIT`的查询，通过优先选择有序索引来避免`filesort`。然而，当数据分布不均匀且索引选择性极低（如性别、状态字段）时，优化器可能错误地选择该索引，导致大量的随机回表 IO，其开销远超全表扫描后的`Filesort`。文章通过具体 SQL 示例和`EXPLAIN`结果对比，直观展示了`prefer_ordering_index`开启和关闭时查询计划的差异。作者指出，由于 MySQL 尚未智能化解决此问题，对于业务和 DBA 而言，大部分情况建议关闭此选项，以规避潜在的性能风险。

💡 主要观点

  1. `prefer_ordering_index`参数在特定场景下可能导致 MySQL 性能下降 该参数在数据分布不均匀或索引选择性极低时，可能促使优化器选择效率低下的有序索引，而非更优的全表扫描加`Filesort`方案。
  2. 优化器错误选择索引导致大量随机回表 IO，远超全表扫描开销 当查询命中绝大部分数据行时，如果优化器仍选择低选择性索引进行逐行扫描和回表，将产生巨大的随机 IO 开销，严重影响查询性能。
  3. 在 MySQL 未智能化解决前，建议多数情况关闭`prefer_ordering_index` 由于该问题在当前 MySQL 版本中尚未得到智能化的解决，DBA 和开发者通常选择关闭此选项，以避免因优化器误判导致的性能问题。
