本文由一位认证讲师撰写，深入探讨了后端开发团队常见的 Kotlin 反模式、解决方案以及适应 CI/CD 的可靠异步测试策略。

📝 详细摘要

这篇分两部分的客座文章由 JetBrains 认证的 Kotlin 培训师 José Luis González 撰写，旨在解决有效的 Kotlin 后端开发中的关键方面。文章首先指出了三个主要反模式：过度依赖 Java 风格的继承、滥用全局单例以及将协程视为“更好用的线程”。针对每个反模式，文章提供了现代 Kotlin 惯用解决方案，如密封类、数据类、上下文参数、值类和结构化并发。接着，文章详细介绍了一种在 CI/CD 环境中测试异步 Kotlin 代码的稳健模式，强调了调度器注入、`runTest`、`StandardTestDispatcher` 和确定性时间控制。最后，文章提供了一个诊断 Kotlin 微服务中意外内存消耗的核对清单，重点提到了诸如过多线程栈、无界协程/集合和 HTTP 层缓冲等问题，并给出了 `limitedParallelism`、背压和显式 JVM 内存限制等解决方案。内容侧重于实际问题解决和现代 Kotlin 最佳实践。

💡 主要观点

  1. 自学成才的团队常在 Kotlin 中滥用 Java 风格的继承，导致设计脆弱。 通过运用 Kotlin 的优势来纠正这个问题：使用密封类、数据类和 `when` 表达式来扁平化设计，并优先选择组合而非深度继承，以获得更清晰、更易维护的代码。
  2. 全局单例和滥用 `typealias` 来实现类型安全是有害的反模式。 现代 Kotlin 使用上下文参数来显式声明依赖，而不是使用全局单例。虽然 `typealias` 有其有效用途，但当它被误用于实现*真正的领域类型安全*时，则构成一种有害的反模式，因为值类是创建不同类型的正确惯用且零分配的解决方案。
  3. 对协程的误解可能导致像 `GlobalScope.launch` 和生产环境中的 `runBlocking` 这样的反模式。 始终使用结构化并发，将协程绑定到适当的作用域，将 `runBlocking` 限制在测试或主函数中，并使用 `coroutineScope/supervisorScope` 来组合并发工作，以防止资源泄漏并提高可测试性。
  4. CI/CD 中可靠的异步 Kotlin 测试需要调度器注入和确定性时间控制。 使用 `StandardTestDispatcher` 与 `runTest` 以及 `advanceUntilIdle()` 等方法来消除时间上的不稳定性，确保测试快速、确定性，并验证结果和取消传播。
  5. Kotlin 微服务中的高内存使用通常源于线程相关问题、无界结构或 HTTP 缓冲。 通过分析本机内存和堆来诊断。解决方案包括限制 `Dispatchers.IO` 并行度，对流/通道应用背压，流式传输 HTTP 请求，以及设置显式 JVM 内存限制以优化资源消耗。

💬 文章金句

  • 我发现自学 Kotlin 的团队存在一个基本反模式：他们依旧设计抽象类、工厂和深层继承树的层级结构，因为这是他们学习 Java 时养成的习惯。
  • 上下文参数可以解决这个问题：它作为上下文接收器的后续方案，让函数能够*声明*其所需的服务，并由调用方提供，无需使用全局变量。
  • `GlobalScope` 是一个带有 `@DelicateCoroutinesApi` 注解的应急方案，官方指南将 `runBlocking` 定位为测试和入口点之间的桥梁（或阻塞运行入口点），而非生产环境的调用路径。
  • 关键是注入调度器，而不是硬编码 `Dispatchers.IO`，并使用 `runTest` 和 `StandardTestDispatcher`（或 Android 上的 `MainDispatcherRule`）进行测试。
  • 并确保你没有在使用原始线程，而协程却可以胜任。这是一种常见的“Java 习惯”，悄悄地扼杀了内存效率。
