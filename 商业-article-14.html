马斯克的 Grok 4.5 刚追上 Claude，转头就把用户整个代码库偷偷打包带走

7/15/2026, 3:53:00 AM

📌 一句话摘要

文章介绍了 Grok 4.5 模型的性能、成本及使用体验，并揭露其 CLI 工具存在静默上传用户本地文件的安全隐患。

📝 详细摘要

文章围绕马斯克旗下的 Grok 4.5 大模型展开，首先回顾了近期大模型发布节奏，指出 Grok 4.5 在性能上被定位为 Opus 级别，参数规模达 1.5 万亿，成本仅为 0.31 美元，远低于竞品。通过实际测试（如 3D 网页生成、文档转换、深度研究等），作者指出 Grok 4.5 在推理精细度和 token 消耗上接近 Claude Sonnet 4.6，但在某些复杂场景中仍显不足。文章重点曝光了 Grok Build CLI 的安全问题：安全研究员发现该命令行工具在初始化和任务执行时会静默打包用户本地项目（包括敏感配置和 API 密钥）并上传至 SpaceXAI 服务器，即便用户明确禁止读取本地文件也会被绕过。官方回应称可通过 /privacy 关闭数据保留，但用户普遍认为这是产品设计缺陷。整体文章兼具产品评测与安全警示，为开发者提供了使用 Grok 4.5 的参考与风险提示。

💡 主要观点

  1. Grok 4.5 性能与成本表现突出 模型参数达 1.5 万亿，定位 Opus 级别，推理精细度接近 Claude Sonnet 4.6，token 消耗极低，运行成本仅 0.31 美元，比 Claude Sonnet 5 低约五倍。
  2. 实际使用体验参差不齐 在 3D 网页生成、文档转换等任务中，Grok 4.5 能快速完成但输出常带有 bug 或细节不足；在需要严密逻辑的场景（如故宫雪景模拟）则表现更接近宣称的 Opus 水平。
  3. Grok Build CLI 存在严重数据外泄风险 安全研究员通过抓包发现 CLI 在后台静默打包用户整个本地项目仓库（包括敏感配置和 API 密钥）并上传至 SpaceXAI 服务器，即便用户明确禁止读取本地文件也会被绕过。
  4. 官方回应与用户质疑并存 SpaceXAI 声称可通过 /privacy 指令关闭数据保留并删除已上传数据，但用户认为问题在于产品设计本应默认不上传，仅靠退出机制难以建立信任。

💬 文章金句

  • Grok 4.5 的实际推理精细度已完全不亚于 Claude Sonnet 4.6 级别，并且在 Token 消耗上极其节制。
  • Grok Build CLI 在本地初始化和每次任务执行时，会以完全隐蔽的形式，在后台将用户的整个本地项目仓库进行强制性打包，并将其传输至 SpaceXAI 的云端服务器上。
  • 马斯克提到目前的 Grok 4.5 是 1.5T，即 1 万 5000 亿参数大模型。
  • Grok 4.5 任务的运行成本仅为 0.31 美元，低于 GLM-5.2 和 Kimi K2.6，比 Claude Sonnet 5（最高版本）的成本低 5 倍。
  • 马斯克表示，此前上传到 SpaceXAI 的所有用户数据将被彻底删除，不保留任何数据。
