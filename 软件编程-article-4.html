如何在 Python 中构建单例模式（以及为什么你可能不应该这样做）

1/22/2026, 6:13:33 PM

📌 一句话摘要

本文探讨了在 Python 中实现单例模式的多种方法，同时批判性地分析了其缺点，并提出了更符合 Python 惯例的替代方案，如模块级实例和依赖注入。

📝 详细摘要

本文深入探讨了 Python 生态系统中的单例设计模式。它详细介绍了四种实现策略：经典的 __new__ 方法、装饰器模式、元类（metaclass）方法，以及使用双重检查锁定的线程安全版本。除了实现方式，作者还对单例模式提出了强烈的批评，强调了隐藏的全局状态、测试困难以及违反单一职责原则等问题。指南最后提倡使用更简单、原生的 Python 替代方案——特别是模块级对象和依赖注入，并建议仅在处理唯一的物理资源接口或特定的资源池时才保留单例模式。

💡 主要观点

  1. Python 提供了多种实现单例的方法，从装饰器到元类不一而足。 虽然经典的 __new__ 方法很常见，但装饰器提供了更清晰的关注点分离，而元类则在类创建层面提供了更强大的控制力。
  2. 在并发环境中，线程安全是单例模式的一个关键考量因素。 标准实现在多线程场景下会失效；使用线程锁和双重检查模式至关重要，特别是在 Python 3.13+ 的自由线程环境下。
  3. 单例模式通常被视为一种反模式，因为它会影响可测试性和状态管理。 它们引入了全局状态，导致单元测试变得困难，并在不相关的模块之间创建了隐藏的依赖关系，违反了核心工程原则。
  4. 模块级实例是实现单例行为最符合 Python 风格（Pythonic）的方式。 由于 Python 的导入系统会将模块缓存到 sys.modules 中，因此在模块级实例化的对象自然而然地充当了共享的单一实例。

💬 文章金句

  • 单例是一种将类限制为仅有一个实例的设计模式。
  • 单例是伪装的全局状态。全局状态使代码更难理解、测试和维护。
  • Python 的模块系统本身就是一种单例机制：当你导入一个模块时，Python 会执行它一次并缓存结果。

  • 尽量少用单例，如果非要用的话。
