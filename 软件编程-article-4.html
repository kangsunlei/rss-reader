突破 CRUD 限制：构建更贴合业务的工作流 API

9/10/2025, 3:39:44 PM

📌 一句话摘要

本文指出，CRUD 对于复杂业务应用是一种反模式。建议采用以领域动作为中心的工作流 API 设计，以提高清晰度和安全性。

📝 详细摘要

本文 критически рассматривает CRUD 操作（创建、读取、更新、删除）在实际、可扩展应用程序中的局限性。文章解释说，CRUD 是基本数据交互的优秀教学工具，并通过 Node.js、Express 和 SQL 示例进行了说明，但对于复杂的系统来说，它变成了一种反模式，隐藏了业务意图并造成了授权问题。作者展示了诸如“upsert”和“archive”等常见扩展如何已经扩展了 CRUD 模型，以及特定于域的操作（例如，“提交应用程序”、“批准贷款”）如何从根本上破坏了它。通过使 API 与业务流程和显式领域操作保持一致，本文展示了系统如何实现更清晰的意图、内置授权、改进的审计和受控的副作用，最终导致创建更可靠和易于维护的软件。

💡 主要观点

  1. 在复杂的系统中，CRUD 通过将业务意图隐藏在通用操作背后而成为一种反模式。 通用 CRUD 动词（如“更新”）无法准确表达特定的业务操作（如“批准”或“拒绝”贷款），导致歧义，造成技术实现与业务逻辑脱节。
  2. 围绕特定于领域的动作设计 API 可以明确意图并简化授权。 针对特定操作（如“/applications/{id}/approve”）的 API 端点能够清晰地表达操作意图，并支持基于角色的授权规则，从而提高安全性和代码可读性。
  3. API 与业务流程对齐，有助于提高可审计性，并强制执行状态转换。 通过镜像资源的顺序状态（例如，草稿 → 已提交 → 已批准），API 可以自然地防止无效转换并提供已采取措施的清晰审计跟踪。

💬 文章金句

  • 真实系统不仅仅是“更新”或“删除”。它们不是通用 CRUD 操作，而是具有重要意义的**领域特定操作**。
  • 核心问题在于，CRUD 用通用的技术语言掩盖了真实意图。实际的业务流程应通过领域特定操作来表达，而非通用的更新或删除。
  • 通过对领域动作建模（而非 CRUD 操作），意图和权限更加清晰，从而降低错误和安全风险。
  • 摆脱 CRUD，对领域动作建模，能使 API 与实际业务流程保持一致，清晰传达意图，并自然地执行规则和权限控制。
  • 到最后，您会看到 CRUD 的真正面目——一种教学工具，而不是一种设计理念。
