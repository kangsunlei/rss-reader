📌 一句话摘要

本文分享了在 Kubernetes 上的 SGLang P/D 分离架构下，如何通过 RBG 生命周期钩子与推理网关协同实现大模型推理服务的平滑升级，涵盖版本隔离、流量切换、KV Cache 保留及可观测回滚等实践方法。

📝 详细摘要

随着大模型版本、推理引擎及运行配置的持续迭代，如何在 Kubernetes 环境下实现推理服务的平滑升级成为关键挑战。vivo 通过 SGLang 的 P/D 分离架构，将推理网关与 RBG（RoleBasedGroup）生命周期钩子结合，构建了新旧版本实例的隔离与流量切换机制。文章详细阐述了蓝绿部署与滚动升级的适用场景，强调 KV Cache 的保留与复用边界，介绍了从摘流、排空、缓存写出到预热、接流的完整升级流程。最终通过请求成功率、首 Token 延迟、流式输出连续性等指标验证了升级效果，形成了一套可观测、可验证、可回滚的发布流程，兼顾服务质量与资源成本。

💡 主要观点

  1. P/D 分离架构是推理服务平滑升级的核心设计 将推理引擎的推理（P）与分发（D）职责分离，使得新旧版本实例可以在同一集群中独立运行，推理网关负责定向接流，避免跨版本配对和在途请求中断。
  2. RBG 生命周期钩子实现实例的有序摘流与退出 通过 RBG 的生命周期管理，旧实例在停止接收新请求后，完成已有请求处理并写出 KV Cache，方可安全退出；而新实例在预热验证通过后才开始接收流量，确保服务不中断。
  3. KV Cache 的保留与复用是降低冷启动性能波动的关键 结合 HiCache 与独立 Mooncake Store，明确缓存写出完成、缓存可复用与请求可恢复的边界，合理安排缓存预热和重算，显著降低新实例启动后的性能波动。
  4. 蓝绿部署与滚动升级需根据变更类型和回滚要求灵选择用 针对模型、推理引擎、算子或运行参数的不同变更，结合兼容性、GPU 资源预算和回滚要求，判断采用蓝绿部署（完全隔离）或滚动升级（逐步替换）更为合适。
  5. 构建可观测、可验证、可回滚的升级流程 通过监控请求成功率、首 Token 延迟、流式输出连续性、缓存命中率和额外 GPU 占用等指标，制定验收标准，并通过异常演练验证升级与回滚能力，确保服务质量与资源成本的最优平衡。
