16 个 Claude 智能体在几乎没有人工干预的情况下构建了一个 C 编译器

2/14/2026, 12:00:00 PM

📌 一句话摘要

Anthropic 研究员 Nicholas Carlini 展示了一个多智能体系统，其中 16 个 Claude 实例自主构建了一个功能完备的 C 编译器，突显了软件开发正从手动编码转向设计 AI “支架（harness）”的趋势。

📝 详细摘要

本文探讨了 Anthropic 研究员 Nicholas Carlini 进行的一项里程碑式实验。他利用 16 个 Claude Opus 4.6 智能体从零开始构建了一个基于 Rust 的 C 编译器。这些智能体在 Docker 容器中并行运行，通过带有简单锁定机制的共享 Git 仓库进行同步，最终生成了一个包含 10 万行代码的编译器，能够编译 Linux 内核和其他主要开源项目。该项目耗费了 2 万美元的 API 费用，强调了软件工程的未来可能在于设计强大的测试平台和反馈循环（即“支架”），从而让自主智能体能够持续处理复杂任务。尽管这一成就意义重大，文章也提出了怀疑观点，涉及人工设计 CI 流水的必要性以及现有训练数据对智能体输出的影响。

💡 主要观点

  1. 自主智能体可以通过结构化并行处理复杂的、长期运行的工程任务。 通过让 16 个智能体与共享 Git 仓库并行运行，系统在没有中央编排智能体的情况下，成功管理了复杂的依赖关系和任务分配。
  2. “支架（harness）”——即环境和反馈循环——比模型的原始输出更为关键。 成功取决于设计自动化测试平台和 CI 流水线以确保智能体不偏离轨道，这表明工程重点正在从实现转向系统设计。
  3. 像基于文件的锁定机制这样简单的同步机制，可以有效地管理多智能体协作。 研究人员没有使用复杂的协调软件，而是使用了 Git 中基础的文本文件锁定系统，证明了 LLM 能够独立应对标准的开发工作流。
  4. 人工监督对于设计基础设施和解决系统性瓶颈仍然至关重要。 尽管贴上了“自主”的标签，但仍需要人工干预来构建初始 CI 流水线、在智能体失败时重新设计测试，以及为集体性 Bug 创建变通方案。

💬 文章金句

  • 如果你要求解决一个漫长而复杂的问题，模型可能会解决其中的一部分，但最终它会停止并等待持续的输入。
  • Claude 足够聪明，可以自行解决合并冲突。
  • 10 倍效能开发者的核心技能不在于解决复杂 Bug 的能力，而在于设计自动化测试平台和反馈循环的能力。
  • 他们花了 2 万美元的 Token 费用，就为了吐出那些已经在抓取的训练数据中存在的代码？
  • 我们正在进入一个时代，10 倍效能开发者的核心技能不再是解决复杂 Bug 的能力，而是设计自动化测试平台的能力。
