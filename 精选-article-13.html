Java 再升级！JDK21 + 虚拟线程技术大规模落地方案解密

📌 一句话摘要

小红书分享了其自研 RedJDK21 在核心业务大规模落地虚拟线程的实战经验，详细解析了解决 synchronized 阻塞、监控补全及性能优化的底层技术方案。

📝 详细摘要

本文深入探讨了小红书在搜索、推荐、广告等核心 Java 服务中大规模落地 JDK21 虚拟线程的技术细节。文章首先对比了虚拟线程与平台线程的原理差异，指出虚拟线程通过 JVM 层的调度（ForkJoinPool）实现了高并发下的低资源损耗。针对原生 JDK21 中虚拟线程遇到 synchronized 块会产生 Pinning（钉住）导致死锁的痛点，小红书通过在 RedJDK21 中回流 JEP-491 协议，重构了锁实现机制。此外，文章还介绍了如何通过自适应并行度解决 JNI 阻塞、如何实现“无感”接入方案以及完善虚拟线程的监控诊断体系。最终落地结果显示，核心链路实现了 10% 的时延优化和 24% 的 CPU 降低，证明了虚拟线程作为通用优化手段的巨大潜力。

💡 主要观点

  1. 虚拟线程通过解耦 Java 线程与内核线程，彻底解决了高并发场景下的资源瓶颈。 传统平台线程与 OS 线程一一对应，受内核资源限制；虚拟线程由 JVM 管理，仅在执行时挂载到平台线程，阻塞时自动卸载，从而支持百万级并发并显著降低上下文切换开销。
  2. RedJDK21 通过重构锁机制，解决了 synchronized 导致的虚拟线程 Pinning 风险。 针对 JDK21 中 VT 遇到 synchronized 无法卸载的问题，小红书回流了 JEP-491 的能力，引入新轻量级锁和重量级锁映射表，使 VT 在持锁阻塞时也能正常切换，避免了潜在的死锁。
  3. 大规模落地需兼顾“无感接入”与“可观测性”，以降低业务方的迁移成本和心智负担。 通过替换中间件线程池工厂实现透明升级，并补全了 ThreadMXBean 对虚拟线程的支持，确保现有的 Jstack、监控指标等诊断工具在虚拟线程环境下依然精准有效。
  4. 虚拟线程不仅适用于 I/O 密集型任务，还能通过提升 CPU Cache 命中率优化计算性能。 生产实践表明，减少物理线程数能显著降低 Cache Miss。在搜索核心链路中，虚拟线程使 IPC 提升了 13%，证明其在降低系统整体损耗方面具有普适的优化价值。

💬 文章金句

  • 虚拟线程不占用内核线程资源，创建虚拟线程只需要在分配少许内存用于存放虚拟线程对象。
  • 计算的并行度不可能突破物理核数上限，线程数量与物理计算单元数匹配即可。
  • 底层优化技术在生产大规模落地的难点，主要来自于：用户改造成本、心智负担、兼容性担忧、可观测性缺乏。
  • 虚拟线程完全可以作为一个实实在在的通用优化手段。
  • 整个升级流程只需要 '1 个镜像，1 个参数，1 次 Copy'，从我们实践中来看，兼容性表现良好。
