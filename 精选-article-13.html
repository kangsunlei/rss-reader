淘宝百亿补贴数据分析助手 Agent 实战

9/4/2026, 1:55:00 AM

📌 一句话摘要

淘宝技术团队分享百亿补贴数据分析 Agent 实战，通过多 Agent 协同、NL2MDL2SQL 路径和六层知识体系，实现从自然语言到波动归因的全流程自动化，解决传统数据分析取数慢、口径混乱、知识不沉淀等痛点。

📝 详细摘要

bybt-data-analysis-assistant 是淘宝技术团队构建的数据分析智能体，能将自然语言转化为找表、写 SQL、执行查询到深度分析的全流程。系统采用多 Agent 协同架构，包括意图识别层、调度路由层、ReAct 推理循环和保障层。关键技术选型包括 NL2MDL2SQL 路径（通过 WrenAI MDL 语义层确保字段存在和口径正确）、Hologres 外部表加速递归下钻查询、六层知识体系（表能力清单、SQL 片段库、规则库、血缘图谱、指标注册表、会话记忆）。其中 AST 血缘解析引擎采用六阶段管线从 ETL 代码自动提取字段级血缘，指标注册体系支持乘法型、加法和自定义三种公式类型。系统设计强调上下文沉淀而非依赖模型对话长度，通过知识飞轮持续完善。

💡 主要观点

  1. 多 Agent 协同架构优于单 Agent 设计 单 Agent 需要巨大 system prompt 和几十个工具，导致工具选择困难、prompt 膨胀、调用预算浪费。多 Agent 让每个专家只关注相关工具和指令，意图识别层先输出标准化 JSON 参数包，Supervisor 根据意图分发到 Query/Analysis/Ops 三个专家 Agent，每个 Agent 独立运行 ReAct 推理循环。
  2. NL2MDL2SQL 路径解决 Text-to-SQL 的三大问题 直接 Text-to-SQL 存在幻觉字段（LLM 编造不存在列名）、口径错误（不知道必须加的 WHERE 条件）、不可复用（每次从零生成）。通过 WrenAI 引入 MDL 语义层，在生成 SQL 前先用模型定义文件确认字段存在、规则库确认口径约束，确保结果可复用。
  3. 六层知识体系构成 Agent 的记忆底座 从权威等级看：MDL 表结构最强，SQL 规则次之，SQL 片段再次，LightRAG 血缘图谱较弱，指标注册最弱（运营维护可能不准），会话记忆最弱。AST 血缘解析引擎用六阶段管线（Schema Registry 预处理→AST 标准化→节点提取→作用域解析→血缘映射→输出构建）从 ETL 源代码自动提取字段级血缘。
  4. Hologres 外部表按需加速避免全量同步成本 递归下钻查询单次走 ODPS 需 30-120 秒，5-10 次可能超 10 分钟。通过场景闸门（HOLO_ROUTE_MODE）限定仅数据分析场景启用 Holo 直读 ODPS，用 sqlglot 抽取表名按需创建外部表（首次多 1-3 秒建表开销，后续 LRU 命中零开销），并实现切库自愈（检测 relation 不存在错误后清空缓存重建）。
  5. 指标注册体系让归因诊断声明式化 GMV 等指标拆解需要明确的乘法型恒等式（如 IPVUV×CVR×AOV=pay_amt），因子相乘后约分必须恰好等于 total_col。支持 column/ratio 两种类型，维度按供给/渠道两个正交轴分类，运营同学通过 Web 向导接入新指标而无需改代码。

💬 文章金句

  • 直接 Text-to-SQL 有三个致命问题:幻觉字段、口径错误、不可复用
  • 单 Agent 需要一个巨大的 system prompt 和几十个工具，导致工具选择困难、prompt 膨胀、调用预算浪费
  • Holo 加速仅对 stream_analysis 生效，普通 NL2SQL、CLI 脚本、运维查询一律走 ODPS
  • 因子相乘后约分必须恰好等于 total_col
