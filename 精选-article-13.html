Noi 编程实战：Fable 没那么强，GPT 也没那么弱

7/4/2026, 12:37:00 PM

📌 一句话摘要

文章通过 Noi 项目中一个插件兼容 bug 的调试经历，对比 Fable 与 GPT 的表现，深刻反思了 AI 编程中复杂系统调试的方法论与责任边界。

📝 详细摘要

文章以作者在 Noi 项目中集成 Chrome 插件时遇到的一个顽固 bug 为线索，记录了使用 Fable 和 GPT（Codex）进行 AI 辅助调试的全过程。Fable 因安全策略拒绝分析插件源码，无奈转向 Codex。初期 Codex 被错误日志误导，进行局部修补但无效。关键转折点是作者发出「你自己去 debug 吧」的 prompt 后，Codex 在长时间探索中设计了一个 A/B 实验：保留浏览器原生的 runtime messaging 而非用兼容层覆盖，结果页面成功渲染。由此发现根因是兼容层错误地抢占了原生能力，且后台生命周期未就绪。文章穿插介绍了 Noi 的 AgentOS 架构与 Harness 自进化闭环，并引申出对复杂工程调试的反思：不能只追报错，要设计能改变判断权重的实验；sleep 式修复不可靠；责任链闭合比局部补洞更重要。最后，作者表达了对 Agent 时代工作方式的期待——允许探索、允许犯错，但每一步都有证据和约束。

💡 主要观点

  1. 复杂系统调试不能只追报错，需要设计能改变判断权重的实验。 作者指出报错日志只显示痛处，不告诉根因；A/B 实验通过改变单一变量观察结果变化，才能从「看起来有效」推进到「因果上站得住」。
  2. 兼容层应只补缺口，不应抢走原生系统的所有权。 调试发现，自己写的兼容层覆盖了 Electron 原生已实现的 runtime messaging 能力，导致页面渲染失败；保留原生能力后问题解决。
  3. Agent 时代值得期待的不是模型一次给出完美答案，而是搭出允许探索、有证据约束的工作方式。 作者认为，复杂工程中模型能力只是一部分，任务环境、上下文、反馈和验证方式同样决定结果；应构建「意图→文档→代码→证据→架构优化」的持续循环。

💬 文章金句

  • 不要把模型当成一次性答案机器，也不要在它失败时立刻归因成「降智」。
  • 调试很少从第一分钟就看见根因，它更像是在一堆半对半错的线索里，设计出那个能改变判断权重的实验。
  • 复杂系统里的 bug，很少只是某一行代码坏了，更多是责任链断了。
