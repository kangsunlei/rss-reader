面试官皱眉：“你用过 LangChain 里的 Deep Research 吗？”，我：“就是多搜索几次，再让模型生成一篇更长的报告”

9/20/2026, 6:12:00 AM

📌 一句话摘要

Deep Research 不是 LangChain 核心包里的固定开关，而是一类研究型 Agent 架构，核心在于动态规划、子课题隔离、证据核验与统一写作，而非简单多搜几次。

📝 详细摘要

文章以面试对话切入，澄清了 LangChain 生态中 Deep Research 的定位：它不是核心包里的固定功能，而是面向开放问题的研究型 Agent 架构，官方提供 open_deep_research 参考实现和更通用的 Deep Agents SDK。核心流程为六步：澄清问题并确定范围、生成 Research Brief、Supervisor 拆分子课题、Researcher 并行检索与核验、压缩证据并检查研究缺口、统一生成最终报告。文章解释了拆分子 Agent 的首要目的是隔离上下文而非单纯加速，并强调研究质量应沿「来源→证据→结论」反向追查，链接多不等于证据可靠。成本控制需同时限制宽度（并行研究单元）和深度（迭代轮数），并设置总 Token、搜索费用和超时预算。安全方面需防范网页提示词注入，工具优先只读、最小权限、高风险操作人工审批。适用场景为竞品分析、技术调研、文献综述、供应商尽调等开放式、多来源、可拆分任务。

💡 主要观点

  1. Deep Research 是一类研究型 Agent 架构，而非 LangChain 核心包中的固定开关 LangChain 提供模型、工具和 Agent 等高层积木，LangGraph 负责有状态流程编排；open_deep_research 是具体研究应用参考实现，Deep Agents 是通用 Agent 开发框架，两者定位不同，不能混为一谈。
  2. 核心流程是六步：澄清范围、生成 Brief、拆分子课题、并行检索、压缩核验、统一写作 先澄清用户目标并生成 Research Brief 作为成功标准，Supervisor 拆出相对独立的子课题，Researcher 在隔离上下文中多轮检索并保留来源，证据压缩后检查缺口并补搜，最后由统一写作阶段综合论证、处理重复、区分事实与推断。
  3. 拆分子 Agent 的首要目的是隔离上下文，并行只是自然结果 多个主题混在同一上下文会互相干扰，子 Agent 只处理一个子课题并只返回压缩结论和来源，主 Agent 不必背负全部搜索过程；只有相互独立的子课题才适合并行，依赖关系强的任务仍须串行，Agent 越多调用、费用、限流和协调成本越高。
  4. 研究质量应沿「来源→证据→结论」反向追查，链接多不等于证据可靠 先看来源是否一手可信，多篇转载可能同源，不能当交叉验证；再确认来源是否真正支持结论，报告应区分事实、推断与不确定性；冲突时追查发布时间、统计口径和原始出处；结论不稳则回查搜索词、子课题重复、停止条件和工具失败等过程问题。
  5. 成本与安全必须同时控制宽度、深度和不可信输入 宽度是并行研究单元数量，深度是迭代轮数，需分别限制并设置总 Token、搜索费用和超时预算，补充重试、缓存、限流和取消策略；网页和外部文档是不可信输入，可能含提示词注入，工具应优先只读、内部数据最小权限、密钥不暴露、高风险操作人工审批并保留 Trace。

💬 文章金句

  • Deep Research 的关键不是「搜索很多次」，而是让系统围绕研究目标动态决定：下一步搜索什么、哪些问题可以并行、证据是否充分，以及何时停止。
  • 所以，拆出子 Agent 首先是在隔离上下文。每个 Researcher 只处理一个子课题，最终只返回压缩后的结论和来源，主 Agent 不必背着全部搜索过程继续思考。
  • 研究报告很长、链接很多，并不代表质量高。判断质量时，可以沿着「来源 -> 证据 -> 结论」反向追查。
  • 多篇转载却可能都来自同一篇文章，不能因为链接数量多就当成交叉验证。
  • 网页和外部文档都是不可信输入，可能包含诱导 Agent 泄露密钥或执行危险操作的提示词注入。
