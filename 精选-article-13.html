让老手机刷抖音也流畅：我们做对了这三件事

4/3/2026, 6:39:00 AM

📌 一句话摘要

字节跳动分享了针对 Android 老旧机型在内存（ART 堆扩容）、FD（突破 1024 限制）和线程（M:N 用户态线程）三个维度的深度底层优化实践。

📝 详细摘要

本文深度揭秘了抖音客户端团队为挽救老旧 Android 手机用户体验所实施的三项核心技术突破。首先，针对 Android 5-9 系统，通过动态释放并重建 ART 虚拟机的 Malloc Space 和 Region Space，实现了 Java 堆内存的跨越式扩容，显著降低了 OOM 率。其次，通过修改内核 rlimit 并结合 inline hook 技术，将栈上的 fd_set 映射到堆上的扩展对象，突破了 libc 中 1024 的硬上限。最后，针对部分厂商对进程线程总数的限制，开发了 M:N 透明用户态线程方案，利用实时信号实现抢占式调度和上下文切换，使单个轻量级进程（LWP）能承载多个逻辑线程，保障了极端资源受限环境下的业务运行。

💡 主要观点

  1. 通过动态重建 ART 虚拟机的内存空间实现 Java 堆扩容。 利用 copy GC 机制中 main space 与 backup space 互相备份的特性，在锁定 GC 后释放并重建更大的空间，从而突破系统 build.prop 预设的 heap 大小限制。
  2. 结合内核 rlimit 修改与用户态映射突破 FD 1024 限制。 通过 setrlimit 提升内核上限，并利用 inline hook 拦截 libc 的 fd_set 相关调用，将受限的栈内存操作映射到自定义的堆内存扩展对象上。
  3. 实现 M:N 透明用户态线程以绕过系统线程数限制。 拦截 clone 系统调用，利用实时信号（SIGRT）触发时间片轮转，在用户态手动保存和恢复包括通用寄存器、TLS（tpidr_el0）在内的上下文，实现多线程复用单一 LWP。
  4. 针对非信号安全系统调用的中断补偿机制。 在用户态线程调度中，通过 daemon 线程代理 select/poll 等阻塞式调用，并对 nanosleep 等不可重启调用进行特殊逻辑处理，确保业务逻辑正确性。

💬 文章金句

  • 出现问题的这类机型的 art 虚拟机 heap 大小仅为 256MB。这些 256MB 的机型并不是抖音 app 没有声明 largeHeap 或者 largeHeap 未生效的问题，而是厂商在 build.prop 中声明的最大 heap 就是 256MB。
  • 我们可以限制 copy gc 的发生，从而限制 art 虚拟机暂时只能工作在一个 space 上，释放掉此时没有在使用中的 backup space，并创建更大的一块 backup space。
  • 内核对于 syscall 是支持超过 1024 的，那么只需要关系如何修改用户态 libc 中的限制即可。
  • 我们只要能实现周期性将 pthread 的 context 进行 swap，就可以实现一个 LWP 承载多个 pthread，进而突破系统内核对 500 线程（进程）的限制。
  • 这个方案保障了遇到 500 线程限制的用户的体验下限，解决了能不能用的问题，还是有非常大的价值的。
