Agent 评测：方法论与体系设计

7/2/2026, 10:09:00 AM

📌 一句话摘要

本文系统性地提出了一套面向生产环境的 Agent 评测方法论与工程体系，覆盖指标、数据集、评分、根因分析、自动优化与闭环。

📝 详细摘要

本文系统总结了 Agent 评测的方法论与工程体系。作者首先阐述了 Agent 评测与传统软件测试的本质差异——非确定性、黑盒化与错误级联放大，指出评测必须嵌入研发流程而非上线前抽查。接着按 Agent 类型（对话型、任务型等）区分评测侧重，并专门讨论对话 Agent 的多轮特殊性。指标体系方面提出五大类指标（P0/P1/P2 分层），并强调生产场景更应关注「连续成功率」而非单次通过率。数据集建设主张以高风险路径与失败模式为核心设计黄金评测集，而非随机采样。评分部分主张以规则 Scorer 为主判，LLM-as-Judge 辅助语义/策略维度，并给出 Judge 校准、人工评分路由等工程建议。Badcase 分析部分详细介绍了证据汇总、范围收敛、分模块诊断、责任判定与结构化落盘的完整流程，并提出根因标签体系与自动聚类。最后讨论了从发现问题到闭环反馈的工程建设，包括质量资产库、反馈生产线与样本治理。文章兼具方法论与工程可操作性。

💡 主要观点

  1. Agent 评测必须嵌入研发流程，而非上线前人工抽查。 Agent 输入输出状态空间开放，非确定性、黑盒化与错误级联放大的特性决定了评测需要持续收敛智能行为为可发布工程质量。
  2. 评测集不能随机采样线上数据，需围绕高风险路径与失败模式设计。 线上样本存在幸存者偏差，随机采样会漏检关键边缘场景；黄金评测集应包含专家用例、扩展用例、线上回流与对抗集。
  3. 评分应优先使用规则 Scorer，LLM-as-Judge 仅补充语义与策略等非确定性维度。 能写成代码的硬条件由规则主判；LLM-as-Judge 需明确评分标准、输出 reason、few-shot 示例并定期校准，且需防范偏差。
  4. Badcase 根因定位需先按问题现象映射候选模块，再分模块诊断，避免无差别排查。 维护「问题现象×功能模块」映射表可快速缩小范围，再结合 Trace 与证据进行分模块诊断与责任判定，最终结构化落盘。

💬 文章金句

  • Agent 评测是把「不稳定的智能行为」持续收敛成「可发布的工程质量」，不是上线前抽查。
  • 跑几条 case 感觉还行远远不够。
  • 评测平台的终点不是报告，而是把线上失败持续转化为可复用的研发资产。
