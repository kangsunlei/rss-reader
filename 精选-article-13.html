编程智能体的上下文工程

2/5/2026, 3:36:00 PM

📌 一句话摘要

本文为 AI 编程智能体中的“上下文工程”提供了一个全面的框架，探讨了如何通过战略性地策划提示词、工具和接口来优化 LLM 的性能。

📝 详细摘要

文章将上下文工程定义为对提供给 LLM 的信息进行刻意策划，以提高其输出质量。它将上下文分为“可重用提示词”（区分特定任务的指令 Instructions 和通用指南/规则 Guidance/Rules）以及“上下文接口”（工具、MCP 服务器和技能 Skills）。作者以 Claude Code 为主要案例研究，详细介绍了各种配置功能，例如用于项目级规范的 CLAUDE.md 以及用于特定文件约束的模块化规则。一个核心主题是上下文规模的“金发姑娘”挑战：既要提供足够的信息以保证准确性，又要避免因上下文过多而导致的性能下降和成本开销。最后，作者强调，尽管使用了“工程”一词，该过程仍然是概率性的，需要迭代优化和人工监督，而不是期望确定性的控制。

💡 主要观点

  1. 上下文工程是对模型所见内容的战略性策划，旨在改善结果。 它不仅涉及提示词，还包括规则、技能和接口的配置，这些配置定义了智能体如何与代码库和外部数据源进行交互。
  2. 区分针对特定任务的“指令”和针对通用规范的“指南”。 指令告诉智能体要做什么（例如：编写测试），而指南则提供了在各项任务中应遵循的护栏和风格规范（例如：使用特定的库）。
  3. 像 MCP 和技能这样的上下文接口允许对相关信息进行“懒加载”。 这些接口使 LLM 能够仅在确定当前任务需要时才获取特定数据或执行脚本，而不是将所有文档都塞进提示词中。
  4. 有效的上下文管理需要平衡信息密度与模型性能。 过多的上下文会导致更高的成本并降低模型效能；开发者应迭代地构建上下文文件，并使用能提供上下文使用透明度的工具。
  5. 上下文工程仍然是一项概率性的尝试，而非确定性的。 尽管有复杂的配置，LLM 的行为永远不是 100% 确定的。开发者必须保持人工监督，并将智能体的输出视为高概率建议，而非保证性的结果。

💬 文章金句

  • 上下文工程就是策划模型所看到的内容，以便获得更好的结果。
  • 当智能体获得过多的上下文时，其效能会下降，当然，过多的上下文也是一个成本因素。
  • 逐步构建像规则文件这样的上下文，不要从一开始就往里塞太多东西。
  • 只要涉及 LLM，我们就永远无法确定任何事情，我们仍然需要以概率思维思考，并选择合适的人工监督水平。
  • 强大的上下文工程正成为这些工具开发者体验的重要组成部分。
