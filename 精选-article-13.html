把 Agent 的判断与行动变成可恢复的软件事实｜KDC 系列 工程篇

11/4/2026, 12:00:00 PM

📌 一句话摘要

本文提出了将 Agent 的判断与行动转化为可恢复软件事实的工程方法，通过双链结构（业务因果链与运行事实链）和若干合约（Resume、Progress、Evaluation），实现生产级 Agent 的持续性、可治理和可追溯。

📝 详细摘要

在 AI Agent 系统中，单纯的循环推理（ReAct）无法满足生产环境对状态恢复、跨端一致、业务授权和现实验证的需求。本文区分了三种事实层次：领域现实、业务判断事实和软件运行事实，并构建两条可连接的链条——业务因果链与运行事实链。通过稳定身份（runId、turnId、toolCallId 等）将两条链关联，进而提出 Session、Harness、Sandbox 等解耦结构，并定义 Run、Turn、Runtime Event、Checkpoint、Pending Approval 等运行对象。文章进一步阐述了 State、View、Control 的分离原则，以及语义责任分离、物理存储统一的平衡方案，最后给出最小 State Schema 示例，为实现可恢复、可控制的 Agent 运行提供了完整的工程框架。

💡 主要观点

  1. Agent 运行需要双链结构连接业务因果链与运行事实链 业务因果链解释系统为何行动，运行事实链确保执行可恢复、可控。两条链通过稳定身份（runId、toolCallId 等）关联，避免仅靠推理或仅保存调用记录导致的恢复失败或授权失效问题。
  2. 三种事实必须分离：领域现实、业务判断事实、软件运行事实 领域现实是最终参照物，业务判断事实说明系统依据目标与知识形成结论，软件运行事实记录执行进度。混合使用会导致恢复不准确或授权失效，必须分别管理。
  3. State、View、Control 必须严格分离 State 保存可恢复的运行事实，View 从 State 派生展示，Control 提交命令请求。UI 不能直接修改 State，否则会破坏恢复一致性。
  4. 最小运行对象确保恢复归属 Run、Turn、Runtime Event、Checkpoint、Pending Approval、Artifact Reference 等对象定义了 Agent 运行的最小职责边界，若状态影响恢复、审批或跨端一致，必须持久化。
  5. 语义责任分离，物理存储可以统一 通过统一的追加事件日志实现物理存储统一，同时为不同语义建立强类型事件和投影，既简化架构又确保高风险事实显式记录，防止从文本推断错误状态。

💬 文章金句

  • 会执行一次循环，不等于可以运行一个产品
  • 三种事实不能混在一起：领域现实、业务判断事实、软件运行事实
  • 生产级 Agent 需要两条可以连接的链：业务因果链与运行事实链
  • State、View 和 Control 必须分开：Runtime 写运行事实，View 读取运行事实，Control 提交命令
