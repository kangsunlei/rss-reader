100G 内存下，MySQL 查询 200G 大表会 OOM 么？

7/14/2025, 11:15:00 PM

📌 一句话摘要

文章深入解析了 MySQL 在内存受限环境下，通过“边读边发”机制和 InnoDB 改进型 LRU 算法，有效避免大表全表扫描导致内存溢出。

📝 详细摘要

文章详细阐述了 MySQL 如何应对 200G 大表在 100G 内存主机上进行全表扫描而不会导致内存溢出（OOM）的问题。首先，从 Server 层角度分析，MySQL 采用“边读边发”策略，通过 net_buffer_length 参数控制每次发送的数据量，当网络栈满时会暂停读取，从而避免一次性加载全部结果集到内存。其次，文章深入探讨了 InnoDB 存储引擎的影响，重点介绍了 Buffer Pool 的工作原理。核心在于 InnoDB 对传统 LRU 算法的改进：将 Buffer Pool 划分为 New 区和 Old 区，并引入 innodb_old_blocks_time 参数，确保冷数据全表扫描时新读入的数据页优先进入 Old 区，且在短时间内不会晋升到 New 区，从而保护热点数据不被频繁淘汰，维持 Buffer Pool 的高命中率。文章还区分了`Sending data`和`Sending to client`两种`show processlist`状态的含义，提供了实用的排查建议。最终结论是 MySQL 的精巧设计使其能够高效处理远超内存容量的大表查询。

💡 主要观点

  1. MySQL Server 层通过“边读边发”机制避免大查询结果集占用过多内存 MySQL 不会在 Server 端保存完整的查询结果集，而是获取一行发送一行，通过`net_buffer_length`控制缓冲区大小，当客户端接收慢时会阻塞发送，而非耗尽服务器内存。
  2. InnoDB 改进型 LRU 算法有效保护热点数据不受全表扫描影响 InnoDB 将 Buffer Pool 分为 New 区和 Old 区，新读入的数据页（尤其是全表扫描的冷数据）优先进入 Old 区，并需停留一定时间才可能晋升 New 区，确保热点数据不被轻易淘汰。
  3. 正确理解`show processlist`中的`Sending data`与`Sending to client`状态 `Sending data`表示查询正在执行的任意阶段，而`Sending to client`特指服务器端网络栈写满，等待客户端接收结果的状态，有助于准确判断问题根源。

💬 文章金句

  • 一个查询在发送过程中，占用的 MySQL 内部的内存最大就是 net_buffer_length 这么大，不会达到 200G
  • 所以 MySQL 其实是'边读边发'。
  • 这个策略最大的收益，就是在扫描这个大表的过程中，虽然也用到了 BP，但对 young 区完全没有影响，从而保证了 Buffer Pool 响应正常业务的查询命中率。
  • MySQL 采用的是边算边发的逻辑，因此对于数据量很大的查询结果来说，不会在 server 端保存完整的结果集。
  • 冷数据的全表扫描，对 Buffer Pool 的影响也能做到可控。
