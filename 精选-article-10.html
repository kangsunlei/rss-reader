错误码排查从 3～8 小时到分钟级，Agent 怎么做到的？

9/23/2026, 9:30:00 AM

📌 一句话摘要

腾讯团队用单 Agent 挂载知识库、代码图谱、可观测平台与代码托管四类能力，构建错误码治理 Agent，将排查从 3～8 小时压缩到分钟级，action_type 与人工标注一致率从 66% 提升到 88%、硬冲突率降至 0%。

📝 详细摘要

文章介绍腾讯基于智能体编排平台搭建的错误码治理 Agent 实践。SRE 过去面对去重后数百个错误码告警，需跨系统检索文档、代码、日志与 trace，人工排查单个错误码耗时 3～8 小时。方案选择单 Agent 挂载知识库、代码关系图谱、可观测平台、代码托管平台四类能力，保留渐进式探索的完整上下文，由工作流负责入参预处理与结果组装、Agent 负责自主排查并输出 JSON、Skill 承载排查流程与规则。文章重点分享三个实践：一是多源证据交叉验证，代码怎么写不等于现场怎么跑，置信度按知识库、代码定位、实际源码、运行时证据各计 1 分分级；二是用 11 个节点的工作流与快慢双路径解析保证稳定输出，并给出分支变量统一、新增字段同步三处、批处理限频等工程细节；三是基于 v3 与 v4 的 50 条 case 对比做 5 轮 Prompt 调优，把加白判断改为先排除再判断、为修复建议划定边界。效果上一致率 66%→88%，需人工介入率 34%→12%，硬冲突率 20%→0%，日均处理数百条告警，high 置信度约 90%，失败率约 1%。作者强调可复用的是方法而非整套规则，并指出 50 条样本同时用于调优与回归、不代表泛化效果。

💡 主要观点

  1. 错误码治理的核心难点是证据分散，而非告警数量本身。 错误码只是一个数字，含义、业务规则、服务职责、仓库映射、handler 与上下游关系、错误日志与 trace 分散在四类系统中，单独查到其中一部分仍无法确认根因，因此人工排查一个错误码需 3～8 小时，且转给开发后往往还要再查一遍。
  2. 错误码排查属于渐进式探索任务，单 Agent 挂载全部能力优于多 Agent 协作。 排查路径是查到 handler 后追上游、日志显示限流后再确认错误码定义，下一步依赖上一步结果；多 Agent 分工虽职责清晰，但通信与编排复杂、上下文传递易丢失。作者也尝试过按路径拆分多个 Skill 和动态子任务编排，因切换依赖 Agent 自觉、通用规则重复维护、状态管理成本高而未采用。
  3. 静态代码与运行时证据必须交叉验证，才能区分责任点与修复动作。 静态代码显示 A 调用 B，只有结合 trace 才能区分是 A 内部多次串行调用累积超时，还是请求到达 B 后由 B 报错；前后端也需相互验证，前端源码未获取到就明确说明，不能凭后端代码推断。置信度模型据此把知识库、代码定位、实际源码、运行时证据各计 1 分，代码托管平台的变更信息不计分。
  4. 稳定输出依赖输出契约与解析兜底两端配合，而非只靠一次 json.loads。 Agent 输出可能含 Markdown 代码块、前后说明或缺失字段，工作流用 11 个节点、快路径四层容错解析加慢路径 LLM 提取 9 个字段兜底，并强调字段独立、非空输入全默认值时最多重试 3 次。Skill 侧明确管道符直接写 |、反引号不转义，输出前执行 17 项检查。
  5. Skill 迭代应案例驱动、规则显式化，而不是不断堆提示词。 v4 把加白条件与禁止加白场景从并列陈述改为显式三步（先排除禁止场景、再判断加白条件、最后区分 whitelist 与 whitelist_and_refine），并为修复建议补充只改实际触发入口、优先复用集中处理表、新增错误码前评估 ROI 三条边界；限流错误码 30110013 与 Redis 超时两个案例展示了规则迁移而非记答案。
  6. 评测既要看结论也要看过程，才能区分有证据地判断正确与碰巧说对。 评测维度覆盖最终结果、过程完整性、工具可靠性、证据与边界、效率与稳定性；已落地版本对比（按 request_id 对齐 v3/v4 生成迁移矩阵）、回归 case 固化（保留 6 条 v3 覆盖 v4 的 case）、badcase 反哺 Skill 三层机制，避免 Skill 越来越厚、越来越慢。

💬 文章金句

  • 让 SRE 从"告警搬运工"升级为"修复建议审核员"。
  • 工作流是"骨架"，Agent 是"大脑"，四类能力是"感官"。
  • 工作流的坑不一定在代码里，也可能在节点配置里。
  • Skill 工程设计不是写更多提示词，而是对比驱动、案例驱动、规则显式化。
  • 上线不是终点，是新一轮迭代的起点。
