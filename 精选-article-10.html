如何搭建一个端到端业务需求专家 Agent

6/15/2026, 12:30:00 AM

📌 一句话摘要

本文详细阐述了一套在真实业务需求上跑通的端到端业务需求专家 Agent 系统，通过组织上下文、串联工具和沉淀反馈，将需求研发过程从人工串联转变为 Agent 自主推进、人在关键节点确认的闭环。

📝 详细摘要

文章指出，AI 写代码已不是瓶颈，真正的瓶颈在于需求从 PRD 到上线过程中的串联成本。作者基于阿里内部实践，提出并实现了一套「业务需求专家 Agent」系统。文章从横向架构（上下文输入层、业务专家编排层、工具执行层、反馈学习层）和纵向流程（需求进入、澄清、技术方案、实现与内部质量门、CR/Issue 协同、验收验证、发布与变更观察、结项沉淀）两个维度，详细拆解了系统如何将上下文组织好、工具串起来、人工确认放在正确位置、过程反馈收回来。文章重点强调了 TDD 驱动的实现、硬性质量门禁（如 git hook）、人机反馈的留痕与复用、以及结项时的知识蒸馏。最后，作者坦诚讨论了当前存在的接入成本、度量体系缺失等问题，并展望了从单 Agent 走向多 Agent 协作（Agent Team）的未来方向。

💡 主要观点

  1. AI 写代码已不是瓶颈，代码之外的串联成本才是。 需求从 PRD 到上线需经历多个环节，AI 虽能参与各环节，但若能力分散，最终仍需人工串联，导致上下文切换、经验差异和时间占用成为主要瓶颈。
  2. 系统核心是围绕需求交付组织上下文、工具和反馈。 通过四层架构（上下文输入、业务专家编排、工具执行、反馈学习），将分散的需求材料、平台工具和人工反馈组织成闭环，减少人工重复劳动。
  3. TDD 和硬性质量门禁是实现阶段的关键设计。 采用 TDD 驱动实现，让测试定义正确行为而非事后装饰。通过 git pre-push hook 将 PMD 校验和测试覆盖率检查变为硬性卡口，确保质量。
  4. 结项沉淀是系统自我成长的关键，实现知识的复利。 结项时对过程材料进行选择性蒸馏，将稳定知识沉淀到长期 wiki，将流程问题转化为 skill/prompt 改进候选，让每个需求都提升 Agent 的业务理解基线。

💬 文章金句

  • AI 写代码本身已经不再是主要瓶颈。但一个业务需求从 PRD 到上线，中间要经过需求澄清、方案确认、实现、CR、验收、发布观察和结项沉淀——代码生成只是其中最标准化的一段，真正贵的是代码之外的串联成本。
  • 这些门禁不能只靠提示词约束，必须变成 Agent 绕不过去的硬规则。
  • 人不应该继续在每个需求里反复补位，而是把这些补位动作沉到系统里。
