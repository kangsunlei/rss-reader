从模型到 Harness：WorkBuddy 如何把 Agent 做成可用产品

7/10/2026, 4:05:00 AM

📌 一句话摘要

本文从产品视角完整拆解 WorkBuddy 如何通过 Context Engineering、Memory 系统、Harness Engineering 等机制，将 LLM 模型能力转化为稳定可用的 Agent 产品，而非仅依赖模型或提示词。

📝 详细摘要

文章前半部分为 Agent 基础概念科普，清晰解释 LLM 无状态性、工具调用、System Prompt、MCP、Skill 与 Plugin 的层次与区别，并通过对比表格说明不同外接能力的适用场景。后半部分深入 WorkBuddy 的产品实现，重点论述 Context Engineering 的五类动作（写入、选择、检索、压缩、隔离）、Memory 系统的作用域分层与准入判断（明确不将程序性记忆纳入长期记忆）、以及 Harness Engineering 如何通过引导、约束与整合解决方向偏离、安全边界与系统编排问题。全文以一次完整调研任务作为案例串联所有机制，强调 Agent 可靠性来自模型外部的工程系统而非模型本身。

💡 主要观点

  1. 模型能力只是起点，Agent 产品可靠性取决于模型外部的 Context Engineering 与 Harness Engineering。 作者以 WorkBuddy 实战经验说明，工具接入、上下文组织、权限边界、结果验证与反馈纠正等工程机制，远比更换更强模型更能决定 Agent 能否稳定完成任务。
  2. Context Engineering 追求相关、准确、及时，而非堆砌 token，包括写入、选择、检索、压缩、隔离五类动作。 每轮模型调用应只包含当前决策所需的最小信息集，避免无关内容占用上下文窗口并干扰模型判断；同时提出渐进式加载、工具按需暴露等具体实践。
  3. Memory 系统需有准入判断与分层作用域，程序性记忆应通过 Skill 管理而非注入长期记忆。 WorkBuddy 明确区分陈述性记忆（用户事实、偏好）与程序性记忆（做事方法），后者作为 Skill 可版本化、评审、测试和回滚，避免局部经验泛化为通用策略而干扰模型推理。
  4. Harness Engineering 通过方向引导、安全约束与系统编排，将模型输出转化为稳定可控的执行过程。 当 Agent 执行写文件、运行命令等操作时，Harness 负责校验方向、拦截误操作并组织能力，确保 Agent 行为可预测、可审计、可回退。

💬 文章金句

  • Context Engineering 追求相关、准确、及时，不是单纯堆 token。
  • 让正确的过去，在正确的时候，以正确的作用域，正确的方式重新出现。
  • 模型无状态，但产品可以有状态。
