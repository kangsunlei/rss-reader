📌 一句话摘要

本文深度解析了 Claude Code 的六层架构与工程实践，提出了从上下文治理、技能设计到验证闭环的系统化 Agent 开发方法论。

📝 详细摘要

文章基于作者半年深度使用 Claude Code 的实战经验，系统性地将其拆解为六层架构：CLAUDE.md（长期上下文）、Tools/MCP（动作能力）、Skills（按需工作流）、Hooks（强制拦截）、Subagents（隔离执行）和 Verifiers（验证闭环）。作者指出，Agent 的核心痛点不在于模型智力，而在于上下文污染、工具冗余及缺乏确定性约束。文章详细讨论了如何通过 Prompt Caching 优化成本、利用 Skills 实现“渐进式披露”、以及通过 Hooks 和验证层构建工程化的 Agent 协作体系，旨在帮助开发者从简单的工具使用者晋升为系统设计者。

💡 主要观点

  1. 构建六层架构模型是实现 Agent 确定性治理的核心框架。 通过将系统拆分为契约、能力、方法论、拦截、隔离和验证六个维度，可以有效解决 Agent 在复杂任务中出现的上下文混乱和状态漂移问题。
  2. 上下文工程的本质是噪声治理，而非单纯追求长文本容量。 MCP 工具定义是隐形的 Token 杀手，应采用分层加载策略，将非高频信息通过 Skills 或 Subagents 进行按需加载和隔离，以保持核心上下文的纯净。
  3. Skills 应设计为按需加载的标准化工作流，而非静态 Prompt 模板。 优秀的 Skill 需具备明确的触发时机、执行步骤和停止条件，通过“渐进式披露”机制，让模型在需要时才获取领域细节，降低常驻开销。
  4. Prompt Caching 的前缀匹配机制决定了 Agent 系统的成本与性能结构。 开发者需遵循特定的 Prompt 布局，将静态的系统指令和工具定义置于首部，动态对话置于尾部，并避免中途切换模型以维持高缓存命中率。
  5. 验证闭环（Verifiers）是区分实验性 Demo 与工程化 Agent 的关键标志。 不能仅依赖模型的自我判断，必须引入命令退出码、Lint、测试用例等硬性校验手段，确保 Agent 的输出可验证、可审计且可回滚。

💬 文章金句

  • 卡住的地方几乎从来不是模型不够聪明，更多时候是给了它错误的上下文，或者写出来了但根本没法判断对不对。
  • 给 Claude 的工具和给人写的 API 不是一回事。给人用的 API 往往会追求功能齐全，但给 agent 用，重点是让它更容易用对。
  • 假如一个任务你都说不清楚「什么叫做完」，那它大概率也不适合直接丢给 Claude 自主完成。
  • 工程界有句话 'Cache Rules Everything Around Me'，对 agent 同样如此，Claude Code 的整个架构都是围绕 Prompt 缓存构建的。
  • CLAUDE.md 更像是你和 Claude 之间的协作契约，不是团队文档，也不是知识库，里面只放那些每次会话都得成立的事。
