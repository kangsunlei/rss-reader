从 AI Coding 到 Harness Engineering 的端到端工程开发实践

7/3/2026, 9:36:00 AM

📌 一句话摘要

本文系统介绍了腾讯应用宝活动平台团队从对话式 AI Coding 迈向 Harness Engineering 的实践，涵盖知识库工程（结构化知识自动生成与检索）和端到端开发工程（状态文件驱动、专家 Agent 体系、DAG 并行编排），并总结了核心工程原则。

📝 详细摘要

文章基于腾讯应用宝活动平台重构的真实案例，详细记录了团队从对话式 AI Coding 走向 Harness Engineering 的工程实践。首先指出对话式 AI Coding 的四个核心痛点：上下文快速膨胀、缺乏完整业务知识、缺乏工程自动化闭环、无法并行。随后提出整体架构：知识库工程（Knowledge Engineering）作为底座，端到端开发工程（End-to-End Development Engineering）构建其上。知识库工程采用结构化目录（三层：总览-域层-服务层），通过 Skill 实现从代码到文档的自动生成，采用渐进式分层加载与 grep 替代传统 RAG 检索，并引入文档新鲜度检测机制。端到端开发工程以状态文件驱动流程，设计 12 个单一职责的专家 Agent、引入 DAG 并行编排与 Fork-Join 模式，对冲突治理提出事前隔离与串行收口策略，并将确定性操作脚本化（AI 负责认知，脚本负责执行），同时集成公司内 TAPD、Codar、123 等多平台实现 DevOps 全流程闭环。最后总结了核心工程原则（AI 负责认知、长链路状态化、知识库结构化、Agent 职责隔离、脚本化执行、Workflow 优于 Prompt）以及对调度架构演进（从 Agent 驱动转向强类型代码编排）等反思。

💡 主要观点

  1. 对话式 AI Coding 在复杂业务中面临上下文膨胀、缺乏业务知识、缺乏自动化闭环、无法并行四大瓶颈。 单窗口随迭代膨胀导致遗忘，每次需求需人工梳理多个服务背景，编码外环节仍需人介入，串行执行效率低，这是转向 Harness Engineering 的直接动因。
  2. 知识库是 Harness 体系的底座，采用结构化目录 + AI 自动生成 + 人工补充 + 渐进式检索来保障业务上下文准确、新鲜。 通过自动生成 8 类服务文档（overview、interfaces、architecture 等）并保留人工注释，配合基于 meta.yaml 的渐进式分层加载，替代传统 RAG，避免模糊匹配与高维护成本，同时利用 git hash 检测文档新鲜度，防止过期知识误导 AI。
  3. 端到端开发工程通过状态文件驱动、专家 Agent 体系、DAG 并行编排实现从需求到提交的全流程自动化。 将流程各步状态持久化为 JSON 文件，使流程可中断恢复；每个 Agent 单一职责、上下文隔离；DAG 分层 + Fork-Join 模式支持多任务并发开发；冲突治理采用事前文件隔离、串行收口等策略。
  4. 确定性操作脚本化、认知任务留给 AI，是提升系统稳定性与降低 token 消耗的核心原则。 将状态解析、git worktree 创建、编译发布等确定性步骤封装为脚本直接执行，避免 AI 因 Shell 错误或不稳定行为引入随机性，同时显著节省 token。
  5. 从项目实践中提炼出七条核心工程原则，强调查工程化设计比 Prompt 更关键。 包括 AI 负责认知/脚本负责执行、长链路状态化、知识库结构化、Agent 职责隔离、执行步骤脚本化、Workflow 比 Prompt 更重要等，并指出调度架构应从 Agent 驱动转向外部强类型代码编排。

💬 文章金句

  • AI 负责认知，脚本负责执行。
  • 长链路必须状态化——状态脱离上下文落盘，才能稳定续传。
  • 过期知识比没有知识更危险。
  • 知识库必须结构化，AI 才能精准检索。
  • Workflow 比 Prompt 更重要——流程编排的确定性，胜过反复打磨 prompt。
