提示词工程、上下文工程都过时了，现在是 Harness Engineering 的时代

3/13/2026, 1:02:00 PM

📌 一句话摘要

本文介绍了 Harness Engineering（线束工程）这一 AI 开发新范式，强调工程师的核心工作正从编写代码转向为 AI Agent 设计运行环境与反馈回路。

📝 详细摘要

文章探讨了 AI 辅助开发从提示词工程（Prompt Engineering）、上下文工程（Context Engineering）向线束工程（Harness Engineering）的演进。核心观点认为，决定 AI Agent 产出质量的关键不再是模型智力，而是其所处的“环境”。通过分析 OpenAI 的零手写代码实验、Stripe 的大规模 PR 合并实践以及 LangChain 的基准测试，文章提出了线束工程的三大维度：上下文工程（渐进式信息披露）、架构约束（机械化围栏）和熵管理（防止规则腐化）。这标志着工程师角色向“环境设计师”的重大转型，需通过构建自动化的验证机制和可观测性体系来确保 Agent 的可靠性。

💡 主要观点

  1. 决定 AI Agent 性能的最大变量已从模型智力转向其运行的外部环境。 通过优化文档结构、验证回路和追踪系统等外部环境，底层模型无需改动即可在基准测试中获得显著的排名提升，证明了环境工程的杠杆效应。
  2. 线束工程通过渐进式披露模型解决 Agent 的信息过载与上下文失效问题。 摒弃庞大的单一说明文档，采用结构化的目录体系（如 AGENTS.md），在正确时机为 Agent 提供正确粒度的信息，模拟人类工程师的入职逻辑。
  3. 构建专为 AI 设计的机械化架构围栏，实现“违规-检测-修复”的自动化闭环。 通过重写 Linter 错误输出格式使其对 AI 可读，并结合审计 Agent 强制执行架构依赖流向，确保 Agent 生成的代码在长期内保持一致性。
  4. 引入熵管理机制，防止线束系统随代码库规模增长而发生规则腐化。 部署专用清理 Agent 定期扫描文档漂移和模式违规，确保约束系统自身不随时间退化，从而避免 Agent 因读到混乱指令而输出低质代码。
  5. 工程师的核心职责正从直接编写代码转向定义业务意图与设计自动化验证机制。 工程师需具备更强的系统抽象能力，通过构建可观测性基础设施和防呆验证门禁，让 Agent 在受控的“盒子”内高效且安全地完成任务。

💬 文章金句

  • 在 AI Agent 编码领域，决定结果好坏的最大变量，往往不是模型有多聪明，而是模型被放在了一个什么样的环境里。
  • Prompt Engineering 管的是「说什么」，Context Engineering 管的是「知道什么」，Harness Engineering 管的是「在什么环境里做事」。
  • 每当你发现 Agent 犯了一个错误，你就花时间设计一个解决方案，使 Agent 永远不再犯同样的错误。
  • 工程师的核心工作，正从写代码转向设计环境。
  • 系统理解的深度，比写代码的速度重要得多。
