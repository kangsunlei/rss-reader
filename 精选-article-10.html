AI Coding 的下一步不是写得更快，而是可验收：蚂蚁数科 Harness 工程实践

9/4/2026, 10:05:00 AM

📌 一句话摘要

蚂蚁数科魏长征分享 Harness 工程实践：AI Coding 的核心矛盾不在代码生产而在验证，通过约束层、对抗验证层和证据层的闭环设计，将 60 万行 C++ 存量项目的代码缺陷率从 20% 以上降至个位数。

📝 详细摘要

文章基于蚂蚁数科两个真实项目（40 万行 Rust 新项目、60 万行 C++ 存量项目），系统阐述 Harness 工程如何构建 AI Coding 的研发闭环。核心观点：AI Coding 没有创造全新问题，而是以更高产能将需求模糊、目标漂移、事实冲突等旧问题集中放大；检验标准从「代码写得好不好」演变为「任务能否被约束、验证、验收」。Harness 架构分五层：约束层（任务目标/非目标、唯一事实源）、对抗验证层（多视角 Agent Code Review）、证据层（可视化测试报告）、状态写入层（工作流持久化）、目标对齐层（任务拆解）。存量项目改造路径为：先用 AI 扫描重建事实源，再逐步植入 Review 规则和 CI 门禁。

💡 主要观点

  1. AI Coding 的核心矛盾是验证能力滞后于代码生产能力，而非代码本身的质量问题 Agent 一天可完成过去三个月的代码量，原本分散数月的问题集中爆发。传统研发中的需求评审、Code Review、测试准出机制仍适用，但需适配高速循环。
  2. Harness 不是具体技术，而是一套围绕约束、验证和验收建立研发闭环的方法论 包含五层架构：约束层（明确目标、事实源、文档规范）、对抗验证层（多视角 Agent Review）、证据层（可视化报告）、状态写入与目标对齐。源自传统软件工程经验，而非 AI 时代发明。
  3. 存量项目改造必须先补 Harness 再引入 Agent，否则只会放大既有问题 60 万行 C++ 项目因历史文档缺失、事实源不统一，AI 介入后缺陷率飙升至 20%+。治理路径是先用 AI 扫描梳理文档与代码一致性、重建唯一事实源，再逐步植入 CI 门禁和 Review 规则，缺陷率降至个位数。
  4. 测试可信度不取决于数量和覆盖率，而取决于路径覆盖的充分性 通过 HTML 可视化报告展示测试覆盖的状态机跳转，发现「一百个测试只覆盖两个状态之间跳转」的低质量模式，倒逼返工。硬门禁检查约束合规，软门禁由不同 Agent 从 Contract、减法、复用三个维度 Review。
  5. AI Coding 对工程师的要求反而更高，核心能力从编码转向目标定义和验收判断 模型越强，期望完成的复杂任务越多，暴露的问题也越多。工程师需具备需求澄清、边界识别、架构判断和结果验收能力，人机协作将持续，目标是让验证速度匹配生产速度。

💬 文章金句

  • AI Coding 的产能提升得非常快，但研发团队的验证标准、验证方法和验证工具是否同步跟上了，这是目前最核心的矛盾。
  • AI Coding 放大的是研发流程中原本就存在的需求模糊、认知偏差、事实冲突和质量欠账。
  • Harness 并不是一种具体技术，更像是一套验证闭环的思想。
  • 测试是否可信，不能只看数量和覆盖率，还要看它实际覆盖了哪些路径。
  • AI Coding 对工程师的要求会越来越高。
