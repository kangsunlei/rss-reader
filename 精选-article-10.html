还好大促前刷到了！一种基于分布式缓存的强一致性热点库存扣减方案

11/4/2026, 11:15:00 PM

📌 一句话摘要

本文介绍了一种基于 Redis 分桶计数和 DB 合并提交的强一致性热点库存扣减方案，通过分布式缓存提升 TPS，同时通过锁库存、合并扣减、回收模块和防超卖设计，实现了在保证数据准确性的同时显著提升了库存扣减性能。

📝 详细摘要

文章详细阀述了针对热点深库存抢购场景的强一致性库存扣减方案。该方案基于 Redis 分桶进行扣减计数，实际扣减通过 DB 明细和合并提交实现。核心设计包括：锁库存模块将库存从可售字段锁定到预锁字段，初始化 Redis 计数；下单扣减先扣 Redis 再插入 DB 明细；合并提交模块延迟扫描明细并批量提交 DB 变更；库存回收模块处理商家编辑和临界场景；防超卖设计通过 Redis 屏障和 SQL 层控制确保不超卖；自动锁库存模块提前锁定热点库存。压测显示 TPS 从 1.4 万提升至 3.2 万，线上成功率从 80%提升至 100%，耗时从 15ms 降至 7ms。

💡 主要观点

  1. 基于 Redis 分桶的计数与 DB 合并提交架构 Redis 仅用于扣减计数防止超卖，实际扣减通过 DB 明细记录，最终由合并提交模块批量写入 DB，既保证了强一致性，又提升了 TPS 性能。
  2. 锁库存模块的非侵入式设计 锁库存时不修改 sq 字段，而是直接加到 lq 字段，库存展示链路无需关心锁定库存，大幅降低了链路复杂度。
  3. 防超卖少卖的双重保障机制 Redis 扣减受低位限制防止负数，DB 扣减通过 SQL 条件控制 sq-lq-δq>0；同时利用 Redis 屏障防止合并提交扫描遗漏单据导致的并发超卖。
  4. 合并提交模块的延迟扫描与批量写入 下单后延迟 1 秒扫描该分桶关联的扣减明细，计算实际扣减量后一次性提交到 DB，显著提升了扣减 TPS 和稳定性。
  5. 自动锁库存与库存回收的全链路治理 通过热点识别提前锁库存，后续自动触发；库存回收模块处理商家编辑和临界场景，确保锁库存及时释放，维持系统健康。

💬 文章金句

  • 如何在保证扣减强一致性的同时，提升库存热点扣减 TPS 和扣减稳定性？
  • Redis 只用来做扣减计数以防止超卖，实际扣减是否成功以库存扣减明细为准。
  • 我们把通用形态接到自己的研发系统上。属于我们自己的是四件事：需求系统接入、spec 自动召回、用完打分回写、全链路 trace。
  • 从压测效果上看，单行热点扣减场景下，非合并扣减 tps 峰值约 1.4w，合并扣减峰值 3.2w；整体提升 1 倍以上扣减性能。
  • 走到合并扣减的热点品，库存扣减成功率在 100%，接口扣减耗时 7ms+；未走到合并扣减的热点品，库存扣减成功率在 80%上下，接口扣减耗时 15ms+。
