如何让 Agent 记得住、查得准、改得对？腾讯 Octop Memory 实践

11/27/2026, 1:01:00 AM

📌 一句话摘要

文章详解了腾讯 Octop Memory 项目的五环记忆架构，围绕写入、提炼、晋升、召回、存储五个可配置环节，构建 Agent 长期记忆体系，实现记忆沉淀、检索准确与跨任务持续。

📝 详细摘要

本文聚焦腾讯开源项目 Octop Memory 的设计与落地实践。作者从 Agent 记忆的核心痛点出发，提出将记忆拆解为五个可配置、可编排的环节：写入（被动留存与主动保存），提炼与整理（从 RawEvent 到 Candidate），晋升与审批（治理机制与人工审核），召回与查证（被动预取与主动检索），存储底座与维护（SQLite/PostgreSQL 存储、生命周期清理与迁移）。文章详细阐述了每一环节的实现方式、配置选项及其在实际场景中的应用，如研发助手、个人助理等。通过默认即最佳实践的设计，普通用户可零配置使用，高级用户可精细调控。同时，文章展望了 Octop Memory 2.0 的演进方向，包括 MCP 原生支持、多 Agent 记忆协同与跨场景评测体系。

💡 主要观点

  1. 记忆五环架构：写入、提炼、晋升、召回、存储形成闭环 通过解耦设计，将记忆的写入方式、提炼节奏、治理规则、召回策略和存储实现分别独立配置，使记忆系统既能自动沉淀，又能按需精调。
  2. 写入支持被动留存与主动保存双路径 宿主可选择仅启用 capture_turn 自动记录对话，或挂载 memory_save 工具让 Agent 主动锁定关键结论，二者组合可实现证据完整与结论明确的双轨记忆。
  3. 晋升与审批机制确保记忆质量 候选记忆需经过价值评估、证据核验、冲突治理等流程方可成为正式记忆，支持自动晋升与人工审核双模式，防止错误决策被长期依赖。
  4. 召回策略灵活：被动预取与主动检索可混合 宿主可在对话前自动注入核心记忆，Agent 遇到细节追问时再主动检索原始证据，实现高效响应与深度溯源的平衡。
  5. 存储支持本地轻量与服务端分布式部署 可选 SQLite 实现零依赖本地部署，或 PostgreSQL 支持多实例分布式，同时通过 namespace 实现逻辑隔离，支持跨宿主迁移与生命周期清理。

💬 文章金句

  • 人类最大的优势，是可以把反复验证过的经验沉淀为直觉。对 Agent 来说，能在恰当的时候想起、核对并更新过往经验，才能称得上好的 Agent 记忆。
  • Octop Memory 把这些问题拆开处理。写入兼顾被动证据留存与主动直写，提炼和核验值得长期使用的内容，召回按主被动策略带回任务，存储与维护负责跨周期的持久化、清理与迁移。
  • 保存了对话、提炼出候选，并不意味着内容已经成为正式记忆。后台提炼产出的内容首先进入候选层（Candidate），必须经过晋升与审批治理，才能成为可被正式召回的原子记忆（AtomCard）。
  • 更重要的是，这些配置思路在实际项目中完全支持灵活混搭：例如，一个日常研发助手，平时依靠系统自动预取获得核心技术约定；一旦遇到架构选型分歧，便由模型自主调用工具去翻阅原始对话证据。
  • 我们期待更多开发者能加入 Octop 的开源生态，从真实的痛点出发，像搭积木一样组合这些强大的原子能力，搭建出真正懂得沉淀经验、越用越懂你、甚至能陪你一起成长的专属 Agent。
