📝 详细摘要

本文深入探讨了围绕 Redis“单线程”模型的实际情况，特别是 Redis 6.0 引入的多线程 IO 特性。文章首先回顾了 Redis 命令执行仍是单线程的核心，并介绍了 4.0、6.0 版本引入后台线程及 IO 多线程的演进，同时提及了近期 Valkey 8.0 在异步 IO 上的进展及相关社区背景。接着，文章详细解析了 Redis 6.0 多线程 IO 的配置、读写流程概述、基于源码的初始化和具体流程分析，包括其动态暂停与开启机制。通过性能测试数据，文章展示了多线程 IO 在 GET/SET 操作下相对于单线程的显著性能提升，尤其在高并发、小数据量场景。最后，文章客观分析了 Redis 6.0 多线程 IO 在 CPU 利用率和异步能力等方面的现有不足，并展望了 Valkey 8.0 的进一步改进，为理解 Redis 网络模型演进提供了全面的视角。

💡 主要观点

  1. Redis 核心命令执行仍为单线程模型，但 IO 操作可在多线程并行 澄清 Redis 单线程模型仅指命令执行，Redis 6.0 引入多线程 IO 处理网络读写和协议解析，是其性能提升的关键。
  2. 多线程 IO 通过主线程分发任务并阻塞等待 IO 线程完成 主线程负责接收连接、分配客户端到 IO 线程读写，然后等待 IO 线程处理完毕，再执行命令或处理后续写操作。
  3. Redis 6.0 多线程 IO 可根据待写客户端数量动态暂停与开启 当待写客户端数量少于线程数两倍时，会暂停多线程 IO，切换回同步处理，减少线程切换开销。
  4. 开启多线程 IO 显著提升 Redis 性能，尤其在高并发、小数据场景 性能测试结果显示，在特定环境下，开启 4 个 IO 线程可使 GET/SET QPS 翻倍，证明了多线程 IO 的有效性。
  5. Redis 6.0 多线程 IO 在 CPU 利用率和异步能力上仍有不足 IO 线程需等待主线程，未充分利用 CPU；缺乏完全异步能力限制了进一步性能提升，为后续版本改进方向。

💬 文章金句

  • 我们常说 Redis 是单线程模型，是指 Redis 采用单线程的事件驱动模型，只有并且只会在一个主线程中执行 Redis 命令操作
  • 在 Redis6.0 中引入了多线程 IO 特性，将 Redis 单节点访问请求从 10W 提升到 20W。
  • Redis6.0 引入多线程 IO，但多线程部分只是用来处理网络数据的读写和协议解析，执行命令仍然是单线程。
  • 从上面可以看到 GET/SET 命令在设置 4 个 IO 线程时，QPS 相比于大部分情况下的单线程，性能几乎是翻倍了。
  • CPU 核心利用率不足：当前主线程仍负责大部分的 IO 相关任务，并且当主线程处理客户端的命令时，IO 线程会空闲相当长的时间
