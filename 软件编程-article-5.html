Authress 如何通过韧性设计在重大 AWS 中断中保持服务可用性

12/28/2025, 11:00:00 AM

📌 一句话摘要

Authress 实施了“可靠性优先”设计，采用多区域 DNS 故障转移、边缘优化架构和简化基础设施，以在重大 AWS 中断中维持服务可用性。

📝 详细摘要

这篇 InfoQ 文章详细介绍了身份和认证服务公司 Authress 如何设计其基础设施以抵御重大的云中断，其中一个突出例子就是 2025 年 10 月的一次重大 AWS 中断。Authress 首席技术官 Warren Parad 解释了他们的“可靠性优先”设计，该设计以多区域故障转移路由策略为中心，利用 DNS 动态路由和自定义健康检查来快速检测和响应区域故障。除了基本的故障转移，Authress 还采用了边缘优化架构，结合 AWS CloudFront 和 Lambda@Edge，不仅通过将服务置于更接近用户的位置来减少延迟，还实现了跨多个相邻区域的细粒度、多阶段数据库故障转移。该策略还考虑了应用层故障，认识到无 bug 代码是不可实现的，并强调采用简化的、重复的基础设施而非 DRY 原则，以最大限度地降低复杂性和与变更相关的风险。他们全面的方法包括根本原因分析、验证测试和 AI 驱动的事件过滤。

💡 主要观点

  1. Authress 利用 DNS 动态路由在主次区域之间实现快速多区域故障转移。 此核心策略利用 DNS 在主区域出现问题时自动将流量重定向到健康的故障转移区域，从根本上确保在重大中断期间的服务连续性。
  2. 自定义健康检查对于可靠的事件检测至关重要，避免了对外部或内部 AWS 管理检查的依赖。 Authress 在各种组件（数据库、SQS、授权逻辑）中实现自己的一系列检查，并监控请求延迟，以准确确定区域健康状况并启动故障转移，从而避免了默认或第三方监控的潜在不可靠性。
  3. 结合 CloudFront 和 Lambda@Edge 的边缘优化架构可实现数据库的多阶段、细粒度故障转移。 这种高级设置不仅通过从边缘位置为用户提供服务来减少延迟，还允许在多个相邻数据库区域之间进行顺序故障转移，提供了比简单的区域级故障转移更强大的恢复机制。
  4. 基础设施设计优先考虑简单性和重复性，而非严格的 DRY 原则，以降低复杂性和风险。 通过保持单个基础设施组件的简单性并在服务中重复使用它们，Authress 有意避免了复杂的相互依赖性，并降低了变更频率，从而最大限度地减少了错误的发生，并增强了稳定性。

💬 文章金句

  • 简单来说，我们的策略是利用 DNS 动态路由。这意味着请求会进入我们的 DNS，它会自动在我们正在使用的主区域和出现问题时的故障转移区域之间进行选择。
  • 我们不知道这是否是 AWS 基础设施服务之间的通信问题，或者是默认 Route 53 健康检查端点的问题，又或者是这些特定项与我们实际使用的代码之间的某种复杂交互问题。
  • 使用 CloudFront 给了我们一个高度可靠的 CDN，它将请求路由到本地可用的计算区域。从那里，我们可以与本地数据库交互。当该区域的数据库发生健康事件时，我们会自动故障转移，并检查第二个相邻区域的数据库。当第二个区域也出现问题时，我们再次对第三个区域执行此操作。
  • 一旦您的系统变得足够复杂，总会有东西损坏，您必须为此做好准备。检测和响应变得与预部署测试同样重要。
  • 我们已将基础设施拆分为各个服务，因此每个基础设施部分也都很简单。实际上，我们的基础设施并未严格遵循 DRY 原则，而是更多地采用重复性设计，这样做的好处在于能够避免通常因尝试减少代码重复而带来的复杂性。
