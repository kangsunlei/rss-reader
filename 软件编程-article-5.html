OpenAI 将单主 PostgreSQL 扩展至支持 ChatGPT 每秒数百万次查询

2/12/2026, 3:00:00 PM

📌 一句话摘要

OpenAI 通过利用广泛的地理分布式只读副本并卸载写密集型工作负载，成功将单主 PostgreSQL 架构扩展到支持 ChatGPT 每秒数百万次的查询。

📝 详细摘要

本文详细介绍了 OpenAI 在扩展 PostgreSQL 以支持超过 8 亿 ChatGPT 用户过程中的架构演进。尽管规模巨大，OpenAI 仍通过实施多层优化策略维持了单主实例。关键策略包括部署近 50 个地理分布式只读副本以保持低延迟读取，并将非关系型、写重型工作负载卸载到 Azure Cosmos DB 等分片系统中。技术深度解析涵盖了减少冗余写入的应用级调优、使用 PgBouncer 进行事务级连接池管理以及减轻 MVCC 开销。此外，文章还强调了缓存击穿风暴和 ORM 导致的查询效率低下等运维挑战，并引入了“级联复制”作为减轻主节点 WAL 流传输负担的方法。

💡 主要观点

  1. 在诉诸复杂的分布式分片之前，最大限度地发挥单主 PostgreSQL 的效用。 OpenAI 证明了通过积极的只读副本扩展和写入卸载，单主实例可以支持数百万 QPS，从而推迟了全分片关系型数据库带来的运维复杂性。
  2. PostgreSQL 与分布式 NoSQL 系统之间的战略性工作负载分离。 通过将 PostgreSQL 保留给需要强一致性的任务，并将大流量、可分片的写入迁移到 Azure Cosmos DB，OpenAI 维持了主数据库的稳定性和性能。
  3. 实施级联复制以克服主节点瓶颈。 为了解决将 WAL（预写日志）流传输到数十个副本所导致的 CPU 和网络开销，OpenAI 使用中间副本转发数据，从而节省了主节点资源。
  4. 严格的运维防护措施对于高并发数据库环境至关重要。 通过 PgBouncer 管理连接限制、强制执行事务超时以及优化 ORM 生成的查询，对于防止缓存击穿风暴等连锁故障至关重要。

💬 文章金句

  • 这一努力凸显了在写密集型工作负载需要额外的分布式解决方案之前，单主 PostgreSQL 实例可以被推向何种极限。
  • 由于版本更迭和清理（vacuum）成本，PostgreSQL 的 MVCC 模型在重度更新下会增加 CPU 和存储开销。
  • 每个数据库的优化方式都不同，需要适当的调优才能在大规模环境下运行。
  • OpenAI 正在尝试级联复制，即由中间副本向下游转发 WAL，在支持未来增长的同时减轻主节点的负载。
