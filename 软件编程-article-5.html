Agent 工程思考：从 ReAct 到 Agent Harness

7/22/2026, 12:00:00 PM

📌 一句话摘要

文章阐述 Agent 工程从 ReAct 的模型循环转向通过 State Schema、运行事实与 UI 边界构建可交互、可恢复、可控制的 Agent Harness，实现事实可追溯、可恢复的产品能力。

📝 详细摘要

文章深入分析了传统 ReAct 循环仅关注模型的 Thought‑Action‑Observation 交互，不足以满足真实产品对状态恢复、用户审批、子 Agent 管理等工程需求。作者提出 Agent Harness 概念，通过前后端共享的 State Schema 明确事实边界，将运行时事件（如 tool.approval_required、artifact.created）统一写入系统状态，确保刷新、重启、停止等操作后仍能恢复、可控制、可审计。文章详细阐述了 State Schema 的设计要点、UI 只能消费事实而不能自行补写事实、以及如何为子 Agent、artifact、pendingApproval 等关键事实提供明确归属，从而实现可靠的产品化 Agent 系统。

💡 主要观点

  1. Agent 不仅是模型+循环，而是需要系统层面的事实协议。 文章指出单纯的 ReAct Thought‑Action‑Observation 循环无法解决运行时恢复、审批、子 Agent 状态等工程问题，必须通过 State Schema 定义并持久化关键事实。
  2. State Schema 为 Agent 运行提供统一的事实边界。 通过定义 messages、activeRun、checkpoint、pendingApproval、artifactRef 等状态字段，系统能够在运行时统一生成并持久化事实，确保多端一致性和可追溯性。
  3. UI 只能消费事实，不能自行补写事实。 强调前端渲染应基于 runtime 写入的 state，避免在刷新或重启后失去审批状态等关键信息，从而保证系统行为的可靠性。
  4. Agent Harness 通过事件驱动的协议实现可交互、可恢复、可控制。 文章提出从 runtime 事件到 agent.state、agent.view、UI 的数据流，以及 control 命令的设计，使得用户操作、系统恢复和状态持久化形成闭环，满足产品级可靠性要求。

💬 文章金句

  • 大模型不是马，是大脑，而且是一颗刚刚觉醒的大脑。
  • ReAct 解释的是模型怎样一步步决定下一步。Harness 保证这些步骤在软件系统里发生过、能恢复、可控制、可审计。
  • 系统要记得发生过什么，才能让模型行为在产品里可被信任。
