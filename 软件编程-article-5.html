当 K8s 遇见 Ray：大模型时代 AI Workload 调度的通用范式

7/10/2026, 12:30:00 AM

📌 一句话摘要

本文深入剖析 K8s 与 Ray 在大模型时代 AI Workload 调度中的协同范式，从需求分析、核心设计到腾讯内部的联邦架构与跨层弹性调度实践，系统阐述了这一黄金组合的技术价值与落地经验。

📝 详细摘要

文章首先梳理了大模型时代 AI Infra 的技术栈演进，指出 K8s + Ray + PyTorch + vLLM 已成为业界黄金组合。通过多模态数据处理和强化学习（RLHF）两个典型场景，归纳出 AI Workload 的四大调度需求：异构资源、动态分配、高容错和原生 Single-Controller。随后展示 Ray 的核心 API 如何满足这些需求，并通过与 Spark、Flink、PyTorch 的对比，论证 Ray 在进程级调度上的灵活性。在协同调度层面，文章明确了 K8s 负责物理资源调度、Ray 负责应用层编排的分工，并介绍了 KubeRay Operator 作为桥梁。核心实践部分详细描述了腾讯 TEG 内部如何解决跨 K8s 联邦集群部署的挑战，从 Virtual Kubelet 架构演进到 KubeRay 联邦方案，并设计了跨层弹性调度与跨层自动化容灾机制，显著提升了大规模 RL 训练的稳定性。最后展望了更原生的联邦架构、通用分布式底座和统一的 Agentic RL Infra 方向。

💡 主要观点

  1. K8s + Ray + PyTorch + vLLM 构成大模型 AI 基础设施的黄金组合。 三者分别承担物理资源调度、应用层编排、训练框架和推理引擎，贯穿数据处理到在线推理全链路，业界 90% 以上 RL 训练框架构建于此组合。
  2. AI Workload 的核心调度需求是异构资源、动态分配、高容错和原生 Single-Controller。 多模态数据处理需要 CPU/GPU 异构算子的高效匹配与动态扩缩容；RLHF 要求多角色协同与细粒度容错，传统 SPMD 范式难以胜任，Ray 通过进程级调度全面满足。
  3. Ray 以进程级计算单元为调度核心，支持无范式通用分布式计算。 相比 Spark、Flink、PyTorch 绑定特定计算范式，Ray 提供灵活的 @ray.remote API，可在异构节点上动态创建/销毁 Worker 进程，实现细粒度容错与资源分配。
  4. 腾讯基于 KubeRay 联邦方案解决了跨 K8s 集群部署 Ray 的难题。 面对底层 CPU 与 GPU 集群分离的现状，团队从 Virtual Kubelet 架构演进到 KubeRay 联邦架构，实现了跨集群组网与全局 Autoscaling，兼顾开源兼容性与规模化生产需求。
  5. 跨层弹性调度与自动化容灾机制显著提升大规模 RL 训练稳定性。 通过动态扩缩容、Pod 重调度、任务重调度三级自动调优，以及故障感知-标记-替换的闭环容灾，将故障处理从人工介入转为自动恢复，解决了 RL 训练频繁因故障卡中断的问题。

💬 文章金句

  • 本质上，Ray 作为分布式计算引擎，其调度的核心对象是“进程级计算单元”。
  • K8s 负责将资源从统一资源池中分配给 Ray；而 Ray 负责将分配到的资源以更细粒度分配给上层任务。
  • 当 K8s 遇见 Ray，大模型时代的 AI Workload 调度正在开启新的篇章。
