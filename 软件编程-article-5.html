这被允许吗？模型上下文协议（MCP）中的身份验证与授权

1/21/2026, 3:00:00 PM

📌 一句话摘要

本文深入探讨了模型上下文协议（MCP）的身份验证与授权机制，重点关注远程服务器的 OAuth 2.1 集成。

📝 详细摘要

文章探讨了模型上下文协议（MCP）的安全架构，这是 AI 智能体与服务通信的标准。它区分了依赖操作系统级进程隔离和环境变量的“stdio”（本地）传输，以及利用 OAuth 2.1 的“可流式 HTTP”（远程）传输。针对远程服务器，作者详细介绍了复杂的握手过程，包括资源元数据发现（RFC 9728）、授权服务器发现（RFC 8414）以及动态客户端注册。该工作流确保 AI 智能体（客户端）获取有范围限制的访问令牌，以便安全地与 MCP 服务器交互。此外，本文还涵盖了下游授权（MCP 服务器如何向后端 API 进行身份验证）、PKCE 的重要性、令牌刷新策略，以及新兴扩展，如客户端 ID 元数据和用于智能体间通信的客户端凭据。

💡 主要观点

  1. MCP 身份验证依赖于传输方式，分别利用本地进程隔离或 OAuth 2.1。 本地（stdio）服务器继承父进程的安全上下文，而远程（HTTP）服务器实现完整的 OAuth 2.1 流程，以验证智能体的身份和权限。
  2. 远程 MCP 服务器使用标准化的发现机制，引导客户端访问受信任的授权服务器。 通过返回带有资源元数据（RFC 9728）的 401 Unauthorized 状态，服务器动态地告知客户端在哪里进行身份验证，从而实现灵活且去中心化的安全模型。
  3. 下游授权必须考虑最终用户的身份，而不仅仅是 MCP 服务器的身份。 作为中间件的 MCP 服务器应使用令牌交换（RFC 8693）等技术，确保后端服务能够根据原始请求者做出细粒度的访问决策。
  4. 协议正朝着更简单的注册方式和更细粒度的权限模型演进。 较新的规范正从复杂的动态客户端注册转向客户端 ID 元数据文档，并探索用于精细控制的丰富授权请求（RAR）。

💬 文章金句

  • MCP 服务器类似于 REST API：它提供对资源、数据和功能的标准化远程访问。
  • MCP 服务器代表 MCP 客户端执行操作，该信息应成为任何授权或身份验证决策的一部分。
  • MCP 服务器绝不能接受并非明确为该 MCP 服务器签发的任何令牌。
  • 与难以升级软件客户端的 API 不同，在 MCP 中，权限范围由资源服务器控制，并在初始的 WWW-Authenticate 响应头中提供。
  • 为了实现简单，MCP 核心规范有意对服务器间身份验证保持沉默。
