Uber 通过 CacheFront 改进实现每秒 1.5 亿次读取

10/6/2025, 2:00:00 PM

📌 一句话摘要

Uber 增强了其 CacheFront 架构，通过更强的 一致性实现了超过每秒 1.5 亿次的读取，通过新的写直达协议和更紧密的集成解决了过期数据问题...

📝 详细摘要

本文详细介绍了 Uber 对其 CacheFront 架构的重大升级。通过此次升级，系统能够处理超过每秒 1.5 亿次的读取，同时保证更强的数据一致性。先前的 CacheFront 设计虽然可扩展到每秒 4000 万次读取，但由于生存时间（TTL）和变更数据捕获（CDC）的缓存失效机制，存在最终一致性问题，导致过期读取和不一致，如“读己之写”和“负缓存”。新的实现引入了强大的写直达一致性协议。这涉及位于查询引擎和 Uber 的 Flux 流式系统（Flux streaming system）之间的去重层，其中每个 CacheFront 节点现在直接使用 Docstore 验证数据新鲜度。存储引擎层包含已删除行的墓碑标记（tombstone markers），用于标记已删除的行，以及 MySQL 会话分配的严格单调时间戳，确保在提交之前有效地识别和读取所有修改的键，从而防止即使在极端负载下也提供过期数据。事务完成后，存储引擎返回提交时间戳和受影响的行键，注册的回调函数会使用这些时间戳，立即将失效标记（invalidation markers）写入 Redis，从而使相应的缓存条目失效。Flux 继续通过跟踪 MySQL 二进制日志（binlogs）进行异步缓存填充。这种协同方法——结合直接查询引擎更新、立即失效标记和异步 Flux 跟踪——保持了强大的数据一致性，同时支持极高的读取吞吐量。这些改进还导致专用 API 的弃用、降低的运营复杂性、增强的可观察性以及缓存命中率的提高，超过 99.9% 并具有延长的 TTL。

💡 主要观点

  1. 先前的 CacheFront 设计在大规模应用中面临着严重的最终一致性问题。 依赖 TTL 和 CDC 进行失效导致过期读取、读己之写和负缓存不一致，这对于需要最新数据的延迟敏感服务来说是不可接受的。
  2. 一种新的写直达一致性协议可确保实时数据的新鲜度和完整性。 此协议将 Docstore 验证、单调时间戳和墓碑标记集成到存储引擎中，从而保证即使在高事务负载下也不会提供过期数据。
  3. 多种缓存填充和失效机制协同工作以实现强大的性能。 直接查询更新、通过回调立即进行 Redis 失效标记以及异步 Flux 二进制日志跟踪共同实现了强大的数据一致性、高缓存命中率和出色的读取吞吐量。

💬 文章金句

  • Uber 工程师已经更新了 CacheFront 架构，以每秒 1.5 亿次的读取提供服务，同时确保更强的一致性。
  • 使用 TTL 和 CDC 进行缓存失效的最终一致性在某些用例中成为限制因素。
  • 每个 CacheFront 节点现在都使用 Docstore 验证数据新鲜度，然后再提供响应。
  • 总之，这三种缓存填充机制：直接查询引擎更新、失效标记和 TTL 过期，以及 Flux 跟踪，协同工作以保持强大的数据一致性，同时支持极高的读取吞吐量。
