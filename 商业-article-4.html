产品经理如何把 Claude 变成自己的工作系统

5/20/2026, 2:09:00 PM

📌 一句话摘要

本文总结了一场深度播客内容，系统介绍了产品经理如何利用 Cowork、Claude Code、Skills、MCP 和 Dispatch 等工具，将 Claude 从聊天工具升级为可积累、可复用、可自我改进的工作系统。

📝 详细摘要

本文是对 Aakash Gupta 与 AI PM 专家 Pawel 播客内容的深度整理。文章核心观点是，产品经理不应将 Claude 仅当作聊天工具使用，而应将其构建为一个完整的工作操作系统。文章详细介绍了这套系统的核心组件：Cowork 用于处理真实文件和流程，Claude Code 用于与代码库交互，Skills 作为可复用的工作协议，MCP 作为连接外部服务的接口，以及 Dispatch 实现移动端远程任务派发。文章特别强调了知识库的自我改进机制，即通过 rules、hypotheses 和 rejected patterns 三类知识，让系统从每次交互中学习。作者认为，PM 的复利不在于收藏 prompt，而在于构建一套能吸收反馈、持续进化的系统。文章还讨论了生产自动化与个人自动化的边界，指出生产环境需要硬规则和代码级 guardrails。

💡 主要观点

  1. 产品经理应将 Claude 从聊天工具升级为完整的工作操作系统。 不应只停留在 chat 界面，而应使用 Cowork、Claude Code、Dispatch 等工具，让 AI 处理真实文件、代码库和连续工作流，实现从对话到系统执行的转变。
  2. Skills 是最高 ROI 的投资，可实现工作流程的复用和迭代。 将高频任务拆解为可复用的 Skills（工作协议），每次执行后根据反馈自动优化，避免每次都从零开始提示，形成工作方法的复利效应。
  3. 知识库需要自我改进机制，从错误中学习。 将知识分为已确认的 rules、待验证的 hypotheses 和被否定的 rejected patterns，通过三行提示词（review rules、apply rules、update knowledge）让系统持续进化。
  4. 生产自动化需要硬规则，不能完全依赖自主 agent。 个人工作流可让 agent 探索，但生产环境中的权限、隐私、重试等关键环节必须通过代码和 guardrails 固化，将可确定的步骤从 agent 决策中剥离。

💬 文章金句

  • 最大的错误，是每次都从零开始提示它，没有让系统从错误中学习。
  • CLAUDE.md 应该负责路由，不是堆知识。
  • 已经没有什么好理由，只通过普通网页聊天框和 Claude 对话了。
  • PM 的复利不在 prompt 收藏夹里，而在一套会吸收反馈的工作系统里。
  • 在生产环境里，凡是不需要自主的部分，就不该交给自主 agent。
