Anthropic 团队是怎么协作和运转的？

5/28/2026, 2:19:00 PM

📌 一句话摘要

本文深入拆解了 Anthropic 团队围绕 AI Coding 工具 Claude Code 构建的内部协作与工程流程，揭示了其高效运转的核心并非“低流程”，而是将传统流程改造为可执行、可审查、可回滚、可验证的系统。

📝 详细摘要

文章基于 Anthropic 多位产品、设计、研发负责人的公开分享、官方文档及工程案例，系统性地分析了其团队协作模式。核心观点是，Anthropic 的高效并非源于流程简化，而是将“开会、写文档、来回交接”等传统环节，转化为可运行代码、可审阅 diff、可重复 evals、可触发的 GitHub workflow 及可被 AI 读取的项目上下文。文章从协作、工程、产品、设计四个维度展开：协作上，构建者即用户，反馈链路极短，跨职能 pod 是基本组织单位；工程上，流程从“写代码”转变为“决定做什么、怎么验证”，强调计划先行、分层授权、AI 先审人再审的双层 Code Review 结构；产品上，采用“能力触发型剧本”而非固定路线图，通过失败模式和发布级别字段管理不确定性；设计上，设计师可直接用 Claude Code 修改代码，将视觉调整和文案变更的等待时间压缩至最低。最后，文章指出 Anthropic 的模式依赖于其特殊结构（控制底层模型、构建者即用户等），其他团队不应照搬“低流程”的表象，而应学习其将流程系统化的方法论。

💡 主要观点

  1. Anthropic 的高效源于将传统流程系统化，而非流程简化。 文章指出，Anthropic 并非没有流程，而是将会议、文档、交接等环节转化为可被 AI 工具读取和执行的代码、diff、evals 和 workflow，从而大幅压缩了人与人之间的等待时间。
  2. 构建者即用户（Builder = User）是反馈循环极短的核心原因。 当工程师、设计师和产品经理本身就是产品的目标用户时，从发现问题到提出解决方案再到验证，几乎不需要经过需求翻译和传递的环节，形成了极短的信号链路。
  3. 工程流程的核心是从“写代码”转向“做判断”。 Claude Code 承担了代码生成、测试、PR 创建等执行工作，将工程师的注意力解放出来，专注于计划制定、方案评审、风险判断和最终决策等更高价值的工作。
  4. 产品策略采用“能力触发型剧本”，而非固定路线图。 面对快速变化的 AI 模型能力，Anthropic 准备一组候选打法，当新能力或用户反馈出现时快速选择执行，并通过“失败模式”和“发布级别”等字段来结构化地管理产品不确定性。
  5. 设计师可直接修改代码，消除了设计与工程之间的交接成本。 设计师利用 Claude Code 直接操作代码库进行视觉调整和文案修改，省去了需求传递、异步审查和来回反馈的等待时间，但架构和复杂逻辑仍由工程师把关。

💬 文章金句

  • Anthropic 不是没有流程，而是把传统流程里大量'开会、写文档、来回交接、人肉传话'的部分，挪进了可运行代码、可审阅 diff、可重复 evals、可触发的 GitHub workflow，以及可被 AI 读取的项目上下文里。
  • 会议没有消失，只是被压缩了；PRD 没有消失，只是变薄了，但验收变厚了；Code review 也没有消失，而是变成了 AI 先做、人再做的双层结构。
  • 当 AI 把'写代码'的速度提上去之后，真正的瓶颈就从'怎么写'转到了'决定做什么、怎么验证、怎么合并、怎么发布'。
  • AI 产品的机会，不只是'模型出来以后在外面包一层界面'，而是产品、研究、工程要一起判断模型能力会打开什么新动作。
  • 真正值得复制的，不是'低流程'，而是这个动作：把流程改造成可执行、可审查、可回滚、可验证的系统。
