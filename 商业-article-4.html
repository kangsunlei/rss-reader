构建企业级 Agentic AI 的语义层

9/8/2026, 12:26:00 PM

📌 一句话摘要

本文提出企业级 Agentic AI 的核心瓶颈在于缺失受治理的语义层，主张通过构建语义层与上下文层，将业务逻辑从提示词中解耦，实现 AI 驱动的数据分析在准确性、一致性与安全性上的规模化扩展。

📝 详细摘要

文章指出，LLM 作为概率推理引擎缺乏企业内部的业务定义，导致 Agent 在生产环境中出现指标漂移和幻觉。作者区分了语义层（受治理的词汇表）与上下文层（包含元数据、权限、指引的更广范围），并强调 MCP 仅是传输协议而非含义本身。文中详细对比了 Google Cloud、Microsoft、AWS、Databricks 和 Snowflake 在构建语义层上的不同技术路径，并提供了一个基于 YAML 的零售营收语义模型示例。最终建议采用「Agent $\rightarrow$ MCP $\rightarrow$ 语义层 $\rightarrow$ 数据仓库」的架构，禁止 Agent 直接访问原始表，以确保企业 AI 的可信度与安全性。

💡 主要观点

  1. LLM 的概率推理特性与企业级业务逻辑之间存在天然断层。 LLM 不了解企业的私有定义（如净营收的计算方式），直接将原始 Schema 交给模型会导致其自信地编造业务逻辑，产生指标漂移。
  2. 语义层与上下文层是 Agentic AI 的「心脏」，提供唯一事实源。 语义层定义指标和维度，上下文层则涵盖技术、语义、运营、关系、信任及 Agent 指引六类元数据，共同为 Agent 提供受治理的业务含义。
  3. 构建语义层能显著提升 AI 应用的准确率、安全性与成本可控性。 通过语义层查询可将准确率提升数倍，且能原生集成 RBAC 权限控制，避免在提示词中重复定义逻辑，降低 Token 成本。
  4. 主流云平台已提供多样化的语义层实现方案。 从 Google 的 Knowledge Catalog 到 Snowflake 的 Semantic Views，各平台通过将业务指标与物理表解耦，使模型能够通过标准接口（如 MCP）触达受治理的数据。
  5. 理想的架构应将语义层作为 Agent 触达数据的唯一受控入口。 Agent 不应获得原始仓库访问权，而应通过 MCP 调用语义层工具，确保所有查询均经过业务逻辑过滤和权限校验。

💬 文章金句

  • 如果 LLM 是 Agent 系统的大脑，语义层就是心脏。
  • 没有受治理语义的 AI 无法扩展。
  • MCP 是管道，不是含义。
  • 大模型会持续变得更便宜更聪明。但企业持久的优势是语义层
