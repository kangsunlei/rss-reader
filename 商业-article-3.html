Day 21/60: 短链接服务详解 — 7 个字符如何支撑 3650 亿条链接？

10/18/2026, 2:12:14 AM

📌 一句话摘要

短链接服务通过将分布式 ID（雪花算法）转换为 Base62 编码，实现了在 7 个字符内唯一标识高达 3.5 万亿条记录，并利用缓存和 301 重定向优化读效率，同时避免哈希碰撞带来的重复生成问题。

📝 详细摘要

本推文详细介绍了短链接服务的核心工作原理，包括 API 设计（生成与重定向）、编码方式（Base62），以及高并发下的存储和安全策略。通过使用唯一递增 ID 结合 Base62 转换，能够高效、无冲突地生成短链，同时采用 Redis 缓存和 301 永久重定向提高响应速度。此外，还分析了自定义短码碰撞处理、可预测性风险，并通过具体数值估算展示了 7 个字符能支持 10 年的超大规模链接存储。

💡 主要观点

  1. Base62 编码与唯一性 使用 Base62（0-9， a-z， A-Z）将分布式 ID 转换为 7 个字符的短链，每个字符可取 62 种状态，因此 7 位共支持 62^7 ≈ 3.5 万亿种组合——远超 10 年内的 3650 亿条记录需求。相比哈希取模，这种方法完全避免了碰撞，无需重试或布隆过滤器。
  2. 读写优化与缓存 由于读比写多 10 倍，短链 → 长链映射被缓存在 Redis 中，热点链接几乎不需要访问数据库。同时，301 永久重定向允许浏览器本地缓存，进一步减轻服务器压力。写请求则通过分布式 ID 生成器（如雪花算法）确保顺序递增，然后存储在高性能 NoSQL 或 SQL 数据库中。
  3. 安全性与碰撞处理 虽然 ID 递增易于预测，导致短链可被枚举（安全风险），但可通过加盐或非连续分配 ID 缓解。对于自定义短码冲突，当用户指定特定字符串与系统生成冲突时，采用“先到先得”原则，即先提交的（无论是系统还是用户）优先拥有该短链。这通过事务锁或乐观锁来保证。
