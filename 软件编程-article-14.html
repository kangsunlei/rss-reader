WebAssembly 在企业应用：安全、便携与商业化准备

12/3/2025, 1:28:00 PM

📌 一句话摘要

本文探讨 WebAssembly 在企业中的应用，重点介绍其在 JVM 中通过 Chicory 实现的安全、高效集成及优化方案。

📝 详细摘要

本文深入探讨了 WebAssembly (Wasm) 对于企业应用的变革潜力，尤其是在与广泛应用的 Java 虚拟机 (JVM) 集成时。文章强调了 Wasm 作为浏览器中一种快速、安全和便携的二进制格式的起源，并将其优势扩展到服务器端执行。核心论点是，相较于使用外部函数接口(FFI)可能损害 JVM 的安全性、可移植性和可观察性，直接在 JVM 中使用 Chicory（Red Hat 首席工程师 Andrea Peruffo 维护的纯 Java Wasm 运行时）运行 Wasm 更具优势。通过 JRuby (Ruby 解析器)、Trino (Python 用户自定义函数)、Debezium (Go SMTs) 和 SQLite 等详细案例，作者展示了 Chicory 的提前编译 (AOT) 编译器，结合 wasi-vfs 和 Wizer 等工具，以及优化的内存管理（预分配、延迟字段访问）如何显著提高性能并解决常见的集成挑战。结论强调了 Wasm 适用于安全、多语言、高性能插件系统和具有稳定 API 的受限问题域，并将其定位为未来企业架构的关键技术。

💡 主要观点

  1. WebAssembly 为服务器端企业应用程序提供了显著优势，尤其是在无缝集成到 JVM 中而无需依赖存在潜在问题的外部函数接口时。 Wasm 提供了一个安全、便携和多语言的执行环境。将其直接集成到 JVM 中可以保持安全边界、可观察性，并避免与本地库相关的分发和运行时问题。
  2. Chicory 的提前编译 (AOT) 编译器通过将 Wasm 字节码转换为原生 Java 字节码，显著提高了 WebAssembly 在 JVM 上的性能。 这种转换使 Wasm 模块能够作为纯 Java 代码运行，利用 JVM 的 JIT 编译和其他优化，与基于解释器的执行相比，实现了 10 倍到 40 倍的加速。
  3. 解决 Wasm 的启动和运行时挑战需要专门的工具和技术，如嵌入式文件系统、预初始化和优化的内存管理。 wasi-vfs（用于嵌入静态文件）和 Wizer（用于预热模块）等工具显著减少了启动延迟，而预分配策略可防止代价高昂的增量内存增长操作。
  4. WebAssembly 促进了基于 JVM 的应用程序中高效的多语言插件系统和优化的数据访问模式。 它使开发人员能够使用各种语言（Go、Python、C）编写插件，并将它们与 Java 应用程序集成，从而允许延迟、直接访问主机内存，从而避免了昂贵的序列化/反序列化周期。

💬 文章金句

  • WebAssembly 旨在嵌入到系统中，它将在无法逃脱的安全沙箱中执行，这意味着在那里运行的代码将完全由外部系统控制。
  • 在另一种语言中执行 WebAssembly 是一种超能力，这就是为什么今天我们将专注于讨论在 Java 中运行 WebAssembly，这要归功于 Chicory。
  • 如果必须随 Java 代码一起提供本机库，则必须为目标架构和操作系统对其进行编译。这是一个问题，因为您始终需要在将要运行的目标上进行编译。相反，使用 WebAssembly，这是完全分离的，您可以只编译一次到 WebAssembly 并提供您的 WebAssembly，它将在任何不同的平台上未经修改地运行。
  • 如果您考虑 WebAssembly 字节码并查看它，它与 Java 字节码非常相似。差别不大。在两者之间实现一个翻译器非常容易，并且实际上可以使事情运行得更快，因为它们是纯 Java 代码，而无需解释器逐条指令地执行您的代码。
  • 当您有一个非常稳定的 C、C++、Rust，即底层 API，它定义得非常好，或者当您有一个应用程序二进制接口，它非常稳定时，WebAssembly 工作得非常好，例如用于单个消息转换或用于排队系统，因此在您的应用程序和 WebAssembly 模块应该执行的操作之间有一个非常清晰的边界。
