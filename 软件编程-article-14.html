Slack 的蜂窝架构迁移

5/2/2025, 12:00:00 AM

📌 一句话摘要

Slack 通过迁移到蜂窝架构，实现了可用区级别的故障隔离和快速流量转移，从而提高了整体可用性。

📝 详细摘要

本文介绍了 Slack 从单体架构到蜂窝架构的迁移过程，旨在提高可用性，并实现快速隔离故障区域的能力。在遇到 Amazon U.S.-east-1 可用区网络问题后，Slack 意识到其现有架构无法有效应对单可用区故障。文章详细描述了 Slack 之前的架构，其中所有重要工作都在 U.S.-east-1 区域内进行，服务之间跨可用区通信频繁。为了解决这个问题，Slack 采用了蜂窝架构，将每个可用区视为一个独立的单元，并通过 Envoy 和 xDS 的流量权重功能进行流量控制。文章还讨论了在迁移过程中遇到的挑战和决策，例如如何处理 Vitess 等有状态服务和强一致性数据存储，以及 Memcache 从全局迁移到 per-cell Memcache + 全局 Memcache layer 的过程。最终，Slack 成功地实现了在五分钟内从可用区转移流量，且不影响用户体验的目标。文章后半部分重点阐述了项目成功的关键因素。

💡 主要观点

  1. 蜂窝架构提高了 Slack 的可用性和容错能力。 通过将每个可用区视为独立的单元，可以快速隔离故障区域，避免单点故障影响整个系统。
  2. 流量控制是实现蜂窝架构的关键。 使用 Envoy 和 xDS 可以实现细粒度的流量控制，从而在不影响用户体验的情况下，快速从可用区转移流量。
  3. 处理 Vitess 等强一致性数据存储是迁移到蜂窝架构的关键挑战，需要精细的 failover 机制。 需要仔细考虑如何处理有状态服务和强一致性数据存储，例如 Vitess。数据一致性和可用性是关键。
  4. 增量式迁移和灰度发布是保障迁移过程平滑的关键策略。 通过小流量的逐步迁移，可以及时发现和解决问题，避免对用户造成影响。

💬 文章金句

  • A cell is a set of services in an AZ. That set may be drained or removed from service as a unit.
  • 一个 Cell 是 AZ 中的一组服务。该组服务可以作为一个单元被下线或停止服务。
  • Remove as much traffic as possible from an AZ within five minutes.
  • 在五分钟内从一个 AZ 移除尽可能多的流量。
  • Drains must not result in user visible errors.
  • 流量下线不应导致用户可见的错误。
  • Drains and undrains must be incremental.
  • 流量下线和上线必须是增量的。
