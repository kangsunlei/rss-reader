205 个测试全绿，打开是 3 个 500：我用 Workbuddy 做 UI 自动化测试，翻了三次车

10/20/2026, 11:58:00 PM

📌 一句话摘要

作者分享使用 Workbuddy (AI Agent) 配合 Playwright 进行 UI 自动化测试的踩坑经历，揭示了「测试全绿但线上崩溃」的陷阱，并总结了一套三层排查路径。

📝 详细摘要

本文通过一次真实的回归测试实践，探讨了 AI 驱动的 UI 自动化测试中容易被忽视的风险。作者在面对「205 个测试全绿但页面 500 报错」的矛盾现象时，分析出「模板新、进程旧」导致的环境不一致问题；在验收环节中，反思了「用想象代替事实」的误判习惯。随后，作者利用 Playwright 抓取截图、文本和页面高度，发现了数据口径断层、内部标识外露等深层 UI 问题。最后，作者将这些经验沉淀为一套可复用的三层排查路径（进程重启 $ ightarrow$ 路由检查 $ ightarrow$ 字段口径），旨在提醒开发者不要过度依赖测试结果，而应关注真实的渲染输出。

💡 主要观点

  1. 警惕「测试全绿」与「线上崩溃」的共存现象 测试环境加载的是新代码，而线上服务进程未重启仍运行旧代码，导致模板要求的新变量在旧路由中缺失，产生 500 错误。结论是：在报告完成前，必须对实际运行的服务进行状态码验证。
  2. 验收 UI 必须「看结果」而非「猜实现」 开发者习惯性地通过检查代码中是否有特定标签（如 .modal）来判断功能是否存在，但实际实现可能采用自定义定位层。正确的验收姿势是观察渲染后的视觉事实和交互结果。
  3. 利用 AI Agent 结合多维数据进行 UI 审计 单纯的测试脚本无法发现「合理但错误」的数据。通过结合全页截图、页面高度（scrollHeight）和 innerText 文本分析，可以发现如页面过长、数据口径错误（0 与未采集混淆）等逻辑缺陷。
  4. 构建标准化的三层排查路径以降低调试成本 将常见错误分层：第一层检查进程状态（重启服务），第二层检查路由挂载（curl 状态码），第三层检查字段口径（读写 Key 一致性）。按此顺序排查可快速排除环境干扰，定位业务逻辑问题。

💬 文章金句

  • 测试是对的，用的是新的；线上是旧的。两件事都真，合起来就是"打不开"。
  • 猜实现，一定会错；看结果，才作数。
  • 假数最危险的地方不是离谱，是合理。
  • 工具不替你负责，它只帮你把"你以为"变成"你看见"。
