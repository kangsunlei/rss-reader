借鉴 Kotlin/Android 经验，在 SwiftUI 中构建可扩展的 iOS 应用架构

2/26/2026, 9:00:00 AM

📌 一句话摘要

本文展示了如何通过将经过验证的 Android 架构模式（如显式状态、基于 Action 的 ViewModel 和响应式 Repository）适配到 SwiftUI 框架，来构建可扩展的 iOS 应用程序。

📝 详细摘要

本文探讨了 iOS 开发者面临的一个共同挑战：难以将简单的 SwiftUI 示例扩展为复杂的生产级应用。作者从 Android 生态系统的结构化方法中汲取灵感，倡导一种与平台无关的架构观。核心建议包括：使用显式枚举替换碎片化的状态属性，以消除不可能的 UI 状态；通过将所有变更汇聚到单个 action 方法中来采用单向数据流（UDF）。这种集中化增强了可测试性并简化了调试。此外，作者引入了“Screen 与 Content”分离的概念，将 ViewModel 的所有权与 UI 渲染解耦，从而显著提高了 Xcode Previews 的可靠性。该架构通过涉及响应式 Repository 的多层数据流得以完善，Repository 作为单一数据源，确保数据更新能自动传播到所有观察中的屏幕，从而解决了大规模应用中数据过期的问题。

💡 主要观点

  1. 使用显式状态枚举在类型层面上消除不可能的 UI 状态。 通过将多个独立的 @Published 布尔值替换为单个 Loadable 枚举，开发者可以确保 UI 不会同时处于“加载中”和“错误”等矛盾状态，利用 Swift 编译器来强制执行单一数据源。
  2. 实现基于 Action 的 ViewModel 以集中变更并启用单向数据流。 将所有用户意图汇聚到单个 perform 方法中，可以创建一个清晰的公共契约。这种方法通过提供可追溯的状态变化序列，促进了集中化日志记录、通过单一断点简化调试，并使单元测试更具可读性。
  3. 将 Screen 逻辑与 Content 渲染分离，以增强可重用性和 Xcode Previews。 将持有 ViewModel 的组件（Screen）与渲染 UI 的组件（Content）解耦，可以实现“纯粹”的 UI 视图。这使得为预览注入 Mock 数据以及在不同功能间重用布局变得非常简单。
  4. 采用响应式 Repository 模式以维护单一数据源。 当 Repository 持有数据并通过 Publisher 暴露数据时，对底层数据的任何更新都会自动传播到所有观察中的 ViewModel。这消除了手动回调或通知的需求，从而保持不同屏幕间的同步。

💬 文章金句

  • 优秀的架构是与平台无关的。使 Android 应用易于维护的原则在 iOS 上同样适用。
  • 密封类（Sealed Class）就是契约。如果一个 Action 没有在那里声明，ViewModel 就无法执行它。
  • 视图持有它们的 ViewModel，这破坏了预览并限制了可重用性。
  • ViewModel 不持有数据。它们观察数据并将其暴露给视图。当它们需要更改某些内容时，会请求 Repository。
  • 如果没有它（单一数据源），你就是在几十个屏幕上玩处理过期数据的“打地鼠”游戏。
