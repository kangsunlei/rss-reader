PHP Swoole 协程模型详解：协程与线程/进程、调度、常驻内存及与 Go goroutine 的异同

📌 一句话摘要

本文深度解析了 Swoole 协程模型，对比了其与线程、进程及 Go goroutine 的区别，并介绍了协作式调度、常驻内存的陷阱及解决方案。

📝 详细摘要

文章详细分析了 PHP 传统 FPM 模型的局限性，并介绍了 Swoole 如何通过协程（Coroutine）解决并发问题。通过对比进程、线程与协程在调度方式、切换成本和内存隔离上的差异，阐述了“协作式调度”的本质。作者特别强调了在常驻内存模式下的常见坑，如全局/静态变量导致的请求污染、内存泄漏、数据库连接失效等，并提供了使用 Co::getContext() 协程上下文、连接池以及 WaitGroup 机制等详细的实战代码示例和建议。

💡 主要观点

  1. PHP 传统 FPM 模型的瓶颈 FPM 每一个请求对应一个进程，并发能力受限于进程数，且每个请求结束都会释放内存和连接，无法实现连接的高效复用。
  2. 协程的协作式调度的本质 Swoole 协程是用户态的轻量级执行流，由程序自己调度，只有在遇到 IO 或显式 yield 时才会让出控制权，避免了内核态切换的开销。
  3. 常驻内存模式下的核心陷阱 在 Swoole 环境中，进程不结束，使用 static 或全局变量存储请求数据会导致不同请求间的数据污染；未清理的全局数组或引用会导致内存泄漏并引发 OOM。
  4. 针对协程问题的工程化解决方案 通过 Co::getContext() 使用协程上下文实现请求级隔离；利用连接池维护数据库连接状态；并使用 WaitGroup 管理子协程生命周期。

💬 文章金句

  • 进程是资源分配的最小单位，线程是 CPU 调度的最小单位；协程不是操作系统概念，而是用户态轻量级执行流。
  • 协程上下文是替代「全局变量存请求数据」的正确姿势。
