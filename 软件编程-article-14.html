搭 Agent 系统，是搞“人海战术”，还是给团队“瘦身”？Meta 和 A 社给出了完全不同的答案

10/23/2026, 7:30:00 AM

📌 一句话摘要

文章对比了 Meta 和 Anthropic 在 Agent 系统架构上的不同策略：Meta 通过瘦编排器隔离领域知识解决规则串用问题，Anthropic 则合并子 Agent 以减少交接损耗，两者均基于实际失败案例调整架构，为团队提供数据驱动的优化思路。

📝 详细摘要

本文探讨了构建 AI Agent 系统时的架构权衡，以 Meta 和 Anthropic 的实践为例。Meta 最初让一个 Agent 处理推荐系统的数据列接入，但进入生产环境后出现规则混用问题，成功率从演示时的正常降至仅 10%至 20%。为此，Meta 拆分架构为瘦编排器（负责流程控制和可靠性检查）和 14 个专业 Agent（隔离领域知识），新方案在无需逐任务手写提示词的情况下成功率约 70%，线上回滚率约 0.2%。Anthropic 则发现多 Agent 系统存在交接损耗，类似“传话游戏”，导致用户条件丢失和延迟增加；一家客户将多 Agent 流程合并回主循环后，运行时间缩短约一半。Anthropic 建议按需加载知识（通过 Skills 和工具），保留独立验证、并行处理等场景的子 Agent。文章强调，团队应基于生产日志中的失败记录（如规则串用或交接遗漏）来调整架构，先挑选 10 个真实任务进行评估，再逐步优化，避免盲目添加或删除 Agent。

💡 主要观点

  1. Meta 通过瘦编排器隔离领域知识，解决单 Agent 规则串用问题 Meta 最初让一个 Agent 处理多数据源规则，生产环境失败率高达 80%至 90%。拆分后，编排器负责流程控制，14 个专业 Agent 隔离上下文，成功率提升至约 70%，且约三分之二的系统改动无需大量人工修改。
  2. Anthropic 合并子 Agent 以减少交接损耗，提升响应速度 Anthropic 发现多 Agent 系统存在“传话游戏”问题，用户条件在交接中丢失。合并回主循环后，运行时间缩短约一半，但需通过按需加载 Skills 和工具来管理知识，避免规则再次混用。
  3. 架构调整应基于数据驱动的失败记录，而非直觉 文章建议团队先分析生产日志，识别具体失败案例（如规则串用或交接遗漏），再针对性调整架构。例如，先保留原方案结果，只动一个边界重新测试，避免平均分改善但关键任务退化。
  4. Agent 架构需平衡隔离与效率，无一刀切方案 Meta 的隔离方案适合领域知识复杂的场景，Anthropic 的合并方案适合用户上下文连续的场景。独立验证、并行处理等仍需保留子 Agent，团队应根据具体需求选择策略。

💬 文章金句

  • 演示时有效，进了生产环境却开始出错。
  • 后一个 Agent 拿到的是前一个留下的摘要，细节和判断理由可能已经没了。
  • 下次有人提议“再加一个专家 Agent”，先问他要解决哪条失败记录。
  • 平均分更好看，用户要的答案反而丢了。
