Redis key 消失之谜

10/29/2025, 12:01:00 PM

📌 一句话摘要

文章详细分析了生产环境中 Redis key 消失的问题，定位到是由于请求积压导致内存飙升触发淘汰，并提供了从紧急修复到根本解决的方案。

📝 详细摘要

本文从生产环境业务服务报错 Redis key 获取不到的现象入手，通过监控日志、Redis 指标和抓包分析，逐步排除了 key 正常过期、内存告警失效等初步怀疑。最终定位到问题根源在于业务集中请求 Redis（特别是通过 Pipeline 方式），导致客户端输出缓冲区（client-output-buffer）数据量激增，进而使 Redis 实例的内存使用量超出`maxmemory`限制，触发`volatile-lru`淘汰策略驱逐了大量 key。文章详细阐述了 Redis 内存构成，并强调了客户端输出缓冲区积压在内存管理中的重要性。针对此问题，提供了包括临时扩大内存、限制缓冲区大小、业务限流削峰及增加 MySQL 兜底机制等紧急修复措施，以及业务逻辑优化、打散请求等根本性解决方案。

💡 主要观点

  1. Redis 内存限制不仅包含业务数据，还包括客户端缓冲区，积压可能导致淘汰。 Redis 的`maxmemory`参数限制的是实例总内存，其中包括客户端输入/输出缓冲区。当大量请求导致客户端输出缓冲区积压时，会迅速消耗内存，进而触发淘汰策略。
  2. 大量集中请求（特别是 Pipeline）可能导致客户端输出缓冲区激增，进而引发内存问题。 即使是 GET 请求，通过 Pipeline 批量执行时，如果结果不能及时发送，其回包会暂存在客户端输出缓冲区，导致`client_longest_output_list`指标飙升，耗尽内存。
  3. 生产环境问题解决应结合紧急止损与根本优化，并增加兜底机制提升系统韧性。 针对此类内存溢出导致的数据丢失问题，应采取临时扩容、限流等紧急措施，同时从业务层面优化请求模式，并建立数据回源的兜底机制，确保业务连续性。

💬 文章金句

  • Redis 的 maxmemory 参数限制的是 Redis 实例可以使用的最大内存，这部分内存主要包括以下几个部分：业务数据占用的内存、客户端连接的输入/输出缓冲区、复制积压缓冲区、AOF 缓冲区以及其他一些内部开销。
  • 这里有个经常被忽略的场景，就是 Redis 其实支持 pipeline 命令执行方式的，简单来说就是 Redis 支持一次性接收一个客户端的多个指令，具体执行过程中会把这些指令的结果不断暂存，然后在后续流程中集中回包，如果这时候不能及时地把数据通过网络发出去，就有可能出现 reply 链表长度激增的现象，进而导致客户端占用内存激增，这正是我们本次遇到的场景。
  • 本次问题是由于业务集中请求 Redis，导致缓存积压内存增长达到最大内存限制，触发 Redis 淘汰策略对 key 进行驱逐。
  • 同时，对于 Redis 淘汰策略，对于数据比较重要的集群，可以考虑使用不驱逐的方式。合理设置 TTL 保留时间，把 Redis 的内存使用率保持在安全的区域。
