OpenViking × LLM-Wiki：让团队文档不再“各说各话”

9/23/2026, 10:06:00 AM

📌 一句话摘要

OpenViking 结合 Karpathy 提出的 LLM-Wiki 范式，通过资料导入、Compile 编译、Skill 定义与 Agent 检索，把散落文档变成可追溯、可复用的团队知识网络。

📝 详细摘要

文章以「客户问未保价怎么赔、团队三人给出三个答案、Agent 也无法判断适用口径」的真实场景切入，指出团队缺的不是更多文档，而是围绕客户、产品、规则和流程组织的 Wiki 网络。作者引用 Andrej Karpathy 于 2026 年 4 月提出的 LLM-Wiki 范式：在原始资料与用户之间增加一层由 LLM 维护的持久化 Markdown Wiki，新资料进入时同步更新实体页、概念页与对比页，并标记新旧材料之间的矛盾。随后给出基于 OpenViking 的零代码落地路径：先用 Connector 把本地文件、Git 仓库、飞书文档等导入同一处；再用 Compile 功能配合自定义或官方 llm-wiki Skill，把原始数据编译成带出处、相互链接、有导航入口的 Wiki；团队成员可在控制台查阅、编辑、补齐条件；最后通过 MCP、CLI、API、SDK 把 OpenViking 接入 Codex 等 Agent，并用检索 Skill 规定「何时查、去哪查、怎么核实、如何回答」。文章强调检索采用层级式渐进读取以节省 Token，并指出换用日报、知识蒸馏、知识图谱等 Skill 可让同一批知识服务不同场景。

💡 主要观点

  1. 团队知识的核心痛点不是文档缺失，而是适用关系没有理清 赔付案例中三个人都能翻出正式材料却给出不同答案，Agent 虽能检索并给出引用，仍无法判断哪条口径适用于眼前客户，说明问题出在客户、产品、规则之间的关联缺失，而非资料数量不足。
  2. LLM-Wiki 在原始资料与用户之间增加一层由 LLM 维护的持久化 Wiki 该范式由 Andrej Karpathy 于 2026 年 4 月提出，新资料进入后需同步更新实体页、概念页、对比页，补充交叉引用并标记新旧材料矛盾，使新证据更新的是同一套知识而非另生成一份互不相认的答案。
  3. OpenViking 用 Connector + Compile + Skill 三步把散落资料编译为团队 Wiki Connector 支持本地上传、链接接入 Git 仓库、飞书文档同步及 add-resource 定时同步；Compile 通过 --from、--to、--skill、--instruction 四个参数指定读取来源、产物目录、生成规则与补充说明；Skill 则把「怎样才算一份好 Wiki」写成可复用规则。
  4. 编译 Skill 与检索 Skill 分工明确，前者生成知识、后者规定查阅方法 编译 Skill 决定如何处理资料、生成什么内容；检索 Skill 则向 Agent 交代何时使用、去哪查、怎么沿「客户→服务→产品→规则」核实适用关系、如何给出结论与来源，依据不足或口径冲突时明确说明而不补猜。
  5. Wiki 的价值在于把一次性搜索与讨论沉淀为可复用的共同知识 一线看到的不再是三份互相打架的文档，而是包含确认口径、适用产品地区时段与例外、历史版本与变更关系、未解决冲突及每句话来源的可展开知识链；确认结果回到同一套知识，下一位同事不必重新找三个人。

💬 文章金句

  • 团队沉淀了很多文档和知识库，AI 办公工具也有，但资料都找到了，适用关系却还没有理清。
  • 把散落的文档编织成一张可以按需查找、关联和更新的业务知识网络，沉淀成可以继续生长的团队知识。
  • 它不只是让 Agent"搜得更快"，而是把一次次搜索、讨论和确认，变成团队下一次可以直接复用的共同知识。
