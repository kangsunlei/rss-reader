📝 详细摘要

本文深入且实践性地演练了如何重构现有的混乱 CSS 代码库，以有效地利用 CSS Cascade Layers。作者超越了理论解释，使用真实的 Discord 机器人网站作为案例研究，展示了迁移遗留项目所涉及的实际挑战和解决方案。涵盖的关键方面包括规划结构化的层架构（重置、基础、布局、组件、实用程序、动画），理解 `!important` 声明对层优先级的重要影响，将有问题的 ID 选择器重构为更易于维护的类选择器，并针对媒体查询在层结构中的放置位置提供明智的建议。文章详细地描述了将现有样式迁移到其适当层的过程，将徽标、导航等特定元素转换为可复用的组件，并清理冗余代码。它强调保持模块化、可预测性和长期可维护性，为每个重构步骤提供清晰的代码示例和理由。

💡 主要观点

  1. 在遗留项目中集成 CSS Cascade Layers 需要周密的规划和结构化的重构。 不鼓励将所有样式直接移动到单个“遗留”层中；一个经过深思熟虑的层结构（例如，重置、基础、布局、组件、实用程序、动画）对于长期的模块化和可维护性至关重要。
  2. `!important` 颠倒了层叠优先级，增加了样式解析的复杂度。 当使用 `!important` 时，在先声明的层中的样式优先级会高于后续层中的普通样式。因此，在重构过程中需要仔细考虑，避免样式被意外覆盖。
  3. 将 ID 选择器重构为类选择器可以显著提高可维护性并降低特异性。 将高特异性的 ID 选择器转换为类，减少对 ID 选择器的依赖，可以避免特异性冲突，使样式在层结构中更易于管理和覆盖。
  4. 媒体查询通常应与影响它们的元素位于同一层中，以实现可预测的覆盖。 将响应式样式与同一层中的基础元素样式保持在一起，可以确保行为一致，并与现代的组件化架构更好地结合。虽然这可能会导致响应式逻辑分散在不同层中。

💬 文章金句

  • 这背后的想法是分享一个完整、未经筛选的视角，了解如何将 CSS Cascade Layers 集成到现有的遗留代码库中。
  • 如果在 `legacy` 层之后添加了更多层，那么根据层叠规则，后续层*应该*覆盖 `legacy` 层中的样式。这是因为层叠层的优先级由声明顺序决定，后声明的层优先级更高。
  • 我倾向于将所有样式都组织在明确定义的层中，因为这能保证代码的**模块化**和**可维护性**，至少在当前上下文中是这样。
  • 我坚信尽可能多地使用类选择器而不是 ID 选择器。默认情况下，它可以保持较低的特异性，从而防止特异性冲突，并使代码更易于维护。
  • 我的理由是，这样做能够：将响应式样式与基础元素样式放在一起；使样式覆盖行为更可预测；更好地适应现代 Web 开发中常见的组件化架构。
