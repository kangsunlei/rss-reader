工信部把“智能体软件”写进专项行动，下一代软件到底会变成什么？

9/14/2026, 9:09:40 AM

📌 一句话摘要

工信部将智能体软件写入专项行动，文章从产品视角指出软件的设计对象正从孤立功能转向完整工作流，并拆解下一代软件必须补上的四层能力。

📝 详细摘要

文章以工信部《“人工智能+软件”专项行动实施方案》为切入点，讨论智能体软件对产品设计的影响。作者认为，传统软件擅长把工作拆成一个个 Function，而大模型让 AI 能围绕同一目标连续做事，产品面对的从孤立功能变成需要持续推进的 Work。Agent 未必取代传统软件，但会改变产品作为唯一入口的地位，产品能力需要同时面向人和 Agent 两套入口。Agent 开始替人行动后，能力、系统权限、业务授权、正式效果和责任必须拆开设计，治理进入每一次关键行动。作者提出下一代软件要补四层能力：认得清（Workspace 与 Context）、接得上（Knowledge 与 Memory）、推得动（Work Loop）、兜得住（Governance 与 Responsibility Boundary）。

💡 主要观点

  1. 软件的设计对象正从 Function 转向 Work 传统软件把现实工作拆成查询、生成、审批等确定功能，产品经理围绕功能设计页面与流程；当 AI 能围绕同一目标连续理解、调用工具、判断下一步，产品面对的就不再是孤立功能，而是需要持续推进的一项工作。Function 没有消失，但开始变成完成 Work 的能力。
  2. Agent 未必吃掉软件，但会改变产品作为入口的地位 合同事实、账务规则、状态权限不会因通用 Agent 出现而失去价值，真正变化的是入口。用户更自然的起点可能是“把这件事做完”，背后调用 CRM、知识库还是项目系统退到第二层。产品经理因此要多考虑 Agent 如何发现、调用和约束产品能力。
  3. 未来软件要同时“给人用”和“给 Agent 用” 服务模式正从产品销售转向持续服务运营，能力可能通过 API、Skill、Agent 服务被调用。产品拆分时除了内部架构复用，还要考虑能否被外部 Agent 安全调用、需要什么上下文、权限如何判断、异常如何退出、结果如何回到业务系统，形成人的入口与 Agent 的入口长期共存。
  4. Agent 能做得越多，越要设计“什么时候不能做” 作者主张把能力、系统权限、业务授权、正式效果和责任五件事拆开：有能力不代表有权使用，有系统权限不代表本次业务已授权，接口成功不代表业务效果成立，结果生效也不代表责任可推给 AI。这些区别最终要落成建议、候选结果、人工确认、授权时效等具体设计。
  5. 下一代软件至少要补四层能力 认得清对应 Workspace 与 Context，接得上对应 Knowledge 与 Memory，推得动对应 Work Loop，兜得住对应 Governance 与 Responsibility Boundary。四层能力共同回答一个产品经理最熟悉的问题：产品能不能把用户的一件事真正承接下来。

💬 文章金句

  • Function 没有消失，但 Function 开始变成完成 Work 的能力。
  • 它冲击的未必是产品本身，而是产品作为唯一入口的地位。
  • 一个 Agent 产品设计得好不好，除了看它会不会做事，还要看它知不知道什么时候必须停下来。
  • 这四层不是为了再造一套新名词。它们其实都在回答一个产品经理最熟悉的问题：这个产品到底能不能把用户的一件事情真正承接下来？
  • 我们到底还在设计一组功能，还是开始设计一个能够持续参与工作的产品？
