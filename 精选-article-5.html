AI 写代码飞快，为何交付没有变快？小红书 Muse 的 Agentic 架构实践

9/19/2026, 5:30:00 AM

📌 一句话摘要

小红书 AI Coding 总架构师郑鑫祺拆解 Muse 平台如何通过 Agent Team 编排、Harness 控制、企业知识工程与 Agent OS，把「会生成代码」的模型变成能交付、兜底和恢复的研发系统。

📝 详细摘要

文章是小红书 AI Coding 总架构师郑鑫祺在 AICon 大会的演讲整理。作者指出，AI 生成代码速度虽快，但从需求到上线的周期并未同步缩短，节省的编码时间被设计规范、跨仓上下文、安全检查与协作断点重新消耗。为此，小红书构建了 Vibe Coding 平台 Muse，试图打通需求共创、设计、编码与交付，让产品经理、设计师和开发者共享同一条上下文链路。文章系统拆解了 Muse 的技术架构：从 Workflow、Pipeline 到 Agent Team 的模型控制演进，Agent 生命周期中的 Hook 与四类检查位置，幂等键与副作用日志，以及「不要把对话记录当成运行状态」的教训。在企业知识层面，作者提出知识应像 Research 一样被推理链组织，并通过删除实验、召回率、单位成功任务成本等指标量化。底层则建设 Agent OS、统一 Memory Workspace、沙箱隔离与审计体系，最终指向 Agent App 与 Agent Swarm 的全景架构。

💡 主要观点

  1. AI 写代码快不等于交付快，瓶颈已从编码转移到上下文与协作链路 AI 生成的代码可能不符合公司设计规范、存在安全问题或不满足现有工程体系要求，节省的编码时间被检查、提测、修复、反复沟通甚至推翻重做重新消耗。企业级 AI Coding 面临三类问题：AI 不了解企业资产、上下文分散在不同平台、从需求到交付的能力链路尚未贯通。
  2. 模型控制架构从 Workflow、Pipeline 演进到 Agent Team，三者并存而非替代 Workflow 强调确定性控制，Pipeline 提升任务分流与局部控制，Agent Team 让编排更动态。多 Agent 只在子任务确实独立、可并行、上下文可分离时才有收益；若需竞争写同一份可变资源或严格串行推理，不如一条清晰的 Pipeline。评测时除成功率外还需记录重复工作率、冲突率和汇总失败率。
  3. 高可用依赖可验证的程序化护航，而非把规则写进 Prompt 祈祷模型记得 系统在 Agent 生命周期中设置 Hook，检查分为框架级和业务级；四类检查放在不同位置：请求进入模型前拦截、结果离开系统前校验、工具参数与返回值本地校验、副作用动作前暂停等人确认。写操作需带幂等键和副作用日志，记录谁批准、哪组参数、作用在哪个资源版本、能否回滚。
  4. 不要把对话记录当成运行状态，结构化状态才可恢复 Transcript 是审计材料，不适合恢复任务。真正需要结构化保存的是不可变的任务目标、用户约束、计划版本、已完成和待完成步骤、工具证据、副作用日志、审批记录、产物、失败次数和剩余预算。上下文压缩不保证保留业务上必须精确审计的字段。
  5. 企业知识应像 Research 一样被推理链组织，并通过删除实验量化 传统 RAG 难以 Debug，知识图谱化若仍用片段化匹配则核心问题未变。每条进入上下文的证据应带来源、时间、归属和权限信息，召回后需重排、去重和压缩。关键方法是删除实验：去掉某类上下文看成功率是否真的下降，若指标无变化则它只是在消耗窗口和成本。
  6. 评测要分层，成本要按成功任务算 最外层是结果评测，中间层是轨迹评测，最内层是组件评测，中间层最容易被忽略。最终结果正确但轨迹不合格的情况很常见，只按成功率统计会把运气当成能力。失败应分为模型、路由、工具、状态、控制和交付几类。成本口径应看每个成功任务的成本，把重试、升级配置、验证器开销和人工返工都算进去。

💬 文章金句

  • AI 写代码已经足够快，但从需求提出到生产上线，企业研发未必因此更快。
  • 过去的比稿依赖体力，AI 时代的比稿更依赖判断力。
  • 我们希望通过可验证的程序化护航，取代「把规则写进 Prompt，然后祈祷模型一定记得」。
  • 不要把对话记录当成运行状态。Transcript 是审计材料，它并不适合用来恢复任务。
  • 能否在正确的时间，把正确的知识交给正确的 Agent。
  • 权限可解释、状态可恢复、审计可追溯 往往比现在模型能力领先几个百分点更有价值。
