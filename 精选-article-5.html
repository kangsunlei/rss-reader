Loop engineering：把 agent 放进工程循环

9/21/2026, 6:02:00 AM

📌 一句话摘要

文章系统拆解了 Loop engineering 这一理念，提出工程循环的六个必备动作与六大支撑组件，并给出自动化判定标准、失败模式与权限分层建议。

📝 详细摘要

文章从「不要再只是提示 agent，要设计提示 agent 的 loop」这句话切入，指出当 coding agent 能自己读代码、改代码、跑测试、开 PR 后，工程师的重心应从逐轮操作转向设计自动化循环。作者先界定概念：一个可工作的工程 loop 至少包含读取外部状态、判断下一步、执行任务、验证结果、写入状态、判断停止条件六个动作，缺少状态写入只是一次会话，缺少停止条件就是烧 token 的定时器。文章把 loop 与 prompt engineering、context engineering、harness engineering 做了区分，并引用 Addy Osmani、Birgitta Böckeler、OpenAI Cookbook、Amplitude Ralph loop 及两篇论文作为背景。随后详细拆解六大组件：Automations 负责唤醒并需同时写 feedforward 与 feedback；Worktrees 解决并行文件冲突但不解决 review 带宽；Skills 把项目知识移出对话上下文；Plugins 与 connectors 让 loop 接触真实工具并需按风险分层授权；Sub-agents 分离 maker 与 checker；Memory 保证状态在对话之外持久化。最后给出 CI triage、review comment、harness maintenance 三个可落地示例，五个自动化筛选条件，以及目标函数过粗、验证被吞、状态无人读、并行制造理解债、成本无上限五类失败模式。

💡 主要观点

  1. 工程 loop 必须包含六个动作，缺一不可 读取外部状态、判断下一步、执行任务、验证结果、写入状态、判断停止条件。缺少状态写入，loop 退化为一次性会话；缺少停止条件，loop 变成烧 token 的定时器。
  2. loop engineering 与 prompt / context / harness engineering 是分层关系 prompt 关心一句话怎么写，context 关心给模型什么材料，harness 关心工具、权限与运行环境，loop 关心这些东西如何持续运转。只有调度没有控制件就是定时犯错，只有控制件没有循环就还是一次性工具。
  3. 六大组件构成 loop 的支撑骨架 Automations 负责唤醒并需同时写 feedforward 约束与 feedback 传感器；Worktrees 解决并行文件冲突但不解决 review 带宽；Skills 把稳定项目知识移出对话；Plugins/connectors 接入真实工具；Sub-agents 分离 maker 与 checker；Memory 保证状态在对话之外持久化。
  4. 权限应按风险分层，而非一步到位追求全自动 分为 observe（只读）、propose（可生成 patch/PR 不可合并）、act with approval（关键步骤需人批准）、autonomous（仅限低风险可回滚任务）。大多数团队应先把 observe 和 propose 做扎实。
  5. loop 的失败模式集中在目标、验证、状态、并行与成本五处 目标函数太粗会被 agent 翻译成无关动作；验证被 agent 自己总结吞掉应直接判失败；状态文件没人读就只是日报；并行 agent 会积累理解债；没有预算上限的 loop 终将被成本或误操作叫停。

💬 文章金句

  • 少了第 5 步，它只是一次会话。少了第 6 步，它就是烧 token 的定时器。
  • 只有调度，没有控制件，就是定时犯错；只有控制件，没有循环，就还是一次性工具。
  • 模型可以忘，系统状态不能忘。
  • 并行只用于低耦合任务，合并仍然按人的理解能力限流。
  • 很多团队会先迷上"让 agent 写更多代码"，但更该先问的是：怎样让 agent 少犯同一种错。
