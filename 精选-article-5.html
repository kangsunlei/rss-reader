Redis Stream 还是传统 MQ？队列选型全攻略（适用场景、优缺点与实践建议）

12/23/2025, 11:16:00 PM

📌 一句话摘要

文章深度对比了 Redis 作为消息队列的 List、Pub/Sub、Stream 三种模式与专业消息队列（Kafka/RabbitMQ）的优劣，并提供了选型实践建议。

📝 详细摘要

文章详细探讨了将 Redis 用作消息队列的各种可能性。首先，介绍了 Redis List 和 Pub/Sub 模式的特点和局限性。随后，重点分析了 Redis Stream 作为队列的成熟特性，包括阻塞拉取、发布订阅（消费者组）和消息不丢失的机制。接着，文章将 Redis 与专业的 Kafka 和 RabbitMQ 等消息队列在生产者消息不丢、消费者消息不丢、队列中间件消息不丢以及消息积压处理能力等方面进行了全面对比。最终，文章强调技术选型不仅是技术问题，更要结合团队、运维能力和组织结构等非技术因素做出平衡的决策，并给出具体选型建议。

💡 主要观点

  1. Redis List 和 Pub/Sub 模式在作为消息队列时存在明显局限性，不适合高可靠或多订阅场景。 List 模式不支持重复消费和消息丢失风险，Pub/Sub 模式不具备消息持久化和离线消息处理能力，使得它们仅适用于简单、低可靠要求的场景。
  2. Redis Stream 通过消费者组和 ACK 机制，解决了传统 Redis 队列的消息不丢失、重复消费和阻塞拉取等问题。 Stream 提供了 XADD、XREADGROUP 等命令，支持多消费者组并行消费，并能通过 XACK 确保消息成功处理，大幅提升了 Redis 作为 MQ 的可靠性。
  3. 与专业 MQ 相比，Redis 在数据持久化和消息积压处理方面仍有不足，但在特定场景下具备优势。 Redis 的内存存储和异步持久化可能导致数据丢失，且不擅长处理大规模消息积压。但其轻量易用，可作为中小型项目或低延迟场景的替代方案。
  4. 技术选型应综合考虑技术特性、团队能力、运维资源和业务需求，而非单一技术指标。 选择消息队列不应仅关注技术本身，还需评估团队对复杂中间件的运维能力，以及公司是否有足够资源支持，避免盲目追求“最佳技术”导致落地困难。

💬 文章金句

  • 很多人在做技术选型时会遇到一个问题：把 Redis 当作消息队列合适吗？
  • Stream 是新增加的数据类型，它与其它数据类型一样，每个写操作，也都会写入到 RDB 和 AOF 中。
  • Redis 在以下 2 个场景下，都会导致数据丢失：1）AOF 持久化配置为每秒写盘，但这个写盘过程是异步的，Redis 宕机时会存在数据丢失的可能；2）主从复制也是异步的，主从切换时，也存在丢失数据的可能。
  • 但 Redis 的定位则不同，它的定位更多是当作缓存来用，它们两者在这个方面肯定是存在差异的。
  • 所以，做技术选型不只是技术问题，还与人、团队、管理、组织结构有关。
