大多数 MCP 都设计错了！

7/5/2025, 9:04:00 AM

📌 一句话摘要

文章深入剖析了当前 MCP 设计中普遍存在的 API 包装器问题，并提出应以用户意图为中心、响应即提示的 AI 原生设计原则。

📝 详细摘要

文章指出当前许多 MCP（Model-Controller-Provider）服务器的构建存在严重误区，即简单地将现有 API 进行包装，而非针对 AI 模型交互特性进行设计。作者通过 Reddit 网友的激烈讨论引出问题，并引用开发者 Tiemensma 的观点，强调 API 是为人类开发者设计，而 MCP 是为 AI 模型设计。传统 API 包装会导致 Token 膨胀和概念混淆。文章提出 MCP 设计应围绕用户意图，而非 API 端点，并将每一次工具响应都视为对模型的“提示”，尤其在错误响应中提供教育性指引。最终，文章呼吁开发者摒弃 API 包装器思维，将 MCP 视为一种“全新应用形态”来设计，以真正赋能大模型和智能体。

💡 主要观点

  1. 多数 MCP 服务器设计不当，仅为 API 包装器，而非 AI 原生设计 将现有 API 简单包装为 MCP，忽略了 AI 模型与人类开发者在交互方式上的根本差异，导致模型使用效率低下，甚至无法正常工作。
  2. API 式 MCP 导致 Token 膨胀和概念混淆，严重限制模型性能 传统 API 的复杂 Schema 和术语对 AI 模型造成理解障碍，消耗大量 Token，并引发模型对不同概念的混淆，影响其决策准确性。
  3. 优秀的 MCP 设计应围绕用户意图，并将每次响应视为对模型的“提示” MCP 应从用户期望完成的任务出发设计工具，并通过工具响应（包括错误信息）提供清晰的下一步指引，帮助模型持续进行推理和纠正。
  4. 错误信息应具备“教育性”，引导模型进行有效纠正和下一步操作 一个好的错误响应不仅指出问题，更要告诉模型问题原因和如何解决，减少初始 Prompt 的冗余，提升模型自主纠错能力。

💬 文章金句

  • 大多数 MCP 服务器都是错建的。
  • MCP 不仅仅是一个协议封装器，它是一份'设计契约'------规范了大模型该如何与你的系统交互。
  • API 是为人类开发者设计的，而 MCP 是为 AI 模型设计的。
  • 优秀的 MCP 设计，是把每一次工具响应都当作'提示模型'的机会。
  • 错误信息，就是当下的文档，它必须具备'教育性'。
