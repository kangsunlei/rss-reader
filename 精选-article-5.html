别再让计算等着搬权重了！KTransformers 让 CPU 直接参与 MoE 微调计算

10/26/2026, 4:00:00 PM

📌 一句话摘要

KTransformers-FineTune (KT-FT) 提出 CPU/GPU 协同计算范式，让 CPU 直接利用 AVX-512/AMX 指令集完成 MoE 专家计算，配合语义感知布局引擎与动态线程调度，在千亿参数 MoE 模型上实现比传统卸载范式快 2.5–21.2 倍的 LoRA 微调吞吐。

📝 详细摘要

文章介绍了清华 MADSys 实验室与趋境科技联合 LlamaFactory 团队开发的 KTransformers-FineTune (KT-FT)。针对大规模 MoE 模型微调时显存不足、PCIe 传输权重成为瓶颈的问题，KT-FT 打破传统“卸载范式”，提出 CPU/GPU 协同计算：CPU 留存专家权重并就地完成前向/反向矩阵运算，GPU 专注 Attention 计算。为消除布局转换与线程负载不均开销，设计了语义感知主动布局引擎（提前按张量用途分配内存、后台原地转换布局与 GPU 计算重叠）和动态线程调度器（细粒度任务队列+工作窃取）。实验在 DeepSeek-V3.1-671B、Qwen3.5-397B、Qwen3-235B-2507 上验证，单卡/多卡、Intel AMX/AMD AVX-512 平台均显著超越 ZeRO-Offload 等基线。进一步提出 LoRA Expert (LE) 系统-算法协同设计，利用剩余显存增设共享适配路径缓解专家更新不均，缩短达到目标质量的时间。KT-FT 已集成至 LlamaFactory，提供一键微调部署，并在企业适配、模型研发、高校实验三大场景落地。

💡 主要观点

  1. 传统卸载范式在 MoE 稀疏负载下失效，PCIe 传输专家权重耗时远超 GPU 计算时间 MoE 专家计算极快，权重传输却无法被掩盖：ZeRO-Offload 94% 单步时间花在通信同步，APTMoE 仍占 86%。理论带宽下传输 1B BF16 参数需 62.5ms，而 RTX 5090 计算仅 2.8ms，传输是计算的 22 倍。
  2. KT-FT 提出 CPU/GPU 协同计算范式：CPU 直接用主存权重完成专家计算，GPU 负责 Attention 利用 CPU AVX-512/AMX 指令集执行 MoE 专家前向/反向，避免权重搬运。但仅改变执行位置不够，还需解决布局转换与线程同步开销，否则 PyTorch(OneDNN) 直译实现甚至比卸载更慢。
  3. 语义感知主动布局引擎与动态线程调度器消除关键路径开销 布局引擎按张量用途预分配最优内存布局，后台线程跨层原地转换并与 GPU 计算重叠，仅保留一份参数副本；调度器将专家工作拆解为细粒度任务入共享队列，工作窃取平衡热/冷专家负载，减少派发停顿。
  4. 实验显示协同计算范式吞吐达卸载基线 2.5–21.2 倍，短序列优势最大 覆盖三款千亿 MoE、单/多卡、AMX/AVX-512 平台。同分工下 PyTorch 仅 12.1 tokens/s，KT-FT 达 166.8 tokens/s，证明系统优化对落地收益至关重要。
  5. LoRA Expert (LE) 系统-算法协同利用剩余显存加速收敛 在每层 MoE 增设常驻 GPU 的共享 LoRA 适配路径，所有 token 共同训练，缓解路由倾斜导致的冷门专家更新不足。Time-to-Quality 指标验证 LE 比单纯扩大原有适配路径或动态迁移专家更有效。

💬 文章金句

  • 仅搬运专家权重，就比 CPU 完成专家计算耗时更长
  • 卸载所依赖的"用计算掩盖搬运"因此失效
  • CPU 专家计算耗时与布局、同步开销之和，必须低于原先的权重传输时间
  • KT-FT 的标准 LoRA 微调吞吐达到卸载基线的 2.5--21.2 倍
  • LE 的共享分支由所有 token 共同训练：即使某个 token 被分配给冷门专家，也能利用这条共享路径学到的适配信息
