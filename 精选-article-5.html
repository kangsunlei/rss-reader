一个 7B 模型服务冷启动要 2 分半，我们把它压进了 12 秒

11/27/2026, 10:01:00 AM

📌 一句话摘要

本文通过剖析 7B 模型冷启动耗时构成，提出「少做一点、并行做一点、做过的事情尽量别重来」三大优化策略，将启动时间从 43 秒压至 12 秒，系统化解决稀疏流量下的模型弹性调度问题。

📝 详细摘要

本文聚焦稀疏流量场景下的模型服务冷启动问题，目标是将 7B 模型启动从 43 秒压至 12 秒。作者拆解了 vLLM 启动流程，发现模型加载仅占 7.4%，其余时间在 Python 依赖导入、进程间等待、KV Cache 初始化、编译等环节。通过三类优化：减少重复工作（移植非必要依赖、避免跨进程重复导入、使用 fork 加速模型检查）、并行化处理（提前完成 API 组件准备、并行算子预热、重叠权重加载与 KV Cache 测量）、复用已有准备（持久化 Triton/CUDA 编译缓存、复用显存测量记录），最终实现显著加速。文章还指出瓶颈会随优化移动，需持续关注端到端链路。

💡 主要观点

  1. 冷启动瓶颈在于 Python 依赖导入和进程间串行等待，而非模型加载 在热缓存条件下，模型加载仅占启动总时的 7.4%，而依赖导入、配置解析、进程握手等耗时显著，需重点优化这些串行环节
  2. 通过减少跨进程重复导入和使用 fork 加速模型检查，显著缩短启动准备阶段 同一批导入最高可重复三次，采用进程内检查和 fork 机制可将启动准备时间从 29 秒降至 3 秒
  3. 并行化算子准备与权重加载，重叠执行提升整体启动效率 将部分算子准备任务放入后台线程，在模型加载期间并行完成，同时调整握手顺序，使 API 组件准备与引擎初始化真正并行
  4. 持久化编译缓存和复用显存测量记录，避免重复计算 Triton 等编译产物若存于容器可写层将随容器消失，需持久化；复用历史显存测量记录可跳过部分 profile_run，但需注意整体响应收益有限
  5. 优化顺序随时间缩短而变得更关键，需关注端到端链路 当总时间从 40 秒降至 10 秒时，一秒已占 10%，性能优化越往后，对「一点点」的定义越敏感，需持续拆解用户实际等待的完整链路

💬 文章金句

  • 少做一点、并行做一点、做过的事情尽量别重来
  • 模型加载只占全部启动时间的约 7.4%。在缓存已经准备好的这组实验里，即使施展魔法，把模型加载时间直接变成零，剩下的等待依然接近四十秒。
  • 同一批导入最多可能被做三遍：API 主进程一遍、一次性的检查子进程一遍、EngineCore 又一遍。
  • 当启动还要四十多秒时，不到一秒好像不值一提；当总时间只剩十秒左右，一秒已经是将近 10%了。
  • 局部函数变快，不代表端到端一定变快。
