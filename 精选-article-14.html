深入剖析 MySQL 单表建议不超过 2000 万行的技术原理，揭示 B+树与 16KB 数据页如何影响数据库性能。

📝 详细摘要

文章详细解释了 MySQL 单表数据量不宜超过 2000 万行的业界经验法则背后的技术原理。首先介绍了 InnoDB 存储引擎中数据页（16KB）的结构及其在磁盘 I/O 优化中的作用。接着阐述了 B+树索引的构建方式，包括聚簇索引和二级索引，并以具体示例演示了 MySQL 如何利用 B+树进行数据查询，强调了 B+树“矮胖”特性（高扇出值）对查询效率的重要性。文章核心部分通过计算非叶子节点指针数量和单页行数，推导出三层 B+树能够承载约 2500 万行数据，从而解释了 2000 万这一经验值的由来。同时指出，单行数据大小是影响实际上限的关键因素。最后，文章对比了 B 树与 B+树在相同数据量下的性能差异，并提供了控制单行大小、分库分表、冷热分离等优化建议，强调了 MySQL 在磁盘 I/O 和内存效率之间的平衡。文章最后还解答了 16KB 页设计、字符串索引、中文字符串索引及索引长度限制等拓展问题。

💡 主要观点

  1. MySQL 单表 2000 万行上限源于 B+树层高与 16KB 数据页的承载能力 文章通过计算非叶子节点扇出值和叶子节点单页行数，得出三层 B+树在典型配置下可承载约 2500 万行数据，解释了这一业界经验值的技术依据。
  2. B+树的高扇出特性是 MySQL 高效查询的关键，有效减少磁盘 I/O B+树通过在非叶子节点存储主键和页指针，实现极高的扇出值，使得数千万级数据仅需 2-3 次磁盘 I/O 即可定位，显著提升查询性能。
  3. 单行数据大小是影响单表实际容量上限的核心因素 2000 万并非绝对上限，若单行数据较小，三层 B+树可支持更多行；反之，若单行数据较大，则可能在更少行数时即达到性能瓶颈，需根据实际情况评估。
