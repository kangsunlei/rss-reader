一次缓存引发的文件系统数据不一致问题排查与深度解析

9/10/2025, 12:30:00 AM

📌 一句话摘要

文章深度剖析了分布式文件系统客户端 EFC 在引入缓存后，因数据版本回退和内核 PageCache 交互问题导致的文件系统数据不一致故障，并提供了详细的排查与修复方案。

📝 详细摘要

本文详细记录了一次阿里 EFC 分布式文件系统客户端在 CTO 测试中遇到的数据不一致问题。起初，作者误判为缓存读取旧数据，但通过 NFS 挂载对比，发现是文件系统数据本身被破坏，表现为正常字符被空字符替换，且错误数据集中在单个 4K 页内。经过日志分析和行为推测，作者定位到核心问题是：在一次追加写操作中，文件系统扩容后填充了 NULL，而另一个客户端在分布式缓存中读取并缓存了这些 NULL 数据。随后，由于网络慢请求导致数据版本（dv）回退，当客户端进行“先读后写”的 Buffer Write 操作时，从缓存中读到了旧版本的 NULL 数据到 PageCache，再与新数据一同刷回文件系统，最终导致了数据损坏。文章不仅详细复原了问题流程，提出了通过维护本地递增缓存版本号并丢弃回退版本来解决的方案，并通过测试验证了修复效果。此外，文章还深入揭示了 Linux 内核对 POSIX 文件操作（如 pwrite， ftruncate， fsync， close）的底层优化行为，以及这些行为与缓存机制结合时可能引发的复杂问题，为读者提供了宝贵的系统级调试经验和先验知识。

💡 主要观点

  1. 分布式缓存中数据版本（dv）回退是文件系统数据不一致的根本原因 慢网络请求可能导致客户端记录的数据版本被旧版本覆盖，进而从缓存中读取到过期数据，特别是在 Buffer Write 的“先读后写”机制下，会污染 PageCache 并最终写坏文件系统。
  2. Linux 内核对 POSIX 文件操作的优化行为可能与分布式缓存机制冲突 内核对 pwrite、ftruncate 等操作的延迟提交、合并处理及“先读后写”逻辑，在分布式缓存场景下，若版本管理不当，极易导致数据不一致。
  3. 深入理解系统底层机制是解决复杂数据一致性问题的关键 通过 Hexdump 分析、日志定位和对 PageCache、文件系统 RPC 交互的深刻理解，才能从表象的“读缓存旧数据”深入到“写坏文件系统”的本质问题。

💬 文章金句

  • CTO：Close-to-Open，指当一个文件被关闭后，再次 open 时，文件系统必须保证之前所有通过 close 操作提交的数据已经持久化到文件系统，并且读取时能获取到最新的、一致的状态。
  • 文件系统数据被破坏掉了，也宣告着读到缓存中的旧数据的想法破产。
  • 错误的根本原因在于：版本号发生回退，客户端使用了旧版本号从缓存中读到了旧数据。
  • 若在此期间读取文件，可能读取到未填充的空洞数据（本文 bug 读取到缓存的数据就发生在这次 setattr 和下一次 write 之间）
  • 这个错误从发现到最后解决耗时了半个多月，从开始时发现文件系统错误时的迷茫，到发现空字符的错误数据以及位于一个 page 内，提供了 pagecache 写坏刷到文件系统的想法，之后不断根据日志分析可能存在的写坏文件系统操作，并验证猜想。
