SQLite 为什么总受质疑？它明明可以替代一切……

9/20/2026, 11:15:00 PM

📌 一句话摘要

本文系统论证 SQLite 凭借稳定可靠、零运维和丰富扩展能力，可在全文检索、文档存储、消息队列、向量索引等十余种场景替代独立中间件，并给出其单机单写的明确边界。

📝 详细摘要

文章以「SQLite 的寿命比你现在运行的大多数系统都要长」开篇，指出它常被误认为玩具数据库，实际却是全球部署最广泛的数据库引擎。作者从三点立论：稳定可靠（2000 年发布、测试代码量约为库代码的 500 倍、MC/DC 100% 分支覆盖、公共领域、承诺维护到 2050 年）、易于运行安装扩展（内置于主流语言与操作系统，测试与生产用同一套库文件，垂直扩展为函数调用而非网络跳转，Litestream/LiteFS 提供复制备份）、以及简化 IT 架构。随后逐一展开替代场景：用 FTS5 替代 Solr/Elasticsearch，用 JSON 与 jsonb 替代 MongoDB，用一张表加 BEGIN IMMEDIATE 与 RETURNING 替代 Kafka/RabbitMQ，用文件分区与汇总表替代 ClickHouse，用 sqlite-vec 做 AI 工作流向量库，用 WAL 与内存模式替代 Redis 缓存，用 BLOB 替代文件系统（官方基准称快 35%），用递归 CTE 与 simple-graph 替代图数据库，用 json_object() 替代微服务，甚至用 CTE 渲染曼德博集合。结论强调「简单，才是快速迭代的根基」，同时明确 SQLite 单线程写入、单机运行的能力上限，建议触及天花板后再迁移到 PostgreSQL。

💡 主要观点

  1. SQLite 的核心竞争力是零运维与稳定可靠，而非功能孱弱 它 2000 年发布，测试代码量约为库代码的 500 倍，在 MC/DC 标准下实现 100% 分支覆盖，属于公共领域且官方承诺维护到 2050 年。内置于主流语言与操作系统，测试与生产使用同一套库文件，消除了环境不一致问题。
  2. SQLite 可替代大量独立中间件，因为索引与业务数据天然同事务 FTS5 全文检索、JSON/jsonb 文档存储、队列表、向量索引都直接运行在应用进程内，不存在跨系统的数据同步延迟，作者称「为什么搜索索引数据过期」这类故障根源来自本非必需的复杂架构。
  3. 本地函数调用在延迟上系统性优于网络调用 SQLite 一次往返是函数调用而非网络跳转，页面缓存预热后单点查询约 1 微秒，而本地回环上的 Redis GET 约百微秒；对 100KB 以内 BLOB，官方基准称比文件系统快 35% 且磁盘占用少约 20%。
  4. SQLite 的能力边界明确：单线程写入、单机运行 它没有 SKIP LOCKED，多个消费者在写锁上串行执行，入队速率达到每秒数万条时会出现瓶颈；也无法跨节点分布式分片。作者建议先用 SQLite，等真实业务指标证明不够用时再迁移到 Kafka 或 PostgreSQL。
  5. 技术栈每增加一个组件都会带来隐性成本，简化本身就是迭代速度 每个组件都需要部署、监控、加固、升级、备份、付费并向新同事解释。作者建议面对新需求先问两个问题：SQLite 能否直接搞定？我们真的需要那些新技术吗？

  • 看不见的问题，几乎不可能被稳定解决。
  • 最快的网络调用，就是直接本地函数调用。
  • 简单，才是快速迭代的根基。
  • 你的图数据规模大概率只有一万个节点。一万个节点完全可以放进 CPU 的 L3 缓存。
