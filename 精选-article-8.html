Agent 越改越乱之后，我用评测和轨迹把它拉回来了

8/13/2026, 11:21:00 AM

📌 一句话摘要

作者把 Agent skill 迭代变成一套可重复的自进化流程，用评测结果与操作轨迹生成 patch，经四层 gate 验证与黑名单回滚，把安全审计 Agent 准确率从 77.8% 稳定提升到 88.9%。

📝 详细摘要

本文是阿里安全工程师关于 Agent skill 迭代的深度实践总结。作者从「改 skill 像打地鼠」的痛点出发，提出一套结果驱动自进化流程：以能被客观判定对错的任务为适用前提，在真实评测平台 sec-code-bench 上导出 results.jsonl 与 sessions/ 轨迹日志，经过 trace_parser 三层压缩后，由确定性规则完成联合归因。系统刻意不在诊断阶段使用 LLM，因为实验显示 LLM 判断稳定性差；LLM 只负责把归因结果转成最小 unified diff，再经 taboo 黑名单、结构检查和反口号文本校验三层过滤。修改必须通过 target、guardrail、holdout、verify 四层 gate 才能写入主线，被拒 patch 进入跨版本共享的黑名单。作者还设计了 gt_auditor 审计 ground_truth 标注，避免为错误标注改歪 skill，并给出收敛判据与自动回滚机制。文末附真实评测数据：Kimi 从 77.8% 提到 84.1%，GLM 从 77.8% 提到 88.9%，DeepSeek 从 82.5% 提到 87.3%。

💡 主要观点

  1. 把改 skill 变成可重复流程，靠评测结果与轨迹日志驱动自动迭代。 作者用 results.jsonl 和 sessions 日志构造闭环：诊断失败原因、生成 patch、验证与回滚，把打地鼠式的经验修补变成可追踪的工程流程。
  2. 自进化只适用于输出可客观判定对错的任务。 判据是结论是否收敛、有无标准答案；代码安全审计的 true/false 输出天然满足，开放式文案生成任务则不适合。
  3. 诊断阶段不用 LLM，只用确定性规则，避免结果漂移。 实验显示 LLM 判断 skill 问题稳定性差，换 prompt 就漂移；规则诊断宁可漏判也不飘判，并把 LLM 限制在生成候选 diff 这一环。
  4. 四层 gate 与黑名单机制保障进化不破坏旧能力。 target、guardrail、holdout、verify 分别检查修复有效、无回归、泛化不减、文档质量不降；黑名单记录被拒 patch，防止反复横跳。
  5. 系统会审计 ground_truth 标注，避免迁就错误数据改歪 skill。 gt_auditor 用五个确定性信号打可疑度分数，提醒 patch 生成阶段不要为了错误标注而调整。

💬 文章金句

  • 我不假设模型会突然变聪明，只是把它容易"犯糊涂"的地方收进工程约束里。
  • 改 skill 有种打地鼠的感觉，按下这个又会冒出那个。
  • 诊断宁可少判，也不要飘着判。
  • 搞坏比没改好严重得多。
  • 如果你在写 patch 的时候能看到测试答案，那就是在"背答案"了。
