到底什么是 Context？万字长文谈 Pi Agent context 管理

9/19/2026, 4:00:00 PM

📌 一句话摘要

本文以 Pi Agent 为例，系统拆解了 Agent 中 Context 的构成、动态增长、预算控制与压缩重建机制，指出 Context 是 Harness 组装、随执行动态演进的信息环境，而 Compaction 本质是 Context 表示的降维与重建。

📝 详细摘要

文章从「Skill 是 Prompt 还是 Context」的讨论切入，先给出区分：Prompt 是相对静态的指令设计，Context 是 Agent 运行中动态形成的信息环境。随后以 Pi Agent 为例展开：Context 由 System Prompt、Tool Definitions、User Messages、Assistant Messages、Tool Results 五部分组成，前两者构成静态前缀，后三者随执行追加，并遵循前缀稳定、动态后置、标准消息结构三条 KV Cache 友好原则。文章介绍了 AgentSession 与 AgentSessionRuntime 的分层、Services 对 cwd 相关依赖的封装，以及 Context 的标准化表示（systemPrompt / messages / tools）。在长程任务部分，说明 runLoop 中 Context 持续增长、agent_end 只结束本轮更新而非清空历史，并给出工具输出「预算内全量保留、超预算只留预览、完整输出落盘按需读取」的三步预算策略，以及 Provider 层与 Session 层两种 Failover 对 Context 的不同处理。最后用九个细节点拆解 Compaction：token 预算选切点且不切在 Tool Result 上、split-turn 补摘要、增量合并 previous summary、摘要自身有预算、生成 task continuation state 而非聊天总结、文件操作程序化保留、摘要不走 Agent Loop、压缩后真正重建 messages、Compaction 记录持久化。

💡 主要观点

  1. Prompt 与 Context 的本质区别在于静态指令与动态信息环境 Prompt 提前定义模型「应该怎么做」，相对静态；Context 随任务推进不断变化，决定模型「此刻基于哪些信息来做」。因此 Skill 归类之争背后是更基础的 Context 定义问题。
  2. Context 由五部分组成，且由 Harness 而非模型管理 System Prompt 与 Tool Definitions 构成相对静态前缀，User Message、Assistant Message、Tool Result 随执行产生和变化。Model 只负责基于当前 Context 决策，Harness 负责组装管理 Context 与执行工具，Environment 承载真实状态。为 KV Cache 友好，需保持前缀稳定、动态信息向后追加、使用标准消息结构。
  3. Pi Agent 用 Session 分层与 Services 封装解决会话与环境一致性问题 AgentSession 管「这个会话怎么跑」，AgentSessionRuntime 管用哪个 Session 及其生命周期；由于 Session 与 cwd 强绑定，切换 Session 时必须重建 Services，否则会出现运行 repo-b 会话却加载 repo-a 配置的资源错配。
  4. 长程任务中 Context 持续增长，需要预算管理与回滚能力 runLoop 中 AssistantMessage 与 ToolResultMessage 不断追加，agent_end 只结束本轮更新，历史沉淀到 Session State 成为下一轮起点。工具输出采用「预算内全量、超预算预览、完整落盘按需读取」三步策略，受行数与字节数双重限制。Failover 分 Provider 层（同一次调用重发）与 Session 层（回滚失败消息后重建 Model Input），说明 Context 需支持回滚与重建。
  5. Compaction 是 Context 表示的降维与重建，而非简单截断历史 压缩由 Session 层在 Run 结束、新 Prompt 前或手动触发时执行，按 token 预算选切点且不能切在 Tool Result 上；若切断执行过程则补 split-turn 摘要；多次压缩通过 previous summary 增量合并；摘要本身有独立预算；生成的是 task continuation state 而非聊天总结；文件读写等确定性事实由程序扫描 Tool Call 直接保留；摘要生成是单次 LLM 调用、不走 Agent Loop；压缩后真正重建 agent.state.messages；Compaction 记录持久化以保证多轮压缩边界连续。

💬 文章金句

  • Prompt 更偏向相对静态的指令设计，而 Context 更偏向 Agent 在运行过程中动态形成的信息环境。
  • Model 负责基于当前 Context 决定下一步；Harness 负责组装和管理 Context、校验并执行工具；Environment 则负责承载真实状态，并产生新的执行结果和观察。
  • agent_end 结束的是这一轮 Run 对 Context 的持续更新，而不是 Context 本身。
  • 语义信息交给 LLM 蒸馏，确定性事实则由程序直接保留。
  • 把远端历史从高成本的原始消息表示，转换成低成本的结构化摘要表示，同时尽可能保留继续完成任务所需要的状态。
