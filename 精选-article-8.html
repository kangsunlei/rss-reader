AI 不缺智商缺纪律：一场 Harness 工程化实践

6/10/2026, 12:24:00 PM

📌 一句话摘要

本文系统复盘了作者在 Harness 工程化实践中，如何通过分层约束、状态外置与确定性评测，将 AI Coding 从「堆 prompt 约束」演进为「结构化框架」的完整历程。

📝 详细摘要

文章以作者在 Harness（AI 编码工程框架）上两个月的演进复盘为主线，系统阐述了 AI Coding 的瓶颈正从「模型能力」转向「流程工程」。作者从最初依赖 CLAUDE.md 堆砌规则导致上下文爆炸、模型选择性遗忘的失败教训出发，逐步演进至一套三层加载架构（常驻入口层、原子规则层、按需上下文层），并引入 Agent 调度编排（dispatcher 状态机 + 文件交接）与确定性评测平台。文章详细拆解了每层设计意图、代价与边界，对比了 Workflow、Agent Team 等现成编排方案的适用场景，并分享了 4 条关键踩坑教训。最后，作者将这套模式提炼为可迁移的工程化思维：任何「能力够强但输出不稳定、且过程可观测」的 AI 工作流，都可以通过分层约束、外置状态与确定性评分来工程化。

💡 主要观点

  1. AI Coding 的瓶颈正从「模型能力」转向「流程工程」。 模型已足够聪明，但输出不稳定；稳定性必须由外部框架供给，而非靠堆 prompt 说服。
  2. Harness 的核心设计是「把上下文当预算管理」，而非草稿纸。 通过三层加载（常驻入口层、原子规则层、按需上下文层）将主会话常驻上下文压至 ≤8K，深度内容按需加载，避免模型被规则淹没。
  3. Agent 编排的核心是「职责隔离 + 状态外置」，而非让主会话全能。 主会话退化为纯执行器，只执行 dispatcher 指令；各 agent 通过文件系统交接，状态持久化，支持跨天续跑与审计。
  4. 确定性评测是驱动 Harness 自进化的关键。 用 100% Python 确定性逻辑、零 LLM 调用、7 维评分，确保 3 次跑分完全一致，使「改 harness 凭感觉」变为「改完有分、好坏可对比」。
  5. 流程强制执行必须从 LLM 推理中外置到确定性基础设施。 门禁（G1-G8）必须是确定性代码，独立于上下文窗口，fail-closed（默认拒绝），不依赖模型「记住」该执行哪个步骤。

💬 文章金句

  • 对付 AI 的不确定性，堆 prompt 是负债，做框架才是资产。
  • prompt 约束是说服，不是强制。模型「理解」了规则不等于「遵守」了规则——你无法用更多的字来对抗概率性的遗忘。
  • 宁要可复现的「粗糙分」，不要会漂移的「精准分」。
  • 模型负责聪明，我们负责让它守纪律。
  • 真正推动架构演进的从来不是「想要更好」，是「现在的做法已经崩了」。每一阶段的切换都并非优化，而是止损。
