📌 一句话摘要

本文系统梳理了 Harness（约束工程）过去十五个月的技术演进，将其拆解为流程管控、并发调度和质量验证三层架构，并指出其本质是随模型能力动态迁移的「补偿面」，真正的护城河在于追踪这种迁移的能力。

📝 详细摘要

文章深度复盘了 Harness Engineering 从 2024 年底到 2026 年上半年的完整演进史。作者将 Harness 定义为围绕大模型建立的「工业级管理制度」，并拆解为三层：第一层解决单 Agent 不听话的问题，通过 JSON 物理锁、三步唤醒仪式、Git 存档与 Context Reset 等机制强制其遵循流程；第二层解决多 Agent 并发时的无政府状态，引入 Planner-Worker-Judge 层级架构和二分调试法；第三层戳破模型的盲目自信，通过引入 Evaluator 对抗生成、8 通道盲审和严格沙盒隔离来保证交付质量。文章最后指出，随着模型能力提升，Anthropic 已开始拆除 Context Reset 和 Sprint Contract 等过时组件，揭示 Harness 的每个组件都是对模型当前短板的「补丁」，其价值是相对的，真正的护城河不是架构的厚度，而是追踪「补偿面」迁移的速度。

💡 主要观点

  1. Harness 的本质是一套补偿模型能力短板的「工业级管理制度」，而非一劳永逸的架构。 文章通过 Anthropic、OpenAI 和 Cursor 的实践，证明 Harness 的每一层（流程管控、并发调度、质量验证）都是为了解决模型「记不住、不听话、看不清自己」等具体缺陷而生的补丁。
  2. Harness 的价值是相对的，随模型能力动态迁移，真正的护城河是追踪「补偿面」迁移的速度。 Anthropic 在 Opus 4.6 发布后，果断拆除了不再必要的 Context Reset 和 Sprint Contract 组件，证明架构越厚转身越慢，知道何时「拆」比一味「加」更重要。
  3. 多 Agent 并发需要强硬的控制流架构来终结无政府状态。 Cursor 的实验表明，数百个 Agent 共享代码库会陷入锁竞争和无效修改。解决方法是引入 Planner-Worker-Judge 层级和 DAG 引擎，用物理状态机强行压制个体的盲目性。
  4. 模型天生无法客观评估自身产出，必须引入外部对抗验证机制。 Anthropic 引入 Evaluator Agent 与 Generator 形成对抗循环，Cursor 则采用 8 通道并行盲审加多数投票，都是为了戳破模型「自信地赞美」自己平庸工作的幻觉。
  5. 通往简单的 Harness 设计，必须经过复杂的搭建与验证过程。 文章以 Sutton 的「Bitter Lesson」为镜，指出 Anthropic 若不先搭建 Context Reset，就不会发现 Opus 4.6 不再需要它。每一层被拆掉的补偿，都曾经被认真搭过。

💬 文章金句

  • Harness 的每一个组件，都编码了一条关于模型做不到什么的假设。当假设不再成立，组件就该走了。
  • 真正有价值的不是补偿的厚度，是追踪补偿面迁移的能力，知道下一寸该加什么，上一寸该拆什么。
  • 护城河不在 harness 的厚度，在迁移的速度。
  • 通往简单的路，必须经过复杂。
