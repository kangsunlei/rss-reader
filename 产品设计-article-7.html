📌 一句话摘要

作者分享了从 Codex 5.6 升级到 6.0 后，在产品上线部署过程中遭遇的资源高消耗、Docker 打包环境不一致及耗时长等痛点，反思了跨平台开发与部署流程规划的重要性。

📝 详细摘要

文章记录了作者将 AI 编码助手 Codex 从 5.6 升级到 6.0 后的实际踩坑经历。虽然 Codex 6.0 编码能力强，但在产品上线时暴露出三大问题：一是排查问题时自动执行“分析-测试-看日志-修改”的闭环导致 Token 资源消耗极快；二是由于在 Windows 本地开发而部署到 Linux 云端，导致 Docker 打包时频频出现缺少依赖库和数据库表不完整的问题；三是 Codex 思考与打包过程耗时过长。作者由此反思，开发一套系统必须从一开始就规划好后续的部署方式，避免在环境不一致上浪费时间。

💡 主要观点

  1. Codex 6.0 的自动排错机制导致 Token 资源消耗剧增 Codex 6.0 在排查问题时会自主进行“分析定位、写测试用例、跑日志、修改代码”的完整闭环，虽然智能化程度高，但单次排错极易耗尽数小时的额度。
  2. 跨平台开发（Windows 本地到 Linux 云端）导致 Docker 部署频频踩坑 本地测试正常的镜像在云端部署时常出现缺少库或数据库表不完善的问题，迫使开发者在本地反复修改并重新打包，暴露出开发与部署环境不一致的痛点。
  3. AI 编程工具的思考与打包机制导致上线耗时过长 Codex 在打包时需要经历复杂的思考过程并下载第三方组件，导致等待时间久，影响了整体的上线效率。
  4. 独立开发需从一开始就规划好部署方式，避免重复造轮子 作者反思，不能仅满足于本地代码跑通，必须在项目初期就考虑好后续的部署环境与流程，否则会在环境调试上耗费大量无谓的时间。

💬 文章金句

  • 它排查一个问题，基本上就能把你 5 个小时的用量给消耗完。
  • 本地测试没问题的镜像，到云端之后就会有问题，都是一下缺少库，数据库表不完善的问题。
  • 完整的开发一套系统，从一开始就要思考清楚后续的部署方式，我这种就熟悉典型的重复造轮子，只是浪费时间，并没有实质性的业务进展。
