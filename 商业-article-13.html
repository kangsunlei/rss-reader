#168. Agent 的 12 要素：构建可靠 LLM 应用的模式

7/7/2025, 11:00:00 PM

📌 一句话摘要

深入剖析了 AI Agent 在生产环境中的脆弱性，颠覆性地提出“工具调用有害论”，倡导回归软件工程本质，通过掌控控制流、Prompt 和上下文来构建可靠的 LLM 应用。

📝 详细摘要

本期播客深入探讨了当前 AI Agent 在实际应用中面临的普遍困境，特别是其在生产环境中的脆弱性问题。嘉宾 Dex Horsey 提出一个颠覆性观点，认为“工具调用”这一概念本身可能是有害的，因为它模糊了 LLM 输出 JSON 并由确定性代码执行的本质。他倡导开发者应回归软件工程的第一性原理，将 Agent 视为普通软件来构建。核心思想是开发者必须夺回对 Prompt、上下文窗口和核心控制流的掌控权，而非盲目依赖现有框架的抽象。播客详细阐述了如何通过精细化控制输入输出 Token 质量、构建确定性工作流中嵌入小型 Agent 循环、以及实现智能错误处理和人机协作模式来提升 Agent 的可靠性和智能水平。最后，分享了 HumanLayer 正在研发的 2H 协议，旨在解决 AI Agent 与人类交互的难题，推动自动化技术进步，强调通过精准控制和软件工程方法构建具有极大灵活性的可靠 LLM 应用。

💡 主要观点

  1. LLM 应用应回归软件工程本质，警惕“工具调用”的过度抽象 许多 AI Agent 在生产环境中脆弱，原因在于过度依赖“工具调用”的抽象，而非将其视为普通软件，导致控制流复杂且不可靠。
  2. 构建可靠 Agent 的核心在于掌控 Prompt、上下文和控制流 开发者需亲自管理 LLM 的输入（Prompt）和上下文窗口，并设计清晰的控制流，以确保模型输出的质量和任务执行的精确性。
  3. 推荐在确定性工作流中嵌入小型、专注的 Agent 循环以提升可靠性 大型复杂任务可拆解为确定性代码与小型 Agent 的结合，并强调将“联系人类”作为一等输出选项，促进人机协同。

💬 文章金句

  • 我发现大多数生产环境里的 agent 其实智能程度没那么高，他们本质上还是软件，但是很多开发者都在做一些核心的事情，存在一些特定的模式，能让他们基于 LM 的应用做得非常出色。
  • 第一条要素，LLM 最神奇的能力，跟循环 switch 语句、代码工具或者其他任何东西都无关。它最神奇的地方是能把这样一句自然语言转换成这样一段 Jason。
  • 今天我也想斗胆说一句，工具调用是有害的。我加上引号是因为我说的不是让 agent 接入外部世界，这个能力那当然非常厉害。但我认为让事情变复杂的是工具调用这个概念本身。
  • 你真的需要掌控那个核心循环，掌控所有东西是如何组合在一起的这就是统一管理，暂停和恢复第二条要素。
  • 所有能让 A 正变好的方法，归根结底都是上下文工程。Context engineering 你有你的 prompt，你的记忆，你的 rag，你的历史记录站。这一切都是关于我们如何把正确的 token 送进模型，好让他给我们一个非常好的答案，解决用户的问题，或者主要是解决我自己的问题。
