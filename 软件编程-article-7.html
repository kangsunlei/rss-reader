QQ 飞车 Agentic 研发转型过程中的 Loop Engineering

9/8/2026, 4:04:00 AM

📌 一句话摘要

腾讯通过 Loop Engineering 将 AI Agent 融入 QQ 飞车研发，实现从 hook、CI 到工作流的闭环自愈，提升并发度并降低人工注意力。

📝 详细摘要

文章基于腾讯高级后台开发工程师任磊达在 AICon 大会上分享的《QQ 飞车 Agentic 研发转型过程中的 Loop Engineering》进行整理，系统阐述了 Loop Engineering 的概念、四层循环结构以及在实际研发中的落地实践。作者从 hook 级别的自定义 Linter、CI 流程中的自动审查与 auto‑approve、事前‑事中‑事后工作流拆分，到团队层面的 Graph Engineering，展示了如何通过确定性规则回路、闭环自愈和注意力管理，把 agent 从“提示词工程”升级为可复用的工程能力，并分享了并发提升、 token 消耗、冲突修复等具体案例与踩坑经验。

💡 主要观点

  1. Loop Engineering 将 agent 循环化，分为 hook、CI、工作流和组织层四层，实现自动化自愈。 通过自定义 Linter、CI 中的自动 review 与 auto‑approve，以及事前‑事中‑事后交互模型，形成写‑检查‑反馈‑修复的闭环，提升研发并发度并降低人工干预。
  2. 确定性规则回路是约束模型输出的关键。 作者指出不能靠“许愿”约束模型，而是使用 Linter 等硬规则在 agent 写文件后立即触发检查，形成最小单元的 closed loop，确保错误被及时修复。
  3. CI 流程中的评论闭环与 auto‑approve 能显著减轻人工注意力。 在 MR 流水线中，linter 失败自动触发自愈，review 通过规则自动提问并由 agent 回答，issue 与冲突定时清理，使得代码审查过程实现机器主导。
  4. Graph Engineering 用于团队层面的能力复用，避免烟囱式工作台。 通过将个人 loop 抽象为插件化、可编排的 graph，团队成员可以共享、复用已有的自动化流程，提升整体产出并降低重复建设成本。

💬 文章金句

  • loop 的目标是解决具体场景的具体问题，而且在不同环境下有很大的类似性。
  • 我们使用自动驾驶的原因，就是想把重复的事情交给机器，机器可能做得比我们更好。
  • 不能靠"许愿"来约束模型输出，而要依赖确定性的规则回路。
  • linter 报错后自动修、review 提问后自动答、issue 和冲突定时清，这些都是在 CI 流水线的框架内构建的一个个小型闭环。
  • 只有当这三个指标同步向好，才能说 loop 真正在迭代，而不是在空转。
