别让 AI 瞎猜了：用 Harness Engineering 终结无限返工

5/14/2026, 4:02:00 AM

📌 一句话摘要

本文提出 Harness Engineering 方法论，主张通过为 AI Agent 准备稳定的任务入口、执行依据、工具边界、验证反馈和结果记录，将 AI 从一次性生成工具转变为研发流程中可靠的协作执行者。

📝 详细摘要

文章基于爱奇艺技术团队的实践经验，系统阐述了 Harness Engineering 的概念、原理和实践方法。核心观点是：AI 编程工具在局部生成上已足够强大，但稳定交付仍依赖清晰的依据、边界、验证和记录。文章将传统 Prompt Engineering 与 Harness Engineering 对比，指出前者解决“这一轮怎么说清楚”，后者解决“项目里如何持续做对”。 文章详细介绍了最小可用 Harness 的组成，包括任务约束与规则、工具执行入口、上下文和计划工件、权限控制与失败恢复、验证评审与结果记录五类要素。通过前端（Pencil → Storybook → 真实页面）和后端（docs → plan → verify → 实现）两个案例，展示了如何将协作链路工程化。 文章还提供了落地路径，从轻量 Harness 开始，分三个阶段推进：让 Agent 找得到入口、让任务能被复盘和复用、让重复问题逐步机械化。最后给出了适用边界判断标准，并附带了辅助初始化 Prompt。

💡 主要观点

  1. Agent 的可靠性不只来自模型能力，更来自工程条件。 Agent 要稳定参与研发，需要任务入口、执行依据、工具边界、验证反馈和结果记录等工程条件提前准备好，而非仅靠模型回答质量。
  2. Harness Engineering 的核心是将临时上下文迁移到稳定的项目位置。 把项目背景、任务范围、实现偏好、验证方式等从对话中移出，写入 AGENTS.md、docs、plan 等仓库文件，实现信息复用和协作标准化。
  3. 前端和后端场景均可拆分为三层：执行依据层、状态暴露层、交付实现层。 前端用 Pencil 和 Storybook 分别固定结构和状态，后端用 docs 和 verify 脚本固定语义和验证条件，Agent 在结构和状态明确后补实现。
  4. 落地应从轻量 Harness 开始，分阶段推进。 先固定任务统一入口和仓库入口地图，再补充复杂任务计划和可复用验证，最后将高频问题升级为 lint、script 或 CI gate。

💬 文章金句

  • Agent 要可靠参与研发，不能只靠模型回答。项目需要给它准备任务入口、执行依据、工具边界、验证反馈和结果记录。
  • Prompt 解决的是这一轮怎么说清楚，Harness 解决的是项目里如何持续做对。
  • AI 可以加快生成，但稳定交付仍然依赖清晰的依据、边界、验证和记录。
  • 从 Prompt Engineering 走向 Harness Engineering，重点也就在这里：不只追求这一轮让模型回答得更好，而是让项目本身具备一套能支持 Agent 反复接手、验证和回写的工作方式。
