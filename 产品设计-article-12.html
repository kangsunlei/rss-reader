CSS 中的砌体式布局：网格布局应该进化还是为新模块让路？—— Smashing Magazine

5/6/2025, 1:00:00 PM

📌 一句话摘要

分析三种在 CSS 中实现砌体式布局的竞争提案的激烈辩论：网格布局扩展、独立模块或苹果的统一元素流布局方案。

📝 详细摘要

文章分析 CSS 实现砌体式布局的三种竞争方案。第一种建议扩展 CSS 网格布局并加入实验性砌体布局支持（目前已在 Firefox Nightly 中实现），第二种主张开发独立的砌体布局模块以保持网格布局的简洁性。最新提案来自苹果 WebKit 的'元素流布局'，旨在将网格布局、弹性盒布局和砌体式布局概念统一为一个系统。分析涵盖每种方案的技术优势，包括浏览器兼容性挑战、对开发体验的影响，以及替代当前 JavaScript 解决方案的潜力。虽然网格布局集成方案更易上手，独立模块能提供更明确的语义，而元素流布局承诺最全面的解决方案——所有选项仍在讨论中，尚未达成共识。

💡 主要观点

  1. 当前的 JavaScript 解决方案带来性能和维护负担 现有的 Masonry.js 实现需要动态计算，导致布局跳动和响应式问题，凸显了对 CSS 原生解决方案的需求。
  2. CSS 网格布局扩展面临兼容性和复杂性挑战 虽然 Firefox Nightly 的 `grid-template-rows: masonry` 实验性属性展现了潜力，但有限的浏览器支持和增加的网格布局复杂性可能阻碍采用。
  3. 独立砌体布局模块提供语义明确性 专用的 `display: masonry` 属性将提供专门构建的功能而不会使网格布局复杂化，但需要学习新语法。
  4. 元素流布局提案提出统一布局方案 苹果创新的元素流布局方案将网格布局、弹性盒布局和砌体式布局合并为一个系统，通过 `item-pack` 和 `item-slack` 等属性实现精细控制。
  5. 浏览器实现和社区共识将决定结果 最终解决方案取决于厂商支持、工作组决策以及开发者对这些竞争方案的反馈。

💬 文章金句

  • 网格布局规范已经包含 `align-content` 和 `grid-auto-flow` 等属性。在现有规范基础上叠加砌体布局功能可能使其变得过于复杂。
  • 独立模块能保持它们各自特性：网格布局负责秩序，砌体式布局负责流动。
  • 元素流布局旨在使砌体式布局成为这些属性的自然结果，而非独立功能。
  • 开发者需要流畅的体验，从开发效率角度来说，用脚本改造网格布局需要频繁上下文切换。
  • WebKit 团队的愿景是通过统一的元素流属性，结合网格布局的结构优势与砌体式布局的流动性。
