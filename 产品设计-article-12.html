MCP 和 CLI，到底怎么选？

9/3/2026, 11:00:00 PM

📌 一句话摘要

一篇来自 HR SaaS 产品团队的真实踩坑笔记，从原子化接口改造出发，系统梳理了 CLI 与 MCP 两种 Agent 对接方案的差异、适用场景与混合策略，并提出了权限分级管控的商业化思路。

📝 详细摘要

作者所在公司是一家做 HR SaaS 十余年的企业，面对客户直接调用算薪能力的需求和接入 WorkBuddy、千问办公等 Agent 平台的压力，开始探索 MCP 与 CLI 的选型方案。文章首先提出必须先完成「原子化接口」改造——现有面向 GUI 的 OpenAPI 不能直接复用给 Agent，需在鉴权体系和上下文窗口两方面重新设计。随后对比 CLI 与 MCP 的核心差异：CLI 需要硬编码 Skill 编排流程，适合自建 Agent；MCP 提供标准化 schema，Agent 可自主理解调用，更适合对接第三方平台。作者最终策略是同时维护两套方案：自建 Agent 走 CLI+Skills，第三方渠道走 MCP+Skills HTTP 模式，并以权限分级（100 个基础接口 vs 全量 200 个）作为商业化护城河。

💡 主要观点

  1. 不要复用现有的 GUI 导向 OpenAPI，必须单独建设面向 Agent 的原子化接口能力层。 现有 API 的鉴权体系（OAuth 2.0 + 用户 session）和返回格式都不适合 Agent 调用——鉴权需要 API Key/Token，上下文窗口容易被大量数据撑爆。换班案例中因缺少细粒度接口导致 7 分钟失败，加单天查询接口后缩到 1-2 分钟就是典型证明。
  2. CLI 和 MCP 不是替代关系，而是不同场景的最优解。 CLI=基础接口+Skills（必须），强在流程控制，适合自建 Agent；MCP=基础接口+Skills（可选），强在标准化 schema 和远程接入能力，适合对接第三方平台。WorkBuddy 两者都支持，千问办公只支持 MCP+HTTP。
  3. 自建 Agent 应封装为「虚拟员工」，通过差异化能力形成商业化护城河。 相同底层接口，搭配不同 Skill 编排、知识库和性格设定，可塑造出薪酬专员、考勤专员等角色。权限分级策略——第三方渠道只开放 100 个基础接口，全量 200 个+长期记忆留给自建 Agent——既满足多渠道对接，又保护产品售卖空间。

💬 文章金句

  • CLI 跟 MCP 的关系是什么？它们跟接口的关系又是什么？如果想对接到 WorkBuddy 或千问办公等 Agent 产品，到底怎么选？
  • CLI 的核心是流程控制——Skill 告诉 Agent 先干嘛后干嘛，出错了怎么办。Agent 就是个执行者，按剧本走。
  • MCP 和 CLI 真不是谁替代谁，是不同阶段、不同场景的产物。自建 Agent，CLI+Skills 更成熟可控；对接第三方平台，MCP+HTTP 是目前的「最大公约数」。
  • 如果 WorkBuddy 里能用的功能和自建虚拟员工一模一样，客户凭啥还买你的 Agent？
