你觉得 Kimi K3 又慢又贵是吧，我来告诉你为什么

8/11/2026, 7:16:00 AM

📌 一句话摘要

文章解释了 Kimi K3 在刚发布时感觉慢和贵的原因，并说明了模型特性、服务栈优化以及正确使用 Kimi Code 的技巧。

📝 详细摘要

文章首先介绍了作者在使用 Kimi K3 为墨问的 CatReader 添加发现页的实践过程，指出 K3 在前端代码生成和多模态任务上表现出色，被称为前端王者。接着分析了 K3 刚发布时感觉‘慢’的根源：模型参数量巨大（2.8 万亿总参数，激活约 1040 亿），但新模型上线后推理系统（serving stack）的缓存命率、调度等尚未完全调优，导致首 Token 延迟和排队时间增加；同时指出 K3 混合使用 KDA 与 MLA 架构虽然在长上下文下更省显存，但增加了复杂度，需要持续的前缀管理和状态复用优化。随后解释了为何用户觉得 K3 ‘贵’：官方 API 价格相对较高（缓存命中输入 0.3 美元/百万 Token，未命中 3 美元，输出 15 美元），但实际成本还需看完成一个任务的总花费，强大的模型能减少重复读取和修改，从而使总体成本可控；同时提醒用户不要把 Kimi App 的通用额度与 Kimi Code 的专用额度混淆，后者提供本地文件操作、命令执行和会话管理，适合真实代码仓库的连续作业，能显著降低编程任务的 Token 消耗。文章最后展示了作者个人使用数据（7 天 Code 用量 45.45%），并期待 Kimi Code 的订阅计划尽快开放。全文通过技术细节与实操经验相结合，帮助读客全面理解 K3 的性能特点和合理使用方式。

💡 主要观点

  1. K3 初期感觉慢主要是服务栈未完全调优导致的首 Token 延迟和排队时间增加。 尽管模型具备强大的前端代码和多模态能力，但新发布时推理系统的缓存命中率低、调度尚未优化，造成用户在高峰时段感知到明显的延迟。
  2. 成本感知受 API 定价与任务完成效率共同影响，实际使用中总体成本可控。 虽然单 Token 价格较高，但 K3 的强大理解和生成能力能减少重复读取和修改，实际完成一个编程任务的总花费不一定高；此外需区分 Kimi App 与 Kimi Code 的额度使用，避免误判。
  3. 正确区分 Kimi App 与 Kimi Code 可避免不必要的 Token 消耗，提升编程效率。 Kimi App 适合日常问答、写作等通用任务；Kimi Code 提供本地文件读写、命令执行、测试运行和会话管理，使用 Code 能显著降低真实项目开发过程中的 Token 开销。
  4. K3 在前端代码与多模态任务上表现突出，适合真实项目持续使用和迭代。 通过在预训练和后训练阶段加入代码与图像配对数据，K3 在视觉闭环（写代码—看截图—继续修改）中具备较强能力，能够在长上下文场景下稳定生成高质量前端代码。

💬 文章金句

  • K3 确实有种逼近 SOTA 的味道，惊艳，穿云裂帛的感觉
  • 原因是普通用户很容易把刚发布的模型能力当成稳定运行后的能力，还会把模型能力、推理服务、产品入口和计费方式混为一谈。
  • K3 官方 API 价格是：缓存命中的输入每百万 Token 0.3 美元，未命中 3 美元，输出 15 美元。
  • 按照 Kimi 目前的官方说明，Kimi 的会员是共享月度总额度，Kimi Code 另外还有 5 小时和周频控；
  • 我自己用 Kimi Code Web 连续折腾 CatReader 三四天，做了发现页，AskCat 的优化，也做了不少细节调整，7 天 Code 用量 45.45%
