Java 探索载体类，将面向数据编程扩展至 Record 之外

2/4/2026, 2:30:00 PM

📌 一句话摘要

Java 的 Project Amber 正在探索“载体类”和“接口”，旨在将 Record 的减少样板代码和模式匹配优势引入更灵活的传统类设计中。

📝 详细摘要

本文详细介绍了 OpenJDK Project Amber 题为“超越 Record”的新设计笔记。虽然 Java Record（在 Java 16 中引入）通过减少不可变数据的样板代码彻底改变了数据建模，但它们在继承、可变性和内部状态表示方面存在严格限制。该提案引入了“载体类（carrier classes）”，允许开发者在类头中声明状态描述（类似于 Record），同时保留标准类的灵活性。这使得需要缓存字段或复杂内部逻辑的类能够使用编译器生成的访问器和解构模式等特性。此外，该笔记还探讨了“载体接口（carrier interfaces）”以简化类元组抽象，标志着 Java 向面向数据编程（DOP）的更广泛转变，即将数据视为主要的抽象。

💡 主要观点

  1. 当需求超出简单的不可变数据时，Record 会遭遇“悬崖效应”。 当开发者需要可变性、继承或缓存字段时，目前必须回归传统类，从而失去 Record 的所有简洁优势和编译器生成的特性。
  2. 载体类弥补了简洁的 Record 与灵活的传统类之间的鸿沟。 通过允许在类头中进行状态描述，载体类使编译器能够推导出访问器和解构模式，而无需强制类必须是不可变或 final 的。
  3. 该提案支持在数据载体中缓存派生值等高级模式。 与 Record 不同，载体类可以维护不属于公共状态描述的内部状态（如预计算的范数），从而在保持 API 整洁的同时实现性能优化。
  4. 载体接口将模式匹配能力扩展到抽象类型和元组。 这允许接口参与解构模式，简化了多态数据结构的处理，使代码更具表现力且类型安全。
  5. Java 正在战略性地转向通过 DOP 将数据视为主要抽象。 密封类型、Record 以及现在的载体类相结合，鼓励开发者直接建模数据结构，而不是将其隐藏在重重分层的面向对象 API 之后。

💬 文章金句

  • 该文档将这种转变描述为“掉下悬崖”；即与参考模型的微小偏离会导致代码量大幅增加。
  • 提议引入载体类是为了平滑这一转变。
  • 与 Record 不同，载体类不要求将其状态完全存储在这些组件中。
  • Goetz 认为，一个关键挑战是帮助开发者认识到，当把数据视为主要抽象时，可以消除多少辅助代码。
  • 这标志着 Project Amber 在减少样板代码以及将现代语言特性扩展到更复杂的类设计方面所做的持续努力。
