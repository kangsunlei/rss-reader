Agent 的命门是上下文：关键不在少给，而在给对

8/18/2026, 12:45:00 AM

📌 一句话摘要

作者通过三组对照实验与一项重复实验证明，多 Agent 流程的 Token 优化关键不在「少给」而在「给对」，并提出「上下文信息密度 = 当前步骤相关可执行信息 ÷ 进入窗口的全部上下文」的判断框架。

📝 详细摘要

文章来自腾讯云开发者，作者黄照坤基于自研多 Agent 工作流 Devflow，提出「省 Token 不是少给，而是给对」的核心主张。他用一张 2480 万 Token、约 202 元的真实账单作为起点，质疑两条直觉上都在「做减法」的优化——CodeGraph（代码结构图谱）和 RTK（终端输出压缩器）——为何没能压低总成本。 他将「省 Token」拆为三层：局部输出、行动路径、整体结果。CodeGraph 的三组实验显示，结构查询在面向明确符号时能把总 Token 压低 80.0%，但面对完整调用链或精确 path:line 任务时反而增加 95.8%~152.9%，且跨轮次上下文会「存活」抵消局部收益。RTK 的 24 组 pair 实验把终端字符压短 40.19%，但原始总 Token 增加 4.23%（均衡后 5.84%），13 个更贵、11 个更省；重复 10 次实验后，RTK 组方差约为对照组 2.36 倍。 基于这些边界条件，作者在改造后的工作流中做了三件事：把「交接纸条」（Handoff）与「完整材料」（Artifact）分层；让 CodeGraph 只在需要建立结构的前段付一次成本，RTK 改为按场景启用并加熔断与回退；把状态迁移、路由、去重交给脚本，主 Agent 不再在每站重新理解上下文。最终 GLM 模型下平均每步 Token 从 10.68 万降到 6.70 万，Claude 下总 Token 下降 23.34%。

💡 主要观点

  1. 「省 Token」必须分三层评估：局部输出、行动路径、整体结果，缺一不可。 工具输出变短只是成本链路的一个局部信号；它会改变 Agent 下一步搜什么、测什么、改什么，最终落到端到端成本的方向是不确定的，必须把整条任务的步骤都算进来才能判断。
  2. CodeGraph 的成本方向由任务形态决定，且跨轮次上下文会「存活」抵消局部收益。 面向明确符号时可省 80%，但完整调用链与精确行号任务反而增 95.8%~152.9%；第一轮节省 42.5% 后，第二轮即使限制探索，总消耗仍达未启用组的 3.46 倍，两轮合计反贵 31.6%。
  3. RTK 终端字符压短 40%，但原始总 Token 增 4.23%，且可能过滤掉关键线索。 24 个 pair 中 13 个更贵、11 个更省；重复 10 次后未坐实「稳定反增」，但 RTK 组方差为对照组 2.36 倍；宽泛搜索中原生 rg 有 158~178 个关键命中，经过 RTK 后全部归零。
  4. 真正有效的优化是把上下文拆成 Handoff + Artifact，让 CodeGraph 只在前段付一次成本。 同一份代码地图让后续 Architect/Developer/Review/Test 复用，地图只在前段付一次成本，后续角色复用定位结果，再针对自己的判断回到源码；RTK 改为按场景启用，配 Hook、熔断与回退。
  5. 把状态迁移、路由、去重交给程序，模型把精力留给推理和判断。 Architect 完成后直接唤醒 Developer，Main 不再每站重新理解上下文；脚本负责原子 claim、重复派发保护、计划边界检查，让「短 Handoff + 状态机」形成一条新的信息流。

💬 文章金句

  • 省 Token 走到最后，留下的应该是一份当下刚好够用、随时可以回源的上下文。
  • 上下文信息密度 = 当前步骤真正相关、可执行、可验证的信息 ÷ 进入模型窗口的全部上下文。
  • 地图适合帮我找到那几条街。走到门口以后，它就应该收起来。
  • 终端少四成，只能说明终端变短了。
  • 省 Token 不是少给，而是给对。
