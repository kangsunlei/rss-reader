harness-pilot 给代码库加一套"规则说明书"和"自动检查器"

6/17/2026, 10:00:00 AM

📌 一句话摘要

Harness Pilot 通过将项目规范显式化、版本化并集成到 Git 工作流，实现从依赖 AI 自觉的事后检查到编码前强制预验证的范式转变，确保 AI Agent 在架构约束内可靠协作。

📝 详细摘要

文章详细介绍了 Harness Pilot 这一 Claude Code 插件，旨在解决 AI Agent 在代码库协作中因无法感知隐性规则（如分层约束、命名规范、架构约定）而导致的反复违规与上下文污染问题。核心思路是将规则从 Wiki 或口头约定沉淀到 Git 仓库中，实现版本化与自包含。文章阐述了四条设计原则：Git 仓库作为唯一事实来源、.harness/ 目录自包含、关注边界解耦实现、预验证优于事后检查。随后深入介绍了插件的两大核心 Skill（harness-analyze 与 harness-apply）、五类内置 Agent 以及分层模板系统。关键机制包括自动化审查-测试-修复的 Ralph Wiggum Loop、基于文件系统实现跨会话状态持久化的 Handoff 机制、支持增量更新的 Reentrant Apply 以及 Hooks。文章还对比了业界在 Harness 架构上的共识与演进，并提供了完整的架构设计与使用效果示例。

💡 主要观点

  1. AI Agent 协作的核心挑战是隐性规则的不可见性。 项目中的分层约束、命名规范等对 Agent 是隐性的，若未在仓库中显式化，Agent 会反复违规，陷入修复循环，上下文被错误日志填满。
  2. 解决思路是从依赖 AI 自觉的「教」转向依靠自动化脚本的「验」。 现有方案（System Prompt、RAG、CI/CD Lint）的局限在于规则更新滞后、检查时机靠后、约束力依赖自觉。Harness Pilot 通过版本化规则、编码前预验证和自动化强制执行来克服这些局限。
  3. Harness Pilot 的核心机制包括 Ralph Wiggum Loop 和 Handoff。 Ralph Wiggum Loop 是自动化的审查-测试-修复质量循环，最多执行 3 轮。Handoff 机制通过结构化 artifacts（agent-state.json、context.json、resume.json）实现跨会话状态持久化，摆脱对 AI 内部记忆的依赖。
  4. 设计原则强调预验证优于事后检查。 在执行结构性操作前优先验证其合法性，在编写代码前确认可行性，而非事后修补，从而大幅降低代码修复成本。

💬 文章金句

  • 与其试图「教导」AI Agent 如何正确执行任务，不如赋予其自动验证执行结果正确性的能力。
  • 依靠代码、linter 及自动化测试来保障正确性，而非依赖 LLM 的「直觉」。
