📌 一句话摘要

深入剖析 Java `LockSupport.park()` 与 `Thread.interrupt()` 的复杂交互，揭示了 `permit` 机制与中断标志的独立性及其受日志等细微时序影响的阻塞行为。

📝 详细摘要

文章详细探讨了 Java 并发编程中 `LockSupport.park()` 和 `Thread.interrupt()` 的实际行为，挑战了“中断后再次 park 不会阻塞”的普遍认知。通过精心设计的实验，作者发现即使清除中断标记，有时也需要连续两次 `park()` 才能阻塞线程，更令人惊讶的是，日志打印方式（参数化 vs 字符串拼接）竟能影响这一行为。文章深入分析了其核心原因：`permit`（许可）与 Java 中断标志是两套独立机制。`interrupt()` 会隐式调用 `unpark()` 设置 `permit=1`，而 `park()` 消耗 `permit`。`Thread.interrupted()` 仅清除 Java 中断标志，不影响 `permit`。日志格式等细微时序变化会影响 `permit` 的设置和消费时机，从而导致不同的阻塞行为。这为理解 Java 并发中的底层机制提供了宝贵视角。

💡 主要观点

  1. Java 中断标志与 `LockSupport` 的 `permit` 是两套独立机制 `Thread.interrupt()` 会隐式调用 `unpark()` 设置 `permit=1`，而 `park()` 消耗 `permit`。`Thread.interrupted()` 只清除 Java 中断标志，不影响 `permit` 状态，这是导致意外阻塞行为的核心原因。
  2. 细微的时序变化（如日志打印方式）可影响 `park()` 的阻塞行为 参数化日志的延迟拼接可能改变代码执行时序，导致 `permit` 在 `park()` 调用时机上发生微妙变化，从而影响线程是否立即阻塞。
  3. `permit` 为二元许可状态，多次 `unpark` 仅补充一份许可 线程的 `Parker` 对象内部维护的 `_counter`（即 `permit`）是二元状态（0 或 1），多次调用 `unpark()` 不会累加许可，这解释了 `park()` 行为的确定性。
  4. 理解 `park()` 底层原理对并发调试至关重要 深入理解 `Unsafe.park()` 和 `unpark()` 如何与 `Parker` 对象的 `_counter`、条件变量及互斥锁交互，是排查复杂并发问题的关键。
