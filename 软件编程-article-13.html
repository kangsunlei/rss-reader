MCP 走向无状态，开发者追问：这不就又变回 API 了吗？

8/19/2026, 6:33:00 AM

📌 一句话摘要

MCP 2026-07-28 规范移除协议会话实现无状态化，网关可通过新增 HTTP 标头直接路由智能体流量，引发社区关于 MCP 是否沦为 REST API 的激烈讨论。

📝 详细摘要

本文报道 MCP 2026-07-28 规范的核心变更：移除协议会话，新增 Mcp-Method 和 Mcp-Name 两个必需 HTTP 标头，使网关无需解析请求正文即可对智能体流量进行路由、限流和计量。文章梳理了有状态到无状态的技术演进逻辑——早期 MCP 通过 initialize/initialized 握手建立会话，依赖 Mcp-Session-Id 跟踪状态，导致自动扩缩容困难、负载均衡受限；新协议每个请求携带版本、客户端身份和能力，任意请求可落到任意实例。同时，规范还收紧了授权机制（弃用动态客户端注册、采用 RFC 9207/8707），并将 Elicitation 从开放流改为多轮往返请求。Hacker News 社区出现尖锐分歧：一方认为 MCP 最终变成了 REST API，另一方强调其核心价值在于获得 AI 提供商认可的标准地位。文章引用 Anthropic 数据（SDK 月下载量超 4 亿次，今年增长三倍）和 Sentry Cramer 的观点，指出资金正流向网关与身份验证层而非服务器本身，并给出迁移路径建议。

💡 主要观点

  1. MCP 无状态化使网关可直接基于 HTTP 标头路由智能体流量。 新增 Mcp-Method 和 Mcp-Name 标头让网关无需解析 JSON-RPC 正文即可识别工具调用类型，复用现有 API 网关基础设施实现限流、计量和路由。
  2. 社区分歧核心在于 MCP 是否失去了协议独特性。 批评者认为无状态 MCP 最终等同于 REST API 加 OpenAPI 规范；辩护者强调其真正价值是获得 Anthropic 等 AI 提供商认可并推动广泛实现的标准地位。
  3. 授权与 Elicitation 机制同步收紧，工程复杂度降低。 弃用动态客户端注册、采用 RFC 标准进行颁发者标识和资源绑定；Elicitation 从保持连接改为多轮往返，部署更简单但人工审批流程不再位于单次调用内部。
  4. 基础设施投资正从服务器本身转向网关与身份层。 Sentry Cramer 指出只有底层管道不再占据整个故事时智能体才真正有用；咨询案例显示资金流向网关、注册中心和认证层，而非 MCP 服务器。

💬 文章金句

  • 我们发明了一种有状态协议，发现状态难以扩展，于是剥离了状态，最终得到的结果是发一个 POST 请求就行。REST 阵营已经得意地等待这一刻 20 年了。
  • MCP 带来的核心优势在于，它是一项获得 AI 提供商认可的标准，正因为如此，人们有强烈的动力真正去实现它。
  • 只有当底层管道不再占据整个故事时，智能体才真正变得有用。
  • 资金正在流向网关、注册中心和身份验证层，而不是服务器本身。
