相比层出不穷的 Agent 框架，不变的 Agent Protocol 是什么

7/2/2026, 3:05:00 AM

📌 一句话摘要

本文从协议视角拆解 Agent Runtime，提出 Thread、Run、Step、Event、Artifact、Checkpoint 六个跨框架稳定对象，并区分执行模型的两层结构（Loop 承载与编排协议），帮助开发者穿透 API 变化看本质。

📝 详细摘要

文章针对 Agent 框架层出不穷、API 各成体系的问题，从协议层面提出 Agent Protocol 的概念框架。作者首先定义 6 个通用协议对象（Thread/Session、Run/Task、Step、Event、Artifact、Checkpoint），并分层解释具体协议标准、通用协议对象和 Runtime 实现能力。接着深入执行模型，将其拆为两层：Runtime Loop 的承载方式（图式/代码式/托管式）和编排协议模式（ReAct、Plan-and-Execute、Conversation-style coordination）。文章引入 Agent Harness 概念，以 Deep Agents SDK 为例说明如何将 Runtime 能力打包成易用的长任务体验，并对比 LangGraph、OpenAI、AutoGen、Claude SDK 等框架在对应维度上的设计差异。最后讨论了事件驱动 Runtime、Workspace/Sandbox 以及设计决策的取舍。全文贯穿一个核心观点：框架 API 会变，但任务生命周期管理、状态持久化、中断恢复、可观测性等底层问题不变，理解协议边界比追逐新框架更重要。

💡 主要观点

  1. Agent Runtime 的核心不是模型调用，而是任务生命周期管理。 一个生产级 Agent 需要管理任务的启动、上下文携带、步骤执行、事件观察、中断恢复和产物沉淀，这些都围绕 Thread、Run、Step、Event、Artifact、Checkpoint 六个稳定对象展开。
  2. 执行模型应分两层理解：Loop 承载方式与编排协议模式。 Loop 承载方式（图式/代码式/托管式）决定循环在哪里运行和谁掌控控制流；编排协议（ReAct、Plan-and-Execute 等）决定循环内部哪些语义被显式建模为状态对象，两者不可混淆。
  3. Agent Harness 将 Runtime 能力产品化为默认体验，但同时带来约束。 Harness（如 Deep Agents、Claude Agent SDK）向开发者提供开箱即用的规划、子智能体、文件系统、权限模型等，降低了使用门槛，但强封装意味着需理解其决策并在复杂场景下保留覆写能力。
  4. 真正区分玩具 Agent 和生产 Agent 的是状态持久化、中断恢复、可观测性和可评测性。 这些能力对应了 Checkpoint、Event、Trace 等协议对象，决定了 Agent 能否在真实业务中可靠执行、故障恢复和审计追踪。

💬 文章金句

  • 框架会更迭，协议对象会换名字，但生产级 Agent 系统要解决的问题不会消失。
  • Agent Runtime 的核心不是模型调用，而是任务生命周期管理。
  • Protocol 是 Runtime 的外部边界，Runtime 是 Protocol 的内部实现。
  • 真正区分玩具 Agent 和生产 Agent 的，是状态持久化、中断恢复、可观测性和可评测性。
