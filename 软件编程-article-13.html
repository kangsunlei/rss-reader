分享一些 agent 开发中常遇到的解析问题

6/13/2026, 8:41:45 AM

📌 一句话摘要

本文指出当前 Agent 处理复杂文档时因解析过于扁平而丢失关键信息，并提出通过构建可导航的文档状态（Document World State）来提升 Agent 在长任务中的可靠性与记忆能力。

📝 详细摘要

文章从实际开发经验出发，指出当前 Agent 在处理合同、投资备忘录、产品文档等复杂材料时，常因将文档简单视为「一长串文字」而丢失关键信息。作者认为，这种「二维」的扁平处理方式在传统软件中尚可接受，但对于需要记忆、推理和长期任务的 Agent 来说远远不够。Agent 需要理解文档的版本、章节层级、表格图片、批注状态、引用关系等「三维甚至四维」的信息。作者提出解决方案是为 Agent 构建一个可行动的外部世界——Document World State，包含 Document、Section、Chunk、Asset、Metadata、Graph Link、Retrieval Trace 等结构化元素，并介绍了其开源工具 Knowhere 的实现思路与架构分层（Model、Harness、Knowhere、Retrieval Infra），旨在将一次性文件处理转变为 Agent 可长期访问、导航和引用的可操作状态。

💡 主要观点

  1. 当前 Agent 对复杂文档的解析过于扁平，丢失了关键的结构化信息。 合同、投资 memo、产品文档等包含版本、引用、表格、批注、变更记录等复杂关系，简单压成文本片段会导致信息在进入模型前就已丢失。
  2. 长任务 Agent 需要可导航、可记忆的外部文档状态，而非一次性上下文。 Agent 应像人类实习生一样，能反复回到文档、导航引用、记住来源，而不是每次任务都重新处理。作者将此称为「Document World State」。
  3. Knowhere 通过结构化解析与图关系，将文档转化为 Agent 可操作的知识状态。 工具将文档解析为 Document → Section → Chunk → Asset → Metadata → Graph Link → Retrieval Trace 的层次结构，支持 search、open_document、inspect_asset 等细粒度操作。

💬 文章金句

  • 文档不是附件，文档是 Agent 要进入的工作现场。
  • 真正能进入知识工作的 Agent，缺的不是更多上下文，而是一个可以行动的知识状态。
  • 模型会继续变强，材料会继续变杂。
