QCon London 2026：随着 CRA 执行临近，SBOM 从最佳实践变为法律强制要求

3/18/2026, 1:04:00 PM

📌 一句话摘要

本文详细介绍了软件物料清单（SBOM）在欧盟《网络弹性法案》（CRA）下从安全最佳实践向法律强制要求的转变，并概述了其生成和分发的技术工作流程。

📝 详细摘要

本文报道了 QCon London 2026 的内容，重点介绍了 Viktor Petersson 对欧盟《网络弹性法案》（CRA）即将执行的见解。与 GDPR 不同，CRA 授权监管机构禁止不合规产品进入欧洲市场，这使得 SBOM 到 2027 年底成为一项关键的法律要求。讨论涵盖了 SBOM 的技术格局，比较了 SPDX 和 CycloneDX 标准，并详细介绍了高质量生成的四个阶段蓝图：创建、增强、丰富和签名。Petersson 强调了使用特定领域的生成器而非通用容器扫描器的重要性，并指出签名必须在 CI/CD 流水线内进行，以确保可验证的溯源链。最后，文章介绍了透明度交换 API（TEA），作为一种新兴的 ISO 标准，用于安全制品的程序化分发。

💡 主要观点

  1. 欧盟《网络弹性法案》（CRA）将 SBOM 转变为数字产品的强制性法律要求。 随着 2026 年执行工作的开始，CRA 的影响不仅限于罚款，它还允许监管机构禁止不合规软件进入欧洲市场，因此必须立即采用 SBOM 工作流程。
  2. 高质量的 SBOM 生成需要特定领域的工具，而不是通用的容器扫描捷径。 在大型 Docker 镜像上使用通用扫描器通常会导致数据质量低下；开发人员应使用特定于语言的生成器（例如 Python 或 Rust）来确保准确的依赖关系映射。
  3. 在 CI/CD 流水线中进行加密签名对于建立可验证的溯源链至关重要。 在构建流水线中创建 SBOM 时立即进行签名可以防止篡改，并提供一种将软件制品直接与其记录的组件相关联的证明。
  4. 透明度交换 API（TEA）旨在标准化安全制品的程序化分发。 作为一项新兴的 ISO 标准，TEA 提供了一种通用的发现机制，允许消费者和监管机构通过平台无关的 API 检索 SBOM 和漏洞数据。

💬 文章金句

  • SBOM 已成为了解软件构成情况的试金石。
  • CRA 不仅仅是罚款。他们实际上可以阻止销售。你的产品可能会被禁止进入欧洲市场。
  • 有签名总比没有好。请务必在你的流水线中对 SBOM 进行签名，而不是在某人的机器上进行。
  • 如今处理 SBOM 的感觉就像 90 年代管理源代码一样，补丁都是通过电子邮件发送的。
