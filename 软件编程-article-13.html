攻击者主动扫描 LiteLLM AI 服务器，漏洞链可实现无认证 RCE

11/21/2026, 11:07:00 AM

📌 一句话摘要

攻击者通过扫描暴露的 LiteLLM AI 服务器，组合利用 CVE-2026-42271 和 CVE-2026-48710 漏洞，实现无认证 RCE，从而窃取 AI 网关存储的 API 密钥，危害连锁反映 lied。

📝 详细摘要

本文披露了攻击者针对 LiteLLM AI 网关的主动扫描活动，利用两个漏洞链（CVE-2026-42271 和 CVE-2026-48710）实现无认证远程代码执行。第一个漏洞存在于 LiteLLM 的 MCP 测试端点，允许执行任意命令；第二个漏洞为 Starlette 框架的 BadHost 漏洞，可绕过身份验证。攻击者通过伪造的 Bearer 令牌和恶意 Host 头，成功触发 RCE 并窃取存储的 API 密钥。Wiz 研究指出，9.6%的公网暴露 LiteLLM 实例使用默认主密钥或未开启认证。文章建议及时打补丁、下线管理端点、配置 WAF 规则，并检查日志以识别潜在入侵。

💡 主要观点

  1. 攻击者利用 CVE-2026-42271 和 CVE-2026-48710 漏洞链实现无认证 RCE CVE-2026-42271 存在于 LiteLLM 的 MCP 测试端点，允许执行任意命令；CVE-2026-48710 为 Starlette 框架的 BadHost 漏洞，可绕过身份验证。攻击者通过伪造 Host 头和 Bearer 令牌，将请求视为合法，从而触发代码执行。
  2. LiteLLM 网关存储大量敏感 API 密钥，一旦被攻破导致连锁反应 AI 网关通常存储多家模型服务商、云账户的访问密钥，攻击者一旦获得 RCE 权限，可读取环境变量和存储的密钥，进而盗刷服务额度或访问受保护数据，危害极大。
  3. 公网暴露的 LiteLLM 实例安全风险高，9.6%使用默认密钥或无认证 Wiz 研究人员扫描发现，294 个公网暴露的 LiteLLM 实例中有 9.6%使用默认主密钥或未开启身份认证，攻击者可轻易通过弱密钥或暴力破解获取访问权限。
  4. 首要防护措施是及时打补丁并缩减攻击面 用户应将 LiteLLM 升级至 1.83.7 及以上版本，Starlette 升级至 1.0.1 及以上版本。同时应将管理端点和测试端点从公网下线，部署在 VPN 或带认证的反向代理之后。

💬 文章金句

  • 攻击者目前正全网扫描暴露的 LiteLLM 服务器，试图组合利用两个漏洞，无需登录即可获得 RCE 权限。
  • 两个漏洞分别编号为 CVE-2026-42271 和 CVE-2026-48710。
  • LiteLLM 今年已多次成为攻击目标。今年 3 月，攻击者曾通过 PyPI 推送投毒版本，10 月又发生了第二次投毒版本事件。
  • Wiz 研究人员曾扫描 3074 个公网暴露的 LiteLLM 实例，发现其中 294 个（占比 9.6%）要么使用默认主密钥，要么完全未开启身份认证。
