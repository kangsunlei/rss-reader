📝 详细摘要

文章是「Playwright 7 天实战训练营」系列教程的第二篇，聚焦于自动化测试中最核心的元素定位问题。作者首先指出了定位不稳导致用例失败的常见痛点，然后提出了「能用语义定位就不用 CSS，能用 CSS 就不用 XPath」的核心原则。文章详细拆解了 Playwright 提供的 7 种定位方式，按推荐优先级排序：`get_by_role`（最推荐）、`get_by_text`、`get_by_test_id`、`get_by_placeholder`、`get_by_label`、CSS 选择器（通用兜底）和 XPath（万不得已）。每种方式都配有原理说明、代码示例、适用场景和注意事项，并特别讨论了多语言产品下的定位策略。最后，通过重写 Day1 的登录脚本进行实战演示，并提供了常见问题排查指南。文章结构清晰，内容实用，旨在帮助读者建立正确的定位策略，告别因页面变更导致的脚本不稳定问题。

💡 主要观点

  1. 遵循「语义优先」的定位原则，优先使用 `get_by_role` 和 `get_by_text`。 语义化定位（如通过按钮角色和文本）最接近用户视角，不依赖于易变的 ID 或 CSS 类名，因此对前端样式变更的抵抗力最强，代码可读性也更高。
  2. `get_by_test_id` 是企业级项目实现稳定定位和测试左移的最佳实践。 通过开发在元素上添加专用的 `data-testid` 属性，可以实现测试与 UI 样式的解耦，即使开发修改样式或文案，测试脚本也不会失效，但这需要开发团队的配合。
  3. CSS 选择器应作为通用兜底方案，XPath 仅在万不得已时使用。 CSS 选择器虽然通用，但依赖页面结构，稳定性不如语义定位。XPath 可读性差、维护成本高，且对页面结构变化极其敏感，应尽量避免。
  4. 针对多语言产品，需调整定位策略，优先使用 `get_by_test_id` 或 `get_by_role`。 依赖文本的 `get_by_text` 在多语言环境下会因文案变化而失效，因此需要提前与开发协商使用 `test_id` 或利用不随语言变化的角色进行定位。

💬 文章金句

  • 定位是写自动化用例的基础，定位不稳，用例必挂。
  • 能用语义定位就不用 CSS，能用 CSS 就不用 XPath。因为越接近用户视角的定位越稳——用户看到的是‘登录按钮’，不是 #btn-login。
  • `get_by_test_id` 是企业项目首选（需开发配合）。好处：开发改样式、改文案都不影响你，因为 testid 是专门给测试用的。
  • XPath：万不得已才用。为什么不推荐：可读性差，维护成本高，页面结构一改就挂。
