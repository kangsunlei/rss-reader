📌 一句话摘要

本文通过小测试探讨 Claude Code 子代理模型配置策略与对抗审查效果，反思多审查者单裁判架构的局限。

📝 详细摘要

作者通过环境变量测试 Claude Code 子代理模型设置，从 Opus 回答了解全局与分层控制的取舍，并用对抗审查实验对比 Sonnet 5 与 Opus 4.8 的能力。文章反思单一评判者的偏见问题及 vibe coding 时代人类审查耐心的下降，展望未来多裁判交叉验证架构。

💡 主要观点

  1. Claude Code 子代理模型可通过环境变量全局设置，但分层控制更灵活。 全局设置简单但可能导致规划类任务质量下降；按角色在 frontmatter 中指定模型可更好平衡成本与质量。
  2. 对抗性审查中多个审查者能更全面发现 bug，但最终裁判的可靠性是瓶颈。 实验中 Sonnet 5 和 Opus 4.8 都能发现一些 bug，但单一裁判可能引入偏见或遗漏，需要人类介入。
  3. 单一裁判的局限性可能促使未来出现多裁判交叉验证方案。 作者反思 vibe coding 时代人类检查耐心有限，提出让多个裁判交叉审查裁判结果以提高可靠性。

💬 文章金句

  • 如果你会用到 arch 这类规划型子代理，别用全局 env 一刀切；改成'默认继承 + 给轻量代理单独在 frontmatter 里降 Sonnet'。
  • judge 出问题，只有人类亲自检查。但是在越发浮躁的 vibe coding 时代，真的会有耐心去挨个看子代理的返回结果吗？
