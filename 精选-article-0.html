📌 一句话摘要

本文系统性分析了多 Agent 架构的演进路径，从中心调度的 Master Agent、任务看板模式，到按需咨询的 Advisor 模式，阐述了控制权如何从中心下沉到执行者，从而提升系统的并行能力、弹性和专业化决策。

📝 详细摘要

当任务从单次回答演变为长链路工作时，单一 Agent 的智力瓶颈不再是核心问题，关键在于如何组织行动。本文从控制权的视角，梳理了三种典型的多 Agent 协作架构：Master Agent 调度模式将决策集中于中心节点，适合流程固定的场景；任务看板模式通过共享状态实现调度下沉，支持并行领取和故障恢复；Advisor 模式则在执行节点主动寻求专业意见，实现按需咨询。通过中间件巡检的落地案例，作者展示了三种模式如何在实际系统中组合运用，从而实现控制权与问题复杂度的匹配。

💡 主要观点

  1. 控制权决定协作架构的设计哲学 Master Agent 模式将决策集中，适合流程固定的任务；任务看板模式通过共享状态实现调度下沉，提升并行和弹性；Advisor 模式则让执行者主动寻求专业意见，实现按需咨询。
  2. 上下文边界和模型边界是划分 Agent 职责的关键 不同 Agent 应聚焦于特定的上下文范围和信息压缩目标，避免职责模糊；同时，利用小模型进行快速筛选，大模型进行深度推理，可在速度与质量之间取得平衡。
  3. 任务看板需要配合状态机实现可靠的并行处理 通过 PENDING、CLAIMED、RUNNING、SUCCEEDED、FAILED 等状态管理任务生命周期，配合锁或租约机制，确保任务领取、执行和结果传递的一致性与幂等性。
  4. Advisor 模式实现按需专业咨询，降低系统复杂度 执行 Agent 在面临高风险判断或专业盲区时主动向 Advisor 征求意见，Advisor 提供第二意见后，执行 Agent 仍保留最终决策权，避免不必要的流程编排。
  5. 落地案例展示了三种模式的组合应用 在中间件巡检场景中，Master Agent 负责意图提取与路由，任务看板支持 Worker Agent 并行领取和自愈，Advisor 按需提供根因分析，最终形成结构化的巡检报告。

💬 文章金句

  • 多 Agent 架构真正要解决的不是'如何调用更多模型'，而是四个组织问题：谁拆解任务，谁分配任务，谁判断任务完成，以及 Agent 之间共享什么信息。
  • 三种架构分别把'下一步做什么'的决定交给中心节点、共享状态和当前执行者，呈现出一条清晰的控制权下沉路径。
  • 架构选择应让控制权与问题匹配：需要统一顺序的步骤交给编排，可以并行的任务由共享状态协调，执行中的专业疑问通过按需咨询补足。
