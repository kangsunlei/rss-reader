在 React 和 Next.js 中构建动态表单 — Smashing Magazine

📌 一句话摘要

本文对比了构建复杂动态表单的组件驱动（React Hook Form + Zod）与模式驱动（SurveyJS）方法，并强调了何时应将表单视为 UI 以及何时应视为规则引擎。

📝 详细摘要

本文探讨了 React 开发中一个常见的架构挑战：表单何时从简单的 UI 组件转变为复杂的业务规则引擎。文章对比了行业标准技术栈（React Hook Form、Zod 和 React Query）与使用 SurveyJS 的模式驱动方法。通过一个涉及条件显示、派生计算和动态导航的实际多步骤表单示例，作者展示了传统技术栈如何将逻辑分散在 Hook 和 JSX 中，从而导致难以审计。相比之下，模式驱动模型将业务逻辑集中在 JSON 对象中，使其与 React 组件树解耦。这带来了更好的可维护性、更简单的版本控制，并让非工程师在无需部署代码的情况下修改表单行为成为可能。

💡 主要观点

  1. 表单通常会从简单的 UI 组件演变为复杂的业务规则引擎。 随着表单不断累积显示规则、派生值和条件导航，传统的组件驱动模型会失效，因为逻辑变得分散且难以检查。
  2. RHF + Zod 技术栈非常适合逻辑较浅的 CRUD 导向型表单。 当工程师掌握所有行为且逻辑主要由 UI 驱动时，该技术栈表现出色，能为 React 开发者提供高性能和熟悉的思维模型。
  3. 模式驱动表单将业务逻辑集中在 JSON 结构中。 通过使用 SurveyJS 等运行时引擎，开发者可以将显示、校验和计算逻辑移入独立于 UI 渲染层的模式（Schema）中。
  4. 将表单逻辑与代码解耦可实现运营灵活性。 将表单逻辑存储为 JSON 使得逻辑可以在数据库中进行版本控制，或由非工程师（如 PM 或法务团队）编辑，而无需进行完整的软件部署。
  5. 根据业务逻辑的权重选择抽象方式。 当表单主要涉及页面和布局时，使用组件驱动方法；当表单编码了关键且不断变化的业务决策时，使用模式驱动引擎。

💬 文章金句

  • 有些表单始终是 UI，而另一些则悄然变成了规则引擎。
  • 问题在于，当抽象不再匹配问题时，我们往往仍倾向于继续使用它，因为替代方案需要一种不同的思维方式。
  • 表单确实可以运行，但其行为无法作为一个系统进行检查，必须在脑中模拟执行。
  • 如果是页面展示，你需要组件驱动表单；如果是业务逻辑，如阈值和分支规则，你需要模式引擎。
  • React 组件不再包含任何业务逻辑……React 正在做它真正擅长的事情：渲染组件并将其连接到 API 调用。
