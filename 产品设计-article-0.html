📌 一句话摘要

本文探讨了从复杂的 JavaScript 工具提示库向原生浏览器 Popover API 的转变，强调了在无障碍性、代码简洁性和平台级可靠性方面的显著提升。

📝 详细摘要

作者回顾了过去使用 JavaScript 库构建工具提示的必要性，并指出这些库往往会带来脆弱性和无障碍性欠账。通过使用原生 Popover API 重构工具提示，本文展示了浏览器现在如何以声明式方式处理核心交互——例如打开、关闭和 Escape 键关闭。文章详细介绍了“免费”获得的无障碍优势，包括自动 ARIA 状态同步和可预测的键盘焦点管理。虽然作者承认 JavaScript 在优化“人类意图”（如悬停延迟）方面仍然有用，且库在处理复杂定位或大规模设计系统时依然具有价值，但文章认为原生 API 现在应成为现代 Web 开发的默认选择。

💡 主要观点

  1. Popover API 将 UI 责任从临时的 JavaScript 转移到了浏览器平台。 浏览器原生理解组件的生命周期，而不是通过事件监听器和手动状态管理来模拟工具提示行为，从而减少了代码的脆弱性和维护开销。
  2. 原生弹出框提供了难以手动复制的“免费”无障碍优势。 该 API 自动处理 Escape 键关闭、更新 aria-expanded 属性并管理焦点恢复，消除了自定义实现中常见的 Bug。
  3. 像 popovertarget 这样的声明式 HTML 属性取代了复杂的 JavaScript 逻辑。 使用调用者命令允许开发者直接在 HTML 中连接触发器和弹出框，使这种关系对浏览器和辅助技术都变得清晰明确。
  4. JavaScript 的角色从管理基础设施演变为优化用户意图。 随着平台处理了弹出框的“如何实现”，JavaScript 仅用于“为什么实现”——例如添加刻意的延迟以防止快速移动鼠标时的闪烁。
  5. 现在是否使用库应该基于特定的约束，而不是默认的必要性。 虽然像 Floating UI 核心库在处理复杂碰撞检测或大型设计系统方面仍然更胜一筹，但 Popover API 现在是简单 UI 元素最“正确”的起点。

💬 文章金句

  • Popover API 将工具提示从你模拟的东西变成了浏览器真正理解的东西。
  • 核心问题不在于代码，而在于 Web 平台缺乏适当的特性支持。
  • 我没有添加焦点恢复代码；我删除了它。
  • 优势不仅在于减少了 JavaScript 代码行数，还在于你需要担心的事变少了。
  • 有史以来第一次，最简单的工具提示也可以是最正确的。
