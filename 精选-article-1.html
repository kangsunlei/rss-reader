Agentic Harness Workflow 框架：把 AI Coding 变成工程化流程

9/10/2026, 10:00:00 AM

📌 一句话摘要

本文作者详细拆解了自研的 Agentic Harness Workflow 框架，通过引入固定生命周期流水线、阶段级 Sub-Agent 协作、状态落盘与人工门禁，将 AI 编码从不确定的“碰运气”转变为可复现的工程化流程，并分享了实战中的踩坑反思。

📝 详细摘要

本文系统介绍了一种名为 Agentic Harness Workflow 的 AI 编程工程化框架。作者指出直接将长需求丢给 AI 容易导致上下文膨胀、步骤遗漏及过程不可恢复，因此需要引入类似工厂流水线的工程框架。文章首先对比了三种应用拓扑，随后详细拆解了该框架的核心架构：涵盖从初始化到归档的十二阶段生命周期、充当框架入口与知识库的 CLAUDE.md、负责极简调度与状态控制的主会话 Manager、执行特定任务的 Sub-Agent、基于文件落盘的状态机、以及标准化的双向通信协议。此外，文章还探讨了多需求隔离的 Worktree 实践、提交依赖处理、与 DeepSeek Harness 哲学（Everything is a Plugin）的异同，最后坦诚总结了当前面临的上下文重加载、搜索边界、原子写入及可观测性等八大未解痛点。

💡 主要观点

  1. AI 编程的痛点在于缺乏工程约束，需通过 Harness 框架将其转变为固定流水线。 一次性丢给长上下文 Agent 的真实需求容易引发上下文膨胀、结果漂移、跳过步骤、过程不可恢复及缺少人工门禁等问题，必须通过分阶段的子代理协作和状态管控来解决。
  2. 框架核心架构采用「极简 Manager 调度 + 状态全落盘 + 子代理分工」的设计。 主会话 Manager 仅负责状态读写与协议转发，不吞噬大量产物正文保持上下文清爽；各阶段由独立的 Sub-Agent 经由结构化协议驱动，workflow-state.json 确保中断后可无痛续跑。
  3. 通过 Git Worktree 隔离多需求并结合 Loop Engineering 实现自动化闭环。 在进入实现阶段前为各业务仓建立独立 worktree 保证多需求并行不污染主工作区；同时在编写代码、静态审查和端到端测试间引入带有次数上限的自动修复循环（Loop）。
  4. 实践中暴露出上下文重复加载、搜索边界缺失、原子性及可观测性等局限。 作者复盘了八大未解问题，包括子代理每轮重新加载上下文导致浪费、plan 阶段检索无边界致超时、产物与状态非原子写入、缺乏线上运行的可观测监控等，指明了后续优化方向。

💬 文章金句

  • 不是「再造一个很聪明的 Agent」，而是给 AI 编码套一副「工程框架」——把一个需求从提出到归档拆成一条固定的流水线。
  • Manager 有一项我设计的铁律：它只认 Sub-Agent 回传的那个结构化协议，不读任何产物的正文，也不读业务代码。
  • 第一优先级不该是让 AI 去想「怎么修这个」，而是「怎么让下次不再产生」。
