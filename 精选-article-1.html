多 Agent 协作的下一场竞争，不在模型，而在上下文

11/6/2026, 9:38:00 AM

📌 一句话摘要

文章提出多 Agent 协作的核心问题在于上下文传递的折损，认为应通过共享上下文而非转述来实现低损耗协作，Siboot 通过群、Topic、@ 三要素构建共享工作现场。

📝 详细摘要

文章从协作传递什么这一根本问题出发，指出传统协作工具优化的是消息传递，而真正流动的是上下文。当 Agent 介入后，上下文的编码-解码过程出现乘法式叠加的折损。文章提出两条解决方案：一是让 Agent 学会转述，仍依赖通信共享上下文；二是共享上下文来通信，直接消除转述。Siboot 采用群作为共享上下文的场、Topic 聚焦隔离上下文、@ 实现接力不搬运，同时 Agent 需要自己整理文件系统以实现时间维度的沉淀。最终，人从中继器位置解放，回到目标设定、判断、边界划定和验收职责。

💡 主要观点

  1. 协作的本质是上下文传递，传统工具只解决消息传输，折损问题始终存在 人类社会通过会议纪要、需求文档等方式搬运上下文，但每一次传递都有损耗。AI 时代，Agent 进入后，折损从加法变为乘法，每增加一个协作节点都会继承并叠加之前的损耗。
  2. 真正的解决方案是消除转述，实现共享上下文来通信 文章认为，把上下文压成聊天记录让 Agent 逆向解码是倒退。应让人和 Agent 都站在同一份实时上下文上，而不是通过通信来传递上下文。
  3. Siboot 通过群、Topic、@ 构建低折损的上下文流水线 群作为持续在场的上下文容器，Topic 聚焦隔离单个议题，@ 实现接力不搬运。三者组合让上下文在空间上实时共享，在时间上通过 Agent 自己整理的文件系统实现沉淀。
  4. Agent 需要自己整理文件系统才能实现自迭代 仅靠上下文窗口无法长期存储历史。Agent 必须拥有收件区、决策记录、需求/BUG 档案等结构化文件系统，并定期自动归档，才能像可靠同事一样保持连续记忆。
  5. 人从「传声筒」解放，回归目标设定、判断、边界和验收 当上下文共享后，人只需在开头确认需求价值、结尾验收功能，中间所有搬运、转述、同步都由系统处理。人区别于工具的正是判断和责任。

💬 文章金句

  • 协作的全部难题，本质上都是上下文在传递过程中的折损问题。
  • 单人时代，折损是加法：讲一遍，损一点。人-人-Agent 时代，折损是乘法：每多一个协作节点，就多一层转述。
  • 别再让人给 Agent 当传声筒。让大家，看着同一个现场，一起干；让每一次协作，都变成明天还取得回来的沉淀。
