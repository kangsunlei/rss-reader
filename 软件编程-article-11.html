低并发编程｜如何用 720 个请求让后端服务器瘫痪

7/15/2025, 12:31:00 AM

📌 一句话摘要

本文深入分析了一起由核心依赖初始化异常、异常捕获不当和无超时等待导致的低并发下后端服务瘫痪故障的排查与修复过程。

📝 详细摘要

文章详细复盘了一起生产环境中后端服务在低并发下却意外瘫痪的故障。作者首先指出故障的根本原因是应用启动时，核心依赖模块因网络问题初始化失败，但缺乏有效的校验和兜底处理。这导致后续请求在处理过程中抛出`ExceptionInInitializerError`，且该错误未能被上层`catch Exception`捕获，也未能在 Reactor Mono 流的`onErrorResume`之前被处理，从而中断了流处理。最终，订阅方因`blockGet`未设置超时而无限等待，耗尽 HSF 线程池，导致服务不可用。文章详细阐述了从 HSF 线程池满的现象出发，通过线程堆栈分析、日志排查、Arthas 验证等步骤，层层深入定位问题的过程。最后，作者强调了应用启动阶段对关键组件状态检查、全局异常处理策略以及响应式编程中超时设置的重要性，并提出了三项具体的修复措施，为开发者提供了宝贵的故障排查和系统稳定性建设经验。

💡 主要观点

  1. 低并发下的服务瘫痪往往是多重小错误累积的结果 即使是看似微小的初始化异常、捕获范围不足、缺乏超时设置等问题，在特定组合下也能导致系统级故障，需全面审视。
  2. 应用启动时对核心依赖的强校验至关重要 核心组件的初始化成功应作为应用健康上线的强制条件，避免带病上线，从而预防运行时出现不可预测的问题。
  3. 全局异常处理和响应式流的错误处理需全面覆盖 对于可能抛出`Error`或`Throwable`的场景，应使用更宽泛的`catch Throwable`，并在响应式编程中确保兜底机制能正确处理异常，避免流中断。
  4. 阻塞式调用必须设置合理的超时时间 在分布式系统中，任何阻塞等待都应有明确的超时限制，以防止因上游无响应或异常导致下游线程资源耗尽。

💬 文章金句

  • 本次故障的根本原因是应用启动时未对核心依赖模块的初始化异常进行有效校验和兜底处理，导致后续请求处理过程中抛出无法被捕获的初始化错误，进而引发流处理中断与线程阻塞，最终使 HSF 线程池耗尽、服务不可用。
  • 综上所述，本次故障凸显了应用启动阶段缺乏对关键组件状态的有效检查及全局异常处理策略的重要性，下文会展开讲述整个排查过程。
  • ExceptionInInitializerError 是 Java 的一个运行时异常，表示在类的静态初始化过程中发生了错误（如静态代码块或静态变量初始化时抛出异常）。
  • 问题已经比较清晰了：如果这个 error 没有被正确捕获，就会导致流进入错误状态，如果没有正确使用 doOnError 和 onErrorResume，流就会出现终止，从而订阅者永远无法获取到流的结果。
  • 很多很大的空难事件，是由一个个微小错误累计而成的，软件行业也是类似的，很多大型的故障比如最近的 google cloud 认证服务瘫痪导致的 cloudfare 大面积服务不可用竟然是一个错误配置引发的空指针异常引发的一连串连锁反应导致的。
