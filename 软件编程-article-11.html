📝 详细摘要

本文详细介绍了 TCC 分布式事务方案中常见的空回滚和悬挂事务问题，并提出了基于分布式事务记录表的解决方案。事务记录表的核心作用是记录事务状态，用于判断和控制 Try、Cancel 操作，从而解决空回滚和悬挂事务问题。针对空回滚问题，当参与者收到 Cancel 请求时，先查询事务记录表，若无 Try 记录则执行空回滚并记录状态。针对悬挂事务问题，当参与者收到 Try 请求时，先查询事务记录表，若存在 Cancel 记录则拒绝 Try 请求。此外，该表还可用于幂等控制。该方案为解决 TCC 分布式事务中的一致性问题提供了一种实用且易于理解的思路。

💡 主要观点

  1. 空回滚问题需通过事务记录表判断 Try 是否执行 当收到 Cancel 请求时，先查询事务记录表，若无 Try 记录则执行空回滚，避免异常并保证事务正确回滚。
  2. 悬挂事务问题需通过事务记录表判断 Cancel 是否已执行 当收到 Try 请求时，先查询事务记录表，若存在 Cancel 记录则拒绝 Try 请求，避免资源占用无法释放。
  3. 分布式事务记录表可用于实现幂等控制 每次 Try、Cancel、Confirm 请求均查询事务记录表，避免重复执行，确保事务的正确性和可靠性。

💬 文章金句

  • TCC 是一种分布式的事务的方案，将一个事务分成了 TRY - CANCEL - CONFIRM 三个阶段
  • 需要在业务中做好对空回滚的识别和处理，否则就会出现异常报错的情况，甚至可能导致 Cancel 一直失败，最终导致整个分布式事务失败
  • 一次分布式事务，先发生了 Try，但是因为有的节点失败，又发生了 Cancel，而下游的某个节点因为网络延迟导致先接到了 Cancel，在空回滚完成后，又接到了 Try 的请求，然后执行了，这就会导致这个节点的 Try 占用的资源无法释放，也没人会再来处理了，就会导致了事务悬挂
  • 当一个参与者接到一次 Cancel 请求的时候，先去 distribute_transaction 表中根据 tx_id 查询是否有 try 的记录，如果没有，则进行一次空回滚即可
  • 当一个参与者接到一次 Try 请求的时候，先去 distribute_transaction 表中根据 tx_id 查询是否有记录，如果当前存在，并且记录的状态是 cancel，则拒绝本次 try 请求
