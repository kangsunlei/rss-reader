OpenClaw 2.0：欠下的技术债，这次连本带利还清

9/8/2026, 12:45:00 AM

📌 一句话摘要

OpenClaw 2.0 通过会话资源化、控制面客户端化、能力外置、安全分层与记忆可撤销等架构调整，将过去半年高速迭代积累的技术债收拢为可预期的行为，本文剖析了其架构变更、动因与代价。

📝 详细摘要

本文深入分析了 OpenClaw 2.0（v2026.8.1）的架构演进，指出其核心变化是将会话从进程内状态转变为可迁移、可共享、可快照的资源，实现了位置、时间、主体三个维度的解耦，并为此将存储层迁移至 SQLite。控制面 UI 退化为 Gateway 的一个客户端，请求数从 140 降至 45，启动时间从 1.6 秒降至 575 毫秒。能力供给上，核心变薄，多数 provider 外置为按需安装的独立包，并配套了修复、迁移与安全机制。安全设计分为入口、凭证、执行三层防线，并明确声明共享会话与 Incognito 的边界。记忆与自学习功能默认开启，但强调可撤销与来源可追溯。文章还从 200 多条 Fixes 中提炼出四类可靠性模式，并给出了升级建议与风险提示。

💡 主要观点

  1. OpenClaw 2.0 的核心变化是将会话从进程内状态转变为可迁移的资源，实现了位置、时间、主体三个维度的解耦。 会话不再绑定单一机器，可调度到任意执行单元，工作区随之迁移；进度卡片跨端存活，会话可分支回退；共享会话引入可见性与成员角色控制。这使得会话具备可寻址、可迁移、可共享、可快照、可恢复、有访问控制等资源特征。
  2. 控制面 UI 退化为 Gateway 的一个客户端，通过重做数据获取模型，请求数从 140 降至 45，启动时间从约 1.6 秒降至 575 毫秒。 展示层彻底客户端化后，Gateway 成为唯一真相源，UI 间的本地状态成为潜在 bug。因此时钟同步、事件序列、重连语义等一致性问题必须一次做对，2.0 通过大量底层修复偿还了这笔债。
  3. 能力供给上，核心变薄，多数 provider 外置为独立包，内置标准从「是否常用」变为「是否与 Agent 执行循环强耦合」。 只有与执行循环强耦合的模型接入（如 OpenCode Go）保留内置。外置必须同时交付修复、迁移、安全与审计机制，否则将正确性责任从代码转移到运维，可能成为灾难。
  4. 安全设计分为入口、凭证、执行三层防线，并明确声明共享会话与 Incognito 的边界，不指望模型自律。 入口层默认绑定 loopback，凭证层遮蔽输入且 secret 只写不可读，执行层通过会话权限模式与 fail closed 策略做机械作用域约束。官方数据表明模型选型只是第一道缓解，自适应攻击成功率仍超 80%，因此硬执行层不可或缺。
  5. 记忆与自学习功能默认开启，但强调可撤销与来源可追溯，使记忆成为数据资产而非缓存。 默认开启个人会话召回、Grounded dreaming 与自动自学习，同时提供来源查询、排除准入、memory forget 定点删除等机制，源 transcript 完整保留。这四件事凑齐，记忆功能才敢默认开启。

💬 文章金句

  • 把过去半年高速迭代攒下的不确定性收拢成可预期的行为。
  • 会话一旦成为资源，UI 就退化成它的一个观察者。
  • 功能列表可以抄，这套规范抄不来，它只能从足够多的真实故障里长出来。
  • 任何依赖模型自律的方案都不成立，硬执行层只能是工具策略、执行审批与沙箱。
  • 默认开启、显式关闭、来源可追溯、可定点删除，四件事凑齐，记忆才算数据资产而不是缓存。
