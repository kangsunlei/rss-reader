从 yield 到 await：Python 协程的进化史

11/13/2025, 12:31:00 AM

📌 一句话摘要

Python 协程从生成器、社区补丁到 async/await 的二十年演进史，揭示异步编程的抽象升级。

📝 详细摘要

文章深入回顾了 Python 协程的演进历程。它始于 Python 2.2 的`yield`关键字，通过 Python 2.5 的`send()`方法，生成器获得了双向通信能力，具备了协程的雏形。面对复杂嵌套任务的调度难题，社区在`yield from`出现前（如 OpenStack 的`@wrappertask`）提供了“打补丁”式的解决方案，验证了协程组合的实际需求。Python 3.3 引入`yield from`，解决了嵌套生成器的控制流、异常和返回值转发问题。最终，Python 3.5 通过`async def`和`await`引入原生协程，提供了更清晰的异步编程语义，并与`asyncio`事件循环机制整合，形成了现代 Python 异步编程的完整生态。文章强调了痛点驱动创新、抽象逐层递进和清晰优于灵活的演进启示。

💡 主要观点

  1. Python 的`yield`通过`send()`方法从简单生成器演变为可双向通信的协程。 `send()`方法赋予生成器接收外部输入、维护状态和主动暂停的能力，奠定了 Python 协程的基础，使其能与调用方协作。
  2. `yield from`解决了嵌套生成器手动转发控制流、异常和返回值丢失的痛点。 该语法实现了子生成器与调用者之间的直接委托，简化了复杂异步任务的编排，提升了代码可读性和健壮性。
  3. `async def`和`await`提供了原生协程语法，提升了异步编程的语义清晰度和安全性。 专用关键字明确了异步上下文，便于类型检查和静态分析，使得异步代码更易于理解和维护，形成了统一标准。
  4. 社区补丁如 OpenStack 的`@wrappertask`在语言标准化前验证了协程组合的实际需求。 尽管是临时方案，但其大规模应用暴露并验证了生成器代理的普遍痛点，为`yield from`的引入提供了坚实的现实依据。

💬 文章金句

  • 它不再只是'产出值'，而是能接收输入、维护状态、主动暂停的独立执行体。这正是'协程（Coroutine）'的核心定义------一个可中断、可恢复、能与调用方协作的过程。
  • 尽管 yield from 已经成为标准，但绝大多数生产系统仍在使用 Python 2.7，而该语法对 Python 2 完全不可用。
  • 本质上，await 是 yield from 在异步上下文下的专用化版本------去除了通用性，换取更强的语义清晰度。
  • 每一个优雅的 API，都曾经历过无数粗糙的原型与漫长的打磨。
