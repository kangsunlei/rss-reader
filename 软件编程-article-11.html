Agent 长程任务断点续传：从框架 Checkpoint 到跨进程恢复的完整实践

9/9/2026, 9:41:00 AM

📌 一句话摘要

本文介绍淘天直播技术团队针对 Agent 长程任务中断恢复的完整实践，采用框架层 Checkpoint 与上层任务调度两层架构，在不改 Spring AI Alibaba 源码前提下实现进程内与跨进程的断点续传。

📝 详细摘要

文章针对 Agent 长程任务、A2A 协同及人机协作场景的中断恢复需求，提出框架层 Checkpoint + 上层任务调度的两层架构。框架层基于 Spring AI Alibaba（SAA）1.1.2.0 的 Checkpoint 机制，通过扩展 InterruptableAction 与 Hook 机制实现关机信号检测、消息顺序修正、多工具调用 Mock 返回及子图会话 ID 记录，不修改框架源码以避免维护私有 fork。上层调度通过 MQ 摘流防止关机机器消费新消息，结合任务表与 MQ 消息队列协调跨进程恢复。文章详细分析了三个关键问题：恢复时消息顺序错乱（框架 bug，已修复）、多工具调用中间无法保存 Checkpoint（通过 ToolRecordInterceptor 缓解）、子图会话 ID 后缀导致中断失效（通过 metadata 记录原始 threadId 解决），并给出后续优化方向。

💡 主要观点

  1. 采用框架层 Checkpoint + 上层任务调度的两层架构，在不改框架源码的前提下实现断点续传。 框架层负责进程内状态保存与恢复，上层调度处理跨进程任务恢复，避免修改公共依赖源码带来的维护成本，覆盖用户主动、工具执行及系统级中断三类场景。
  2. 通过 Hook 机制注入自定义逻辑，解决框架 Checkpoint 的多个限制。 利用 GraphEnvironmentMonitor 检测关机信号、ResumeMessageOrderHook 修正恢复时消息顺序、ToolRecordInterceptor 配合 HumanInterventionException 实现多工具调用的中断跳过与 mock 返回，以及 CheckpointAgentHook 记录子图原始 threadId。
  3. 上层调度通过 MQ 摘流与任务表协调跨进程恢复。 在下线脚本中先摘流 MQ 再停止应用，防止关机机器消费新消息；任务表记录关键请求信息，新实例启动后通过 MQ 重新消费任务消息触发恢复。
  4. 多工具调用中间无法保存 Checkpoint 是框架侧限制，当前以 mock 响应缓解。 框架在 for 循环中顺序执行工具且中间不保存 Checkpoint，崩溃后所有工具重跑；通过 ToolRecordInterceptor 检测中断标记，未执行工具返回 mock 响应并保存，恢复时已完成的工具不重复执行。
  5. 子图会话 ID 后缀问题会导致中断失效与状态恢复不一致。 SAA 框架为嵌套子图自动拼接 threadId 后缀，通过 Hook 在子图执行前将原始 threadId 记录到 metadata，统一用 ITool.getActualThreadId() 获取，解决中断与状态查询问题。

💬 文章金句

  • 长程任务执行时间不可控、上下文状态庞大，中断后无法通过简单重试恢复，必须从断点续传。
  • 方案的核心约束是完全基于框架已有能力实现断点续传，不修改任何框架源码。
  • 框架是公共依赖，修改源码意味着维护私有 fork，后续升级成本极高。
  • 该机制的核心价值在于：通过异常快速跳出工具执行循环，配合中断标记让后续工具自动跳过，最终通过 Checkpoint 保存完整的工具响应状态。
  • 建议：优先升级框架版本，避免引入额外的 Hook 组件。
