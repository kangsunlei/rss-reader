Azure Cosmos DB 严重漏洞曝光：一条查询可攻破所有租户数据库

8/18/2026, 5:40:00 AM

📌 一句话摘要

文章揭示 Azure Cosmos DB 中的 CosmosEscape 漏洞利用链，通过一条 Gremlin 查询即可获取平台级主密钥并跨租户读写数据库，并探讨修复过程与共享责任争议。

📝 详细摘要

Wiz Research 披露了 Azure Cosmos DB 中的 CosmosEscape 漏洞利用链，攻击者只需一条特制的 Gremlin 查询，利用 .NET 反射逃逸沙箱，获取平台级主密钥，进而可读写任意租户的数据库。Microsoft 在两天内热修复阻断入口点，但完全移除该主密钥并重建凭据模型历时六个月，期间客户无法自行缓解。文章通过 Hacker News、Reddit 等社区讨论，探讨了漏洞归属于云服务提供商的共享责任、修复不可见导致的信任问题、架构重建的复杂性以及集中化风险，并指出缺乏 CVE、CVSS 及 MSRC 公告等信息披露的不足。

💡 主要观点

  1. 漏洞利用链机制：通过特制 Gremlin 查询利用 .NET 反射逃逸沙箱，获取平台级主密钥，可跨租户读写所有 Cosmos DB 数据库。 攻击者构造的查询在编译为 .NET 代码时未受充分限制，利用反射逃出沙箱，在 DB Gateway 上执行任意代码，从而获得可枚举并访问任意租户数据库的主密钥。
  2. 修复过程与时间线：Microsoft 两天内热修复阻断入口点，但移除平台级主密钥并重建凭据模型历时六个月，客户在此期间无法自行缓解。 热修复仅封堵了利用入口，彻底消除风险需要重新设计凭据模型，这一架构性变更在全球所有区域推出耗时半年，客户只能依赖厂商声明。
  3. 共享责任与客户视角：社区普遍认为该漏洞完全属于云服务提供商责任，客户无法采取措施防护，凸显共享责任模型中的盲点。 漏洞存在于 Microsoft 基础设施内部，客户侧没有任何配置或补丁可阻止攻击，因此修复责任 wholly 在云服务提供商一方。
  4. 信息披露与集中化风险：漏洞未分配 CVE/CVSS，也没有 MSRC 公告，暴露时间窗口不明确；事件凸显超大规模云服务集中化带来的系统性风险及依赖厂商透明度的问题。 缺少标准漏洞标识和时间窗口说明，使得外部评估受影响范围困难；同时说明一旦平台级密钥泄露，影响范围可波及众多依赖该服务的内部和外部客户。

💬 文章金句

  • 通过一条 Gremlin 查询实现 RCE，再到完全攻破租户密钥，这是一条残酷的权限升级链。真正超级吓人的是它的简单性，因为只需一条查询，不需要任何特殊工具，就能直达主密钥。
  • 这种漏洞不会出现在任何共同责任模型示意图中。作为 Cosmos DB 客户，我们不可能采取任何不同的措施来阻止它；它完全存在于 Microsoft 的基础设施中。
  • 我不接受这个前提：谁说他们正确地修复了它？
  • 网关此前使用主密钥获取每个账户的私有密钥，然后再转发请求，因此移除主密钥意味着需要重建一项连 Microsoft 自己都依赖的服务的凭据模型。
  • 多年来，他一直主张将关键数据备份到另一家服务提供商或本地环境，但始终未能成功。
