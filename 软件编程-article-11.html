如何构建快速可靠的工作流：重构智能体技能

4/8/2026, 7:00:05 PM

📌 一句话摘要

本文提供了一个实用的框架，通过将“文档密集型”的工具中心化设计转变为“渐进式披露”的工作流中心化架构，来优化 AI 智能体的技能。

📝 详细摘要

作者探讨了 Claude Code 等 AI 编程助手常见的“上下文爆炸”问题，即过于冗长的技能描述会因包含无关信息而消耗上下文窗口。通过将技能重构为元数据（Metadata）、入口点（SKILL.md）和引用（References）三层系统，开发者可以确保智能体仅加载必要数据。文章提倡入口点遵循“200 行规则”，并转向以工作流为中心的技能设计，同时提供了可操作的检查清单和代码片段，以审计和维护精简、高效的 AI 智能体配置。

💡 主要观点

  1. 避免将 AI 技能视为文档堆砌处。 将详尽的 API 参考和教程存储在单个技能文件中会导致上下文臃肿，使模型变慢并失去焦点。技能应该充当路由，而不是百科全书。
  2. 实施三层渐进式披露架构。 将技能结构化为元数据（始终加载）、精简的入口点（SKILL.md，少于 200 行）以及仅在任务明确需要时才加载的独立引用文件。
  3. 从工具中心化设计转向工作流中心化设计。 不要为单个工具创建技能（例如“postgres-skill”），而应按开发阶段（例如“数据库”或“DevOps”）进行分组，以更好地契合智能体的实际任务需求。
  4. 将上下文视为有限的预算。 有效的上下文工程需要像管理资源一样管理 Token 使用。必须定期审计技能的大小和相关性，以防止“文档蔓延”并保持智能体性能。

💬 文章金句

  • 你的问题不是“缺乏信息”，而是“无关信息太多”。
  • 技能的工作是引导智能体在合适的时机找到正确的文件，而不是成为页面上的百科全书。
  • 上下文是一种预算。最好的技能设计应该像工程师一样去花费它，而不是像图书管理员那样。
