【第 3511 期】前端很难

5/19/2025, 12:04:00 AM

📌 一句话摘要

分析现代前端部署复杂性，介绍 SST 开源方案及基于 CloudFront Router 组件如何简化 AWS 部署。

📝 详细摘要

文章深入探讨了现代前端应用部署的复杂性。指出与早期单页应用仅需静态文件托管不同，现代前端框架（如 Next.js， SvelteKit）因支持 SSR、API 路由等功能，需要复杂的后端基础设施配合，导致部署门槛提高。大型云服务商难以快速跟进多样且迭代迅速的前端框架，使得 Netlify、Vercel 等专用服务兴起。文章重点介绍了开源项目 SST 如何通过拆解部署流程、开源适配器（OpenNext）和基础设施配置来支持多种框架。最后，文章详述了 SST 如何利用 CloudFront Functions 和 KeyValueStore 等 AWS 新功能构建 Router 组件。这一创新解决了传统 SST 部署中预览环境速度慢、难以支持多区域等痛点，实现了单 CloudFront 分发管理多个应用、函数、静态文件，支持子域名、路径路由和多区域部署，显著提升部署灵活性和效率，尤其适合复杂和规模化项目。

💡 主要观点

  1. 现代前端部署因需多种基础设施配合而变得复杂。 区别于简单静态文件，现代前端需依赖无服务器函数、边缘计算、CDN 等，构建复杂应用架构，增加部署难度。
  2. 大型云服务商难以快速适配多变的前端框架生态。 前端框架种类多、更新快，而 AWS、GCP 等服务商更新周期长，难以提供全面及时的框架支持，催生了专用部署平台。
  3. SST 通过开源和利用 CloudFront 新功能简化复杂部署。 开源模式使其能快速跟进框架更新，新的 Router 组件利用 CloudFront 能力整合路由，提高部署灵活性和效率。

💬 文章金句

  • 现代前端应用已经不再是简单的静态文件了，现在通常需要搭配多种基础设施：像 S3 存储桶、无服务器函数、数据库、CDN、边缘计算函数、边缘数据存储等。
  • 问题已经复杂到，即使是 AWS 和 GCP 的服务，比如 Amplify 和 Firebase，也难以全面支持这些现代前端框架。
  • 对于开源项目来说，自行托管前端是再合适不过的了。
  • 一个看似微不足道的预发布声明让 CloudFront 变得更具可编程性。
  • 而 SST 真正强大之处在于，当你的项目不断扩展时，它能满足更多复杂的需求，比如：添加多个前端项目、将 API 和前端部署在同一个域名下、在预览环境中不只是部署前端，还包括其他服务
