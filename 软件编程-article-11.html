Vercel 如何构建针对编程智能体的 AEO 追踪系统

2/9/2026, 1:00:00 PM

📌 一句话摘要

Vercel 详细介绍了其 AI 引擎优化（AEO）的技术架构，利用沙箱化 MicroVM 和归一化流水线来追踪自主编程智能体如何引用其品牌。

📝 详细摘要

本文探讨了专门针对 Claude Code 和 OpenAI Codex 等编程智能体的新兴 AI 引擎优化（AEO）领域。Vercel 解释说，由于这些智能体在完整的开发环境中运行，而非简单的聊天 API，因此追踪其行为需要复杂的架构。他们的解决方案包括：使用 Vercel Sandbox 启动临时 Linux MicroVM 以实现隔离执行；通过 AI Gateway 路由 LLM 调用以实现统一的可观测性；以及实现四阶段归一化层以标准化碎片化的记录格式。关键发现显示，编程智能体在 20% 的提示词中会进行网页搜索，并将品牌推荐直接嵌入到生成的代码中，这要求从传统的 SEO 转向结构化的 AEO 策略。

💡 主要观点

  1. 编程智能体需要隔离的执行环境，以实现安全且准确的 AEO 追踪。 与标准的 LLM API 不同，编程智能体需要完整的文件系统和 Shell 访问权限。Vercel 使用临时 Linux MicroVM 提供真实的开发环境，同时确保自主执行期间的安全性和资源隔离。
  2. 使用中心化的 AI Gateway 拦截并归一化智能体与提供商之间的通信。 通过覆盖环境变量（如基础 URL），Vercel 将智能体流量路由到其 AI Gateway。这实现了统一的日志记录、成本追踪和凭据管理，而智能体并不知道自己正在被监控。
  3. 多阶段归一化层解决了智能体记录格式碎片化的问题。 由于不同的智能体以不同的格式（如 JSONL 与 stdout）输出数据并使用不同的工具名称，Vercel 构建了一个流水线来解析、丰富这些事件，并将其扁平化为单一的规范模式以便分析。
  4. 针对编程智能体的 AEO 侧重于工具使用和嵌入代码的品牌推荐。 分析显示，智能体通常通过生成可运行的代码（如 import 语句或配置文件）来推荐产品。与标准聊天模型基于文本的回答相比，这需要不同的评估方法。

💬 文章金句

  • 编程智能体并非为响应单个 API 调用而设计。它们旨在项目内部运行，并期望拥有完整的开发环境。
  • 智能体本身并不知道这一切正在发生，它们的运行方式就像是在直接与提供商对话。
  • 记录格式一团糟。随着智能体 CLI 工具的快速更新，情况变得越来越混乱。
  • 当编程智能体推荐某个工具时，它往往会生成使用该工具的可运行代码……推荐是嵌入在输出中的，而不仅仅是在文本中提及。
  • 难点在于所有上游环节：让智能体运行起来、捕获它的行为，并将其归一化为可以评分的结构。
