小红书 MySQL 内核秒杀能力重磅再升级

1/19/2026, 10:04:00 AM

📌 一句话摘要

小红书通过自研 MySQL 内核“合并秒杀”方案，在不对业务 SQL 进行侵入式改造的前提下，将秒杀场景下的热点行更新性能提升 5 倍以上，大幅提升了高并发写入能力。

📝 详细摘要

小红书数据库团队基于 MySQL 内核，通过自研的“合并秒杀”方案，显著提升了电商平台秒杀场景下的高并发写入能力。该方案在“排队秒杀”的基础上进一步优化，将热点行更新速度提升至 1.5W+/s，相比 MySQL 社区版本有百倍性能提升，相对于此前的排队秒杀方案也有 5 倍以上性能提升。核心设计包括在内核层实现对 SQL 的透明优化选择，通过 Leader-Follower 机制在内存中合并扣减库存，再由 Leader 一次性写入存储引擎，并对行锁释放和 Binlog 提交进行了优化，以实现 Pipeline 式的并发处理。此外，文章还详细讨论了如何在保障数据可见性和一致性的前提下，处理 Crash Recovery 的兼容性问题。该方案对业务无感知，无需修改 SQL 即可受益，适用于库存、优惠券等高抢购场景以及热门笔记点赞等高频写入场景。

💡 主要观点

  1. 合并秒杀方案实现 5 倍性能提升并对业务透明。 小红书自研的 MySQL 内核“合并秒杀”方案，在原有“排队秒杀”基础上将写入能力再次提升 5 倍，且对业务层完全透明，无需修改 SQL，仅需升级内核即可获得性能收益。
  2. 核心技术在于内存合并扣减与 Leader-Follower 机制。 通过引入全局缓存，Leader 线程预读取库存数据，Follower 线程在缓存中合并扣减，最后由 Leader 一次性将合并结果写入存储引擎，大幅减少数据库直接操作次数，缓解行锁竞争。
  3. 优化行锁释放和 Binlog 提交实现流水线并行。 将 SQL 事务的更新和提交阶段分离，允许不同组的事务在第一个组提交之前开始收集数据，形成类似流水线的并行处理，并由 Leader 统一提交 Binlog，提升整体吞吐量。
  4. 保障数据可见性、一致性及 Crash Recovery 健壮性。 方案通过表维度全局缓存解决多线程数据可见性，通过 Leader-Follower 状态流转保证数据一致性，并对 Binlog 组的完整性及 Redolog 记录进行特殊处理，确保 Crash Recovery 的正确性。

💬 文章金句

  • “秒杀”是电商平台最典型的高并发促销场景，双十一等大促活动也常以秒杀能力作为数据库技术实力的标志。
  • 基于 MySQL 内核实现的合并秒杀优化，相对排队秒杀方案，将秒杀写入能力再提升 5 倍，相对 MySQL 社区版本更有百倍的性能提升。
  • 一句话总结本方案：合并秒杀通过 Leader 预读取库存数据写入缓存，在缓存中进行 Follower 库存数据合并扣减，最后 Leader 一次性将合并数据写入存储引擎，提升了写入性能。
  • 将多个组提交按照时间串起来，可以看到上一个组必须 commit 完释放了行锁，才能让下一个组重新申请行锁。所以整个流水线在组内是合并提交的，但是组和组之间是完全的串行。
