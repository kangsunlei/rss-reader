使用 OpenCode + Haiku 的体验和 Cursor + Opus 的体验差距不小，是模型的差异还是工具配置的差异?

6/20/2026, 5:46:36 PM

📌 一句话摘要

本文对比了使用 OpenCode + Haiku 与 Cursor + Opus 的编程体验，指出在复杂任务（如精确 git 操作）中，廉价模型的行为存在显著差距，并探讨了这种差异是源于模型能力还是工具配置。

📝 详细摘要

文章作者分享了自己从 Cursor + Opus 切换到 OpenCode + Haiku 后的编程体验落差。在构建简单应用时，Haiku 在技术选型（如选择 Redux）和环境配置（如 Tailwind CSS）上表现不佳，产生大量 bug。最核心的痛点在于一个 git 操作场景：作者要求 AI 对当前改动进行 git 归档并与相关提交 squash，但 Haiku 直接使用 `git add -A` 提交了所有无关文件，随后在 squash 过程中卡在 `git rebase -i`，甚至在作者介入后错误地删除了无关文件。作者对比指出，使用 Cursor + Opus 时，AI 通常能先检查上下文，精确选择相关文件进行操作。文章最后提出疑问：这种体验差距是模型能力（Haiku vs. Opus）的差异，还是可以通过更好的工具配置（如 rules）来弥补。

💡 主要观点

  1. 在复杂任务中，廉价模型（Haiku）与顶级模型（Opus）的体验差距显著。 作者在技术选型、环境配置和精确 git 操作等场景中，观察到 Haiku 的行为远不如 Opus 可靠，容易产生错误和意外行为。
  2. AI 在 git 操作中的精确性差异是核心痛点。 Haiku 在执行精确的 git 归档和 squash 任务时，未能像 Opus 那样先检查上下文并精确选择文件，而是执行了破坏性的 `git add -A` 和错误的文件删除操作。
  3. 体验差距可能源于模型能力与工具配置的双重影响。 作者提出疑问，这种差异是模型本身的理解和推理能力不足，还是可以通过更精细的提示词（rules）和工具配置来改善，为 AI 编程工具的使用者提供了思考方向。
