API 平台 Unkey 因性能困境放弃 Serverless

12/31/2025, 8:30:00 PM

📌 一句话摘要

API 平台 Unkey 将其整个身份验证服务从 Serverless 架构的 Cloudflare Workers 迁移到有状态的 Go 服务器，通过解决延迟问题和无状态架构的“复杂度税”，实现了 6 倍的性能提升。

📝 详细摘要

API 身份验证平台 Unkey 公开详细说明了其放弃 Serverless Cloudflare Workers 架构并转而采用有状态 Go 服务器的决定。联合创始人 Andreas Thomas 解释说，Cloudflare 缓存带来的高延迟（P99 超过 30ms）是 Serverless 无状态设计的根本限制，这使得他们无法实现请求路径内服务总响应时间低于 10ms 的目标。此次迁移带来了 6 倍的性能提升，消除了大量针对缓存和事件日志的变通方案（如自定义代理和复杂的多层设置），简化了代码库，并显著降低了运营成本。此外，这一转变还解锁了更简单的本地开发和客户自托管等功能，而这些在 Serverless 架构下非常繁琐。Unkey 的经验，连同 Amazon Prime Video 从微服务回归单体架构的类似举动，凸显了 Serverless 在处理高吞吐量、延迟敏感型生产负载时的局限性，表明它更适合真正的间歇性、事件驱动型任务，而非需要持久状态和极致性能的任务。

💡 主要观点

  1. Serverless 的无状态特性为 Unkey 的关键 API 身份验证服务引入了显著的延迟和复杂性。 由于 Serverless 函数是无状态的，缓存数据必须通过网络检索，导致 P99 延迟超过 30ms。这与他们低于 10ms 的性能目标直接冲突，并迫使他们构建复杂的自定义缓存和事件日志变通方案，这本质上是在复制传统服务器原生提供的有状态行为。
  2. 迁移到有状态的 Go 服务器产生了巨大的性能和运营收益。 此次转变带来了 6 倍的性能提升，通过消除大量辅助服务和自定义代理简化了架构，降低了运营成本，并由于单体 Go 应用的可移植性，使本地开发和客户自托管变得更加容易。
  3. Serverless 为需要持久状态或低延迟的负载引入了“复杂度税”。 Unkey 的经验表明，虽然 Serverless 平台很稳定，但其固有的无状态性迫使工程师构建和维护复杂的基础设施，以实现有状态服务“免费”获得的性能和状态管理能力，从而分散了开发客户功能所需的资源。
  4. 是否使用 Serverless 的决策应基于具体的负载特征，特别是延迟和状态需求。 Unkey 和 Amazon Prime Video 的案例表明，Serverless 是间歇性、事件驱动型负载的理想选择，但不太适合能从持久状态和内存缓存中获益的高吞吐量、延迟敏感型服务，在这些场景下，其“按调用付费”模式在经济上可能变得不利，且架构上更加复杂。

💬 文章金句

  • 当一个服务处于数千个应用程序的请求路径中时，‘每一毫秒都至关重要’。
  • 零网络请求永远比一个网络请求快。无论堆叠多少外部缓存，都无法绕过这个根本限制。
  • Thomas 表示，团队花在评估和集成新 SaaS 产品上的时间比开发功能的时间还要多，因此他们是在解决 Serverless 架构产生的问题，而不是客户面临的问题。
