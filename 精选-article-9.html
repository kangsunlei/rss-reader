面试官：“Agent 接了上百个工具，怎么选？”

9/22/2026, 6:12:00 AM

📌 一句话摘要

面对 Agent 接入上百个工具的场景，应通过工具注册表、确定性权限过滤、粗分类与混合检索召回、LLM 精选的分层 Tool Routing 方案，替代把全部 Schema 塞进 Prompt 的做法。

📝 详细摘要

文章以面试对话切入，指出把上百个工具的名称、描述和参数 Schema 全部塞进 Prompt 会带来四类问题：Token 占用、相似工具选择混淆、权限暴露风险和延迟压力。作者区分了 Tool Routing（决定当前 Agent 能看到和调用哪些工具）与 Multi-Agent Routing（决定任务交给哪个 Agent）两个不同层次。随后给出完整的分层路由链路：先建立包含命名空间、标签、适用边界、Schema、权限与状态的工具注册表；再按产品、租户、角色、环境做确定性过滤，强调先鉴权再召回；接着用规则或轻量分类模型粗分业务域；在候选域内用关键词、BM25、Embedding 或混合检索召回 Top-K；最后只把少量候选工具的完整 Schema 动态绑定给 LLM 做精选和参数生成，执行前仍需服务端鉴权。文章还讨论了 Skill 渐进加载与 Tool Routing 的配合关系、工具描述与 Schema 质量对路由上限的决定作用、分层评测指标（Recall@K、选择准确率、参数合法率、任务成功率、越权暴露率等）以及低置信度、工具不可用、正确工具未召回等失败场景的兜底策略。

💡 主要观点

  1. 把全部工具 Schema 塞进 Prompt 会同时引发 Token、混淆、权限和延迟四类问题 工具定义占用上下文空间，相似工具描述重叠导致模型选错，暴露无权工具扩大误调用与提示词注入面，更长输入增加传输与预处理开销。Prompt Cache 只能降低重复输入成本，不能让模型当前可见的工具变少。
  2. Tool Routing 与 Multi-Agent Routing 路由的对象不同，不能混为一谈 Tool Routing 决定当前 Agent 此刻能看到、能选择哪些工具，输出候选工具集或具体工具；Multi-Agent Routing 决定任务或子任务交给哪个 Agent，输出下一位执行者或 Handoff。两者可上下分层配合，但无原则地拆出大量 Agent 只会把工具目录变成 Agent 目录，增加切换与调试成本。
  3. 分层路由的核心是先确定性过滤，再分层召回，最后让模型精选 先按产品、租户、角色、环境、工具健康状态做硬过滤，把无权或不可用的工具排除在检索范围之外；再用规则或轻量分类模型粗分业务域；然后在候选域内用 BM25、Embedding 或混合检索召回 Top-K；最后只把少量候选的完整 Schema 动态绑定给 LLM 判断是否调用、选哪个、如何填参数。
  4. 安全原则是先鉴权再召回，隐藏工具不等于执行安全 检索器只能在当前请求有权看到的工具集合内搜索，不能先全库召回再靠 Prompt 约束。隐藏工具只减少暴露，执行工具时仍要在服务端重新鉴权，因为权限还可能取决于具体参数和资源归属，例如同一订单详情工具对不同租户订单的访问权限不同。
  5. 工具描述与 Schema 质量决定路由上限，评测需按链路分层拆解 名称要具体、描述要写清做什么、何时用、何时不用，相似工具要直接写出差异，参数 Schema 尽量收紧。评测应分三层：候选召回看 Recall@K 与候选集大小、Schema Token；模型精选看选择准确率、误选率、拒选准确率、参数合法率；业务结果看任务成功率、延迟、成本、越权暴露率与审批覆盖率。

💬 文章金句

  • 工具一多，难点已经不只是让模型「会调用」，而是怎样让它在当前这一刻只看到少量、相关而且有权使用的工具。
  • 先鉴权，再做相关性召回。检索器只能在「当前请求有权看到的工具集合」里搜索，不能先从全库召回，再指望 Prompt 告诉模型「这个不能用」。
  • 相似不等于可调用。用户权限、租户隔离、工具状态和参数条件都没检查，而且检索也可能漏召回。
  • Tool Routing 路由的是「工具候选集」，Multi-Agent Routing 路由的是「任务由哪个 Agent 接手」，这两个层次可以配合，但不能混为一谈。
  • 如果两个工具总是被混淆，不要只修改 Prompt。先检查它们是不是职责重叠，能否合并，或者把一个大而全的工具拆成边界清楚的查询与执行工具。
