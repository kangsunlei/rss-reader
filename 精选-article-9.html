智能体连接沙箱的两种模式

2/10/2026, 4:32:35 PM

📌 一句话摘要

本文分析了将 AI 智能体与隔离执行沙箱集成的两种架构模式，权衡了安全性、开发者体验和系统耦合度之间的利弊。

📝 详细摘要

文章探讨了 AI 智能体需要隔离“工作区”（沙箱）以安全执行代码而不损害宿主系统的迫切需求。它正式提出了两种主要的集成模式：“智能体在沙箱内”和“沙箱作为工具”。在模式 1 中，智能体驻留在沙箱内部，提供类似于本地环境的开发体验，但会引入 API Key 泄露和知识产权外泄等风险。在模式 2 中，智能体在外部运行并通过 API 调用沙箱，这有助于更快的迭代、更好的凭据安全性以及推理与执行的清晰分离。文章最后给出了使用 deepagents 框架的实际实现示例，帮助开发者根据对耦合度、安全性和速度的具体需求选择合适的架构。

💡 主要观点

  1. 智能体在执行代码时必须使用沙箱以保持系统隔离。 随着智能体越来越多地执行安装包和运行脚本等任务，沙箱提供了必要的边界，以防止对凭据、文件或网络的未经授权访问。
  2. 模式 1（智能体在沙箱内）提供了紧密耦合，但增加了安全风险。 在沙箱内运行智能体简化了环境访问，但需要将 API Key 存放在隔离空间内，使其容易受到提示词注入或沙箱攻破的影响。
  3. 模式 2（沙箱作为工具）优先考虑安全性和快速迭代周期。 通过保持智能体逻辑在外部，开发者可以即时更新代码并将敏感的 API Key 留在执行环境之外，尽管他们必须管理网络延迟。
  4. 模式的选择取决于所需的环境持久性和安全级别。 模式 1 更适用于模拟本地开发的复杂有状态环境，而模式 2 则更优于推理与执行应当解耦的模块化系统。

💬 文章金句

  • 构建这些智能体的团队面临的问题不是是否使用沙箱，而是如何将它们与智能体架构集成。
  • 在模式 1 中，智能体拥有直接的文件系统访问权限并可以修改其环境。当智能体与执行环境紧密耦合时，这非常有用。
  • 如果你的智能体在沙箱中运行，窃取智能体的全部代码和提示词会变得容易得多。
  • 模式 2 提供了更清晰的关注点分离：智能体状态存在于智能体运行的地方，与沙箱分离。
  • 持久沙箱与推理框架之间的环境需求将会产生分歧。
