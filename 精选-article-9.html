📌 一句话摘要

本文系统梳理了 Agent 架构的核心工程实践，涵盖 Agent Loop、Harness、上下文工程、工具设计、记忆系统、多 Agent 组织、评测与追踪等关键技术维度，并结合 OpenClaw 开源实现展示设计原则的落地方式。

📝 详细摘要

这是一篇来自蚂蚁集团工程师的 Agent 架构深度实践文章，基于团队业务落地经验进行系统梳理。文章核心观点包括：1）Agent Loop 核心逻辑不到 20 行代码，遵循感知->决策->行动->反馈循环；2）Harness（测试验证基础设施）比模型本身更关键，决定系统稳定运行；3）上下文需要分层管理，常驻层要短而稳定，知识按需加载；4）工具设计遵循 ACI 原则，描述要说明何时用、何时不用，返回要结构化；5）记忆分四种类型（工作记忆、程序性记忆、情景记忆、语义记忆），需要协作设计；6）评测系统本身的问题往往比 Agent 问题更难发现；7）调试 Agent 应优先检查工具定义而非模型能力。文章最后用 OpenClaw 开源实现展示了五层架构设计原则的完整落地。

💡 主要观点

  1. Harness 比模型更关键，决定 Agent 系统稳定运行 在代码编写等高可验证任务上，验收基线、执行边界、反馈信号和回退手段等外围工程条件往往比模型选择更能决定系统可靠性，OpenAI Codex 的实践验证了这一点。
  2. 上下文要分层管理，知识按需加载 上下文失效的常见原因是信息密度不对，常驻层应短而稳定（身份定义、项目约定），Skills 和领域知识描述符常驻但完整内容触发时再注入，避免无关内容稀释关键信号。
  3. 工具设计遵循 ACI 原则，描述决定调用准确性 好工具对应 Agent 目标而非 API 操作，描述要说明何时用、何时不用，返回结构化错误和修正建议。调试 Agent 时应优先检查工具定义，多数选择错误出在描述不准确。
  4. 评测系统本身的问题往往比 Agent 问题更难发现 评测的环境噪声（资源不足、评分器 bug、测试用例脱节）可能造成模型退化的假象，需要先排查环境再修改 Agent 代码。
  5. 多 Agent 协作要把协议、任务图、隔离边界先定下来 多 Agent 通过 JSONL inbox 协议通信，用 Worktree 隔离文件修改，协作方式不能靠自然语言对齐，需要结构化协议防止幻觉互相放大。

💬 文章金句

  • 模型虽然重要，但决定系统能不能稳定运行的，往往是这些外围工程条件。
  • 调试 Agent 时应先检查工具定义，大多数工具选择错误的原因出在描述不准确，不在模型能力。
  • 别把确定性逻辑放进上下文，凡是可以通过 Hooks、代码规则或工具约束表达的内容，都应交给外部系统处理。
  • 评测系统本身的问题很多时候比 Agent 出问题更难发现，如果一直在 Agent 代码上反复调，效果未必明显。
  • 多 Agent 协作一旦靠自然语言来对齐，很快就会出问题。
